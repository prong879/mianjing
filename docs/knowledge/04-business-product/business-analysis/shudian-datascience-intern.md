## 三、你需要掌握的知识（备考清单）

按「数据工程底座 → 业务分析 → 可视化 → 机器学习协作 → 软技能」组织；打钩项建议结合 [冲刺路线](/guide/exam-cram) 与 [数分高频题](/interviews/01-data-analytics/highlights) 自测。

### 1. SQL（岗位要求「复杂查询」）

- **多表关联**：INNER/LEFT JOIN、一对多膨胀的控制、去重策略。
- **聚合与分组**：GROUP BY、HAVING、常见业务口径（去重用户数、订单数、金额）。
- **窗口函数**：`ROW_NUMBER` / `RANK`、`SUM() OVER (PARTITION BY … ORDER BY …)`、移动平均、同比环比。
- **留存与漏斗**：按 cohort 定义首日、次日/7 日回访；漏斗步骤表设计与转化率计算思路。
- **数据质量**：NULL、重复键、时间区、边界日期、增量表的 **snapshot vs event** 区别。

### 2. Python 数据分析栈（JD：Pandas / NumPy / Matplotlib / Seaborn）

- **Pandas**：索引、merge、groupby、透视、缺失与异常值处理、内存与数据类型优化（大表场景）。
- **NumPy**：向量化基础；与统计量的衔接。
- **可视化**：趋势、分布、相关性、分组对比；图表**服务于结论**而非堆图。
- **自动化**：定时任务、日志、可复用配置（与实习中「定时入库」叙事一致）。

### 3. 指标体系与业务分析

- **OSM / 北极星**：O 目标—S 策略—M 度量；避免指标堆砌。
- **拆解**：乘法拆解（如流量×转化×客单）、加法拆解（分部汇总）、维度下钻（渠道、版本、客群）。
- **异动分析框架**：确认口径 → 拆分维度 → 排除已知活动/故障 → 假设验证 → 建议与下一步数据需求。
- **漏斗**：定义步骤事件、流失环节、时间窗口一致；与埋点/日志的关系（若公司有数仓可简述分层）。

### 4. 用户行为 / 留存 / 转化（补足互联网语境）

- **留存**：次日/7 日/30 日、粘性（DAU/MAU）、cohort 表逻辑。
- **转化**：注册→激活→关键行为→付费（按业务替换）；**关键行为**如何与业务共创定义。
- **用户分群**：RFM 思路、行为序列简化版本；与「因子分层」「风险分层」类比。

### 5. BI 工具（Tableau / Power BI）

- **概念迁移**：数据源、度量/维度、计算字段、参数、刷新策略。
- **看板设计**：受众（高管/运营/产研）、一页一决策、异常高亮、下钻路径。
- **实操**：任一工具跟一门短教程做出「趋势 + 漏斗 + 分渠道」样板项目写进话术。
- **场景命题**：见下文 **第四节末「看板设计：业务命题演练」**，覆盖高管经营舱、运营活动、产品功能、技术侧与 ToB 健康度等典型问法。

### 6. 机器学习协作（特征、标注、验证、调参）

- **特征工程**：连续/类别处理、缺失、Scaler、时间特征泄漏防范。
- **标注**：规范、一致性、抽检、难例回流；与人协作流程。
- **验证**：训练/验证/测试、交叉验证概念、baseline 重要性、过拟合与样本外。
- **指标**：分类（准召、AUC 等）、回归（MAE/RMSE），与业务成本的挂钩。
- **与您项目的连接**：时序切分、滚动窗口、结论可解释性（Streamlit 展示思路）。

### 7. 大数据/数科实习通用软技能

- 与业务对齐**口径**的书面习惯（字典、CHANGELOG）。
- **周报结构**：结论先行—核心数字—拆解—假设—数据需求—风险。
- 对 **Agent/LLM**：作为「辅助标注、摘要、SQL 草稿、文档生成」的定位，强调**可追溯与人工复核**。

## 四、二十问速答（本 JD 核心 · 建议优先背诵）

下列 20 题严格对齐**第一节存档 JD**，覆盖**清洗与标准数据集**、指标体系与周月报、行为/留存/漏斗、BI、ML 协作、调研与文档、SQL/Python、院校与出勤、公司认知与场景；**同节末尾**附 **看板设计业务命题（A～F）** 供 Tableau/Power BI 面试深挖。**口播时可把括号内换成你的真实经历与公司具体业务名。**

### 1. 你怎么理解这个「数据科学实习生」的日常工作？

**答案：** 我理解是「**承上启下**」：对上承接分析师/科学家拆好的业务问题，把**脏数据洗成可信、粒度清晰的标准数据集**；中间参与**指标字典与看板**，盯**产品/运营/技术**相关指标异动并写**周或月报洞察**；对下在 ML 项目里做**特征、标注、验证与调参**的辅助，保证离线效果**可解释、可复现**。杂项还包括**数据调研和文档**，本质是让别人能**按文档重复你的结论**。

### 2. 「清洗、预处理、质量校验」之后，怎样才算「标准化分析数据集」？

**答案：** 至少满足四件事：**（1）口径书面化**——主键（如用户日、订单 ID）、时间字段语义、去重规则、是否含退款/测试。**（2）质量可量化**——缺失率、重复键、值域与环比异常阈值。**（3）可追溯**——来源表、Transform 版本、刷新频率。**（4）消费友好**——字段命名统一、宽表或星型结构符合团队习惯，能直接进 SQL/BI/Notebook。不是「洗过一次」，而是**能进线上周报链路且改版有 changelog**。

### 3. 参与「核心指标体系」搭建与维护，你会怎么做？

**答案：** 先和业务用 **OSM** 对齐：**O** 这一阶段的核心目标是什么、**S** 关键策略有哪些、**M** 用哪些度量跟进（**北极星 1 个 + 结果指标少数 + 过程指标可控数量**）。再落成**指标卡片**：中英文名、分子分母、统计粒度、延迟、负责人。维护上：**异动时不先改口径**，先查数据新鲜度与已知活动；版本变更写进字典并@**消费方**（报表/看板）。

### 4. 周 / 月度「数据洞察报告」你建议怎么组织？

**答案：** **执行摘要 5 行**：本期结论 + 需业务动作。**核心数字**：北极星与同环比、贡献前二的拆解。**专题**：如留存、漏斗、某版本——每节都是「现象—假设—证据—未决问题」。**数据质量与局限**：延迟、口径调整、样本偏差。**附录**：关键 SQL/图表索引。原则：**第一屏就能回答「所以呢、谁要干嘛」**。

### 5. 用户行为分析你通常从哪切入？

**答案：** 先定**分析单元**（人/会话/设备）和**关键路径**（注册—激活—核心行为）。从**渗透与频次**看功能是否被用起来，从**路径与停留**看卡点，从**分群**（渠道、新老、端）看是否局部问题。缺埋点时诚实说需要 **v0 代理指标 + v1 埋点** 路线，不硬编结论。

### 6. 做留存分析前，你必须和业务对齐什么？

**答案：** **「活跃」操作定义**（登录 / 关键行为 / DAU 规则）、**首日 cohort 锚点**（注册日还是首活）、**自然日 vs 滚动 24h**、**时区**、是否剔测试账号。这些不定，留存曲线**不可比**。

### 7. 漏斗分析最容易踩的坑？你怎么避免？

**答案：** **步骤事件不对等**（前端 PV 混后端下单）、**时间窗不一致**（有的按会话、有的按 7 日）、**窗口内重复计次**、**强依赖缺失步骤埋点**。避免方式：与产品写清**事件名 + 属性 + 窗口 + 去重规则**，上线前**单行样本对账**。

### 8. Tableau / Power BI 做「监控向」看板，你最坚持哪三点？

**答案：** **（1）指标语义在界面上可读**（脚注或 tooltips 写口径与更新时间）。**（2）刷新与延迟**和业务预期一致，标注**数据截至时点**。**（3）受众分层**——老板看「北极星+异常」；执行同学能**下钻维度**。必要时做**异常高亮规则**，避免纯「漂亮但读不懂」。

### 9. JD 写了解 BI，你目前不熟，怎么回应？

**答案：** 诚实说当前熟练度，补一句**迁移能力**：已在 Python/（或 Streamlit）里做过 **度量×维度×筛选**，理解 **语义层** 概念；入职前/第一周会按团队选型刷 **官方教程 + 一个脱敏 demo（趋势+漏斗+下钻）**，并在**度量/DAX 或 LOD**上各做一小练。接受团队规范为主。

### 10. 参与 ML：特征工程举例，如何避免信息泄漏？

**答案：** （例）用时序或行为构造滞后特征、滚动统计时**严格按时间切分**：训练集只用 \(t\le T\) 的信息，验证/测试集在 \(T\) 之后；不用「**当时还不知道」**的标签或全样本统计填回过去。分类任务注意**目标编码**、**样本权重**里的泄漏。交付时写**特征说明表**方便他人 audit。

### 11. 协助「数据标注」时你怎么控质量？

**答案：** **指南写死**：边界案例、**否定示例**、输出格式（JSON/枚举）。**双人抽检 + 不一致率**入周报；难例回流迭代指南。大模型辅助标注时坚持**人工终审**与**可追溯 ID**，不把生成当金标准。

### 12. 「模型效果验证与调优」你会汇报什么给团队？

**答案：** **任务与 baseline**（规则/简单模型）对比；**主指标 + 业务成本相关副指标**（如误报代价）；**分群表现**（避免均值骗人）；**稳定性**（时间外推）；**bad case** 类型与是否接受。**调参**记录关键实验表，避免「魔法数字」。

### 13. JD 要求 SQL 复杂查询，你熟悉哪些典型模式？

**答案：** 多表 **JOIN** 与一对多控制、**GROUP BY + HAVING**、**窗口函数**（累计、同比、排名）、**留存 cohort**（首活日 join 次日事件）、**漏斗**（步骤事件与时间窗）。能口述**一次你写过或读过的较复杂分析 SQL 的业务目的**即可。

### 14. Python（Pandas/NumPy）做分析，你如何保证可复现？

**答案：** 固定**数据源版本与时间切片**；脚本**参数化**（路径、日期）；**随机种子**；依赖 **requirements**；大表注意 **dtype** 与分块。**输出**不仅 notebook，还有**可运行的脚本或入口**，方便定时跑。

### 15. 「数据调研」文档你会写哪些部分？

**答案：** 背景与问题、**干系人**、现有数据源清单（表/字段/延迟）、**缺口与风险**、竞品或行业**参照**（若适用）、建议的**指标草案与 POC 计划**、时间与人力估算。目的是：**读文档的人能决定是否立项、数据从哪来**。

### 16. 报表数字和业务后台不一致，你怎么处理？

**答案：** **不对抗、先对账**：对齐**单行样本**、过滤条件（测试/退款）、**时间边界**（创建/支付/完成）、**关联键是否膨胀**。分层查**同步延迟、ETL bug、口径版本**。输出简短**根因+修复 owner+预防监控**，写进字典或群公告。

### 17. 早会发现「核心指标」异动很大，但业务体感不符，你第一步做什么？

**答案：** **锁口径与新鲜度**：定义变没、调度延迟、分区是否齐；再**与后台/日志抽样**核对。排除数据问题后再做**维度下钻**与**假设列表**。在结论未稳前**避免对外传「大变盘」**，标注数据状态。

### 18. JD 写了院校门槛（985/211 或 QS 前 100），你怎么得体回应？

**答案：** 若符合：简洁陈述**学校与在读学位**，转到**能力与匹配**。若边界情况（如强专业弱排名）：强调**专业训练（统计/计量/代码）+ 可验证项目（实习/Git）**，表态尊重公司人力政策并欢迎用**笔试/作业**证明。**不贬低其他院校**。

### 19. 北京线下、每周至少 4 天、3 个月以上、尽快到岗——你如何回答？

**答案：** 按事实说：**可到岗日期**、每周哪几天、持续多久；若**课程/论文**可能冲突，说清**如何提前两周沟通与交接**。强调理解**出勤**对业务节奏的意义，不空口承诺。**住房与通勤**若稳定可一句带过增加可信度。

### 20. 你为什么投数巅？对公司有什么了解？

**答案：** **匹配**：JD 要的 **SQL+Python+指标+BI+ML 协作** 与我的 **（实习：口径/管道/异动/模型验证）** 同构。**公司**：数巅公开信息多指向 **数据智能、企业数据资产与智能化**（含大模型应用语境）；**以官网为准**，我关注 **ASK/BI 或 X-Engine 等产品线** 如何落到「可信数据 + 分析 + 决策」。**反问**：当前团队**数仓栈、BI 选型、ML 主要场景**是什么——显得做过功课且不胡编细节。

### 看板设计：业务命题演练（Tableau / Power BI 口述结构）

下列场景为面试高频：**先问受众与决策频率，再定北极星与下钻路径**；工具上统一说成 **「总览 KPI 区 + 趋势 + 分布/结构 + 明细或跳转」**，并强调**全局筛选器（日期/渠道/端/客群）**与**数据更新时间**脚注。公司若为 **ToB / 数据产品**，把「租户」当作**分析粒度**即可迁移。

#### 场景 A：CEO 要「每周花 10 分钟看清公司经营」

**命题：** 管理层不看 SQL，要一张经营驾驶舱，且每周例会直接用。

**设计思路：**

1. **受众与节奏**：周更、周一早会前刷新；允许 T+1 延迟需在页眉**标注截至时点**。  
2. **首屏 KPI 条**（同比/环比 + 小趋势 sparkline）：**收入或 GMV**、**活跃用户数（或合同侧 ARR/续费若 ToB）**、**获客或转化主指标**、**单位经济或毛利类**（按公司实际四选三～四，忌超过 6 个）。  
3. **第二屏拆解**：**贡献结构**（渠道/产品线/地域 stacked bar 或瀑布）+ **异常列表**（Top 涨跌维度）。  
4. **下钻**：从 KPI 点进到「维度详情 Tab」，预置**「本周异动简报」**文本框位（可接周报结论）。  
5. **权限**：高管全量；敏感成本项单列权限或脱敏。  
**坑：** KPI 堆砌、没有「**So What**」区；环比与外推活动**未标注活动日历**。

#### 场景 B：运营负责人要「大促 / 活动复盘」看板

**命题：** 活动周期间每日盯转化，结束后要归因与经验沉淀。

**设计思路：**

1. **时间轴控件**：**活动期 vs 前同台期**对比（或 baseline 7 天）。  
2. **漏斗主线**：曝光 → 访问/线索 → 下单/付费（步骤与窗口与埋点**书面一致**）。  
3. **分渠道/创意**：**转化与成本并排**（若有投放数据）；否则至少**渠道 + 客群**。  
4. **增量 Attempt**：有实验桶则展示**实验组 vs 对照**；无则**醒目注明「描述性相关、非因果」**。  
5. **沉淀区**：**爆款路径 / 失利环节 / 下次活动检查清单**（可接文档链接）。  
**坑：** 活动流量污染**留存 cohort**；**退款/取消**未统一过滤。

#### 场景 C：产品经理要「新功能是否被用起来、对留存有没有帮忙」

**命题：** 上线 4 周内评估**功能渗透率**与**行为–留存**相关线索。

**设计思路：**

1. **功能定义**：**关键事件** + **首用/复用**分开；**版本号**全局筛选。  
2. **渗透率**：**功能用户数 /  eligible 用户数**（eligible 与产品对齐，如近 30 天活跃）。  
3. **留存辅助视图**：**用过该功能的用户 vs 未用**的 **D7/D30** cohort（分层控制：新老、渠道；高级可做 PSM **口播提一句即可**）。  
4. **体验路径**：从**入口来源**到**完成核心任务**的 Sankey 或步骤条（数据不足则简化为步骤转化率）。  
**坑：** eligible 口径不稳导致渗透**虚高/虚低**；把**相关当因果**写进看板标题。

#### 场景 D：技术负责人要「稳定性 + 性能」与「业务影响」同屏（JD 中「技术等维度」）

**命题：** 故障、延迟、错误率如何和**核心业务分钟级指标**对齐复盘。

**设计思路：**

1. **技术条**：**可用性 / P99 延迟 / 错误率 / 发布事件**时间线（与监控告警源一致）。  
2. **业务条**：**请求量、订单创建成功率、支付成功率**等同粒度时间序列。  
3. **联动**：**竖线标注**「部署/故障窗口」，支持**框选时段**对比前后 Δ。  
4. **明细**：**Top 接口 / Top 错误码**表，可跳转日志或工单。  
**坑：** 技术时间 UTC、业务时间本地**未统一**；业务指标**延迟大于**技术指标导致误读。

#### 场景 E：客户成功 / ToB 交付——「租户健康度」监控（贴近数据智能、多租户产品）

**命题：** 多客户订阅，需提前发现**用量下滑**与**流失风险**。

**设计思路：**

1. **租户列表**：**健康分**（如近 4 周登录天数、查询次数、活跃人数、核心功能使用）。  
2. **单体租户页**：**账号数、存储/查询量、关键功能渗透率**趋势；**工单与 NPS** 若有则并列。  
3. **预警规则**：**连续 N 周下滑**、**低于同规模中位数**高亮；对接 CS 责任人字段。  
**坑：** **租户规模不一**未做分桶，健康分**不公平**；数据隔离与**合规**未在权限层处理。

#### 场景 F：面试官追问「一页纸画板布局」——30 秒口述模板

**答案：** **左窄右宽**：左列**全局筛选**（日期、渠道、端）；上排 **4 个 KPI**；中左 **主指标周/日趋势**，中右 **结构图**（渠道或产品）；下方 **TopN 表格 + 异常注释**；页脚**口径与刷新时间**。**原则**：每个区块只回答**一个问题**；超出问题移入二级页或 Tooltip。

## 五、扩展题库（32 组 · 深度演练）

下列答案按你的简历量身定制；口播时请替换虚构数字为真实项目量级。**第 21–27 题为统计与业务拆解补充；第 28–32 题为贴合 JD 的「日常业务场景」演练。**

### 1. 为什么从量化/投研数据产品转向数科实习？

**答案：** 我在证券实习和项目里积累了**数据管道、指标口径、可复用工具化和报告输出**的经验；数科实习只是把「标的物」从券种/成分股换成**业务用户与产品行为**，方法论仍是「定义问题—建指标体系—清洗与建模—验证—沉淀看板与文档」。我希望在更偏 **plumbing + insight + ML 协作** 的环境里补齐互联网业务语境。

### 2. 简述你最自豪的一个数据相关项目（1 分钟）。

**答案：** 我做过 ETF 成分股异动监控与日报 Agent：从 AkShare 拉行情，对大量成分股算收益、量比、超额收益、波动等**规则化异动**；再交给 Explain/Review Agent 生成解释与复核摘要，减少人工筛与写日报时间。另一条线是华福转债多因子系统：**PRD 驱动**的「数据入库—因子计算—查询与可视化」，把研究员手工脚本沉淀成 Flask+MySQL 工具。两条线都体现 **指标—异常—解释—复盘** 的闭环。

### 3. 你在华福实习里梳理的「指标体系」和长宽表，和互联网公司指标体系有什么异同？

**答案：** 相同点：都要 **明确统计口径、主键、时间粒度、更新频率**；都要服务可追溯的报表。不同点：金融侧更强调 **因子可比性、调仓/交易日历法、多空与基准**；互联网侧更强调 **用户粒度、行为事件、漏斗与留存 cohort**。我能把金融里「因子字典 + 计算编排」迁移到「事件字典 + 指标分层（入口/过程/结果）」。

### 4. SQL 题风：如何计算「次日留存」？你会问业务方澄清什么？

**答案：** 澄清 **「活跃」定义**（登录/关键行为/访问页面）、**自然日还是 24h rolling**、**新用户首日是注册还是首访**。典型思路：取每个用户首日 `d0`，再看 `d0+1` 是否出现活跃事件；按 `d0` 分组算留存率。注意时区、去重设备/账号、刷量/测试账号过滤。

### 5. 漏斗转化率在中间一步暴跌，你怎么排查？

**答案：** 先 **对齐漏斗事件与窗口**（同一会话还是 7 日内）；再 **分渠道/版本/客群** 看是否局部问题；检查 **技术故障、埋点缺失、文案/流程改版** 时间点；做 **前后区间对比** 与 **用户回访样本**（若有）。输出：最可能的 2～3 个假设 + 需要补的日志/维度 + 验证排期。

### 6. 数据质量出问题（报表与业务后台对不上），你怎么处理？

**答案：** 分层排查：**采集/同步** 是否延迟；**过滤条件**（取消单、测试单）是否一致；**时间边界**（创建/支付）；**关联键** 是否一对多膨胀；**口径文档**是否版本过期。先与业务对齐「单行样本」对账，再写清结论与修复 owner。

### 7. 你如何设计一个「核心指标驾驶舱」给业务负责人？

**答案：** 一页 **北极星 + 3～5 个结果指标 + 10 个以内过程指标**；每张图能回答一个决策问题；支持 **时间对比与维度下钻**；标注 **口径与数据更新时间**；异常用规则或阈值高亮。工具上用 Tableau/Power BI 或等价方案，关键在 **度量定义稳定**。

### 8. 你没有太多 Tableau/Power BI 经验，入职后怎么补？

**答案：** 我会用一周集中做出 **Demo 看板**：连接示例或脱敏数据，练习 **LOD（Tableau）或 DAX（PBI）** 基础；把我在 Streamlit/Plotly 里做过的图迁移成 **标准商业模板**；向团队要 **样式与权限规范**，保证第一版就符合发布习惯。

### 9. 讲一个你做「特征工程」的例子，如何避免信息泄漏？

**答案：** 在 LSTM/ARIMA 股票预测项目里，特征是滞后收益、滚动波动、成交量变化等；**训练与验证严格按时间切分**，不用未来窗口统计量填过去行；特征解释与 Streamlit 展示绑定，避免「结果驱动」的偷看标签。若标签是未来 K 日收益，则特征只能用到 T 日及以前。

### 10. 模型离线效果好、线上指标平庸，可能原因？

**答案：** **分布漂移**、特征在真实的缺失与延迟、**选择偏差**、训练标签与线上一致性问题、评估指标与业务目标错位、**过拟合**或小样本调参。我会先对齐线上日志能否还原特征，再上 **shadow 验证** 与小流量实验（若公司有实验文化）。

### 11. LLM/Agent 在你过去的项目里做什么？在数科团队里如何定位？

**答案：** Agent 做主流程里的 **解释、辩论复核、日报文字化**；底层异动仍是规则+统计。到数科团队里，Agent 更适合 **工单/反馈摘要、口径文档问答、SQL/代码草稿、标注建议**；核心指标仍以 **确定性 SQL + 可视化** 为准，生成内容必须 **可追溯与抽检**。

### 12. 多 Agent 交易决策项目，对「数据标注与一致性」有什么启示？

**答案：** 多空辩论+Judge 本质是 **多标注员 + 仲裁**；启示是：**任务边界要窄、输出结构要 JSON 化、要有难例集与抽检**；和金融里「研究员复核因子」一样，**人类终审**不能省。可迁移到 ML 团队的 **标注指南迭代** 与 **一致性 KPI**。

### 13. 实习要求每周 4 天、至少 3 个月，你学业怎么安排？

**答案：** （按事实填写：例如研究生入学前/课程阶段）当前可承诺 **每周 X 天**，持续 **不少于 3 个月**；若后续学期有冲突，会 **提前两周** 与 mentor 对齐，优先保证 **数据交付与文档交接**。

### 14. 你最熟的一段 Python 数据处理代码场景是什么？

**答案：** 批量拉取多 ETF 成分股行情、按交易日对齐、计算 Z-score/量比等**向量化或 group 聚合**；异常行写入日志；结果落 **Parquet/SQLite** 供下游 Agent。强调 **可复现配置** 与 **监控字段**。

### 15. 周报怎么写才能让业务愿意看？

**答案：** **结论与行动建议在第一屏**；每张表回答一个问题；数字带 **同比/环比与贡献度**；另附 **「本周限定条件与数据问题」** 防止误读；文末列 **下周数据需求**。我在研究所写半月报/PRD 时也遵循「读者是 busy stakeholder」。

### 16. 偏统计的假设检验在分析里什么时候用？

**答案：** 在 **AB 实验**、**活动增量**、两组转化差异是否显著时用。日常异动分析未必每次都上检验，但要懂 **样本量、功效、p 值误用**；重大决策配合实验或因果设计（见知识库 [A/B 测试](/knowledge/03-statistics-experiment/ab-testing/ab-testing)）。

### 17. 如果业务临时要一个「无法直接取数」的指标，你怎么办？

**答案：** 先 **拆成可操作定义**；找 **近似代理指标**；评估 **数仓是否有事件** 支撑；给出 **v0 手工样本 + v1 埋点/ETL** 路线图；写清 **误差来源与迭代条件**。

### 18. 讲一个你与研发/业务「扯皮口径」并解决的经历。

**答案：** （用华福实习真实故事）转债因子 **字段含义、缺失填充、回溯窗口** 与研究员手工稿不一致时，我组织 **单行对账表 + PRD 附录口径**，把「可计算定义」固定下来，并在页面展示 **指标说明 tooltip**，减少反复问。

### 19. 你认为数科实习生的「产出物」应该是什么？

**答案：** **可信赖的数据集/SQL、稳定的看板或报表、指标体系文档、可复用的 notebook 或任务、以及周度洞察**；若有 ML，则包括 **特征说明、评估报告、bad case 清单**。避免只「跑过模型」没有业务叙事。

### 20. 你对数巅了解多少？为什么投我们？

**答案：** 我了解数巅是 **数据智能** 方向的团队，公开材料里常强调企业侧 **数据平台、数据资产与智能化能力**，并与大模型时代的数据与算法应用相结合；这与 JD 中「清洗标准化—核心指标—行为/漏斗分析—BI 看板—ML 协作」高度一致。我选择数巅，一是因为岗位需要 **指标 + 可视化 + ML 协作** 的 T 型能力，与我 **PRD 驱动工具化、Python/SQL、异动检测与模型验证** 的经历匹配；二是希望进入 **数据与平台密度高、迭代快** 的环境，把金融场景里的口径与 pipeline 经验迁移到更普适的企业数据问题。**产品线、客户类型与团队当前技术栈** 我希望在反问环节再向您对齐。

### 21. 本科和硕士学习期间，哪一门课对你未来做现在这个职位最有帮助？为什么？

**答案：** 我会重点举 **两门互补的课**，分别对应「统计推断」与「工程落地」。（任选与你成绩单一致的表述。）

- **金融计量学 / 经济计量 / 概率统计：** 系统训练 **回归、显著性检验、置信区间与模型假设**，和岗位上 **指标异动判断是否「可能只是噪声」、实验/对比组结论是否稳健** 直接相关；论文实证里也会反复用到 **t 检验、F 检验、稳健性检验**，思维可迁移到 AB 与经营分析。  
- **数据库（MySQL）与 Python 程序设计：** 对应 JD 里 **SQL 复杂查询、清洗与标准化数据集、自动化任务**；没有工程载体，统计结论很难规模化交付。

口播可收束为：**计量统计让我会问「证据强度够不够」，数据库与 Python 让我能把口径固定下来并复现——数科岗位正好是两者的交叉。**

### 22. 你对「假设检验」如何理解？

**答案：** 假设检验是在 **样本有噪声** 的前提下，对**总体**的某种陈述（通常写成原假设 \(H_0\)）做**可操作的决策规则**：选一个检验统计量、给定显著性水平 \(\alpha\)，看样本实现是否落在「在 \(H_0\) 为真时足够罕见」的区域；或用 **p 值** 概括该罕见程度。

我理解的三点是：  
1. **证伪倾向**：经典表述是「拒绝 \(H_0\)」或「不拒绝 \(H_0\)」，而不是把 p 值当成「\(H_1\) 为真的概率」。  
2. **预设规则**：\(\alpha\)、单侧/双侧、样本量与功效（1−β）要在分析前或方案里说清，避免事后挑结果。  
3. **与业务的衔接**：检验回答的是「**随机波动能否解释眼前差异**」；业务还要补一句「**即使显著，效应量多大、是否值得做**」。

### 23. 你如何理解第一类错误和第二类错误？

**答案：**  
- **第一类错误（Type I）**：\(H_0\) 实际为真，却 **拒绝了 \(H_0\)** ——「**假阳性**」。控制它的概率是显著性水平 **\(\alpha\)**。  
- **第二类错误（Type II）**：\(H_0\) 实际为假，却 **没有拒绝 \(H_0\)** ——「**假阴性**」。其概率常记 **\(\beta\)**，**检验功效**为 **\(1-\beta\)**（正确检出真实效应的能力）。

**权衡：** 把 \(\alpha\) 卡得很严会减少误报，但样本量不够时会增大漏报；**增大样本**通常能同时改善两类风险（在固定 \(\alpha\) 与真实效应下提高功效）。业务上：**强合规/资金相关**常更忌讳第一类错误；探索性分析可先接受较高 \(\alpha\) 或强调置信区间与效应量，再配合实验复现。

### 24. 之前实习或项目里，有没有把假设检验真正用在实操里？请举例。

**答案：** （按你真实经历二选一或合并。）

- **（论文）CSSCI 实证：** 在面板回归与机制检验后，对核心系数做 **显著性判断**；通过 **更换样本窗、替换变量、缩尾/稳健标准误** 做 **稳健性**，本质是在检验「结论是否依赖某种设定」；汇报时配合 **置信区间** 说明经济含义与统计精度。  
- **（量化/因子）华福实习：** 更常见的是 **回测与分组检验**：例如某因子分组多空收益与基准的差异，是否在统计上 **不兼容于「纯运气」**（具体用 t 检验、Newey–West 调整等视团队规范）；以及 **策略上线前的显著性/稳定性** 与业务侧「敢不敢用」对齐。  

若实习未做到严格检验，可诚实说：**日常报表以描述统计为主，但论文项目里完整用过检验思维；** 入职后会按团队规范补 **实验设计与多重检验校正**。

### 25. 泊松分布和二项分布的区别是什么？

**答案：**  
| 维度 | 二项分布 | 泊松分布 |
| --- | --- | --- |
| 典型场景 | **固定 \(n\) 次**独立试验，每次成功概率 \(p\)，成功次数 \(X\) | **固定时间/空间窗口**内，**稀有事件**发生次数，均发生率 \(\lambda\) |
| 参数 | \(n,\,p\) | \(\lambda\)（单位时间平均次数） |
| 取值 | \(0,1,\ldots,n\) | \(0,1,2,\ldots\) |
| 关系 | 当 \(n\) 大、\(p\) 小且 \(np\to\lambda\) 时，**二项近似泊松** | 可作为「很多小概率事件」的极限模型 |

**业务直觉：** **二项**适合「\(n\) 个用户每人是否转化」「\(n\) 次曝光中点击次数」；**泊松**适合「单位时间内到达数、请求数、缺陷数」等 **率驱动** 的计数（需检查是否过离散/是否独立同分布等假设）。

### 26. 你在量化实习里说参与搭建了因子相关体系，具体是怎么建立的？

**答案：** 我们的目标不是炫技因子数量，而是服务 **B 端用户在可转债上的因子分析、回测复盘、选券** 这一条链路，所以体系是 **「业务步骤 → 可计算定义 → 数据与任务 → 展示与口径」** 四层对齐出来的。

1. **对齐业务与范围：** 和研究员梳理「从拿到数据到输出结论」的步骤：**数据输入 → 指标/因子计算 → 结果查询与可视化 → 复盘导出**；沉淀成功能清单与 **指标口径表**（含字段含义、缺失规则、是否复权、回测截止日等）。  
2. **因子分层与字典：** 按投研习惯把因子归入大类（如估值、动量、质量等——以所内框架为准），每个因子有 **英文名、公式/数据源、更新频率、适用场景与已知坑**。  
3. **数据与工程：** 行情与基本面入库 **MySQL**（或团队指定库），用 **Python** 批量算因子、**定时任务** 增量更新，避免手工脚本不一致。  
4. **产品与文档：** 用 **PRD** 固定页面字段、交互与异常提示；上线前用 **单行对账 + 与手工稿对比** 做验收。  

面试收束：**因子体系的本质是一张可执行的「字典 + pipeline + 验收口径」，能被非写代码的研究员稳定使用。**

### 27. 若研究新客、老客谁对「销量下滑」影响更大，怎么量化各自贡献？

**答案：** 先统一 **销量定义与时间窗**（GMV、件数、是否剔退款、同比还是环比），再选一层 **可解释** 的分解，避免拍脑袋。

**（A）可加分解（最直白）：**  
设总销量 \(S = S_{\text{新}} + S_{\text{老}}\)。基期与本期分别有 \(S^0=S^0_{\text{新}}+S^0_{\text{老}}\)，\(S^1=S^1_{\text{新}}+S^1_{\text{老}}\)。  
总变动 \(\Delta S = S^1-S^0 = \Delta S_{\text{新}} + \Delta S_{\text{老}}\)，其中 \(\Delta S_{\text{新}}=S^1_{\text{新}}-S^0_{\text{新}}\)。  
**贡献度**可报：**各自变动占 \(|\Delta S|\) 的比例**（若 \(\Delta S<0\) 为下滑，可说明「下滑额中多少来自新客、多少来自老客」，并注意分母为 0 或符号混乱时的叙述方式）。

**（B）再下钻一层（找驱动）：** 对每类客群拆 **量 × 率 × 单**：例如新客的 **获客数 × 首单转化 × 客单价**，老客的 **活跃老客数 × 购买频次 × 件单价**，看哪一项拖累最大（**结构 vs 行为**）。

**（C）需控制混杂时：** 可补充 **分区域/分渠道** 的对照，或 **Shapley/Oaxaca** 等更正式的分配（面试答到前两层通常足够；若团队有因果诉求再上实验或模型）。

### 28. 业务场景：早会前发现「昨日核心指标」异动很大，和业务体感不一致，你怎么做？

**问题本质：** 指标异动来自 **数据问题** 还是 **真实经营变化**（或两者兼有）。  
**答案：**

1. **锁三样：** 指标 **定义**、统计 **时间窗与时区**、**数据新鲜度**（调度是否延迟、分区是否写满）。  
2. **快速对照：** 与 **业务侧后台/抽数 SQL 单行样本** 对账；看 **昨日是否口径变更、过滤条件是否动过**（测试单、灰度用户）。  
3. **分拆：** 按 **渠道/产品/客群/版本** 下钻，判断是 **全场** 还是 **局部**；若局部集中，优先怀疑 **发布、活动、故障**。  
4. **沟通：** **1 小时内**给对方「当前证据链」：已排除/未排除的假设 + 建议 **暂停对外结论** 或 **标注数据延迟**；修复后补一篇简短复盘（可类比我在 **ETF 异动监控** 里先规则命中再人工复核的思路）。

---

### 29. 业务场景：运营要从「周/月报」里固定加三个新指标进经营分析，你怎么接需求并落地？

**问题本质：** 把模糊业务语言变成 **可计算、可复现、可进 BI** 的指标资产。  
**答案：**

1. **澄清：** 每个指标服务 **哪个决策**；**分子分母、去重维度、时间粒度**（自然日/滚动 7 天）；与现有指标是否 **重叠**。  
2. **字典：** 在指标表里写清 **英文名、中文名、SQL 伪代码或源表字段、刷新频率、负责人、变更记录**（和我在华福做的 **因子/指标口径表 + PRD** 同一套路）。  
3. **验证：** 抽样 **与业务手工表对数**；边界情况（空值、跨天、退款）。  
4. **进看板：** 在 Tableau/Power BI 设 **统一过滤器** 与 **口径说明页**；版本迭代时 **标注生效日**，避免周报「悄悄换定义」。

### 30. 业务场景：周报显示「留存」连续走低，产品希望一周内知道「优先怀疑谁」——你怎么分析？

**问题本质：** 留存是 **结果指标**，要拆成 **获客质量、产品体验、运营节奏、外部季节** 等可讨论假设。  
**答案：**

1. **对齐 cohort：** 看的是 **次日/7 日/30 日** 中哪一个；新用户定义是否变动。  
2. **分层：** 按 **注册渠道、活动、版本、地域、设备** 拆 cohort，是否 **某一两条线在拖累整体**（类似 **因子分组** 里看哪一段截面异常）。  
3. **行为链路：** 对走弱 cohort 看 **激活/关键行为** 是否未达成（漏斗中段是否塌方）。  
4. **时间对照：** 与 **历史同季节、大促后回落** 对比，避免把 **可预期波动** 当事故。  
5. **输出：** **Top 3 假设 + 每条假设需要的补充数据或实验**；不写「全是产品问题」这种无法下结论的套话。

---

### 31. 业务场景：分析师要在看板里加一个「转化漏斗」，但数仓里缺少关键一步的事件，你怎么推进？

**问题本质：** 分析需求倒逼 **埋点/日志/ETL** —— 数科常在 **业务—数据—工程** 之间翻译。  
**答案：**

1. **定义步骤：** 与产品把漏斗画成 **事件序列 + 时间窗**（同会话/24h/7d）。  
2. **缺口清单：** 哪一步缺事件、缺 **属性**（如商品类、实验桶）；是否可用 **页面 PV/接口日志** 代理。  
3. **路径：** **v0** 用现有近邻指标或抽样埋点验证；**v1** 走正式埋点/表结构评审，明确 **验收方式**（测试环境抓包、分区首日落盘检查）。  
4. **预期管理：** 说明 **回填不可得**，从 **新数据生效日** 起建 funnel；周报里 **分段注释**，避免和历史错误拼接。

---

### 32. 业务场景：算法同事要你协助做一个排序/分层模型，但业务提供的标签噪声大、正负样本混了活动流量，你怎么协作？

**问题本质：** JD 里的 **特征工程、标注、模型验证**——**垃圾进则垃圾出**，产品化要先清标签与评估协议。  
**答案：**

1. **标签治理：** 与业务逐条写 **标注规则**（什么算正例、剔除大促/券、冷启动期是否单独处理）；做 **双人抽检与不一致率**。  
2. **特征：** 与时间相关的特征 **严格防泄漏**（对齐我做时序预测时的切分方式）；记录 **缺失与延迟**，用 **baseline（规则/浅模型）** 先打穿链路。  
3. **验证：** **时间外推** 或 **分桶 hold-out**；看 **分群上的指标** 而不只看总体 AUC，防 **头部偏差**。  
4. **上线姿态：** 建议 **shadow（只看不决策）→ 小流量 → 护栏指标**；周报单独设 **bad case 与漂移监控**——与 **Agent 项目里「机器生成+人复核」** 同一原则：**高风险决策不自动兜底**。

## 七、考前速背（关键词）

- **指标**：北极星、拆解、口径、同环比、cohort、漏斗、渗透率、异动贡献。
- **数据**：事实表/维度表（基础概念）、增量、分区、主键、一对多。
- **假设检验**：\(H_0/H_1\)、\(\alpha\)、p 值、第一类/第二类错误、功效 \(1-\beta\)、效应量、不拒绝≠不证明。
- **分布**：二项（固定 \(n\)、成功次数）、泊松（单位时间到达、稀有事件）、二项→泊松极限。
- **销量下滑贡献**：\(\Delta S=\Delta S_{\text{新}}+\Delta S_{\text{老}}\)、客群下钻量率单、与显著性/混杂控制区分。
- **业务场景**：异动先排数据新鲜度/口径、指标字典四件套、cohort+漏斗下钻、埋点缺口 v0/v1、ML 标签治理与 shadow。
- **看板设计（口述）**：先受众与刷新节奏；**高管**=KPI 条+贡献拆解+异动列表；**运营活动**=活动期对比+漏斗+渠道；**产品**=版本筛选+功能渗透+留存对照（慎谈因果）；**技术×业务**=统一时区+发布/故障标线；**ToB**=租户健康分+分桶；**一页布局**=左筛选、上 KPI、中趋势+结构、下 TopN+口径脚注。
- **ML**：泄漏、baseline、离线在线、标注指南、bad case。
- **协作**：PRD式口径、对账、周报结构、优先级（影响×可行性）。

### 3. 假设检验 · 第一/二类错误（检索共识）

- **第一类错误（弃真）**：\(H_0\) 为真却拒绝；概率上由 **显著性水平 \(\alpha\)** 控制。  
- **第二类错误（采伪）**：\(H_0\) 为假却未拒绝；概率为 **\(\beta\)**，**功效**为 **\(1-\beta\)**。  
- **常见结论**：固定样本下两类错误往往 **此消彼长**；**增大样本量** 通常可同时降低两类错误风险；实务中常 **优先严格控制第一类错误**（领域不同会有差异，金融/合规场景尤为敏感）。细节可跟踪统计教材或 [腾讯云开发者社区 · 数据分析面试手册（统计篇）](https://cloud.tencent.com.cn/developer/article/2159999) 类长文系统复习。
