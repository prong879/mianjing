## 三、你需要掌握的知识（备考清单）

按「数据工程底座 → 业务分析 → 可视化 → 机器学习协作 → 软技能」组织；打钩项建议结合 [冲刺路线](/guide/exam-cram) 与 [数分高频题](/interviews/01-data-analytics/highlights) 自测。

### 1. SQL（岗位要求「复杂查询」）

- **多表关联**：INNER/LEFT JOIN、一对多膨胀的控制、去重策略。
- **聚合与分组**：GROUP BY、HAVING、常见业务口径（去重用户数、订单数、金额）。
- **窗口函数**：`ROW_NUMBER` / `RANK`、`SUM() OVER (PARTITION BY … ORDER BY …)`、移动平均、同比环比。
- **留存与漏斗**：按 cohort 定义首日、次日/7 日回访；漏斗步骤表设计与转化率计算思路。
- **数据质量**：NULL、重复键、时间区、边界日期、增量表的 **snapshot vs event** 区别。

### 2. Python 数据分析栈（JD：Pandas / NumPy / Matplotlib / Seaborn）

- **Pandas**：索引、merge、groupby、透视、缺失与异常值处理、内存与数据类型优化（大表场景）。
- **NumPy**：向量化基础；与统计量的衔接。
- **可视化**：趋势、分布、相关性、分组对比；图表**服务于结论**而非堆图。
- **自动化**：定时任务、日志、可复用配置（与实习中「定时入库」叙事一致）。

### 3. 指标体系与业务分析

- **OSM / 北极星**：O 目标—S 策略—M 度量；避免指标堆砌。
- **拆解**：乘法拆解（如流量×转化×客单）、加法拆解（分部汇总）、维度下钻（渠道、版本、客群）。
- **异动分析框架**：确认口径 → 拆分维度 → 排除已知活动/故障 → 假设验证 → 建议与下一步数据需求。
- **漏斗**：定义步骤事件、流失环节、时间窗口一致；与埋点/日志的关系（若公司有数仓可简述分层）。

### 4. 用户行为 / 留存 / 转化（补足互联网语境）

- **留存**：次日/7 日/30 日、粘性（DAU/MAU）、cohort 表逻辑。
- **转化**：注册→激活→关键行为→付费（按业务替换）；**关键行为**如何与业务共创定义。
- **用户分群**：RFM 思路、行为序列简化版本；与「因子分层」「风险分层」类比。

### 5. BI 工具（Tableau / Power BI）

- **概念迁移**：数据源、度量/维度、计算字段、参数、刷新策略。
- **看板设计**：受众（高管/运营/产研）、一页一决策、异常高亮、下钻路径。
- **实操**：任一工具跟一门短教程做出「趋势 + 漏斗 + 分渠道」样板项目写进话术。
- **场景命题**：见下文 **第四节末「看板设计：业务命题演练」**，覆盖高管经营舱、运营活动、产品功能、技术侧与 ToB 健康度等典型问法。

### 6. 机器学习协作（特征、标注、验证、调参）

- **特征工程**：连续/类别处理、缺失、Scaler、时间特征泄漏防范。
- **标注**：规范、一致性、抽检、难例回流；与人协作流程。
- **验证**：训练/验证/测试、交叉验证概念、baseline 重要性、过拟合与样本外。
- **指标**：分类（准召、AUC 等）、回归（MAE/RMSE），与业务成本的挂钩。
- **与您项目的连接**：时序切分、滚动窗口、结论可解释性（Streamlit 展示思路）。

### 7. 大数据/数科实习通用软技能

- 与业务对齐**口径**的书面习惯（字典、CHANGELOG）。
- **周报结构**：结论先行—核心数字—拆解—假设—数据需求—风险。
- 对 **Agent/LLM**：作为「辅助标注、摘要、SQL 草稿、文档生成」的定位，强调**可追溯与人工复核**。

## 四、二十问速答（本 JD 核心 · 建议优先背诵）

下列 20 题严格对齐**第一节存档 JD**，覆盖**清洗与标准数据集**、指标体系与周月报、行为/留存/漏斗、BI、ML 协作、调研与文档、SQL/Python、院校与出勤、公司认知与场景；**同节**附 **「张茂源简历 × 数巅 JD」mentor 追问 20 题（表格）** 与 **看板设计业务命题（A～F）**。**口播时可把括号内换成你的真实经历与公司具体业务名。**

### 1. 你怎么理解这个「数据科学实习生」的日常工作？

**答案：** 我理解是「**承上启下**」：对上承接分析师/科学家拆好的业务问题，把**脏数据洗成可信、粒度清晰的标准数据集**；中间参与**指标字典与看板**，盯**产品/运营/技术**相关指标异动并写**周或月报洞察**；对下在 ML 项目里做**特征、标注、验证与调参**的辅助，保证离线效果**可解释、可复现**。杂项还包括**数据调研和文档**，本质是让别人能**按文档重复你的结论**。

### 2. 「清洗、预处理、质量校验」之后，怎样才算「标准化分析数据集」？

**答案：** 至少满足四件事：**（1）口径书面化**——主键（如用户日、订单 ID）、时间字段语义、去重规则、是否含退款/测试。**（2）质量可量化**——缺失率、重复键、值域与环比异常阈值。**（3）可追溯**——来源表、Transform 版本、刷新频率。**（4）消费友好**——字段命名统一、宽表或星型结构符合团队习惯，能直接进 SQL/BI/Notebook。不是「洗过一次」，而是**能进线上周报链路且改版有 changelog**。

### 3. 参与「核心指标体系」搭建与维护，你会怎么做？

**答案：** 先和业务用 **OSM** 对齐：**O** 这一阶段的核心目标是什么、**S** 关键策略有哪些、**M** 用哪些度量跟进（**北极星 1 个 + 结果指标少数 + 过程指标可控数量**）。再落成**指标卡片**：中英文名、分子分母、统计粒度、延迟、负责人。维护上：**异动时不先改口径**，先查数据新鲜度与已知活动；版本变更写进字典并@**消费方**（报表/看板）。

### 4. 周 / 月度「数据洞察报告」你建议怎么组织？

**答案：** **执行摘要 5 行**：本期结论 + 需业务动作。**核心数字**：北极星与同环比、贡献前二的拆解。**专题**：如留存、漏斗、某版本——每节都是「现象—假设—证据—未决问题」。**数据质量与局限**：延迟、口径调整、样本偏差。**附录**：关键 SQL/图表索引。原则：**第一屏就能回答「所以呢、谁要干嘛」**。

### 5. 用户行为分析你通常从哪切入？

**答案：** 先定**分析单元**（人/会话/设备）和**关键路径**（注册—激活—核心行为）。从**渗透与频次**看功能是否被用起来，从**路径与停留**看卡点，从**分群**（渠道、新老、端）看是否局部问题。缺埋点时诚实说需要 **v0 代理指标 + v1 埋点** 路线，不硬编结论。

### 6. 做留存分析前，你必须和业务对齐什么？

**答案：** **「活跃」操作定义**（登录 / 关键行为 / DAU 规则）、**首日 cohort 锚点**（注册日还是首活）、**自然日 vs 滚动 24h**、**时区**、是否剔测试账号。这些不定，留存曲线**不可比**。

### 7. 漏斗分析最容易踩的坑？你怎么避免？

**答案：** **步骤事件不对等**（前端 PV 混后端下单）、**时间窗不一致**（有的按会话、有的按 7 日）、**窗口内重复计次**、**强依赖缺失步骤埋点**。避免方式：与产品写清**事件名 + 属性 + 窗口 + 去重规则**，上线前**单行样本对账**。

### 8. Tableau / Power BI 做「监控向」看板，你最坚持哪三点？

**答案：** **（1）指标语义在界面上可读**（脚注或 tooltips 写口径与更新时间）。**（2）刷新与延迟**和业务预期一致，标注**数据截至时点**。**（3）受众分层**——老板看「北极星+异常」；执行同学能**下钻维度**。必要时做**异常高亮规则**，避免纯「漂亮但读不懂」。

### 9. JD 写了解 BI，你目前不熟，怎么回应？

**答案：** 诚实说当前熟练度，补一句**迁移能力**：已在 Python/（或 Streamlit）里做过 **度量×维度×筛选**，理解 **语义层** 概念；入职前/第一周会按团队选型刷 **官方教程 + 一个脱敏 demo（趋势+漏斗+下钻）**，并在**度量/DAX 或 LOD**上各做一小练。接受团队规范为主。

### 10. 参与 ML：特征工程举例，如何避免信息泄漏？

**答案：** （例）用时序或行为构造滞后特征、滚动统计时**严格按时间切分**：训练集只用 \(t\le T\) 的信息，验证/测试集在 \(T\) 之后；不用「**当时还不知道」**的标签或全样本统计填回过去。分类任务注意**目标编码**、**样本权重**里的泄漏。交付时写**特征说明表**方便他人 audit。

### 11. 协助「数据标注」时你怎么控质量？

**答案：** **指南写死**：边界案例、**否定示例**、输出格式（JSON/枚举）。**双人抽检 + 不一致率**入周报；难例回流迭代指南。大模型辅助标注时坚持**人工终审**与**可追溯 ID**，不把生成当金标准。

### 12. 「模型效果验证与调优」你会汇报什么给团队？

**答案：** **任务与 baseline**（规则/简单模型）对比；**主指标 + 业务成本相关副指标**（如误报代价）；**分群表现**（避免均值骗人）；**稳定性**（时间外推）；**bad case** 类型与是否接受。**调参**记录关键实验表，避免「魔法数字」。

### 13. JD 要求 SQL 复杂查询，你熟悉哪些典型模式？

**答案：** 多表 **JOIN** 与一对多控制、**GROUP BY + HAVING**、**窗口函数**（累计、同比、排名）、**留存 cohort**（首活日 join 次日事件）、**漏斗**（步骤事件与时间窗）。能口述**一次你写过或读过的较复杂分析 SQL 的业务目的**即可。

### 14. Python（Pandas/NumPy）做分析，你如何保证可复现？

**答案：** 固定**数据源版本与时间切片**；脚本**参数化**（路径、日期）；**随机种子**；依赖 **requirements**；大表注意 **dtype** 与分块。**输出**不仅 notebook，还有**可运行的脚本或入口**，方便定时跑。

### 15. 「数据调研」文档你会写哪些部分？

**答案：** 背景与问题、**干系人**、现有数据源清单（表/字段/延迟）、**缺口与风险**、竞品或行业**参照**（若适用）、建议的**指标草案与 POC 计划**、时间与人力估算。目的是：**读文档的人能决定是否立项、数据从哪来**。

### 16. 报表数字和业务后台不一致，你怎么处理？

**答案：** **不对抗、先对账**：对齐**单行样本**、过滤条件（测试/退款）、**时间边界**（创建/支付/完成）、**关联键是否膨胀**。分层查**同步延迟、ETL bug、口径版本**。输出简短**根因+修复 owner+预防监控**，写进字典或群公告。

### 17. 早会发现「核心指标」异动很大，但业务体感不符，你第一步做什么？

**答案：** **锁口径与新鲜度**：定义变没、调度延迟、分区是否齐；再**与后台/日志抽样**核对。排除数据问题后再做**维度下钻**与**假设列表**。在结论未稳前**避免对外传「大变盘」**，标注数据状态。

### 18. JD 写了院校门槛（985/211 或 QS 前 100），你怎么得体回应？

**答案：** 若符合：简洁陈述**学校与在读学位**，转到**能力与匹配**。若边界情况（如强专业弱排名）：强调**专业训练（统计/计量/代码）+ 可验证项目（实习/Git）**，表态尊重公司人力政策并欢迎用**笔试/作业**证明。**不贬低其他院校**。

### 19. 北京线下、每周至少 4 天、3 个月以上、尽快到岗——你如何回答？

**答案：** 按事实说：**可到岗日期**、每周哪几天、持续多久；若**课程/论文**可能冲突，说清**如何提前两周沟通与交接**。强调理解**出勤**对业务节奏的意义，不空口承诺。**住房与通勤**若稳定可一句带过增加可信度。

### 20. 你为什么投数巅？对公司有什么了解？

**答案：** **匹配**：JD 要的 **SQL+Python+指标+BI+ML 协作** 与我的 **（实习：口径/管道/异动/模型验证）** 同构。**公司**：数巅公开信息多指向 **数据智能、企业数据资产与智能化**（含大模型应用语境）；**以官网为准**，我关注 **ASK/BI 或 X-Engine 等产品线** 如何落到「可信数据 + 分析 + 决策」。**反问**：当前团队**数仓栈、BI 选型、ML 主要场景**是什么——显得做过功课且不胡编细节。

### 看板设计：业务命题演练（Tableau / Power BI 口述结构）

下列场景为面试高频：**先问受众与决策频率，再定北极星与下钻路径**；工具上统一说成 **「总览 KPI 区 + 趋势 + 分布/结构 + 明细或跳转」**，并强调**全局筛选器（日期/渠道/端/客群）**与**数据更新时间**脚注。公司若为 **ToB / 数据产品**，把「租户」当作**分析粒度**即可迁移。

#### 场景 A：CEO 要「每周花 10 分钟看清公司经营」

**命题：** 管理层不看 SQL，要一张经营驾驶舱，且每周例会直接用。

**设计思路：**

1. **受众与节奏**：周更、周一早会前刷新；允许 T+1 延迟需在页眉**标注截至时点**。  
2. **首屏 KPI 条**（同比/环比 + 小趋势 sparkline）：**收入或 GMV**、**活跃用户数（或合同侧 ARR/续费若 ToB）**、**获客或转化主指标**、**单位经济或毛利类**（按公司实际四选三～四，忌超过 6 个）。  
3. **第二屏拆解**：**贡献结构**（渠道/产品线/地域 stacked bar 或瀑布）+ **异常列表**（Top 涨跌维度）。  
4. **下钻**：从 KPI 点进到「维度详情 Tab」，预置**「本周异动简报」**文本框位（可接周报结论）。  
5. **权限**：高管全量；敏感成本项单列权限或脱敏。  
**坑：** KPI 堆砌、没有「**So What**」区；环比与外推活动**未标注活动日历**。

#### 场景 B：运营负责人要「大促 / 活动复盘」看板

**命题：** 活动周期间每日盯转化，结束后要归因与经验沉淀。

**设计思路：**

1. **时间轴控件**：**活动期 vs 前同台期**对比（或 baseline 7 天）。  
2. **漏斗主线**：曝光 → 访问/线索 → 下单/付费（步骤与窗口与埋点**书面一致**）。  
3. **分渠道/创意**：**转化与成本并排**（若有投放数据）；否则至少**渠道 + 客群**。  
4. **增量 Attempt**：有实验桶则展示**实验组 vs 对照**；无则**醒目注明「描述性相关、非因果」**。  
5. **沉淀区**：**爆款路径 / 失利环节 / 下次活动检查清单**（可接文档链接）。  
**坑：** 活动流量污染**留存 cohort**；**退款/取消**未统一过滤。

#### 场景 C：产品经理要「新功能是否被用起来、对留存有没有帮忙」

**命题：** 上线 4 周内评估**功能渗透率**与**行为–留存**相关线索。

**设计思路：**

1. **功能定义**：**关键事件** + **首用/复用**分开；**版本号**全局筛选。  
2. **渗透率**：**功能用户数 /  eligible 用户数**（eligible 与产品对齐，如近 30 天活跃）。  
3. **留存辅助视图**：**用过该功能的用户 vs 未用**的 **D7/D30** cohort（分层控制：新老、渠道；高级可做 PSM **口播提一句即可**）。  
4. **体验路径**：从**入口来源**到**完成核心任务**的 Sankey 或步骤条（数据不足则简化为步骤转化率）。  
**坑：** eligible 口径不稳导致渗透**虚高/虚低**；把**相关当因果**写进看板标题。

#### 场景 D：技术负责人要「稳定性 + 性能」与「业务影响」同屏（JD 中「技术等维度」）

**命题：** 故障、延迟、错误率如何和**核心业务分钟级指标**对齐复盘。

**设计思路：**

1. **技术条**：**可用性 / P99 延迟 / 错误率 / 发布事件**时间线（与监控告警源一致）。  
2. **业务条**：**请求量、订单创建成功率、支付成功率**等同粒度时间序列。  
3. **联动**：**竖线标注**「部署/故障窗口」，支持**框选时段**对比前后 Δ。  
4. **明细**：**Top 接口 / Top 错误码**表，可跳转日志或工单。  
**坑：** 技术时间 UTC、业务时间本地**未统一**；业务指标**延迟大于**技术指标导致误读。

#### 场景 E：客户成功 / ToB 交付——「租户健康度」监控（贴近数据智能、多租户产品）

**命题：** 多客户订阅，需提前发现**用量下滑**与**流失风险**。

**设计思路：**

1. **租户列表**：**健康分**（如近 4 周登录天数、查询次数、活跃人数、核心功能使用）。  
2. **单体租户页**：**账号数、存储/查询量、关键功能渗透率**趋势；**工单与 NPS** 若有则并列。  
3. **预警规则**：**连续 N 周下滑**、**低于同规模中位数**高亮；对接 CS 责任人字段。  
**坑：** **租户规模不一**未做分桶，健康分**不公平**；数据隔离与**合规**未在权限层处理。

#### 场景 F：面试官追问「一页纸画板布局」——30 秒口述模板

**答案：** **左窄右宽**：左列**全局筛选**（日期、渠道、端）；上排 **4 个 KPI**；中左 **主指标周/日趋势**，中右 **结构图**（渠道或产品）；下方 **TopN 表格 + 异常注释**；页脚**口径与刷新时间**。**原则**：每个区块只回答**一个问题**；超出问题移入二级页或 Tooltip。

## 五、扩展题库（43 组 · 深度演练）

下列答案按你的简历量身定制；口播时请替换虚构数字为真实项目量级。**第 21–37 题为统计、量化实习与业务拆解补充；第 38–43 题为贴合 JD 的「日常业务场景」演练。**

### 1. 为什么从量化/投研数据产品转向数科实习？

**答案：** 我在证券实习和项目里积累了**数据管道、指标口径、可复用工具化和报告输出**的经验；数科实习只是把「标的物」从券种/成分股换成**业务用户与产品行为**，方法论仍是「定义问题—建指标体系—清洗与建模—验证—沉淀看板与文档」。我希望在更偏 **plumbing + insight + ML 协作** 的环境里补齐互联网业务语境。

### 2. 简述你最自豪的一个数据相关项目（1 分钟）。

**答案：** 我做过 ETF 成分股异动监控与日报 Agent：从 AkShare 拉行情，对大量成分股算收益、量比、超额收益、波动等**规则化异动**；再交给 Explain/Review Agent 生成解释与复核摘要，减少人工筛与写日报时间。另一条线是华福转债多因子系统：**PRD 驱动**的「数据入库—因子计算—查询与可视化」，把研究员手工脚本沉淀成 Flask+MySQL 工具。两条线都体现 **指标—异常—解释—复盘** 的闭环。

### 3. 你在华福实习里梳理的「指标体系」和长宽表，和互联网公司指标体系有什么异同？

**答案：** 相同点：都要 **明确统计口径、主键、时间粒度、更新频率**；都要服务可追溯的报表。不同点：金融侧更强调 **因子可比性、调仓/交易日历法、多空与基准**；互联网侧更强调 **用户粒度、行为事件、漏斗与留存 cohort**。我能把金融里「因子字典 + 计算编排」迁移到「事件字典 + 指标分层（入口/过程/结果）」。

### 4. SQL 题风：如何计算「次日留存」？你会问业务方澄清什么？

**答案：** 澄清 **「活跃」定义**（登录/关键行为/访问页面）、**自然日还是 24h rolling**、**新用户首日是注册还是首访**。典型思路：取每个用户首日 `d0`，再看 `d0+1` 是否出现活跃事件；按 `d0` 分组算留存率。注意时区、去重设备/账号、刷量/测试账号过滤。

### 5. 漏斗转化率在中间一步暴跌，你怎么排查？

**答案：** 先 **对齐漏斗事件与窗口**（同一会话还是 7 日内）；再 **分渠道/版本/客群** 看是否局部问题；检查 **技术故障、埋点缺失、文案/流程改版** 时间点；做 **前后区间对比** 与 **用户回访样本**（若有）。输出：最可能的 2～3 个假设 + 需要补的日志/维度 + 验证排期。

### 6. 数据质量出问题（报表与业务后台对不上），你怎么处理？

**答案：** 分层排查：**采集/同步** 是否延迟；**过滤条件**（取消单、测试单）是否一致；**时间边界**（创建/支付）；**关联键** 是否一对多膨胀；**口径文档**是否版本过期。先与业务对齐「单行样本」对账，再写清结论与修复 owner。

### 7. 你如何设计一个「核心指标驾驶舱」给业务负责人？

**答案：** 一页 **北极星 + 3～5 个结果指标 + 10 个以内过程指标**；每张图能回答一个决策问题；支持 **时间对比与维度下钻**；标注 **口径与数据更新时间**；异常用规则或阈值高亮。工具上用 Tableau/Power BI 或等价方案，关键在 **度量定义稳定**。

### 8. 你没有太多 Tableau/Power BI 经验，入职后怎么补？

**答案：** 我会用一周集中做出 **Demo 看板**：连接示例或脱敏数据，练习 **LOD（Tableau）或 DAX（PBI）** 基础；把我在 Streamlit/Plotly 里做过的图迁移成 **标准商业模板**；向团队要 **样式与权限规范**，保证第一版就符合发布习惯。

### 9. 讲一个你做「特征工程」的例子，如何避免信息泄漏？

### 22. 你对「假设检验」如何理解？

**答案：** 假设检验是在 **样本有噪声** 的前提下，对**总体**的某种陈述（通常写成原假设 \(H_0\)）做**可操作的决策规则**：选一个检验统计量、给定显著性水平 \(\alpha\)，看样本实现是否落在「在 \(H_0\) 为真时足够罕见」的区域；或用 **p 值** 概括该罕见程度。

我理解的三点是：  
1. **证伪倾向**：经典表述是「拒绝 \(H_0\)」或「不拒绝 \(H_0\)」，而不是把 p 值当成「\(H_1\) 为真的概率」。  
2. **预设规则**：\(\alpha\)、单侧/双侧、样本量与功效（1−β）要在分析前或方案里说清，避免事后挑结果。  
3. **与业务的衔接**：检验回答的是「**随机波动能否解释眼前差异**」；业务还要补一句「**即使显著，效应量多大、是否值得做**」。

### 23. 你如何理解第一类错误和第二类错误？

**答案：**  
- **第一类错误（Type I）**：\(H_0\) 实际为真，却 **拒绝了 \(H_0\)** ——「**假阳性**」。控制它的概率是显著性水平 **\(\alpha\)**。  
- **第二类错误（Type II）**：\(H_0\) 实际为假，却 **没有拒绝 \(H_0\)** ——「**假阴性**」。其概率常记 **\(\beta\)**，**检验功效**为 **\(1-\beta\)**（正确检出真实效应的能力）。

**权衡：** 把 \(\alpha\) 卡得很严会减少误报，但样本量不够时会增大漏报；**增大样本**通常能同时改善两类风险（在固定 \(\alpha\) 与真实效应下提高功效）。业务上：**强合规/资金相关**常更忌讳第一类错误；探索性分析可先接受较高 \(\alpha\) 或强调置信区间与效应量，再配合实验复现。

### 25. 泊松分布和二项分布的区别是什么？

**答案：**  
| 维度 | 二项分布 | 泊松分布 |
| --- | --- | --- |
| 典型场景 | **固定 \(n\) 次**独立试验，每次成功概率 \(p\)，成功次数 \(X\) | **固定时间/空间窗口**内，**稀有事件**发生次数，均发生率 \(\lambda\) |
| 参数 | \(n,\,p\) | \(\lambda\)（单位时间平均次数） |
| 取值 | \(0,1,\ldots,n\) | \(0,1,2,\ldots\) |
| 关系 | 当 \(n\) 大、\(p\) 小且 \(np\to\lambda\) 时，**二项近似泊松** | 可作为「很多小概率事件」的极限模型 |

**业务直觉：** **二项**适合「\(n\) 个用户每人是否转化」「\(n\) 次曝光中点击次数」；**泊松**适合「单位时间内到达数、请求数、缺陷数」等 **率驱动** 的计数（需检查是否过离散/是否独立同分布等假设）。

### 26. 你在量化实习里说参与搭建了因子相关体系，具体是怎么建立的？

### 27. 你怎么梳理研究员的真实分析流程？团队里不同分析师可能有不同风格，你怎么处理？

**答案：** 我不会只听一个人说“我们平时就是这么做的”，因为投研团队里不同研究员确实会有自己的脚本习惯、指标偏好和复盘方式。我会把它当成一个 **业务流程调研 + 共性抽象 + 个性配置** 的问题来做。

具体方法一般分四步：

1. **先跟一到两个典型研究员跑完整流程：** 不只问“你需要什么功能”，而是看他从拿数据、清洗、算因子、筛券、画图、回测、写复盘，到最后输出结论的完整路径。重点记录每一步的输入、输出、判断条件和痛点，比如哪一步最耗时、哪一步经常对不上、哪一步依赖手工复制。  
2. **把流程拆成标准模块：** 不同研究员风格不同，但底层通常都能拆成 **数据输入 → 口径处理 → 指标/因子计算 → 查询筛选 → 图表展示 → 回测复盘 → 导出报告**。我会先抽象这些共性模块，而不是直接照搬某个人的脚本界面。  
3. **把差异项做成参数或配置：** 例如有的研究员更关注估值因子，有的更关注动量或波动；有的人偏好分层收益，有的人偏好单券明细。这类差异不一定要做成完全不同系统，而是沉淀成筛选条件、因子分组、默认图表、导出模板等可配置项。  
4. **用样本任务反向验证流程：** 选一个真实历史分析任务，让研究员按新流程走一遍，看是否能复现原来的结论，是否减少重复操作；如果某个环节他们仍然绕回 Excel 或私有脚本，说明我抽象得还不够，需要回去补需求。

对于不同分析师风格，我会区分 **“必须统一的口径”** 和 **“可以保留的习惯”**。必须统一的是数据源、字段定义、缺失处理、回测时间边界、因子公式这些会影响结果可信度的东西；可以保留的是看图偏好、排序方式、默认筛选条件、导出格式等使用习惯。这样既不会让系统变成某一个研究员的个人工具，也不会为了统一而牺牲实际使用效率。

面试收束可以说：**我梳理流程的重点不是把所有人的习惯强行磨平，而是先抽象出共性的分析链路和统一口径，再把个性化部分做成配置。这样系统既可复用、可维护，也能让不同研究员愿意真的用起来。**

### 29. 你怎么分析客户提出的需求？请结合你之前实习的经历举例。

**答案：** 我分析客户需求时，一般不会停留在客户原话，而是先判断他背后的业务目标、当前流程卡点、数据是否可得，以及最后怎么验收。以华福实习为例，研究员提出的需求可能是“希望能更方便地看可转债因子、做筛选和复盘”。如果只按字面理解，很容易直接做一个查询页面；但真正要分析的是：他为什么觉得现在不方便，是数据分散、脚本难复用、口径不统一，还是结果展示不够直观。

我会按五步处理：

1. **还原使用场景：** 先问这个需求发生在什么工作节点，比如盘前筛券、盘后复盘、策略回测，还是写报告前取图；不同场景对实时性、准确性和展示方式要求不一样。  
2. **拆出真实目标：** 把“想要一个功能”翻译成“要解决什么问题”。例如研究员说想快速查因子，本质可能是想减少重复跑脚本、统一因子口径、快速比较不同转债或不同时间段。  
3. **确认数据与口径：** 看这个需求需要哪些表、哪些字段、更新频率如何，因子公式、缺失处理、复权口径、回测窗口是否已经明确；如果口径没定，先补口径文档，而不是急着开发。  
4. **划分优先级：** 先做高频、共性、可验证的部分，比如基础筛选、因子查询、图表展示、导出；对个别研究员的特殊偏好，先做成参数或后续迭代，不让第一版过度复杂。  
5. **定义验收标准：** 不是页面能打开就算完成，而是要能用真实样本对账，比如抽一只转债、一个交易日，与研究员原脚本或手工结果一致；同时看是否真的减少重复操作。

这个过程里，我会特别注意区分 **客户说的解决方案** 和 **客户真正的问题**。比如客户说“我要导出 Excel”，可能真实需求是“我要把结果放进报告或和同事复核”；那系统里除了导出，还可能需要字段说明、图表下载、口径注释。再比如客户说“这个因子不对”，不一定是代码错，也可能是缺失值处理、交易日对齐或复权口径不一致。

面试收束可以说：**我分析需求的方式是先还原业务场景，再把客户语言转成可计算的数据口径、可开发的功能模块和可验证的验收标准。这样既能避免只做表面功能，也能减少后续因为口径不清导致的反复返工。**

### 30. 你之前的数据清洗一般是怎么做的？

**答案：** 我做数据清洗一般不是简单地 `dropna` 或删异常值，而是先围绕分析目标确定 **数据粒度、主键、时间口径和关键字段**。以华福可转债项目为例，如果后续要做因子计算和回测，清洗时就必须保证同一只转债、同一交易日的数据唯一且可追溯，否则后面算出来的收益率、分层表现或回测结果都会失真。

具体步骤一般是：

1. **先定口径和粒度：** 明确是一行一只转债一个交易日，还是一行一个因子结果；时间用交易日还是自然日；价格是否复权，停牌和退市怎么处理。  
2. **字段标准化：** 统一证券代码、交易日格式、字段命名和数据类型，避免不同来源表里代码格式、日期格式不一致导致 join 错。  
3. **缺失和重复处理：** 对关键字段看缺失率和重复键；关键指标缺失不能直接填 0，要先判断是停牌、数据源缺失还是业务上本来不存在。重复行则按主键定位原因，看是数据源重复还是 join 膨胀。  
4. **异常值检查：** 对价格、成交量、转股溢价率、收益率等字段做值域和分布检查；极端值不一定直接删除，要判断是市场真实波动、复权问题，还是数据错误。  
5. **对账和留痕：** 抽样拿单只转债、单个交易日和原始数据或研究员手工稿对账；清洗规则写进字段说明或 PRD，保证别人能复现。

面试收束可以说：**我理解的数据清洗不是把数据“弄干净”这么简单，而是把数据变成能被后续指标、回测、看板稳定消费的标准化数据集。每一个缺失、异常和去重规则，都要能解释为什么这么处理。**

### 31. 你的流程拆解过程是怎么做的？

**答案：** 我拆流程时会先从业务结果倒推，而不是一开始就画功能模块。比如华福的需求不是单纯“做一个系统”，而是让研究员更高效地完成可转债因子分析、筛选、回测和复盘，所以我会先问最终交付是什么：是筛选出候选券、输出因子表现，还是生成复盘图表。

具体拆解通常分四层：

1. **角色和目标：** 谁在用，研究员还是实习生；他在什么场景用，是日常跟踪、专题研究还是报告输出；最终要做什么决策。  
2. **业务步骤：** 把真实工作流拆成 **数据获取 → 数据清洗 → 因子计算 → 条件筛选 → 图表分析 → 回测验证 → 导出复盘**，每一步标清输入、输出和依赖。  
3. **数据和规则：** 每一步需要哪些字段、口径、计算规则和异常处理，比如缺失值怎么填、滚动窗口怎么取、筛选条件怎么组合。  
4. **产品和验收：** 哪些步骤适合系统化，哪些保留人工判断；页面需要哪些筛选器、图表和导出；最后用真实样本检查是否能复现研究员原来的结果。

拆解过程中我会特别关注两个点：第一，找 **高频且标准化** 的环节优先沉淀，比如固定字段清洗、因子批量计算、常用图表；第二，把 **需要人工判断** 的环节保留下来，比如因子解释、策略取舍、最终结论，不强行自动化。

面试收束可以说：**我做流程拆解的原则是“先业务目标，后功能模块；先共性链路，后个性配置”。这样拆出来的东西不会只是页面清单，而是能真正支撑用户完成一条完整工作流。**

### 32. 之前你是针对 B 端方向，你一般怎么考虑可视化呈现和可视化分析？思路是什么？

**答案：** B 端可视化我不会只追求图好看，而是先问这个页面服务谁、要支持什么判断、使用频率多高。以华福内部投研工具为例，研究员看图不是为了“浏览数据”，而是为了更快判断某个因子是否有效、某只转债是否异常、某段回测表现是否稳定，所以可视化要服务分析动作。

我的思路一般是四步：

1. **先定受众和决策：** 研究员需要的是筛选、比较、复盘，不是泛泛看大盘；所以首屏要放最关键的因子表现、筛选条件和结果列表。  
2. **按分析链路组织页面：** 从 **总体概览 → 条件筛选 → 单券/分组详情 → 回测或历史走势 → 导出复盘**，让用户能从宏观到明细逐层下钻。  
3. **图表选择服务问题：** 趋势看折线，分布看箱线或直方，分组收益看柱状或分层曲线，单券对比看明细表 + 走势图；不为了炫技堆复杂图。  
4. **把口径和异常写在界面上：** B 端用户很看重可信度，所以图表旁边要标注更新时间、字段口径、缺失处理、筛选条件；异常值最好能点到明细，方便对账。

和 C 端看板相比，B 端可视化更强调 **可解释、可追溯、可下钻、可导出**。比如研究员看到某个因子分层收益异常，不仅要知道图上哪里异常，还要能继续点到具体日期、具体券、具体字段，判断是数据问题、市场事件，还是因子本身有效。

面试收束可以说：**我做 B 端可视化的核心思路是“一页图回答一个分析问题”，并且让用户能从结论回到明细和口径。好看的图只是表现形式，真正重要的是能不能支持业务方更快、更可信地做判断。**

### 33. 你在之前的量化实习中，一般是怎么去处理数据的？

**答案：** 我一般不会一上来就直接写清洗脚本，而是先把这次分析要服务的投研问题和数据粒度定清楚。比如在华福金工组做可转债因子分析和回测复盘时，我会先确认分析对象是 **转债日频**、**正股日频**，还是某个回测窗口下的因子结果；再和研究员对齐字段口径，比如价格是否复权、收益率怎么计算、缺失值和停牌怎么处理、回测截止日能不能用未来信息。

具体处理链路大致分五步：

1. **数据抽取与统一：** 从行情、基本面或内部数据源拉取原始表，用 Python/Pandas 和 SQL 统一证券代码、交易日、字段命名和数据类型。  
2. **清洗与预处理：** 处理重复行、缺失值、异常值、停牌日、非交易日对齐等问题；对关键字段做值域检查，比如价格、成交量、余额类字段不能出现明显不合理值。  
3. **口径与特征计算：** 按研究员定义计算因子或指标，例如估值、动量、波动、转股溢价率相关指标；涉及滚动窗口时只使用当前时点之前的数据，避免回测里出现未来函数。  
4. **质量校验与对账：** 抽样拿单只转债或单个交易日和研究员手工结果对账，检查 join 后是否一对多膨胀、缺失率是否异常、分布是否突然跳变。  
5. **沉淀与复用：** 把稳定字段落到 MySQL 或中间表里，配合字段说明、口径文档和异常处理规则，方便后续回测、可视化和复盘重复使用。

面试时可以收束为：**量化实习里的数据处理，本质是把“原始行情和基本面数据”整理成“口径统一、时间可追溯、能直接做因子计算和回测验证的标准化分析数据集”。这和数巅 JD 里的清洗、预处理、质量校验、标准数据集是同一类能力，只是业务对象从金融资产换成了产品、运营或用户行为数据。**

### 34. 你在之前获取这些数据时，会遇到反爬虫之类的情况吗？你是怎么处理的？

**答案：** 会遇到一些类似问题，但我会把它理解成 **数据源稳定性和合规边界** 问题，而不是想办法“硬绕过去”。在量化实习和个人项目里，优先使用的是公司授权的数据源、公开 API、AkShare 这类封装接口，或者团队已有数据库；如果数据源本身有访问频率限制、返回为空、字段变更、接口偶发失败，我会先做稳定性处理，而不是做高频请求。

具体做法一般是几层：

1. **优先用合规数据源：** 公司内部库、授权终端、公开 API 或已有数据表优先；如果网站明确不允许抓取、需要登录授权或出现验证码，我不会继续绕过，而是向 mentor 确认是否有正式数据接口或供应商权限。  
2. **控制请求频率：** 对允许访问的数据源设置合理间隔、分页和批次，不并发压测；能增量就不全量，避免给对方服务造成压力。  
3. **缓存与断点续跑：** 对日频行情、成分股列表这类数据做本地缓存或落库，失败后从上次成功日期继续，不因为一次失败重复请求全量历史。  
4. **异常与变更监控：** 记录状态码、空表、字段缺失、日期缺口；如果接口字段变了或数据突然断档，先标记数据质量问题，再决定是否切换备用数据源。  
5. **口径留痕：** 在文档里写清数据来源、更新时间、缺失处理和限制，避免后续分析把“数据没取全”误判成真实业务或市场变化。

面试收束可以说：**我处理反爬或限流的原则是合规优先、低频增量、缓存复用、失败可追溯。真正重要的不是突破限制，而是保证数据来源合法、链路稳定，并且让下游知道这份数据的边界。**

### 35. 你在华福证券实习时提到大量使用 AI 提高效率，请举一个具体例子：哪些环节用了 AI？为什么这个环节适合用？你如何判断结果可以接受？

**答案：** 我在华福实习里使用 AI 的方式比较克制，不是让它直接替我做投研判断，而是放在 **低风险、重复性高、可验证** 的环节。一个比较典型的例子是：在梳理可转债多因子分析系统时，我会用 AI 辅助整理 **PRD 初稿、字段口径说明、异常处理清单和部分代码草稿**。

当时研究员的工作流比较分散，很多步骤散落在脚本和口头沟通里，比如某个因子字段是什么意思、缺失值怎么处理、页面上要展示哪些筛选项、异常时要怎么提示。如果完全手工整理，时间会花在大量重复表达和格式化上。所以我会先把自己和研究员确认过的真实流程、字段含义、页面需求整理成要点，再让 AI 帮我生成结构化初稿，例如「字段说明表」「页面模块说明」「异常处理 checklist」「SQL/Pandas 代码框架」。这样能把时间从写文档格式、补模板，更多转移到和研究员确认口径本身。

我觉得这个环节适合用 AI，主要有三个原因：

1. **输入边界清楚：** AI 不是凭空判断因子有效性，而是基于我已经确认过的字段、流程和需求做整理。  
2. **结果容易验证：** PRD、字段口径、代码草稿都可以逐条检查；字段是否存在、公式是否正确、SQL 是否能跑、样本结果是否对得上，都能用确定性方式验收。  
3. **风险可控：** 最终进入系统和文档的内容，需要我和研究员复核；AI 只生成初稿，不直接决定投资结论或上线口径。

对结果是否“可以接受”，我一般看三层：第一，**事实正确**，字段名、数据源、时间粒度、缺失处理不能编；第二，**代码可运行且样本对账通过**，比如抽一只转债、一个交易日和原始表或研究员手工结果对照；第三，**业务方读得懂且愿意用**，PRD 里页面字段、筛选条件和异常提示要能支持研究员真实复盘。只有这三层都过了，我才会把 AI 生成的内容沉淀到正式文档或开发任务里。

面试收束可以说：**AI 在我实习中主要提升的是“从零整理到可讨论初稿”的效率，而不是替代最终判断。凡是事实、口径、代码和投研结论，都必须经过数据校验和人工复核；所以我认为它适合用于文档结构化、代码草稿、异常清单和日报摘要这类可验证环节。**

### 36. 你觉得我们的业务项目中，什么环节可以尝试使用 AI 提升效率？基于什么判断可以使用 AI，你是怎么分析的？

**答案：** 我会先把业务项目拆成一条链路：**数据接入与质检 → 指标口径整理 → 周/月报洞察 → 客户或业务问题归因 → 文档与需求沉淀 → 模型/看板迭代**。不是所有环节都适合 AI，我会优先挑 **重复性高、文本或规则密集、结果可被验证、出错成本可控** 的环节试点。

在数巅这类数据智能/数据科学项目里，我觉得可以优先尝试三类环节：

1. **数据质量与异常解释的辅助：** 比如每日指标波动、空值率、重复键、同步延迟等，先由确定性 SQL/规则发现问题，再让 AI 根据规则命中、历史变更记录和字段说明生成排查摘要。它适合 AI，是因为底层判断来自规则，AI 只是把排查过程组织成可读文本，结果可以通过日志、SQL 和单行样本复核。  
2. **指标口径和项目文档沉淀：** 很多项目会反复写字段说明、指标字典、看板口径、会议纪要和需求变更。AI 可以把业务访谈或需求要点整理成结构化初稿，再由数据分析师确认口径。它适合 AI，是因为这类工作标准化程度高，但最终对错可以逐条检查。  
3. **周报/月报初稿和洞察线索：** 对固定模板的经营周报，可以让 AI 基于已经算好的指标、同比环比、Top 维度变化，生成“现象—可能原因—待验证问题”的初稿。它适合 AI，是因为数据结论来自 SQL/BI，AI 负责组织语言和提出假设，不能直接替代最终归因。

我判断一个环节能不能用 AI，主要看四个标准：**第一，输入是否结构化**，比如有明确字段、指标、日志、规则，而不是完全开放判断；**第二，输出是否可验证**，能不能用 SQL、样本、业务口径或人工抽检确认；**第三，风险是否可控**，AI 结果是否只是草稿或建议，而不是直接触发客户决策；**第四，收益是否明显**，是否能减少大量重复整理、摘要、初稿和问答时间。

如果我入职后做试点，我会先选一个小闭环，例如“指标异动日报摘要”或“指标字典问答助手”：先用 SQL 固定异常规则，再让 AI 生成摘要，最后由分析师抽检准确率、幻觉率和节省时间。如果发现 AI 经常编字段、编原因，说明这个环节还不成熟，需要收窄输入或回到规则系统；如果准确率稳定、人工修改量下降，再逐步推广。

面试收束可以说：**我判断 AI 能否落地，不看它回答得像不像人，而看它是不是接在一个可验证的数据链路后面。适合 AI 的环节通常是“规则先判断、AI 做解释和整理、人做最终确认”；不适合让 AI 直接决定指标口径、业务归因或客户结论。**

### 37. 若研究新客、老客谁对「销量下滑」影响更大，怎么量化各自贡献？

**答案：** 先统一 **销量定义与时间窗**（GMV、件数、是否剔退款、同比还是环比），再选一层 **可解释** 的分解，避免拍脑袋。

**（A）可加分解（最直白）：**  
设总销量 \(S = S_{\text{新}} + S_{\text{老}}\)。基期与本期分别有 \(S^0=S^0_{\text{新}}+S^0_{\text{老}}\)，\(S^1=S^1_{\text{新}}+S^1_{\text{老}}\)。  
总变动 \(\Delta S = S^1-S^0 = \Delta S_{\text{新}} + \Delta S_{\text{老}}\)，其中 \(\Delta S_{\text{新}}=S^1_{\text{新}}-S^0_{\text{新}}\)。  
**贡献度**可报：**各自变动占 \(|\Delta S|\) 的比例**（若 \(\Delta S<0\) 为下滑，可说明「下滑额中多少来自新客、多少来自老客」，并注意分母为 0 或符号混乱时的叙述方式）。

**（B）再下钻一层（找驱动）：** 对每类客群拆 **量 × 率 × 单**：例如新客的 **获客数 × 首单转化 × 客单价**，老客的 **活跃老客数 × 购买频次 × 件单价**，看哪一项拖累最大（**结构 vs 行为**）。

**（C）需控制混杂时：** 可补充 **分区域/分渠道** 的对照，或 **Shapley/Oaxaca** 等更正式的分配（面试答到前两层通常足够；若团队有因果诉求再上实验或模型）。

对应 JD 中常见的 **数据质量与标准数据集、核心指标与周月报、行为/留存/漏斗、BI 看板、ML 协作与文档**；回答时优先 **「先锁口径与事实 → 再拆解与假设 → 再行动与协作」**。

### 38. 业务场景：早会前发现「昨日核心指标」异动很大，和业务体感不一致，你怎么做？

**问题本质：** 指标异动来自 **数据问题** 还是 **真实经营变化**（或两者兼有）。  
**答案：**

1. **锁三样：** 指标 **定义**、统计 **时间窗与时区**、**数据新鲜度**（调度是否延迟、分区是否写满）。  
2. **快速对照：** 与 **业务侧后台/抽数 SQL 单行样本** 对账；看 **昨日是否口径变更、过滤条件是否动过**（测试单、灰度用户）。  
3. **分拆：** 按 **渠道/产品/客群/版本** 下钻，判断是 **全场** 还是 **局部**；若局部集中，优先怀疑 **发布、活动、故障**。  
4. **沟通：** **1 小时内**给对方「当前证据链」：已排除/未排除的假设 + 建议 **暂停对外结论** 或 **标注数据延迟**；修复后补一篇简短复盘（可类比我在 **ETF 异动监控** 里先规则命中再人工复核的思路）。

---

### 39. 业务场景：运营要从「周/月报」里固定加三个新指标进经营分析，你怎么接需求并落地？

**问题本质：** 把模糊业务语言变成 **可计算、可复现、可进 BI** 的指标资产。  
**答案：**

1. **澄清：** 每个指标服务 **哪个决策**；**分子分母、去重维度、时间粒度**（自然日/滚动 7 天）；与现有指标是否 **重叠**。  
2. **字典：** 在指标表里写清 **英文名、中文名、SQL 伪代码或源表字段、刷新频率、负责人、变更记录**（和我在华福做的 **因子/指标口径表 + PRD** 同一套路）。  
3. **验证：** 抽样 **与业务手工表对数**；边界情况（空值、跨天、退款）。  
4. **进看板：** 在 Tableau/Power BI 设 **统一过滤器** 与 **口径说明页**；版本迭代时 **标注生效日**，避免周报「悄悄换定义」。

### 40. 业务场景：周报显示「留存」连续走低，产品希望一周内知道「优先怀疑谁」——你怎么分析？

**问题本质：** 留存是 **结果指标**，要拆成 **获客质量、产品体验、运营节奏、外部季节** 等可讨论假设。  
**答案：**

1. **对齐 cohort：** 看的是 **次日/7 日/30 日** 中哪一个；新用户定义是否变动。  
2. **分层：** 按 **注册渠道、活动、版本、地域、设备** 拆 cohort，是否 **某一两条线在拖累整体**（类似 **因子分组** 里看哪一段截面异常）。  
3. **行为链路：** 对走弱 cohort 看 **激活/关键行为** 是否未达成（漏斗中段是否塌方）。  
4. **时间对照：** 与 **历史同季节、大促后回落** 对比，避免把 **可预期波动** 当事故。  
5. **输出：** **Top 3 假设 + 每条假设需要的补充数据或实验**；不写「全是产品问题」这种无法下结论的套话。

---

### 41. 业务场景：分析师要在看板里加一个「转化漏斗」，但数仓里缺少关键一步的事件，你怎么推进？

**问题本质：** 分析需求倒逼 **埋点/日志/ETL** —— 数科常在 **业务—数据—工程** 之间翻译。  
**答案：**

1. **定义步骤：** 与产品把漏斗画成 **事件序列 + 时间窗**（同会话/24h/7d）。  
2. **缺口清单：** 哪一步缺事件、缺 **属性**（如商品类、实验桶）；是否可用 **页面 PV/接口日志** 代理。  
3. **路径：** **v0** 用现有近邻指标或抽样埋点验证；**v1** 走正式埋点/表结构评审，明确 **验收方式**（测试环境抓包、分区首日落盘检查）。  
4. **预期管理：** 说明 **回填不可得**，从 **新数据生效日** 起建 funnel；周报里 **分段注释**，避免和历史错误拼接。

### 42. 业务场景：算法同事要你协助做一个排序/分层模型，但业务提供的标签噪声大、正负样本混了活动流量，你怎么协作？

**问题本质：** JD 里的 **特征工程、标注、模型验证**——**垃圾进则垃圾出**，产品化要先清标签与评估协议。  
**答案：**

1. **标签治理：** 与业务逐条写 **标注规则**（什么算正例、剔除大促/券、冷启动期是否单独处理）；做 **双人抽检与不一致率**。  
2. **特征：** 与时间相关的特征 **严格防泄漏**（对齐我做时序预测时的切分方式）；记录 **缺失与延迟**，用 **baseline（规则/浅模型）** 先打穿链路。  
3. **验证：** **时间外推** 或 **分桶 hold-out**；看 **分群上的指标** 而不只看总体 AUC，防 **头部偏差**。  
4. **上线姿态：** 建议 **shadow（只看不决策）→ 小流量 → 护栏指标**；周报单独设 **bad case 与漂移监控**——与 **Agent 项目里「机器生成+人复核」** 同一原则：**高风险决策不自动兜底**。

### 43. 你之前提到做过异动监测系统，你怎么判断“异动”是真实信号，而不是临时噪声或虚假波动？

**问题本质：** 异动检测不难，难的是 **降低误报** 并证明结论可复核。  
**答案：**

1. **先过数据质量闸门：** 任何异动先排查数据新鲜度、缺失率、重复键、接口延迟和字段变更。若基础数据异常，先标记“数据问题”，不直接下业务结论。  
2. **做多指标一致性校验：** 不靠单一指标触发。比如我在 ETF 监测里会同时看收益率 Z-score、量比、超额收益、波动等；至少满足“多指标同向异常”才升级为候选异动。  
3. **和历史基线对比：** 用滚动窗口或同周期基线看当前偏离程度，避免把节假日后回补、公告日波动、短时流动性冲击当成异常。  
4. **做横向与纵向双验证：** 纵向看同一标的历史分位，横向看同板块/同主题的相对表现；如果只有单点尖刺、缺乏相对一致性，更可能是噪声。  
5. **加事件语义复核：** 把公告、行业新闻、宏观事件作为二次证据。AI 可以生成解释初稿，但必须保留“证据来源 + 人工复核”两道闸门，防止“看起来合理”的幻觉解释。  
6. **分级输出，不一刀切报警：** 我通常分“疑似异动 / 高置信异动 / 已确认异动”三级，低置信只进入观察池，高置信再进日报主结论，减少误报对业务决策的干扰。

面试收束可以说：**我判断异动是否真实，不是看某个点跳得多高，而是看“数据是否可信 + 多指标是否一致 + 基线是否显著偏离 + 事件证据是否闭环”。只有证据链完整，才把它当成可行动的异动。**

## 七、考前速背（关键词）

- **指标**：北极星、拆解、口径、同环比、cohort、漏斗、渗透率、异动贡献。
- **数据**：事实表/维度表（基础概念）、增量、分区、主键、一对多。
- **假设检验**：\(H_0/H_1\)、\(\alpha\)、p 值、第一类/第二类错误、功效 \(1-\beta\)、效应量、不拒绝≠不证明。
- **分布**：二项（固定 \(n\)、成功次数）、泊松（单位时间到达、稀有事件）、二项→泊松极限。
- **销量下滑贡献**：\(\Delta S=\Delta S_{\text{新}}+\Delta S_{\text{老}}\)、客群下钻量率单、与显著性/混杂控制区分。
- **业务场景**：异动先排数据新鲜度/口径、指标字典四件套、cohort+漏斗下钻、埋点缺口 v0/v1、ML 标签治理与 shadow。
- **看板设计（口述）**：先受众与刷新节奏；**高管**=KPI 条+贡献拆解+异动列表；**运营活动**=活动期对比+漏斗+渠道；**产品**=版本筛选+功能渗透+留存对照（慎谈因果）；**技术×业务**=统一时区+发布/故障标线；**ToB**=租户健康分+分桶；**一页布局**=左筛选、上 KPI、中趋势+结构、下 TopN+口径脚注。
- **ML**：泄漏、baseline、离线在线、标注指南、bad case。
- **协作**：PRD式口径、对账、周报结构、优先级（影响×可行性）。

### 3. 假设检验 · 第一/二类错误（检索共识）

- **第一类错误（弃真）**：\(H_0\) 为真却拒绝；概率上由 **显著性水平 \(\alpha\)** 控制。  
- **第二类错误（采伪）**：\(H_0\) 为假却未拒绝；概率为 **\(\beta\)**，**功效**为 **\(1-\beta\)**。  
- **常见结论**：固定样本下两类错误往往 **此消彼长**；**增大样本量** 通常可同时降低两类错误风险；实务中常 **优先严格控制第一类错误**（领域不同会有差异，金融/合规场景尤为敏感）。细节可跟踪统计教材或 [腾讯云开发者社区 · 数据分析面试手册（统计篇）](https://cloud.tencent.com.cn/developer/article/2159999) 类长文系统复习。

**标准回答：** **60～90 秒**：**学历与栈**（金融 + 计算机、Python·Pandas·SQL、文档化口径）→ **两段经历各 ~20 秒**（转债：流程拆解、PRD、Flask+MySQL 标准化数据集；ETF：规则筛选异动 + LLM 辅助解释与人审）→ **对齐数巅**：协助 **清洗与质量校验**、**指标体系与周/月洞察**、Behavior/留存/漏斗方法论（用类比即可）、**Tableau/PBI**（或表态正在补作品集）、ML 侧 **特征与离线验证** → **收尾**：实习 base **北京海淀**，能保证 **每周至少 4 天、3 个月以上**，希望先把交付跑稳再扩展专题。

### 2. 你提到原始数据清洗和设计指标体系，详细讲讲数据清洗

**我回答时的陷阱或不足：** 清洗与「长期异动监控」混杂；数巅侧还应点到 **事件表 / 埋点 / 增量分区**、**ToC 活跃定义** 等 JD 高频语境（不必虚构项目，用「若接到类似表我会如何做」亦可）。

**标准回答：** **流水线**：数据源（库表/API/日志）→ **粒度与主键**（用户/会话/订单/交易日）→ **口径对齐**（时区、去重规则、dimension 缓慢变化）→ **规则校验**（空值率、枚举域、环比跳变、交叉表对账）→ **异常处理**（规则 + 统计截尾/IQR，记录剔除原因）→ **产出**：标准化分析集 + **质量报告**。金融例子保留的同时，补一句：**用户行为数据**还要盯 **埋点缺失、重复打点、漏斗步骤时间窗**。

### 3. 异常值怎么筛？用了什么算法还是靠业务写脚本？

**我回答时的陷阱或不足：** LLM 分层易让人以为「异常 = LM 判定」；未并列给出 **统计/无监督** 名词与边界。

**标准回答：** **(1) 规则**（业务约束、涨跌停/停牌、成交量为零等）；**(2) 统计与模型**（分位数/Winsorize、z-score、**Isolation Forest**（contamination）、时序残差/STL）。强调 **LM 适合解释与归因**，**判别**仍以规则+模型+人工分级；与数巅 **异动洞察、周报可靠性** 叙事一致。

### 4. 你对数据清洗这块的学习深度 / 日常工作是怎样的？

**我回答时的陷阱或不足：** 因子复盘段略长；宜突出 **定例 pipeline** vs **专题** 与 **可配置化**。

**标准回答：** **定例**：按模板刷新、入库、对账；**专题**：新因子/新指标 → 拆公式 → 补采集 → 样本内外验证。补 **断言、日志、版本**；若对接数巅：**需求 → 指标字典 → SQL/Python → 看板/周报** 同一套纪律。

### 5. 随便介绍一两个机器学习算法，例如某种聚类算法

**我回答时的陷阱或不足：** 面试官要 **聚类**，却答 **Isolation Forest + LSTM**，题型偏移；术语咬准 **Isolation Forest**。

**标准回答：** 先答 **K-means**（目标函数、标准化、K 与轮廓系数、非球状簇局限）或 **层次聚类**。再一句：异常场景用 **Isolation Forest**（路径长度、高维稀疏、contamination）。数巅 JD 下可补：**聚类可用于用户/租户分群特征**，但要谈 **可解释性与业务验收**。

### 6. 使用 Isolation Forest 时，特征构建怎么做？是分析师提还是你们做特征工程？

**我回答时的陷阱或不足：** 只答「买方提需求我们验证」，缺少 **特征列表与处理**。

**标准回答：** **特征**：多窗口收益、波动、量比、换手、均线偏离、残差等；**处理**：缺失策略、Winsorize、（树模型）一致性优先。**标签/伪标签**：规则预标注 + IF 扩召回。**验证**：时间切分、误报成本；若迁移到数巅：**用户分群/流失预警** 可用会话频次、深度、转化步骤间隔等特征 **同理表述**。

### 7. 你们设计的指标体系是什么？要解决什么问题？

**我回答时的陷阱或不足：** 只讲了 **策略回测指标**，未覆盖数巅 JD 的 **北极星—过程—诊断（OSM）**、**产品·运营·技术** 多维与 **漏斗/留存**。

**标准回答：** **双轨答题**：**(A) 投研**：收益/风险/VaR/ES/夏普/回撤/样本外稳健性。(**B) 数巅/互联网**：**北极星**（如活跃/营收/交付成功率，按业务替换）→ **过程指标**（漏斗各步转化、功能渗透、渠道）→ **诊断**（分 cohort、分版本、Top 异常贡献）。每个指标四件套：**定义、公式、出处、刷新频率**；结论服务 **周/月报与迭代决策**，而非堆砌。

### 8. 怎么判断「风险是否可接受」？指标模型具体怎样落地？

**我回答时的陷阱或不足：** VaR 与「拒绝域」混；截距项当「阿尔法」易歧义；缺 **置信水平、持有期、ES**。

**标准回答：** **VaR/ES** 定义 + 业务阈值（回撤、预算）；策略侧衔接夏普、Calmar。**若面试官关心 ToB/平台**：可换 **SLA、故障率、数据延迟、模型漂移监控** 作为「风险可接受」的平行例子——与 JD 中 **质量校验、看板监控** 更近。

### 9. 对大语言模型、Transformer 这类架构有了解吗？

**我回答时的陷阱或不足：** 「学过但忘了」扣分；数巅公开叙事偏 **数据智能 + 大模型应用**，哪怕浅也要 **30 秒骨架**。

**标准回答：** **Transformer**：Attention、并行 vs RNN。**LLM**：预训练 + 对齐；**落地**：RAG、工具/MCP、评测与安全。**态度**：原理有课内基础，实习更关心 **可控、可审计、与数据口径一致**。

### 13. Cursor、Code Agent 相关：介绍一下 Skills

**我回答时的陷阱或不足：** 把 **Cursor Agent Skills（SKILL.md）** 答成考研资料封装，**术语不对齐**。

### 14. MCP 是什么？结合 Agent 讲讲

**我回答时的陷阱或不足：** 类比可保留；**C/S 追问**需严谨（见下题）。

**标准回答：** **Host–Client–Server**；统一对接 DB、Git、内部 API；**治理**：只读账号、审计、限流——贴合 **企业数据智能** 场景。

### 15. MCP 里的客户端和服务端分别指什么？

**我回答时的陷阱或不足：** 客户端 ≠ 笼统「电脑」；服务端 ≠ 仅 GitHub。

**标准回答：** **Host**（Cursor 等）→ **Client**（宿主内 MCP 客户端）→ **Server**（stdio/SSE 进程，注册 tools/resources）；调用链闭环说清楚。

### 16. 数据结构：介绍排序算法

**我回答时的陷阱或不足：** 冒泡后卡壳；数巅笔试/技术面常见 **复杂度底线**。

**标准回答：** 插入/冒泡 **O(n²)**；归并/快排/堆 **O(n log n)**（快排最坏 **O(n²)**）；**Timsort**；**海量数据**提 **外部排序 / 分布式 shuffle**（数仓场景）。

### 17. SQL 写得多么？增删改查分别是什么命令？

**我回答时的陷阱或不足：** **漏 UPDATE**。

**标准回答：** `SELECT` / `INSERT` / **`UPDATE … SET … WHERE`** / `DELETE … WHERE`；删改前 **`SELECT … WHERE` 试跑**。

### 18. 删除满足特定条件的数据怎么做？WHERE 和 HAVING 的区别？

**我回答时的陷阱或不足：** **DELETE 不用 HAVING**。

**标准回答：** `DELETE FROM … WHERE …`；`HAVING` 仅配合 **`GROUP BY` 聚合后过滤**。生产库删改优先 **备份或建新表 swap**，与 JD「复杂查询 + 质量」一致。

### 19. 联表与子查询用过吗？举例说明

**我回答时的陷阱或不足：** 可补 **JOIN 类型 + join key 索引**。

**标准回答：** INNER/LEFT；**事件表 JOIN 用户维度表 ON user_id**；事实表 JOIN 日期维；子查询大数据量时优先改写 JOIN。

### 20. Cursor「掩码泄露」事件、架构是否了解？Cursor 与常见 Code Agent 异同？

**我回答时的陷阱或不足：** 过虚；缺 **工具循环、diff、沙箱、密钥与合规**。

**标准回答：** 事件：**密钥/.env 泄露面** → 轮换、扫描、`.gitignore`、最小权限。**架构**：Plan–Tool–Observe；与 **MCP** 集成差异；表态 **公司数据不外泄、不外连未授权服务**。

### 21. 期望工作 Base？北京和深圳更偏好哪个？

**我回答时的陷阱或不足：** 「都可以」+ 深北摇摆；**数巅实习 JD 明确北京海淀**，应与投递一致。

**标准回答：** **本岗位 base 北京**，可承诺到岗与每周天数；若个人长期更熟悉深圳，如实说 **城市偏好不影响实习履约**，或 **研究生在成都、实习可走北京线下**——避免让面试官担心 **稳定性**。Final：**与 offer 地点对齐 > 泛泛偏好**。
