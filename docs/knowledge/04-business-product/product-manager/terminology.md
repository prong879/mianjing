# 产品经理专业术语清单

面向**金融学背景、补充产品岗位语境**的速查表：听到词能接上话即可，不必背定义。

---

## 一、需求与文档


| 术语                                     | 含义（极简）                                      |
| -------------------------------------- | ------------------------------------------- |
| **PRD**（Product Requirements Document） | 产品需求文档：写清背景、目标用户、功能范围、流程、规则、验收标准，给研发/测试对齐用。 |
| **BRD**                                | 商业需求文档：更偏「为什么要做、赚什么钱/省什么成本」，常比 PRD 更早、更宏观。  |
| **MRD**                                | 市场需求文档：市场机会、竞品、目标客群，介于战略和 PRD 之间。           |
| **User Story**                         | 用户故事：「作为某类用户，我想要…，以便…」，从用户价值写需求。            |
| **Acceptance Criteria（AC）**            | 验收标准：怎样算「做完了」，可测试、可勾选，减少扯皮。                 |
| **Use Case**                           | 用例：用户与系统交互的场景步骤，常带主流程、异常分支。                 |
| **MVP**（Minimum Viable Product）        | 最小可行产品：用最小功能验证核心价值，再迭代。                     |
| **Scope / Scope Creep**                | 范围 / 范围蔓延：做什么的边界；蔓延指需求越加越多导致延期。             |

### PRD 常见组成（可按公司模板增删）

实际项目里常合并章节或拆成多份文档（如交互单独出稿），下面是一份**较完整 PRD 骨架**及每块要写什么。

| 模块 | 写什么 |
|------|--------|
| **修订记录** | 版本号、日期、修改人、变更摘要（方便研发查「哪版为准」）。 |
| **背景与问题** | 业务现状、痛点、为什么要现在做（可引用 BRD/数据/调研结论）。 |
| **目标与范围** | 本期要达成的可衡量目标（指标或定性结果）；**In / Out of Scope** 写清做与不做的边界。 |
| **名词与角色** | 术语表、用户角色（如管理员/研究员/访客）及权限差异。 |
| **用户与场景** | 目标用户、核心场景描述；可附 Persona 或用户故事列表。 |
| **整体流程** | 端到端业务流程（常配图：流程图/泳道图）；与外部系统、人工环节的衔接。 |
| **功能需求** | 按模块或用户故事罗列：功能说明、输入输出、业务规则、异常与边界、权限。 |
| **非功能需求** | 性能、可用性、安全合规、日志审计、兼容性、并发等（B 端/金融类尤其重要）。 |
| **数据与接口** | 核心实体/字段说明、与上下游 **API** 约定要点（字段、错误码可另附接口文档）。 |
| **交互与视觉** | 说明原型/设计稿链接、关键页面状态；若无设计，至少写清关键文案与布局要求。 |
| **验收标准（AC）** | 可测试的 checklist：主流程、异常、权限、数据正确性。 |
| **风险与依赖** | 技术/业务依赖、开放问题、需业务方确认的点。 |
| **上线与回滚** | 是否需要灰度、开关、配置项、监控指标（可与研发运维共写）。 |

**写作原则（面试可顺带提）：** 研发能据此估工与开发，测试能据此写用例，业务能据此验收；避免只写形容词、不写规则与边界。

### PRD 里常要画的图：类型与内容要点

图的作用是**对齐认知**；复杂逻辑「一图胜千言」。下列按出现频率从高到低排列，内容列写每张图**应表达什么**。

| 图类型 | 主要用途 | 图上一般有什么内容 |
|--------|----------|-------------------|
| **业务流程图** | 说清「谁、在什么条件下、先后做什么」 | 开始/结束、活动节点、判断分支、异常回流；可选标注责任角色或系统边界。 |
| **泳道图（跨职能流程图）** | 多角色/多系统协同 | 横向或纵向泳道：用户、产品、运营、研发系统、第三方；步骤在泳道间流转。 |
| **用户旅程图** | 体验与情绪、触点、痛点 | 阶段（认知→使用→留存等）、用户行为、触点（APP/邮件/人工）、痛点与机会点；可简版只保留阶段与行为。 |
| **功能结构图 / 站点地图** | 信息架构与模块层级 | 一级/二级菜单或功能模块树；帮助研发理解导航与页面范围。 |
| **用例图（UML Use Case）** | 系统对外提供的能力与参与者 | 小人（参与者）、椭圆（用例）、可选 `<<include>>`/`<<extend>>`；适合边界清晰的中大型需求。 |
| **状态图** | 对象生命周期、审批流、订单状态 | 状态节点、转移条件、触发事件；避免口语描述「各种情况」导致漏分支。 |
| **时序图（序列图）** | 多系统/多模块调用顺序 | 参与者竖线、按时间向下的消息箭头、同步/异步、返回；适合对接口与前后端协作对齐。 |
| **实体关系示意 / 数据流** | 核心数据从哪来到哪去 | 主要实体、关键字段（可粗粒度）、写入/读取关系；细表结构可放附录或数据字典。 |
| **线框图 / 低保真原型** | 页面结构与关键元素 | 布局区块、主按钮与入口、列表/表单字段、空态与错误态说明；高保真多在 Figma/Sketch，PRD 里链过去即可。 |

**和研发协作时的习惯：** 简单需求「文字 + 一张流程图」即可；涉及多接口、长链路时**时序图**很有用；有审批/状态机务必上**状态图**。医疗设备等偏传统项目里，**活动图/流程图 + 用例**也很常见（与你简历里的需求规格、活动图实践一致）。

## 二、规划与优先级


| 术语                 | 含义（极简）                                              |
| ------------------ | --------------------------------------------------- |
| **Roadmap**        | 路线图：未来一段时间「做什么、大概什么顺序」，常按季度或主题排。                    |
| **Backlog**        | 需求池/待办列表：还没做或排队的需求、任务，由 PO/PM 与团队一起梳理优先级。           |
| **Prioritization** | 优先级排序：在资源有限下决定先做谁后做谁。                               |
| **MoSCoW**         | 必须/应有/可有/暂不（Must/Should/Could/Won’t），一种分档优先级法。      |
| **RICE**           | Reach × Impact × Confidence / Effort，用打分做需求排序的一种方法。 |
| **KANO 模型**        | 把需求分成基本型、期望型、兴奋型等，判断「做了用户会不会更满意」。                   |

## 三、敏捷与研发协作


| 术语                    | 含义（极简）                               |
| --------------------- | ------------------------------------ |
| **Agile / Scrum**     | 敏捷/Scrum：短周期迭代交付、固定仪式（计划会、站会、评审、回顾）。 |
| **Sprint**            | 迭代周期：常见 1～2 周，本周期承诺完成一批需求。           |
| **PO**（Product Owner） | 产品负责人：对 Backlog 优先级和验收负责的人（有时就是 PM）。 |
| **Scrum Master**      | 敏捷教练：保流程、扫障碍，一般不替 PO 定「做什么」。         |
| **Stand-up / Daily**  | 站会：每天简短同步进度与阻塞。                      |
| **Retrospective**     | 回顾会：迭代结束复盘「哪里好、哪里改」。                 |
| **Velocity**          | 团队速率：每个 Sprint 大概能完成多少工作量（用于估算）。     |
| **Spike**             | 技术探针：短时间调研/验证不确定性，再决定是否做、怎么做。        |

## 四、体验与设计


| 术语                                  | 含义（极简）                       |
| ----------------------------------- | ---------------------------- |
| **Persona**                         | 用户画像：典型用户类型及其目标、痛点（虚构但基于调研）。 |
| **User Journey / Customer Journey** | 用户旅程：从认知到使用到流失/复购的关键步骤与触点。   |
| **Wireframe**                       | 线框图：低保真页面结构，不讲视觉细稿。          |
| **Prototype**                       | 原型：可点击演示的稿，用于验证流程。           |
| **Usability Test**                  | 可用性测试：观察真实用户能否完成任务。          |
| **Information Architecture（IA）**    | 信息架构：内容怎么分类、导航怎么组织。          |
| **Edge Case**                       | 边界/异常场景：极端输入、网络失败、权限不足等。     |

## 五、数据与实验


| 术语                    | 含义（极简）                            |
| --------------------- | --------------------------------- |
| **North Star Metric** | 北极星指标：最能代表产品长期价值的一个核心指标（或少量组合）。   |
| **OKR**               | 目标与关键结果：O 是方向，KR 是可衡量结果，常按季度。     |
| **Funnel**            | 漏斗：从曝光→点击→注册→活跃→付费等环节转化率。         |
| **Cohort**            | 同期群：按注册/某行为时间分组，看留存、付费差异。         |
| **Retention**         | 留存：一段时间后还有多少人回来用。                 |
| **DAU / MAU**         | 日活/月活。                            |
| **A/B Test**          | 对照实验：两组用户不同方案，比指标差异（要注意样本与统计显著性）。 |
| **埋点**                | 在关键行为打日志/事件，供分析漏斗与路径。             |
| **Dashboard**         | 看板：核心指标可视化，给业务或产品日常盯数。            |

## 六、商业化与增长


| 术语                          | 含义（极简）                         |
| --------------------------- | ------------------------------ |
| **PMF**（Product-Market Fit） | 产品与市场匹配：用户愿意用、愿意推荐、可持续增长的状态。   |
| **LTV / CAC**               | 用户生命周期价值 / 获客成本；PM 常和增长、投放一起谈。 |
| **Churn**                   | 流失：订阅取消、不再活跃等。                 |
| **Onboarding**              | 新用户引导：首次使用如何把价值讲清、带到「啊哈时刻」。    |

## 七、B 端 / 平台 / 信息化


| 术语                    | 含义（极简）                         |
| --------------------- | ------------------------------ |
| **B 端 / C 端 / G 端**   | 对企业 / 对消费者 / 对政府。              |
| **Workflow**          | 工作流：业务方实际做事的步骤，B 端产品常要嵌进去。     |
| **RBAC**              | 基于角色的权限控制：不同角色看到不同菜单/数据/操作。    |
| **Audit Log**         | 审计日志：谁在何时做了什么操作，合规与追责用。        |
| **SLA**               | 服务等级协议：可用性、响应时间等承诺（对内对外合同里常见）。 |
| **SSO**               | 单点登录：一次登录访问多个系统。               |
| **Integration / API** | 集成/接口：和别的系统对接数据或能力。            |

## 八、与研发沟通的半技术词


| 术语                       | 含义（极简）                         |
| ------------------------ | ------------------------------ |
| **API**                  | 程序之间调用的约定（URL、参数、返回）。          |
| **SDK**                  | 软件开发工具包：别人封装好给你调用的库/文档。        |
| **Webhook**              | 事件回调：某事发生时对方系统主动 POST 一个通知到你方。 |
| **Staging / Prod**       | 预发/生产环境：上线前验证 vs 真实用户环境。       |
| **Rollback**             | 回滚：出问题把版本退回去。                  |
| **Tech Debt**            | 技术债：为赶进度暂时凑合的实现，以后要还。          |
| **Latency / Throughput** | 延迟/吞吐：响应快慢、单位时间处理量。            |

## 九、AI 产品


| 术语                              | 含义（极简）                               |
| ------------------------------- | ------------------------------------ |
| **RAG**                         | 检索增强生成：先查知识库/文档再生成回答，减轻「胡编」。         |
| **Prompt / System Prompt**      | 提示词/系统提示：约束模型角色、格式、安全边界。             |
| **Hallucination**               | 幻觉：模型编造看似正确但事实错误的内容。                 |
| **Eval / Benchmark**            | 评测：用数据集或规则看模型/Agent 是否达标。            |
| **Guardrail**                   | 护栏：内容安全、拒答策略、敏感词与合规限制。               |
| **MCP**（Model Context Protocol） | 让模型通过标准方式连工具/数据源/系统的协议（如 Cursor 生态）。 |
| **Agent**                       | 智能体：能规划步骤、调工具、多轮完成任务的系统，不只是单次问答。     |

| 术语              | 含义（极简）                     |
| --------------- | -------------------------- |

## 金融学背景：清单内仍建议加深 & 清单外可补

下面回答两个问题：**① 本清单里哪些块「光看一句定义不够」；② 清单还没覆盖、但做产品常会碰到什么**。便于你有针对性地科普、补课。

### 一、清单里已有——建议你刻意练「语境」而不仅是记词

| 区块 | 金融学背景常见盲区 | 建议怎么补 |
|------|-------------------|-----------|
| **一、需求与文档** | 容易把 PRD 写成「研究报告」：背景很长、规则很虚、没有 AC。 | 找一份互联网公司的 PRD 模板或样例，对照你写过的需求规格，看「功能点 + 规则 + 异常 + 验收」四件套是否齐。 |
| **二、规划与优先级** | **RICE** 里 Impact/Effort 和做课题时的「显著性」不是一回事，Reach 在内部工具里常是「多少人用、频次多高」。 | 随便拿 3 个需求，自己填一版 RICE，再想想若数据不全 Confidence 怎么降权。 |
| **三、敏捷** | 容易把 Sprint 当成「小组作业周」；**PO 与 Scrum Master** 分工在真实团队里会变体。 | 看一段 10 分钟的 Scrum 流程科普视频，记住「计划会—站会—评审—回顾」各解决什么问题即可。 |
| **四、体验与设计** | 金融训练里少碰 **IA、线框与可用性测试**，容易一上来就讨论「好不好看」。 | 用任意 APP 画一张极简用户旅程（3～5 个阶段），标一个痛点，体会和「写论文机制分析」的差异。 |
| **五、数据与实验** | 你熟回归与显著性，但产品里的 **A/B** 更强调「分流、样本量、指标口径、实验周期」和**业务可接受错误**。 | 把 A/B 想成「带业务约束的假设检验」：主指标一个、护栏指标若干，比 p 值更重要的是「敢不敢全量」。 |
| **六、增长** | **PMF** 偏定性+行为数据，不像资产定价那样有闭式解。 | 读 1～2 个「PMF 案例」摘要即可，面试能举例「什么信号说明找到了 PMF」。 |
| **七、B 端/信息化** | 你懂合规，但未必熟 **RBAC、审计日志、SLA** 在系统里如何落地成功能。 | 结合你实习系统想：若多角色共用，权限按角色拆会怎样；若出事故，日志要记哪些字段。 |
| **八、半技术** | **Staging/Prod、Rollback** 和交易里的「仿真/实盘、撤单」有类比，但工程上还有**配置、开关、灰度**。 | 问一次研发同学：你们环境有几套、上线谁点、出问题怎么回滚。 |
| **九、AI 产品** | 容易只聊模型名，不熟 **Eval、护栏、RAG 边界**。 | 用「准确率/召回+人工抽检+拒答策略」三句话描述你怎么验收一个内部问答助手即可。 |
| **十、协作** | **UAT、Sign-off** 在金融机构里往往更正式，和课堂小组不同。 | 实习或项目中记一条：最终是谁签字、依据什么清单验收。 |

### 二、清单外——做产品还常遇到（可后续按需加进本表）

- **角色分工：** PM / PO / BA（业务分析）/ PMM（产品市场）/ UX / UI / 研发 / 测试 / 运维 各自默认交付物是什么。  
- **用户研究：** 用户访谈、问卷、竞品分析、可用性测试的基本流程与偏见控制（别和「卖方路演」完全混为一谈）。  
- **发布与配置：** Feature Flag（功能开关）、灰度发布、金丝雀发布；与 **Rollback** 搭配理解。  
- **需求形态：** Epic → Story → Task 的拆解；**Story Point** 或工时估算在团队里怎么用。  
- **思维模型（可选）：** Jobs to be Done（JTBD）、双钻模型、价值主张画布——面试偶尔提到，不必背理论，能举一例即可。  
- **体验指标：** NPS、CSAT、CES（满意度/费力度）与业务指标怎么配。  
- **B 端交付：** 实施、培训、客户成功（CS）与「产品上线」往往不是一回事。  
- **略偏工程但 PM 要懂词：** 幂等、限流、熔断、异步队列——听到研发说时能追问一句「对用户侧表现是什么」。

### 三、和你已有优势的「对齐方式」（减少焦虑）

- **数据与实证** → 对齐 **指标定义、实验、漏斗与 cohort**（你换语境快）。  
- **合规与风控意识** → 对齐 **权限、审计、非功能需求、AI 护栏**（金融背景是加分项）。  
- **研报与表达** → 对齐 **PRD 结构化、Stakeholder 沟通**（把读者从教授换成研发与业务即可）。
