## 第二部分：问题

> 后续你发来的图片、文字和面试题会继续整理到这里。当前先收录一组 **Agent 开发实习生一面技术面试题**。

### Agent 开发实习生一面：技术面，约 30 分钟

题目特点：

- 岗位方向：Agent 开发工程师 / Agent 开发实习生
- 面试形式：技术面，约 30 分钟
- 题目数量：18 个技术问题，包含基础概念、架构设计、工具调用、RAG、项目经验和场景题
- 考察重点：是否真正理解 Agent 开发流程，是否具备 Python、LLM API、Tool Calling、RAG、Prompt、Git 协作和项目落地能力

### 一、基础概念题

1. 请做一个 1 分钟自我介绍。
   - 场景提示：面试官重点听你掌握的技术、与 Agent 开发相关的基础，别讲无关内容。

2. 你理解的 Agent 开发，核心要做哪些工作？

3. 用技术语言说明，Agent 的核心架构模块有哪些？每个模块的作用是什么？

---

### 二、Prompt 与模型调用题

1. 你调用过 LLM API，例如 OpenAI、DeepSeek 等吗？在 Agent 开发中，如何封装 LLM API 供 Agent 调用？

2. 开发 Agent 时，如何设计 Prompt 才能让 Agent 更精准地理解任务、调用工具？
   - 场景提示：考察 Prompt 工程与 Agent 开发的结合。

---

### 三、RAG 与知识库题

1. RAG 在 Agent 开发中是如何应用的？开发中如何优化 RAG 的检索精度？
   - 场景提示：面试官引导你结合开发实际，考察应用能力。

2. 向量库，例如 FAISS、Chroma，在 Agent 开发中主要用于什么？开发中如何将向量库与 Agent 的记忆模块结合？

---

### 四、Tool Calling 与 Agent 架构题

1. Agent 开发中，Tool Calling 的核心逻辑是什么？如何实现 Agent 自主调用工具？

2. ReAct 框架在 Agent 开发中的作用是什么？用伪代码简单表示 ReAct 的核心流程。
   - 场景提示：面试官考察你对 Agent 开发框架的掌握，口述即可。

3. 用 Python 写一段简单的 Agent 工具调用 demo 逻辑。
   - 场景提示：现场口述代码，重点说清调用逻辑，不用写完整代码。

4. Agent 的记忆模块开发中，短期记忆和长期记忆如何区分和实现？

---

### 五、框架与项目经验题

1. 开发 Agent 时，你会用哪些 Python 库？说说它们在 Agent 开发中的具体用途。
   - 场景提示：抽查你是否有 Agent 开发相关的工具使用经验。

2. 你做过与 Agent 开发相关的项目吗？课程项目也可以。说说你在项目中实现的 Agent 相关功能。

3. 你了解 LangChain / LlamaIndex 吗？说说它们在 Agent 开发中的优势和使用场景。

4. 若让你开发一个简单的文档总结 Agent，你会设计哪些核心功能、用到哪些技术栈？

---

### 六、工程协作与问题排查题

1. Agent 开发中，Git 的分支管理如何配合开发？说说你平时开发中 Git 的常用操作。
   - 场景提示：考察团队开发适配性。

2. 开发 Agent 过程中，若出现工具调用失败，你会怎么排查和解决？
   - 场景提示：考察问题排查能力。

---

### 七、综合开放题

1. 你在 Agent 开发方面有哪些学习计划？未来想重点深耕 Agent 开发的哪个模块？
   - 场景提示：面试收尾，考察你对 Agent 开发的热情和规划。

### Agent 开发项目深挖追问：RAG、定位 Agent、SFT 与工程基础

题目特点：

- 面试风格：围绕简历项目连续追问，重点考察真实实现细节
- 高频追问方向：RAG 数据链路、OCR、向量库、数据库表设计、问题定位 Agent、SFT 后训练、翻译项目、Java 并发与消息队列
- 准备重点：不能只讲“用了 RAG / 用了 Agent”，要能说清数据从哪里来、怎么存、怎么查、怎么评估、哪里出错、如何优化

#### 一、项目整体介绍与工具链追问

### Agent 开发求职经验与岗位趋势复盘

#### 一、已 OC / 推进中的岗位方向

当前已 OC 或推进中的方向：

- 理想汽车：Agent 开发
- 卓驭科技：移动物理 AI 开发
- 小米：顶尖实习 Agent 开发
- 腾讯：下周有机会 OC，希望顺利推进

这些岗位共同说明：Agent 开发、AI 应用开发、具身 / 物理 AI、智能开发工具等方向正在快速扩招，岗位名称可能不同，但底层能力要求高度重合。

---

#### 二、今年 Agent 岗位的整体感受

今年可以明显感受到是 **Agent 应用快速落地的一年**。如果能比较早切换到 Agent / AI 应用开发方向，会有一定先发优势。

从面试密度看，市场需求比较强：

- 基本每周都有面试机会
- 高峰期可能每天都有面试
- 越到二面、三面，精神压力越大
- 阿里等大厂暑期岗位明显 All in AI

准备策略：

- 不要只等“准备完美”再投，应该边投边面、边面边复盘
- 每次面试结束后，要把不会的问题及时补进知识库
- 高频追问要整理成可复用回答，而不是只记题目

---

#### 三、AI 应用开发岗位的能力要求

AI 应用开发岗位虽然比较新，但并不意味着只会调用大模型 API 就够了。面试官往往会从多个方向考察候选人的综合素质。

常见能力要求：

- 后端基础：接口设计、数据库、中间件、缓存、消息队列、并发
- 工程能力：Git 协作、服务拆分、异常处理、日志、部署
- Agent 能力：Tool Calling、RAG、记忆、工作流、Prompt、评估
- 场景设计：能不能把一个模糊需求拆成可实现的 Agent 系统
- 项目深度：是否真的理解自己项目里的数据链路、工具链路和优化逻辑

典型场景题：

- 设计一个生成单元测试的 Agent
- 设计一个文档总结 Agent
- 设计一个告警定位 / 日志分析 Agent
- 设计一个企业知识库问答 Agent

准备策略：

- 后端八股不能完全放弃，尤其是数据库、缓存、消息队列、并发、JVM
- 场景题要按“需求分析 -> 架构设计 -> 数据流 -> 工具调用 -> 评估与兜底”回答
- 项目不能只讲功能实现，要讲设计取舍、指标、失败情况和优化过程

---

#### 四、面试官很关注最新技术敏感度

Agent 开发方向变化很快，面试官会关心候选人是否持续跟进新工具、新框架和新范式。

需要关注的技术动态：

- OpenAI / Anthropic / Google / DeepSeek / Qwen 等模型更新
- Claude Code、Cursor、OpenHands、OpenClaw 等 AI Coding Agent
- Harness、DevOps Agent、自动测试 Agent、代码生成 Agent
- MCP、Tool Calling、Computer Use、Browser Use 等工具调用协议和能力
- RAG 新实践：Query Rewrite、Hybrid Search、Rerank、Graph RAG、多路召回
- 多模态 Agent、移动端 Agent、具身智能 / 物理 AI

面试经验：

- 有些面试官会直接问近期热门技术，例如 Claude Code、Harness、OpenClaw
- “做 AI 应用，要么学得快，要么就别学”体现出这个方向对学习速度要求很高
- 最新技术不一定要全部做过，但要能说清它解决什么问题、和已有方案有什么区别

准备策略：

- 建一个“Agent 最新技术追踪”笔记
- 每周整理 2 到 3 个新工具 / 新框架的核心思想
- 不只看宣传文章，要思考它能落到什么业务场景

---

#### 五、面试难度上涨：只写功能实现不够

当前暑期面试难度相比年前有所上涨。简历上如果只写“实现了 RAG”“实现了 Agent”“接入了大模型”，很容易被连续追问打穿。

以 RAG 为例，面试官可能继续追问：

- 召回率是多少？
- 用什么数据集评估召回效果？
- 召回不准时怎么排查？
- Chunk 怎么切？Overlap 怎么设？
- 是否做了 Query Rewrite？
- 是否做了 Rerank？
- 是否用了关键词检索 + 向量检索的混合召回？
- 向量库用什么？索引结构是什么？召回耗时多少？
- 检索结果和最终答案之间如何做引用溯源？
- 如果知识库没有答案，模型如何避免胡编？

项目准备原则：

- 每个简历项目都要准备“实现细节 + 指标 + 问题 + 优化”
- 每个技术点都要能回答“为什么这么做，而不是别的方案”
- 每个 Agent 都要说清工具、状态、记忆、工作流、失败兜底和评估方式

---

#### 六、后续准备重点

接下来复习时，可以优先补齐这些模块：

1. RAG 深度优化：Query Rewrite、Hybrid Search、Rerank、召回评估、引用溯源。
2. Agent 工程化：Tool Calling、状态机、工作流编排、失败重试、人工确认。
3. 后端基础：MySQL 索引、Redis、消息队列、并发、JVM、接口设计。
4. 场景设计题：测试生成 Agent、文档总结 Agent、日志定位 Agent、企业知识库 Agent。
5. 最新技术追踪：Claude Code、Harness、MCP、OpenHands / OpenClaw、AI Coding Agent。
6. 项目深挖：每个项目都准备数据规模、链路耗时、准确率、失败案例和优化方案。

### Agent 工程化高质量回答模板

#### 一、工具调用失败或 LLM 幻觉，怎么办？

回答思路：

这个问题要拆成两个子问题，因为 **工具调用失败** 和 **LLM 幻觉** 是两种完全不同的故障模式，不能用同一套方法处理。

工具调用失败通常有明确信号，比如异常、超时、错误码、返回为空或参数校验失败。我的处理会分三层：

1. 第一层是重试与自我修正。对网络抖动、超时、临时错误，可以做指数退避重试；如果是参数错误，可以把上一次工具调用的参数、错误信息和工具 Schema 重新交给 LLM，让模型反思参数哪里不符合要求，再生成修正后的调用参数。

2. 第二层是降级与备用路径。如果重试耗尽，还可以切换备用工具、走规则引擎、返回部分结果，或者提示用户补充必要信息，避免整个 Agent 链路直接失败。

3. 第三层是写操作保护。如果工具涉及写数据库、发消息、下单、删除文件这类有副作用的操作，执行前要记录 Checkpoint，失败后可以回滚到上一个干净状态；同时写操作要设计成幂等，避免重试导致重复执行。

LLM 幻觉更难处理，因为它通常没有明确报错。我的处理方式是：

1. 对关键推理结果做 Self-consistency。比如同一个问题采样多次，看多个回答是否一致，如果差异很大，就说明模型不确定，需要降级或人工确认。

2. 对外部事实型问题做交叉验证。可以用 RAG 检索结果、搜索结果或第二个模型做 Fact-check，要求答案必须能被外部证据支持。

3. 对高风险操作加入 Human-in-the-loop。比如修改数据、发送通知、执行生产操作，不管模型多确定，都要让人确认后再执行。

生产环境里还要做可观测性。我会为每个 Agent 实例暴露健康度指标，例如工具失败率、平均重试次数、幻觉拦截率、人工确认率、熔断次数。一旦超过阈值，就自动熔断并告警。这样 Agent 才不是一个只能跑 Demo 的系统，而是具备上线容错能力的工程系统。

#### 二、Agent 的 Memory 怎么设计？

回答思路：

我会把 Agent Memory 设计成三层，分别对应当前任务状态、历史任务经验和领域知识。

第一层是 **Working Memory**，也就是当前 LLM 的 Context Window。它主要保存当前任务的执行状态、用户输入、工具调用历史、中间观察结果和当前计划。这里的核心问题是容量管理。如果上下文超过窗口长度，我不会直接粗暴截断，而是对较早的消息做摘要压缩，保留任务目标、关键约束、已完成步骤和未完成事项，减少 token 占用。

第二层是 **Episodic Memory**，也就是历史任务记忆。它保存过去的任务轨迹、用户偏好、成功案例和失败案例，通常可以放到向量数据库中，通过语义相似度召回。写入可以在任务结束后异步进行，不阻塞主链路。这一层还需要遗忘机制，否则向量库会无限膨胀。可以给每条记忆打一个重要性分数，例如访问频率、时效性衰减、任务相关度的综合分数，低分记录定期压缩或归档。

第三层是 **Semantic Memory**，也就是领域知识。它存放相对稳定的知识，比如业务规则、产品文档、接口说明、运维手册、术语解释等。这里要根据数据形态做选型：非结构化文档适合向量检索；强结构化、多跳实体关系更适合 Knowledge Graph。因为向量库擅长语义相似召回，但不擅长稳定的多跳关系推理。

如果是多 Agent 场景，还要考虑共享 Memory 的一致性问题。多个 Agent 同时读写记忆时，可以给写操作加版本号，用乐观锁控制并发；读操作做版本校验，避免读到过期或冲突数据。对于关键记忆更新，还可以记录审计日志，方便后续追踪哪个 Agent 在什么时候写入了什么内容。

总结来说，Memory 不是简单把聊天记录塞进向量库，而是要区分当前上下文、历史经验和领域知识，并分别设计存储、召回、压缩、遗忘和一致性机制。

### Agent 架构与 RAG 工程化回答模板：状态、冲突、记忆、评测与部署

#### 一、如果从零设计一个对话 Agent，核心状态有哪些？

核心状态至少要有四类：会话状态、任务状态、工具状态和记忆状态。

- 会话状态：负责当前轮的输入、输出、上下文窗口和用户当前意图。
- 任务状态：描述目标、槽位、依赖关系、执行步骤和是否完成。
- 工具状态：记录调用过哪些外部能力、返回了什么、是否失败、是否可重试。
- 记忆状态：保存长期偏好、历史事实和结构化摘要。

很多对话系统看起来只是“多轮聊天”，实际真正难的是状态机设计。如果状态边界不清晰，模型很容易把临时信息写成长期事实，或者把上一个任务的中间结果错误继承到当前轮。

---

#### 二、如果用户和 AI 对话时生成的问题本身有冲突，系统应该怎么处理？

不能让模型直接“二选一猜一个”，而是要先进入冲突检测和证据仲裁流程。

处理步骤：

1. 先识别冲突类型：事实冲突、时间冲突、约束冲突、角色冲突。
2. 再回溯冲突来源：来自用户多轮表述变化、工具返回不一致，还是知识库版本冲突。
3. 最后根据冲突级别选择澄清、回退、拒答或多解并列输出。

真正线上可用的系统，必须能区分“模型不会”和“输入本身互相矛盾”。否则用户会觉得系统在胡说。

---

#### 三、如果把普通问答项目升级成虚拟对话系统，架构上要改哪些东西？

普通问答项目的核心是检索和生成，虚拟对话系统则要支持持续扮演和持续行动。

需要新增的关键能力：

- Persona 管理：角色设定、身份、风格、能力边界。
- 长期记忆：稳定偏好、历史事实、关系与重要事件。
- 情感或风格状态：语气、情绪、表达习惯的一致性。
- 轮次目标：当前对话到底要完成什么目标。
- 状态压缩：长对话里保留关键状态，避免上下文膨胀。
- 多回合安全控制：避免角色越界、诱导输出和持续错误积累。

如果没有这些能力，所谓虚拟对话只是每轮临时拼 Prompt，轮数一长角色就会漂。

---

#### 四、RAG 在这类 Agent 项目里到底用来解决什么问题？

RAG 不是为了让模型“知道更多”，而是为了解决时效性、事实约束和可追溯性。

模型参数里的知识不可控且难更新，业务上真正需要的是把最新文档、规则、历史记录和用户私有数据接进来，并能指出答案依据在哪里。

在流程型 Agent 里，RAG 不只是给答案供料，还会参与工具前置决策：

- 先查规则，再决定是否允许调用某个接口。
- 先查历史工单，再决定是否升级异常等级。
- 先查用户协议，再判断能不能执行高风险操作。

---

#### 五、RAG 的信息一般怎么存，为什么不能只扔进向量库？

只用向量库存文本块，很快会遇到版本冲突、权限过滤、结构化事实缺失和引用不可追踪的问题。

更合理的做法是分层存储：

- 原文和版本信息：存对象存储或文档库。
- 向量索引：用于语义召回。
- 倒排索引：用于关键词精确匹配。
- 结构化事实：存关系库、图数据库或 KV。
- 元数据：统一挂载权限标签、生效时间、文档来源、章节路径和版本号。

这样检索时才能做到“先过滤再召回”，而不是把所有东西召回后再指望模型自己判断。

---

#### 六、Embedding 模型在项目中应该怎么选？选错会出现什么现象？

Embedding 模型要看语言范围、文本长度、领域适配、向量维度、吞吐和成本。

选错后的典型现象，不只是指标低，而是召回结果出现系统性偏差：

- 术语相似但业务含义不同的块被排到前面。
- 短 Query 发散严重。
- 数字、版本号、接口名、时间表达召回很差。
- 业务文档里的型号、规范、错误码、配置项匹配不稳定。

因此不能只迷信通用榜单分数。实际业务里常常需要 BM25、规则检索和 Dense Retrieval 一起工作。

---

#### 七、Embedding 切 Chunk 应该怎么做？为什么固定长度切分经常不够？

固定长度切分容易把完整知识单元切断，导致召回命中一半证据。

更稳的方案是“结构优先，长度兜底”：

1. 先按标题、段落、表格、代码块、对话轮次等天然边界切分。
2. 对超长块再做二次切分。
3. 保留来源、章节路径、时间、实体标签和父子关系。

目标不是让每个 Chunk 长度均匀，而是让每个 Chunk 在语义上尽量自洽，既能被召回，又不会因为上下文缺失让后续生成偏掉。

---

#### 八、硬切分在实际场景里有哪些典型弊端？

常见问题有四类：

- 标题和正文分离：召回到了内容，但丢了语义锚点。
- 表格跨页或跨段被切裂：数值关系失真。
- FAQ 问答对被拆开：Query 命中问题，但取不到答案。
- 长流程文档被拆散：模型只看到动作，没看到前置条件和约束。

很多看起来像“模型幻觉”的问题，本质上是 Chunk 设计先把证据破坏掉了。

---

#### 九、RAG 里 Hard Negative 怎么构造？为什么比随机负样本更有价值？

Random Negative 太容易，训练出来的检索器只会区分“明显不相关”和“明显相关”，上线遇到真正的近邻干扰样本就失效。

Hard Negative 更接近真实业务中的干扰项，例如：

- 同领域、同实体、同模板、同章节，但回答不了当前问题的文本块。
- BM25 高分但人工判断为负的结果。
- Cross-encoder 重排后的误召回样本。
- 同文档相邻块。
- 同类任务历史 Bad Case。

Hard Negative 的价值不在于单纯增加难度，而是逼模型学会更细粒度的判别边界。

---

#### 十、ReAct 机制在生产环境里怎么设计？为什么不能只靠 Prompt 写几句 Thought / Action？

纯 Prompt 版 ReAct 只适合 Demo。生产环境里要把 Thought、Action、Observation 拆成显式状态并做约束。

关键设计：

- Thought 不能无限发散，要生成结构化计划或动作候选。
- Action 不能越权乱调，执行器要校验工具权限和参数合法性。
- Observation 不能被不可信文本直接污染推理，要做清洗和摘要。
- 每一轮推理都要有最大步数、超时、失败重试和终止条件。

比较稳的做法是：模型先产出结构化计划或动作候选，执行器校验后调用工具，外部结果回填时再清洗摘要，然后进入下一轮推理。这样 ReAct 才是一个可控运行时，而不是“把思维链打印出来”。

---

#### 十一、什么样的项目适合继续做模型重训练？什么样的项目更适合只做 RAG 或规则增强？

如果问题主要来自领域术语、格式稳定、标签可获取、任务目标清晰，并且线上规模足够大，那么有微调甚至继续预训练的价值。

如果问题集中在知识更新快、用户查询高度开放、答案必须引用最新文档，或者错误主要来自召回和上下文拼接，那么优先做 RAG、规则或路由层优化更划算。

很多团队一上来就想重训练模型，但实际上线上问题往往不在模型参数，而在数据链路、任务定义和评测集构建。

---

#### 十二、微调数据集一般从哪里来？怎么判断一批数据值不值得训？

微调数据来源通常有三类：

- 历史真实交互：最真实，但噪声大且分布偏。
- 专家标注样本：质量高，但成本高。
- 高质量合成数据：扩展快，但容易模式单一。

判断一批数据值不值得训，重点不在数量，而在：

- 是否覆盖任务边界。
- 是否覆盖高频失败模式。
- 标签是否一致。
- 是否和线上目标对齐。
- 是否能反映真实业务分布。

如果一批数据只是“看起来有很多问答对”，但没有覆盖高频失败模式，训练价值就很有限。

---

#### 十三、如果部署一个大模型服务，真正要关心的不是能不能跑起来，而是什么？

真正要关心的是吞吐、时延、显存占用、并发隔离、热更新、可观测性和降级策略。

服务能跑起来只是起点。线上更核心的是在高并发、长上下文、工具调用耦合和多租户隔离下还能稳定输出。

部署层常见关键决策：

- 张量并行还是流水并行。
- KV Cache 复用。
- 批处理策略。
- 流式输出。
- 请求超时。
- 抢占和优先级调度。

模型服务一旦进生产，问题基本不是“会不会生成”，而是“生成得稳不稳、快不快、贵不贵”。

---

#### 十四、如果线上要做多轮对话，记忆写入策略怎么定，才能避免越聊越脏？

不能把所有对话都直接写入长期记忆，否则系统很快会把一次性的闲聊、错误中间态和用户临时情绪全记住。

更稳的方式是只写入高置信、可复用、跨轮次有效的信息，例如：

- 长期偏好。
- 稳定身份信息。
- 反复确认过的业务约束。
- 关键结论。

写入前最好做去重、时效判断、冲突检查和来源标记；读取时再按任务类型和时间衰减检索。

记忆系统最重要的不是“记得多”，而是“记得准、删得掉、查得回”。

---

#### 十五、如果设计一套 Agent 评测体系，至少要覆盖哪些维度？

至少要覆盖：

- 路由正确率。
- 工具选择正确率。
- 参数填充正确率。
- 检索证据命中率。
- 最终任务成功率。
- 时延。
- 成本。
- 回退率。
- 人工接管率。

还要能追踪步骤级失败位置：到底是意图识别错了、检索漏了、工具超时了，还是最终生成忽略了证据。

Agent 评测如果只看终局成功，会把太多问题掩盖掉，最后只能得到一个模糊结论：有时能用，有时不行。

#### 二、参考回答：为什么要自己做 Code Agent？难点在哪里？

可以从三个角度回答：

1. 可控性。现成 Code Agent 很多关键环节对用户是黑盒，比如 Prompt 怎么拼、上下文怎么组织、工具什么时候调用、为什么这次做对下次跑偏。自研的价值是把这些关键环节拆开，能观察、能调试、能复盘。

2. 私有化和部署要求。实验室或企业项目有保密约束，不适合直接交给外部闭源服务；自研 Agent 可以接本地模型或内网模型，例如接入已经部署好的 Qwen，让 Agent 在保密场景下也能使用。

3. 场景适配。通用 Code Agent 很强，但未必适合具体业务仓库、工具链和开发流程；自研可以把仓库规范、测试命令、Review 规则、部署约束和任务恢复机制做进去。

比较难的部分：

- 上下文工程：Context 是有限资源，要避免长任务里遗忘最初 Spec、误用旧信息、重复操作、把局部修改扩大成全局破坏。
- 工具设计：Agent 效果不只取决于模型，也取决于工具粒度、工具 Schema、Tool Description、权限和返回格式。
- Harness 设计：任务跨多个 Context Window 时，必须有外层 Harness 管理进度、状态、记忆、验证和恢复，避免失控、卡死、跑偏、忘事和无法追责。
- 评测体系：只看任务是否 Pass / Fail 不够，要能评价步骤是否合理、工具是否冗余、失败点在哪里。
- 安全、权限和可控性：尤其是文件修改、命令执行、Git 操作、外部服务调用，都要有边界。

#### 三、参考回答：用过哪些 Code Agent？工作流是什么？

可以提到：

- Claude Code
- Codex
- Cursor
- Trae
- Kimi Code
- OpenCode

回答重点：

- 如果做 Code Agent，最好能回答自己用过 Claude Code。否则面试官可能会认为你没有真正体验过主流 Code Agent。
- Claude Code 的产品形态和模型推理能力都很强，适合做复杂任务分析、PRD / Tech Design、代码 Review。
- Codex 更像工程师，适合按计划写代码、补测试和执行开发任务。
- Cursor 更适合日常 IDE 内联开发和局部编辑。
- Kimi Code 在中文文档理解和撰写上有优势。
- Trae 可以关注，但复杂编码任务表现还要看模型能力、上下文组织和工具链设计。

一个可讲的 AI Coding 工作流：

1. 用 Claude Code 或强模型写 PRD / Tech Design。
2. 生成执行计划。
3. 用 Codex / Cursor 编码和补测试。
4. 用 Code Agent 做 Code Review。
5. 根据 Review 结果更新 `AGENTS.md` 或项目规则中的 Bad Case。
6. 再用 Claude Code Review 一轮。
7. 用 Agent 做进度管理、Git Commit 和 Push。

可以总结为：好的 Code Agent 更像一个工程团队里的 TL，不是微管理每一行代码，而是清楚任务拆分、能力边界、验收标准和风险控制。

#### 四、参考回答：为什么同一个模型在不同 Code Agent 中表现不同？

同一个基础模型放在不同 Code Agent 里，表现差异通常不主要来自模型本身，而来自 Agent 框架。

可以从五个层面回答：

1. 任务编排不同。有的 Agent 偏大步快跑，有的 Agent 会先规划、再执行、再验证。

2. 上下文构造不同。即使底层模型一样，系统提示词、仓库摘要、检索到的代码片段、历史轨迹、错误日志、测试结果都会影响输入分布。比如 Claude Code 的 `CLAUDE.md` 和 Codex 的 `AGENTS.md` 都会影响模型行为。

3. 工具链和反馈机制不同。工具是否好用、返回是否结构化、错误是否能被模型理解，都会影响成功率。

4. 决策策略不同。比如一步改大还是小步快跑，遇到不确定时先查再改还是直接改，是否允许多轮反思，失败后是否回滚，是否做多候选采样和重排。

5. 约束和安全边界不同。是否允许执行命令、是否允许写文件、是否需要审批、危险操作是否拦截，都会影响最终表现。

结论：Code Agent 的效果是“模型能力 + 上下文工程 + 工具系统 + 执行策略 + 安全约束”的综合结果。

#### 五、参考回答：Claude Code 架构给 Code Agent 的启发

可以只讲公开层面的架构思想，不必展开敏感实现细节。

1. Agent Loop 应该被设计成状态机，而不是普通 REPL。成熟的 Code Agent 会显式管理继续原因、终止原因、恢复路径、上下文压缩和失败降级。这样问题就从“模型回答质量”拉回到“运行时可靠性”。

2. 工具系统应该 Fail-closed。工具不是简单的 Schema 加 Description，而应该有统一契约、严格参数校验、权限链、并发安全判断和结果预算。判断不出来时默认按危险处理，而不是默认放行。

3. 上下文管理不是拼 Prompt，而是做预算。稳定前缀、Memory、Relevant Memory、History、Current Request、工具签名、工作区指纹等都要区分优先级和收缩顺序。Prompt Engineering 到后面会变成 Context Engineering。

4. 复杂任务要先对齐，再执行。类似 Plan Mode 的思想很重要：真正动手前先探索、先写计划、先确认权限和风险，再进入执行。

可以结合 Pico 说：如果项目里有 `ask()` 主循环、`TaskState`、Checkpoint、Resume、Trace、Report、Task State 落盘，就说明不是只保存聊天记录，而是在保存一个可恢复、可复盘的运行现场。

#### 六、参考回答：Harness 在 Code Agent 中怎么理解？

Harness 可以理解为包在模型外层的“运行时管理器”。模型负责推理和生成动作，Harness 负责让这个过程可控、可恢复、可评估。

在 Code Agent 里，Harness 通常负责：

- 任务状态管理：当前目标、计划、步骤、进度、阻塞点。
- 上下文管理：压缩历史、选择相关文件、控制 Token 预算。
- 工具调度：选择工具、校验参数、执行命令、处理结果。
- 权限控制：写文件、运行命令、Git 操作是否需要确认。
- 失败恢复：Checkpoint、回滚、重试、Resume。
- 评测与日志：记录 Trace、工具调用链、耗时、失败点和最终结果。

Code Agent 的 Harness 和普通对话 Agent 的 Harness 不同点在于：它面对的是代码仓库这种有状态、可破坏、可执行的环境，所以更强调文件系统一致性、命令执行安全、测试验证、Git 状态和任务恢复。

#### 七、参考回答：用户终端发指令到 Agent 完成任务的链路

可以按这个链路讲：

1. 接收用户输入：解析自然语言任务、当前仓库路径、Git 状态和运行环境。

2. 意图识别和任务建模：判断是问答、代码修改、Bug 修复、测试生成、重构还是 Review。

3. 上下文构建：读取项目规则、相关文件、目录结构、历史任务、错误日志和测试结果。

4. 计划生成：拆成可执行步骤，明确哪些要读文件、哪些要改代码、哪些要跑测试。

5. 工具调用：搜索代码、读取文件、编辑文件、执行命令、运行测试、查看 Git Diff。

6. Observation 回填：把工具结果清洗、摘要，再喂回 Agent。

7. 迭代执行：直到任务完成、失败、超时或需要用户确认。

8. 验证与收尾：跑测试、检查 Diff、生成报告，必要时提交 Commit。

9. 记忆与复盘：把 Bad Case、项目约束、关键经验写入规则或长期记忆。

---

#### 八、参考回答：如何减少 Code Agent 链路里的幻觉？

关键原则：让 Agent 少凭空猜，多基于工具证据行动。

做法：

- 所有代码判断尽量通过搜索、读取文件、测试结果和 Git Diff 证明。
- 工具返回要结构化，避免把大段不可信文本直接作为 Observation。
- 对高风险操作加确认，例如删除文件、批量改动、运行危险命令。
- 强制引用文件路径、函数名、测试结果，减少泛泛而谈。
- 限制每轮动作数量，避免一次性大改。
- 引入 Checkpoint，失败可以回滚。
- 用评测集记录常见幻觉：误读需求、改错文件、漏跑测试、假称测试通过等。

#### 九、参考回答：Prompt 怎么构建？

Code Agent 的 Prompt 不能只是一段系统提示词，而应该分层构建：

- 稳定前缀：角色、边界、安全规则、输出规范。
- 项目规则：`AGENTS.md`、代码风格、测试命令、提交规范。
- 当前任务：用户需求、成功标准、限制条件。
- 相关上下文：目录结构、相关文件片段、错误日志、历史操作。
- 工具说明：可用工具、参数 Schema、返回格式、权限边界。
- 执行状态：当前步骤、已完成动作、失败记录、下一步候选。

核心是控制优先级和预算：稳定规则不能轻易被挤掉，动态上下文要按相关性进入，历史记录要摘要压缩。

#### 十、参考回答：Memory 与提示词缓存怎么设计？

Code Agent 的 Memory 可以分几类：

- 项目记忆：项目结构、技术栈、测试命令、编码规范。
- 用户偏好：输出风格、提交习惯、常用命令。
- 任务记忆：当前任务目标、计划、执行进度、阻塞点。
- Bad Case 记忆：过去出错的地方和修正策略。
- 相关代码记忆：常改模块、关键入口、依赖关系。

提示词缓存可以围绕稳定上下文做：

- 系统提示词。
- 工具签名。
- 项目规则。
- 仓库摘要。
- 不常变化的依赖信息。

但当前请求、最新代码 Diff、测试输出这类动态内容不能盲目缓存，否则会污染判断。

#### 十一、参考回答：如何引入 Skill / MCP？

Skill 更像“面向任务的能力包”，MCP 更像“标准化连接外部工具和数据源的协议”。

引入方式：

1. 先定义能力边界：哪些任务适合封装成 Skill，例如生成测试、做代码 Review、修复 Lint、生成接口文档。

2. 再定义 MCP 工具：例如读写文件、搜索代码、查文档、跑测试、查 Issue、访问数据库。

3. Skill 内部可以编排多个 MCP 工具：先读规则，再搜索代码，再调用测试，再汇总结果。

4. 加权限和错误处理：高风险工具需要确认，失败要有重试、降级和报告。

5. 加可观测性：记录每次 Skill 调用了哪些 MCP 工具、耗时、失败点和输出。

#### 十二、参考回答：任务恢复是什么意思？

任务恢复是指 Agent 在长任务中断、失败、超时或上下文被压缩后，能够从一个可靠状态继续执行，而不是从头再来。

需要保存：

- 用户原始目标。
- 当前计划和完成进度。
- 已调用工具和返回结果。
- 文件修改 Diff。
- 测试结果。
- Checkpoint。
- 失败原因和下一步建议。

对 Code Agent 来说，任务恢复尤其重要，因为代码仓库是有状态环境。没有恢复机制，Agent 容易改到一半中断，用户也不知道系统做了什么。

Code Agent 常见工具：

- 代码搜索。
- 文件读取。
- 文件编辑。
- Shell 命令。
- 测试运行。
- Git Diff / Status。
- 代码 Review。
- 文档检索。
- 子任务委派。

新增工具时要关注：

- 工具名和描述是否清晰。
- 参数 Schema 是否严格。
- 返回结果是否结构化。
- 是否有副作用。
- 是否需要权限确认。
- 是否可重试。
- 是否有超时和日志。

工具不是越多越好，关键是粒度合适、边界清楚、返回可用。

#### 十四、参考回答：怎么设计 Benchmark？

Code Agent Benchmark 不能只看最终是否完成，还要看过程。

维度：

- 任务成功率。
- 编译 / 测试通过率。
- Diff 是否最小。
- 是否改错文件。
- 是否引入回归。
- 工具调用次数。
- 平均耗时。
- Token 成本。
- 失败后是否能恢复。
- 是否遵守项目规范。
- 是否需要人工接管。

任务集要覆盖：

- Bug 修复。
- 新功能。
- 测试生成。
- 重构。
- 文档更新。
- 代码 Review。
- 多文件改动。
- 长上下文任务。

#### 十五、参考回答：什么是好的 Code Agent？未来趋势是什么？

好的 Code Agent 不只是会写代码，而是能稳定完成真实工程任务。

关键特征：

- 能理解需求和仓库上下文。
- 能拆任务、写计划、执行、验证、复盘。
- 能正确使用工具。
- 能控制修改范围。
- 能跑测试并理解失败。
- 能管理长上下文。
- 能保证安全和权限边界。
- 能从 Bad Case 中积累项目规则。

未来趋势：

- 从“代码补全”走向“工程任务代理”。
- 从单轮生成走向长任务 Harness。
- 从 Prompt Engineering 走向 Context Engineering。
- 从单 Agent 走向多 Agent 协作。
- 从泛化工具走向企业内部私有化、权限化、可审计的工程平台。

### 面试复盘与后续训练策略：算法手感、Agent 底层理解与心态调整

#### 一、手撕题不能只靠“会思路”

这次手撕题卡壳，并且中途被面试官指出代码错误，尤其题目还是 Hot 100 里类似“岛屿数量”这种经典题，说明算法不能只停留在“我知道思路”的层面。

后续训练重点：

- Hot 100 里的经典题要保持手感，不能因为以前做过就完全不练。
- 熟题也要定期闭卷写一遍，尤其注意边界判断、初始化、循环条件和返回值。
- 图搜索、滑动窗口、二分、栈、队列、动态规划这些高频题型要形成可直接落笔的模板。
- 面试中被指出错误时不要慌，先复述问题，再定位错误，再快速修正。

---

#### 二、Prompt / Context / Harness 不能只停留在关注层面

Prompt Engineering、Context Engineering 和 Harness Engineering 不能只是“知道这些词”或“用过相关工具”，还要能讲清底层逻辑和设计取舍。

需要深入的方向：

- Prompt：任务描述、约束、输出格式、Few-shot、错误样本回流、版本管理。
- Context：上下文预算、历史压缩、相关信息选择、稳定前缀、动态上下文、缓存策略。
- Harness：状态管理、工具调度、权限控制、失败恢复、Trace、评测、熔断和降级。
- OpenClaw / Claude Code / Skills：不能只会用，要理解设计亮点、运行链路、边界条件和工程约束。

复盘结论：

- 面试官问的往往不是“你听没听过”，而是“你能不能解释为什么这样设计”。
- 对 Skills、OpenClaw、Harness 这类新概念，要准备“解决什么问题、核心机制是什么、怎么落地、有什么局限”四层回答。

---

#### 三、Agent 面试更偏场景题和组合推理

Agent 开发面试不一定像传统八股那样问标准定义，更多是给一个场景，看你能不能组合使用已有知识解决问题。

常见考察方式：

- 给一个业务场景，让你设计 Agent 架构。
- 追问工具调用失败、上下文过长、RAG 召回不准、模型幻觉怎么办。
- 让你比较 ReAct、Plan&Execute、Reflection、Workflow、Skills、MCP 的适用场景。
- 根据项目细节连续追问数据流、工具链、评测方式、失败案例和优化思路。

应对策略：

- 回答场景题时，先拆问题，再给架构，再讲链路，最后补充评测和兜底。
- 被质疑时不要慌，先承认边界，再补充工程化方案。
- 不要硬背概念，要能把 Prompt、RAG、Tool Calling、Memory、Evaluation、Safety 串成一个完整系统。

---

#### 四、面试失败后的有效动作

沉浸在被挂、焦虑和失落里没有意义。真正有价值的是把失败面试转成下一轮准备材料。

后续动作：

1. 每场面试后立刻复盘：记录题目、卡点、答得不好的原因。
2. 把不会的问题归类：算法、八股、项目深挖、Agent 架构、RAG、Prompt、AI Coding。
3. 对每类问题形成固定训练计划，而不是零散补知识。
4. 对高频项目追问写出 1 分钟、3 分钟、5 分钟三个版本回答。
5. 每周固定练手撕题，保持代码手感。
6. 每周追踪 2 到 3 个 Agent / AI Coding 新技术，但必须沉淀成“原理 + 场景 + 局限”的笔记。

最终目标不是避免失败，而是让每次失败都能明确改变下一轮的准备策略。
