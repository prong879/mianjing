### 九、数据仓库与数据产品习题

#### 1. 数据产品基础题：数仓分层、指标口径、埋点和数据质量通常怎么考？

这一模块常见题型包括：

- 数仓分层题
- 指标口径题
- 埋点设计题
- 数据质量排查题
- 数据产品需求设计题
- AI 数据分析工具设计题

回答时建议围绕“数据从哪里来、怎么算、给谁用、如何验证、如何迭代”这条线展开。

#### 2. AI 数据产品方案题：资源有限时，规则建模、微调开源模型、调用云上 API 怎么选？

**题目（整理版）**：

假设给内容创作者设计“智能数据分析工具”，初期资源有限，应该优先基于规则建模、微调开源算法模型，还是直接调用云上数据分析 `API`？请说明决策框架。追问：哪些因素是底线必须满足，哪些是能权衡的变量？

**参考答法**：

我会先按“业务目标 - 数据条件 - 效果要求 - 成本周期 - 风险合规”来判断，而不是直接选某一种技术。

三种方案可以这样比较：

- **规则建模**
  - 优点：上线快、可解释、成本低、容易控制风险
  - 缺点：泛化能力弱，复杂场景下效果上限有限
  - 适合：早期 `MVP`、规则明确、对准确和可解释要求高的场景
- **微调开源模型**
  - 优点：效果上限更高，可逐步沉淀自有能力
  - 缺点：需要标注数据、训练资源、算法维护能力
  - 适合：已有一定数据积累，且业务场景相对稳定
- **调用云上 API**
  - 优点：接入快，能力成熟，前期研发压力小
  - 缺点：成本、数据安全、稳定性和定制化受限
  - 适合：快速验证需求、内部暂无成熟能力、非核心差异化模块

**底线必须满足**：

- 数据安全和隐私合规
- 结果准确性达到可用阈值
- 服务稳定性和响应时延可接受
- 成本不能超过业务验证阶段的承受范围
- 输出结果不能明显误导创作者决策

**可以权衡的变量**：

- 短期效果和长期自研能力
- 上线速度和可定制程度
- 算力成本和模型效果上限
- 可解释性和智能化程度
- 人工审核成本和自动化程度

一句话总结：

> 初期我会倾向用“规则 + API/轻模型”先做可控的 `MVP`，验证真实需求和核心指标；如果使用频率、业务价值和数据积累都证明值得，再逐步微调模型或建设自研能力。

#### 3. AI 数据产品能力规划：实时监控和精准推荐怎么做技术路径？

**参考答法**：

可以分阶段规划，避免一开始就做重系统。

**第一阶段：离线分析和规则推荐**

- 建立创作者基础画像、内容画像、指标看板
- 每日更新核心指标，例如曝光、点击、完播、互动、涨粉、转化
- 用规则输出简单建议，例如“近期完播率下降，建议优化开头 3 秒”

**第二阶段：准实时监控和异常提醒**

- 接入小时级或分钟级数据流
- 建立异常检测规则，例如环比突降、同比异常、分位数异常
- 推送给创作者或运营同学，提示“哪个指标、从什么时候、在哪类内容上变化”

**第三阶段：个性化推荐和智能归因**

- 根据创作者类型、内容垂类、粉丝结构做分层
- 结合相似创作者、历史内容表现，推荐选题、发布时间、内容结构
- 用模型输出影响因素排序，但保留可解释说明

**第四阶段：闭环迭代**

- 记录用户是否采纳建议
- 观察采纳后的指标变化
- 把 bad case 和反馈回流到规则和模型中

#### 4. AI 数据产品实验设计：分阶段上线时如何证明投入值得？

**参考答法**：

每个阶段都要先定义清楚“投入换来的是什么”。

**MVP 阶段**重点验证需求是否成立：

- 指标：功能使用率、留存率、报告打开率、建议点击率、用户反馈
- 方法：灰度给一小批创作者，对比使用组和未使用组

**实时监控阶段**重点验证是否降低问题发现成本：

- 指标：异常发现时延、问题定位时长、告警准确率、误报率、处理率
- 方法：对比上线前后的运营处理效率，或在部分垂类灰度

**精准推荐阶段**重点验证是否带来业务提升：

- 指标：建议采纳率、内容发布频次、内容表现提升、粉丝增长、商业转化
- 方法：A/B 实验，控制创作者层级、垂类、历史表现等变量

**立项复盘时**可以补充：

> 如果短期业务指标还不明显，也要看是否提升了分析效率、降低了人工服务成本、沉淀了创作者画像和内容理解能力。

#### 5. AI 服务选型题：自研、用集团内部能力、调用外部 API 怎么选？

**参考答法**：

我会从以下维度判断：

- **业务核心程度**：是否是产品核心竞争力
- **数据安全要求**：是否涉及用户隐私、内容浏览、互动记录
- **效果要求**：通用能力够不够，是否需要深度定制
- **成本结构**：调用成本、训练成本、维护成本、算力成本
- **上线周期**：业务是否急需快速验证
- **可控性**：稳定性、限流、故障响应、模型升级节奏
- **长期沉淀**：是否能沉淀内部数据、标签体系和模型能力

一般可以这样回答：

> 非核心、标准化能力可以优先调用成熟 API；和业务强相关、需要沉淀数据资产的能力，优先考虑集团内部能力或自研；涉及高敏数据和长期差异化能力的模块，不宜完全依赖外部 API。

如果被问到字节的云雀模型或其他 AI 服务，可以稳妥表达：

> 我会把它理解为字节体系内面向内容理解、生成、推荐或审核的 AI 能力，适合用于智能客服、内容分析、创作辅助、内容审核、经营分析报告生成、创作者建议推荐等场景。面试里我不会只强调模型本身，而会重点说明它如何和业务数据、用户场景、安全合规结合。

#### 6. AI 数据产品合规题：涉及用户隐私数据时如何和工程、算法团队协作？

**参考答法**：

这类题要先表明底线：隐私和合规不是上线后补救，而是设计阶段就要约束。

可以从四层讲：

1. **数据最小化**
   - 只采集实现功能所需的数据
   - 能用聚合数据就不用明细数据
2. **权限和脱敏**
   - 对用户 ID、浏览记录、互动明细做脱敏或匿名化
   - 建立按角色授权的数据访问机制
3. **模型训练和调用边界**
   - 明确哪些数据能进训练集，哪些只能做实时查询
   - 外部 API 调用时避免传输敏感明细
4. **审计和监控**
   - 保留数据访问日志
   - 对异常导出、异常查询和越权访问做告警

协作方式上可以说：

> 我会先和产品、工程、算法、法务或合规同学确认数据边界和使用目的，再把隐私要求转成字段级权限、脱敏规则、模型输入限制和上线验收标准。

#### 7. AI 项目立项题：大量算力投入如何论证投入产出比？

**参考答法**：

立项报告里不能只说“AI 是趋势”，要把投入和收益量化。

**成本侧**可以拆：

- 算力成本
- 存储和数据处理成本
- 研发和算法人力
- 标注和评测成本
- 后续运维成本

**收益侧**可以拆：

- 直接收入：商业化转化、付费工具、广告效率提升
- 效率提升：减少人工分析、客服、运营诊断成本
- 留存提升：创作者活跃、发布频次、平台黏性
- 内容供给改善：优质内容数量、内容质量、垂类覆盖
- 数据资产沉淀：创作者画像、内容标签、分析规则库、bad case 库
- 长期竞争力：平台智能化能力和创作者服务能力

一句话总结：

> 我会把算力投入拆成明确成本，再用增收、降本、提效、留存、数据资产和长期壁垒去论证回报，并通过分阶段灰度控制投入风险。

#### 8. AI 数据分析工具指标题：除准确率外，还看哪些用户体验和业务价值指标？

**参考答法**：

“分析结果准确率”很重要，但不足以完整评价一个智能分析工具。

还可以看：

- **使用体验**：报告打开率、功能使用率、响应时延、操作完成率
- **信任程度**：建议采纳率、重复使用率、人工修正率、用户反馈评分
- **解释质量**：结论可解释性、证据链完整度、可追溯性
- **业务结果**：内容表现提升、粉丝增长、互动率提升、转化提升
- **效率价值**：节省分析时间、减少人工诊断成本、问题发现时延缩短
- **安全质量**：误导性建议率、投诉率、风险拦截率

如果准确率下降，可以按这条路径排查：

1. **数据问题**
   - 数据延迟、缺失、埋点变更、口径变化、样本结构变化
2. **模型问题**
   - 模型版本更新、训练数据漂移、特征分布变化、过拟合
3. **算法逻辑问题**
   - 规则阈值不适配、排序逻辑变化、召回或过滤策略异常
4. **用户需求变化**
   - 创作者目标变化、平台内容生态变化、业务场景变化
5. **评估口径问题**
   - 准确率标签是否可靠，是否只覆盖部分人群或部分场景

#### 9. AI 数据产品迭代题：如何从 bad case 持续发现机会，并推动算法团队处理？

**参考答法**：

bad case 机制要产品化，而不是靠零散反馈。

可以这样做：

- 建立 bad case 收集入口：用户反馈、运营标注、人工抽检、线上监控
- 给 bad case 分类：数据错误、模型理解错误、规则不合理、推荐不准、表达误导
- 量化影响范围：影响用户数、核心创作者数、业务损失、投诉风险
- 建立优先级：高频、高价值用户、高风险问题优先
- 和算法团队对齐评测集：把典型 bad case 纳入回归测试
- 建立迭代闭环：问题发现、原因归类、修复方案、上线验证、复盘沉淀

推动算法团队时，不要只说“用户觉得不好”，而要拿出证据：

> 我会把 bad case 变成可量化的问题包，比如问题类型、出现频次、影响人群、业务损失和修复后预期收益。这样算法团队更容易判断优先级，也更容易把它纳入模型迭代计划。

#### 10. AI 风险题：AI 生成报告可能误导创作者，产品机制如何防范？如何平衡保守和有用？

**参考答法**：

防范误导要从生成前、生成中、生成后一起做。

**生成前**：

- 明确数据口径和样本范围
- 对低样本量、低置信度场景加限制
- 高风险建议不直接自动生成

**生成中**：

- 输出置信度或证据来源
- 把事实、推断、建议分开展示
- 对不确定结论使用谨慎表达

**生成后**：

- 提供用户反馈入口
- 对高风险建议做人审或运营抽检
- 监控误导性建议率、投诉率、采纳后负向结果

如果风险过滤太严格，导致报告太保守，可以这样平衡：

> 我会按风险分层处理。低风险建议可以更主动，例如选题、发布时间、标题优化；高风险建议要更谨慎，例如商业投入、内容方向大幅调整。同时用置信度、样本量提示和证据链展示，让用户知道建议的可靠程度，而不是简单地全部拦截。

#### 11. AI 公平性题：如何减少 AI 数据分析中的偏见？

**参考答法**：

偏见可能来自数据、模型和产品机制。

常见做法包括：

- **数据层**：检查不同类型创作者、不同垂类、不同粉丝量级样本是否失衡
- **指标层**：不要只优化头部创作者效果，也要看中腰部和长尾创作者体验
- **模型层**：监控不同人群的准确率、推荐曝光、采纳效果是否差异过大
- **规则层**：避免把历史高表现固化成唯一推荐标准
- **产品层**：给用户解释推荐原因，并允许反馈“不适合我”
- **治理层**：定期做公平性评估和 bad case 复盘

一句话总结：

> 减少偏见不是让所有创作者得到完全一样的建议，而是避免模型因为历史数据和平台机制，把机会长期倾斜给某一类创作者。

#### 12. LLM 与文本分析题：常见算法和原理怎么答？

**参考答法**：

如果面试官问“了解 LLM 或文本分析吗”，不要只说用过大模型，可以按传统文本分析和大模型两层回答。

**传统文本分析**：

- 分词、去停用词、词频统计
- `TF-IDF`：衡量一个词对文本的重要程度
- 文本分类：逻辑回归、朴素贝叶斯、`SVM`、树模型
- 主题模型：`LDA`
- 词向量：`Word2Vec`

**LLM 基础理解**：

- 大模型基于 Transformer 架构
- 核心机制是 Attention，用来建模上下文中不同 token 的关系
- 预训练阶段学习通用语言能力
- 指令微调和对齐阶段让模型更符合人类任务表达
- 在业务中可以用于摘要、分类、问答、信息抽取、报告生成和 Agent 任务规划

如果结合数据分析场景，可以说：

> 我会把 LLM 用在文本评论分析、客服工单归因、舆情摘要、报告初稿生成和指标异常解释上，但最终结论仍需要结合结构化数据验证。

#### 13. 大模型追问：大模型幻觉是什么？怎么避免？

**参考答法**：

大模型幻觉指的是模型生成了看起来合理、但实际上不准确、没有依据或与事实矛盾的内容。

常见原因包括：

- 模型本质是在预测下一个 token，不等于真正知道事实
- 训练数据里可能有过时、错误或冲突信息
- 提示词不清楚，模型会自行补全缺失信息
- 缺少外部知识或实时数据支撑
- 复杂推理链路中间步骤出错

降低幻觉的方法：

- **RAG**：先检索可靠知识库，再让模型基于材料回答
- **工具调用**：涉及数据、计算、查询时调用 SQL、API、计算器
- **引用证据**：要求输出依据、来源和数据口径
- **限制输出范围**：不知道就说不知道，不让模型自由编造
- **人工审核**：高风险场景保留人工确认
- **评测和 bad case**：建立幻觉样例库，持续回归测试

一句话总结：

> 幻觉不是简单“模型不聪明”，而是生成式模型缺少可靠事实约束；解决思路是用检索、工具、证据链和人工审核把输出约束在可信信息上。

#### 14. 大模型评估题：如何评估 LLM 输出质量？

**参考答法**：

评估大模型输出不能只看“像不像人说话”，要按任务目标拆。

常见维度：

- **事实准确性**：有没有编造、数据是否正确
- **相关性**：是否回答了用户问题
- **完整性**：关键点是否遗漏
- **逻辑性**：推理链路是否自洽
- **可解释性**：是否给出依据和来源
- **稳定性**：同类问题多次回答是否一致
- **安全性**：是否泄露隐私、越权、输出违规内容
- **业务价值**：是否真的提升效率、转化、满意度或分析质量

评估方式：

- 人工标注评分
- 标准问答集或任务集
- 自动指标，例如准确率、召回率、引用命中率
- 线上 A/B，看真实用户行为
- bad case 分类和回归测试

一句话总结：

> LLM 评估要同时看事实、任务完成、用户体验和安全风险，不能只看语言是否流畅。

#### 15. RAG 原理题：RAG 是什么？为什么能减少幻觉？

**参考答法**：

`RAG` 是 Retrieval-Augmented Generation，检索增强生成。

基本流程：

1. 用户提出问题
2. 系统把问题转成向量或关键词
3. 从知识库中检索相关文档片段
4. 把检索结果和用户问题一起放进 prompt
5. 大模型基于检索材料生成回答

它能减少幻觉的原因是：

- 模型不完全依赖参数记忆
- 回答有外部知识作为依据
- 可以引用最新、私有、结构化的业务资料
- 便于做权限控制和来源追踪

但 `RAG` 也不是万能的：

- 检索不到正确资料，模型仍可能答错
- 检索结果太多或噪声太大，会干扰生成
- 文档切分、召回、排序和权限都很重要
- 仍需要评估引用是否真的支撑结论

一句话总结：

> RAG 的核心是“先找资料，再让模型基于资料回答”，它通过外部知识约束生成结果，但最终效果取决于检索质量、知识库质量和生成约束。

#### 16. AI Agent 评测题：如何评价一个 Agent 的效果？

**参考答法**：

评价 Agent 不能只看最终回答是否像人话，而要看任务完成质量和过程可靠性。

可以从以下维度评估：

- **任务成功率**：是否完成用户目标
- **准确性**：数据、结论、引用是否正确
- **工具调用正确率**：是否调用了合适工具，参数是否正确
- **步骤效率**：是否绕路、重复调用、无效等待
- **稳定性**：同类任务多次运行结果是否一致
- **安全性**：是否泄露隐私、越权访问、执行高风险操作
- **可解释性**：是否能说明关键依据和推理路径
- **用户体验**：响应时间、可读性、可操作性

评测方法：

- 构建标准任务集和标准答案
- 人工评审关键任务
- 线上收集用户反馈和 bad case
- 做回归测试，防止模型或工具升级后退化

一句话总结：

> Agent 评测要同时看结果、过程和风险，不能只看一次回答好不好。

#### 17. 自动化归因工具题：如何设计 AI 自动化归因树？数科在其中做什么？

**参考答法**：

自动化归因树的目标是把“指标异常”自动拆解到可能原因。

**实现思路**：

1. **定义核心指标**
   - 例如 `GMV`、转化率、留存、使用率
2. **建立指标拆解树**
   - `GMV = 流量 × 转化率 × 客单价`
   - 转化率继续拆到曝光、点击、加购、下单、支付
3. **建立维度下钻体系**
   - 时间、地区、渠道、人群、商品、内容、版本
4. **做异常检测**
   - 同比、环比、移动均值、分位数、控制图
5. **做贡献度计算**
   - 找出哪些维度对整体波动贡献最大
6. **生成归因报告**
   - 输出异常现象、主要贡献维度、可能原因和建议动作

**数科或数据分析的作用**：

- 定义指标口径和拆解逻辑
- 设计归因维度和优先级
- 校验算法输出是否符合业务常识
- 建立 bad case 反馈和评测机制
- 推动归因结果进入业务流程

效果验收指标：

- 异常发现准确率
- 误报率和漏报率
- 归因命中率
- 平均定位时长
- 业务采纳率
- 人工分析节省时长

#### 18. 自动化分析工具题：如何把项目分析流程产品化？采用哪些指标？

**参考答法**：

如果要把一次人工分析流程做成自动化工具，可以按“输入 - 处理 - 输出 - 反馈”设计。

**输入层**：

- 指标名称
- 时间范围
- 分析维度
- 对比基准
- 数据权限和口径

**处理层**：

- 数据质量校验
- 异常检测
- 指标拆解
- 贡献度排序
- 相似历史案例召回

**输出层**：

- 异常摘要
- 主要原因排序
- 证据图表
- 可执行建议
- 置信度和风险提示

**反馈层**：

- 用户是否采纳
- 归因是否正确
- 建议是否有效
- bad case 归档

工具指标可以看：

- 使用率、复用率
- 分析耗时节省
- 归因准确率
- 业务采纳率
- 报告打开率
- 用户满意度
- 人工修正率

#### 19. AI 数据评测题：如何评估模型在两个能力维度上做得好不好？

**参考答法**：

如果面试官问“要找数据评测这两个方面做得如何，你会怎么做”，可以先把评测目标拆清楚：到底是评估准确性、相关性、安全性、体验，还是业务价值。

**第一步：定义评测维度**

例如输入法联想可以拆成：

- 上下文契合度
- 用户语言风格匹配度

TTS 角色扮演可以拆成：

- 声音匹配度
- 角色表现力

**第二步：构建评测集**

- 覆盖高频场景和长尾场景
- 覆盖不同用户类型、文本类型和内容难度
- 保留线上真实 bad case
- 标注标准要明确，避免评审口径漂移

**第三步：设计评测方式**

- 机器指标：准确率、召回率、TopK 命中、相似度、错误率
- 人工评测：相关性、自然度、风格一致性、安全性
- A/B 实验：观察真实用户行为和业务指标
- 分层评估：按人群、场景、内容类型分别看

**第四步：建立迭代闭环**

- 按问题类型归因
- 建 bad case 库
- 每次模型或策略升级做回归测试
- 观察线上指标是否同步改善

一句话总结：

> 数据评测不是只给一个总分，而是先定义能力维度，再构造覆盖真实场景的评测集，结合机器指标、人工评审和线上实验判断是否真的变好。

#### 20. AI 产品场景题：微信读书做 TTS 角色扮演听书功能，如何设计和评估？

**题目**：

如果微信读书想做 `TTS`，让 AI 扮演小说中的角色，实现听书功能，你会怎么做？人声匹配要考虑哪些因素？上线前如何评估角色扮演好坏？

**产品设计思路**：

1. **内容解析**
   - 识别小说章节、旁白、对话、角色名称
   - 判断每句话是谁说的
2. **角色画像**
   - 性别、年龄、性格、情绪、身份
   - 主角、配角、旁白区分
3. **声音匹配**
   - 为不同角色匹配合适音色
   - 旁白保持稳定清晰
   - 角色对话要有区分度
4. **情绪表达**
   - 根据文本情绪调整语速、停顿、音量、语调
   - 对疑问、惊讶、愤怒、悲伤等情绪做差异表达
5. **用户控制**
   - 支持切换音色
   - 支持语速调节
   - 支持关闭角色扮演，退回普通听书模式

**人声匹配要考虑的因素**：

- 角色性别和年龄
- 性格和身份
- 情绪表达能力
- 音色区分度
- 长时间收听舒适度
- 和小说类型是否匹配
- 是否存在违和、夸张或出戏感

**上线前评估指标**：

- 角色识别准确率
- 对话归属准确率
- 音色匹配度
- 情绪表达准确性
- 听感自然度
- 角色区分度
- 用户理解成本
- 安全和版权风险

**评估方法**：

- 抽样章节做人工评审
- 让用户盲测普通 TTS 和角色 TTS
- 对不同小说类型分层评估，例如言情、悬疑、历史、玄幻
- 记录用户是否完整听完、是否切换回普通模式
- 灰度上线后看听书时长、完听率、收藏/续听率、负反馈率

一句话总结：

> 角色 TTS 的关键不是“声音越多越好”，而是角色识别准确、声音匹配不违和、情绪表达自然，并且真的提升用户听书沉浸感。

#### 21. AI Agent 实操题：如何用 API 和工作流搭一个智能体？

**参考答法**：

如果面试不是写代码，而是要求用 `API` 和工作流搭一个智能体，可以按“目标 - 输入 - 工具 - 流程 - 评估 - 风险”来讲。

**第一步：明确 Agent 目标**

例如搭一个“业务指标异常分析 Agent”：

- 输入：指标名称、时间范围、对比周期、业务线
- 输出：异常摘要、主要影响维度、可能原因、后续建议

**第二步：设计工作流**

可以拆成：

1. **理解任务**
   - 解析用户问题，识别指标、时间、维度和分析目标
2. **调用数据 API**
   - 查询指标数据、维度拆解数据、历史同期数据
3. **做数据校验**
   - 检查缺失、延迟、异常值和口径变化
4. **执行分析逻辑**
   - 同比、环比、贡献度、漏斗拆解、分群下钻
5. **生成结论**
   - 用结构化模板输出异常原因、证据和建议
6. **人工确认和反馈**
   - 业务方确认归因是否准确，把 bad case 回流迭代

**第三步：需要哪些 API 或工具**

- 指标查询 API
- 元数据/指标口径 API
- 维度下钻 API
- 图表生成或报表 API
- 权限校验 API
- 日志和反馈 API

**第四步：如何评价效果**

- 任务完成率
- 数据查询正确率
- 归因命中率
- 平均分析耗时
- 人工修正率
- 业务采纳率
- 是否有越权、幻觉或错误建议

一句话总结：

> 搭 Agent 不是把大模型接上 API 就结束，而是要把任务拆成可控工作流，让模型负责理解、编排和表达，让数据 API 和规则逻辑保证事实准确。

#### 22. AI 取数题：如何写 prompt 才能让模型正确取数？

**参考答法**：

让 AI 正确取数的关键不是把问题写得很长，而是把“业务口径、表字段、时间范围、筛选条件、输出格式和校验规则”讲清楚。

一个稳定的取数 prompt 可以包含：

1. **角色和任务**
   - 说明你是数据分析助手，需要生成 SQL 或调用数据 API。
2. **指标口径**
   - 明确指标定义，例如 `GMV = 支付成功订单金额，不含退款和取消订单`。
3. **数据范围**
   - 时间范围、业务线、地区、用户范围、是否去重。
4. **表结构和字段**
   - 表名、主键、时间字段、金额字段、状态字段。
5. **约束条件**
   - 不允许编造字段；不确定时先提问；输出前检查分母分子。
6. **输出格式**
   - 输出 SQL、口径说明、潜在风险和校验点。

可以这样表达：

```text
请基于下面表结构生成 SQL，不要编造字段。
目标：计算 2025-03 每日支付 GMV。
口径：只统计 pay_status = 'paid' 的订单，排除退款和取消订单。
表：orders(order_id, user_id, pay_time, pay_amount, pay_status, refund_status)
输出：SQL + 口径说明 + 需要校验的数据质量问题。
如果字段不足，请先指出缺失字段，不要直接假设。
```

一句话总结：

> AI 取数 prompt 要像真实需求文档一样写清楚口径和约束，并要求模型在字段不足时先确认，而不是自由猜表和猜字段。

#### 23. AI 幻觉治理题：如何解决模型幻觉问题？

**参考答法**：

模型幻觉在数据分析场景里尤其危险，因为它可能编造指标、字段、原因或结论。

可以从四层治理：

1. **数据源约束**
   - 接入指标口径库、元数据、数据字典和权限系统。
   - 不允许模型凭空生成字段或口径。
2. **工具调用**
   - 涉及数值计算、SQL 查询、指标口径时必须调用工具。
   - 让模型负责理解和表达，事实由数据 API 或 SQL 返回。
3. **输出约束**
   - 要求输出证据来源、查询时间、样本范围和置信度。
   - 对低样本量、缺失数据和异常波动加提示。
4. **评测闭环**
   - 建立幻觉 bad case 库。
   - 按字段编造、口径错误、归因过度、建议不合理等类型分类。
   - 每次模型或 prompt 更新后做回归测试。

一句话总结：

> 解决幻觉不是单靠“写好 prompt”，而是要用可信数据源、工具调用、证据链和评测闭环把模型约束在事实范围内。

#### 24. AI Agent 场景题：如何搭建能根据实验结果自动输出报告的 Agent？

**参考答法**：

这个 Agent 的目标不是“写一篇漂亮报告”，而是把实验数据、统计检验、指标解释和业务建议串成可复核流程。

**输入**：

- 实验名称、实验时间、实验组和对照组
- 核心指标、过程指标、护栏指标
- 样本量、分流比例、实验配置
- 实验明细或聚合数据

**工作流**：

1. **读取实验配置**
   - 确认分流单元、实验周期、指标口径。
2. **数据质量检查**
   - 检查样本量、分流比例、埋点缺失、异常流量、实验污染。
3. **计算指标**
   - 计算实验组和对照组的均值、比例、差异、提升率。
4. **显著性检验**
   - 根据指标类型选择 z 检验、t 检验、卡方检验、bootstrap 等。
5. **分层分析**
   - 按新老用户、渠道、城市、设备、商家层级等拆解。
6. **生成报告**
   - 输出实验结论、证据表、风险点、是否建议上线。
7. **人工确认**
   - 高风险或结论不明确时交给分析师复核。

**效果评估**：

- 报告生成准确率
- 统计检验选择正确率
- 人工修改率
- 分析耗时节省
- 业务采纳率
- 错误结论率和风险拦截率

一句话总结：

> 自动实验报告 Agent 要把实验平台、指标口径、统计检验和报告模板打通，核心是可复核、可追溯，而不是单纯让大模型总结文字。

#### 25. 职业发展题：AI 时代个人定位是什么？技术栈和后续转型方向怎么答？

**参考答法**：

AI 时代的数据分析师不能只定位成“取数和写报表的人”，更应该成为能把业务问题、数据资产和 AI 工具连接起来的人。

可以这样回答个人定位：

> 我的定位是“懂业务的数据分析师 + 会使用 AI 工具的数据产品思维”。AI 可以提升取数、归因和报告生成效率，但分析师仍然要负责定义问题、确认口径、判断因果、识别风险和推动落地。

**技术栈可以分三层**：

- 数据基础：SQL、Python、统计学、实验设计、因果推断
- 工具产品：BI、数据仓库、指标体系、自动化报表、数据产品设计
- AI 能力：prompt、RAG、Agent 工作流、模型评测、数据安全和幻觉治理

**后续转型方向**可以说：

- 深耕业务分析，成为能独立负责业务线的数据 BP
- 转向数据产品，做指标平台、实验平台、AI 分析工具
- 转向数据科学，强化建模、因果推断和策略评估
- 转向 AI 应用，负责 Agent、自动化分析和智能决策产品

一句话总结：

> AI 不会替代分析师的业务判断和问题定义能力，但会替代低价值重复劳动；所以个人要往“业务理解 + 数据方法 + AI 工具落地”方向升级。
