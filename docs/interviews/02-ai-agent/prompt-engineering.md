## 二、提示词工程 (Prompt Engineering) & 上下文管理

### 提示词技巧

- **开发 Agent 时，如何设计 Prompt 才能让 Agent 更精准地理解任务、调用工具？**

> **参考回答**：采用结构化 Prompt 设计（如 CRISPE 框架：角色、任务、上下文、约束、格式），明确规定输入输出的 Schema（如 JSON 格式）。对于工具调用，提供详细的工具描述（Description）和参数说明（类型、是否必填），并给出 One-Shot 或 Few-Shot 示例，以减少幻觉和参数错误。

- **如何调 Prompt？调 Prompt 过程中遇到过哪些问题？**

> **参考回答**：调优遵循“从简单到复杂、逐步添加约束”的原则。常遇到的问题包括：1) 提示词过长导致模型“迷失在中间（Lost in the Middle）”；2) 模型对否定句理解差（如“不要输出xxx”），应改为肯定句（如“仅输出xxx”）；3) 输出格式不稳定，解决办法是提供强格式约束（如 `<output></output>` 标签包裹）和 Few-Shot 示例。

- **如果不微调模型，模型不按格式输出、乱加戏、产生幻觉，有什么优化方案？**

> **参考回答**：
> 1. **强制结构化输出**：使用 OpenAI 的 Structured Outputs 或 Instructor/Pydantic 结合函数调用强制校验输出。
> 2. **System Prompt 强化**：加入“仅以 JSON 格式输出，不要包含任何前言和后语”等严格指令。
> 3. **后处理（Post-processing）**：用代码或简单正则清理模型回复中多余的 markdown 或自然语言。
> 4. **Self-Correction**：如果解析报错，将错误信息通过 Exception 传回给 LLM，让其自行修正。

- **AI Coding 工具工作流中，你的提示词策略是怎么操作的？人工一般在哪个环节介入审核？**

> **参考回答**：在 AI Coding 中，提示词策略是“分步生成、提供完整上下文”。先让模型输出伪代码或架构设计，再输出核心模块，最后输出测试用例。人工介入通常在两个环节：1) 审核第一步的架构和技术选型是否合理；2) 在最终代码执行/提交前进行 Code Review。

- **上下文与冲突处理**

> **参考回答**：上下文管理直接决定了 Agent 的短期对话表现与多轮推理能力。本部分考察候选人如何应对 LLM 的上下文窗口限制，掌握基于 Token 的截断、摘要压缩等技术，并能设计策略处理用户意图冲突或指令矛盾，确保对话连贯性与系统稳定性。

- **短期记忆如何处理上下文爆炸的问题？**

> **参考回答**：
> 1. **基于 Token 截断**：仅保留最近 N 轮对话。
> 2. **摘要压缩**：当上下文长度超过阈值时，调用 LLM 对历史对话生成摘要（Summarization），用摘要替代原始长文本。
> 3. **系统状态分离**：将业务核心状态（如用户参数、订单信息）持久化到字典中，不再放在 Message History 里。

- **有对上下文长度进行管理吗？压缩算法是什么？具体怎么做？**

> **参考回答**：有。常用的压缩机制不是传统的“算法”，而是基于 LLM 的文本摘要。具体做法是：设置一个 Token 上限（如 4000），当历史消息超过时，保留最近 2-3 轮作为即时记忆，将之前的消息交由 LLM 总结成一段精简的 Context，再放入 `SystemMessage` 或上下文的最前面。

- **压缩时如何保证关键约束、任务目标、工具返回和历史结论不丢失？如何判断哪些上下文可以摘要，哪些必须原文保留？**

> **参考回答**：通过**分层记忆管理**：将“核心系统约束、当前任务目标”放在不可修改的 `System Prompt` 中；将工具返回的结果和历史结论提取出结构化的实体（如 Knowledge Graph 或 Key-Value 字典），存入长期记忆或状态板（Blackboard）中。普通的闲聊对话则可以安全地进行摘要。

- **哪些内容应该留在当前 Context Window，哪些应该摘要压缩，哪些应该写入长期记忆？**

> **参考回答**：
> - **当前 Context**：最近的 3-5 轮用户提问与系统回答、刚执行完的工具返回结果（Observation）。
> - **摘要压缩**：过往的闲聊、已经完成的子任务的详细推理过程（Thought 过程）。
> - **长期记忆**：用户的个人偏好（Profile）、长期的事实性知识、之前定下的关键结论。

- **如果用户和 AI 对话时生成的问题本身有冲突（如意图冲突、信息矛盾），系统应该怎么处理？**

> **参考回答**：在流程前加入**意图对齐层（Intent Alignment）**。当检测到指令矛盾时，暂停执行，Agent 主动向用户发起反问（Clarification Question），让用户确认最终意图。避免 Agent 基于矛盾信息盲目执行操作或产生死循环。

- **幻觉处理**

> **参考回答**：幻觉是大模型应用中最大的风险之一。本部分主要考察候选人是否具备完善的幻觉缓解与兜底策略，包括如何通过 Prompt 强约束、引用溯源（事实校验）、Self-consistency、后置规则校验等手段，来区分和处理“检索不到事实”与“模型未遵循事实”两种不同类型的幻觉。

- **工具调用失败或 LLM 幻觉，怎么办？**

> **参考回答**：在 Agent 框架中实现“异常捕获与重试循环”。如果工具调用失败，捕获异常堆栈，将报错信息作为新的 Observation 提供给 LLM，提示它“调用出错，请检查参数或换用其他工具”。如果它多次重复同样的错误，达到最大重试次数（max_retries）后强制退出。

- **有在模型幻觉这块做过什么处理？如何区分是检索证据不足导致的幻觉，还是模型生成阶段没有遵循证据？**

> **参考回答**：处理包括限制输出范围、要求引用出处等。区分方法：首先单独评估检索（RAG）阶段返回的 Top-K Chunk 是否包含了回答该问题所需的全部事实。如果 Chunk 中没有答案而模型却给出了肯定回答，则是“缺乏证据导致的幻觉”；如果 Chunk 中有答案但模型给出了相反或额外的虚假信息，则是“生成未遵循证据导致的幻觉”。

- **怎么减少链路里面 Agent 的幻觉？是否做过引用溯源、事实校验、Self-consistency 或人工确认？**

> **参考回答**：通过以下手段减少幻觉：1) **引用溯源**：强制模型输出引用的原文片段编号，前端将其高亮以备查。2) **事实校验（Fact-Checking）**：在关键环节引入第二个较小的验证模型，核对输出事实是否与上下文相符。3) **Self-consistency**：多次生成采样并取多数结果（主要用于推理问题）。4) 高风险操作强制引入人工确认（Human-in-the-loop）。



## 四、工具调用 (Tool Calling) 与 MCP

- **原理与实现**

> **参考回答**：工具调用（Tool Calling / Function Calling）是 Agent 能够与外部世界交互的核心。本部分考察候选人对大模型结构化输出与工具路由机制的底层理解，以及如何通过规范的 Schema 设计、清晰的工具描述与 Few-Shot 示例，实现高质量、低错误率的自主工具调用逻辑。

- **Agent 开发中，Tool Calling 的核心逻辑是什么？如何实现 Agent 自主调用工具？**

> **参考回答**：核心逻辑是大模型具备“理解工具参数并输出结构化指令”的能力（通过预训练或微调如 Function Calling API）。实现方法：将可用工具的名称、描述和参数 Schema 作为输入传给 LLM；LLM 识别到需要外部能力时，输出一个特定的指令（如 JSON 格式的函数名和参数）；宿主程序拦截该指令，在本地执行实际代码，然后将结果返回给 LLM。

- **用 Python 写一段简单的 Agent 工具调用 demo 逻辑。**

> **参考回答**：
> ```Python
> import json
> # 假设 llm.chat 返回带 tool_calls 的 response
> def get_weather(location):
>     return f"{location}晴天，25度"
> 
> tools_map = {"get_weather": get_weather}
> response = llm.chat(messages=[{"role": "user", "content": "北京天气如何"}], tools=[...])
> 
> if response.tool_calls:
>     for tool_call in response.tool_calls:
>         func_name = tool_call.function.name
>         args = json.loads(tool_call.function.arguments)
>         result = tools_map[func_name](**args)
>         # 将结果加入 messages 继续对话
> ```

- **模型是怎么和后端的接口 / 工具交互的？带参数复杂查询如何提取参数并调用接口？**

> **参考回答**：通过 Function Calling 机制。开发者将后端 API 的 Swagger/OpenAPI 规范转化为 JSON Schema 提供给模型。模型解析用户意图，将自然语言中的实体提取出来填入 Schema 对应的字段。后端收到模型生成的 JSON 后，使用 Pydantic 校验参数格式，无误后发起真实 HTTP 请求或函数调用。

- **接口字段是英文，模型不知道字段含义，映射关系是怎么实现的？**

> **参考回答**：在定义工具的 JSON Schema 时，为每个参数（Property）提供详细的自然语言 `description`。例如，即便字段名为 `dest_loc`，描述可以写为“The destination city or airport code, e.g., 'Beijing' or 'PEK'”。模型通过读取 `description` 实现自然语言到英文参数的映射。

- **怎么保证模型正确调用工具？如何判断用户问题应该走普通问答、RAG 检索还是工具调用？**

> **参考回答**：保证正确调用：1) 提供清晰且相互排斥的工具描述；2) 使用 Few-Shot 提供正确调用示例；3) 对入参做本地强校验。
> 判断路由：通常通过一个专门的 Router Agent 或是 LLM 内置的 Function Calling 能力。让 LLM 自己判断，如果用户问常识或总结，直接回复；需要实时数据，输出调用 Search Tool 的指令；如果是公司内部资料，输出 RAG Tool 指令。
>
### MCP (Model Context Protocol) 与 Skills

- **MCP 的 Schema 格式是什么样的？协议大概包含哪些内容？**

> **参考回答**：MCP（Model Context Protocol）是一个标准化的客户端-服务器协议。它主要包含：`Resources`（只读的上下文数据，以 URI 形式暴露）、`Prompts`（预定义的模板）和 `Tools`（可执行的函数）。通过一套基于 JSON-RPC 的通信标准，让大模型客户端（如 Cursor、Claude）能直接连接本地或远程的 MCP Server，获取其提供的工具和数据。

- **MCP 和 Function Calling 有什么区别和联系？MCP 的优势是什么？**

> **参考回答**：Function Calling 是 LLM 的底层能力，用于将文本转换为结构化函数参数。而 MCP 是一套**标准化协议**，它利用了 Function Calling，但进一步规范了工具如何被发现、如何传递上下文、如何认证。优势在于：**解耦与复用**。开发者只需编写一次 MCP Server，任何支持 MCP 的客户端都能直接使用，无需针对每个工具写死接入代码。

- **Skills 是什么？解决了什么问题？如何判断一个能力是否需要被封装成 Skills？**

> **参考回答**：Skills（技能）是 Agent 执行特定高级任务的封装模块，通常包含了调用特定 API 的逻辑、前置校验和后置处理。它解决了复杂业务流在 Agent 中重复编写的问题。如果一个能力需要固定的业务逻辑（如“查账单并生成报表”），且需要被多个不同的 Agent 重复调用，就适合封装成 Skill。

- **Skills 和 MCP 有什么区别？什么能力适合封装成 Skill，什么能力适合暴露成 MCP 工具？**

> **参考回答**：
> - MCP 工具通常是**原子化、通用性强、基础的 API**（如查数据库、获取 GitHub PR 列表）。
> - Skills 更偏向于**业务流程编排和场景化能力**（如“解决前端 React 报错并自动提交 PR”），一个 Skill 内部可能会调用多个 MCP 工具。

- **Skills 和 Workflow（如 n8n）有什么区别？为什么不用 Workflow，而用 Skills？**

> **参考回答**：Workflow（工作流）是静态的、基于规则的节点连接，路径是固定的。Skills 是被 Agent 调用的，Agent 可以根据上下文动态决定是否调用这个 Skill、按什么顺序调用，灵活性和自适应能力更强，能处理非标准化的自然语言请求。
>
### 编排、异常与容错

- **Skills 里的工具编排为什么会出现延迟放大问题？多个工具串行调用时，如何降低整体延迟？**

> **参考回答**：因为每调用一次工具，Agent 都会等待工具返回，再请求一次大模型（大模型的 TTFT 延迟较高）。串行调用多次会导致网络和生成延迟叠加。
> 降低延迟方案：1) 使用支持并行工具调用的模型（Parallel Function Calling）；2) 在本地将几个强关联的工具聚合成一个宏命令工具（Macro-tool），一次调用完成；3) 采用流式（Streaming）返回中间结果，优化用户体验。

- **开发 Agent 过程中，若出现工具调用失败（网络超时、报错等），你会怎么排查、重试和解决？**

> **参考回答**：
> 1. 代码层面加入本地重试机制（如 Tenacity 库），解决偶发的网络波动。
> 2. 将后端的报错（Exception）信息作为普通 Observation 传回 LLM，提示其“调用失败，错误详情是 XXX，请检查参数后重试”。
> 3. 设置最大调用次数，超过后终止并在日志系统（如 Datadog 或 LangSmith）中上报。

- **如果 Agent 在调用中陷入死循环，怎么检测和中断？**

> **参考回答**：在 Agent Loop 中记录两个状态：1) 迭代步数（Step Count），超过预设的 `max_steps` 强制抛出异常或返回当前结果；2) 历史行为哈希检测，如果发现 LLM 连续 2-3 轮输出完全相同的 Thought 和 Action 参数，判定为死循环并强制终止。

## 五、记忆机制 (Memory)

- **Agent 的记忆模块开发中，短期记忆和长期记忆如何区分和实现？为什么 Agent 需要记忆？**

> **参考回答**：
> - **短期记忆**：以会话消息列表（Message History）的形式实现，保存在当前上下文窗口中，用于维持当前对话连贯性。
> - **长期记忆**：将对话中提取出的用户偏好、重要事实存入外部数据库（如向量数据库、知识图谱或 Key-Value 库），以便跨会话（跨天、跨月）调用。
> - Agent 需要记忆才能进行持续的多轮复杂任务和个性化交互，而不是成为失忆的 stateless 调用。

- **长期记忆 + 短期记忆具体是怎么提取和存储的？存什么内容（原始语料还是标签）？**

> **参考回答**：
> 短期记忆直接存原始的对话流。长期记忆通常不存原始冗长语料，而是通过一个后台 LLM 任务进行“记忆提取（Memory Extraction）”：将关键信息提取成**结构化的实体、标签或摘要**。例如，用户提到“我喜欢吃辣”，就提取出 `{"user_preference": "spicy food"}` 存入关系型或向量库中。

- **历史对话的持久化存储怎么设计？上下文自动加载怎么做？**

> **参考回答**：持久化通常使用 Redis、PostgreSQL 或专门的记忆库（如 Mem0、Zep），以 `Session_ID` 或 `Thread_ID` 为键。自动加载时，系统接收到新消息，先拦截请求，从数据库中拉取对应 Session 的近期消息（短期）和相关的长记忆片段，合并组装到 LLM 的 Prompt 中再发起请求。

- **用户隐私、权限隔离和多端同步在历史对话存储中怎么处理？**

> **参考回答**：
> 1. 数据隔离：必须在数据库层加入 `User_ID` 和 `Tenant_ID` 字段，严格实行多租户和多用户隔离。
> 2. 隐私保护：对敏感信息（PII，如手机号、身份证）在存入记忆库和传递给 LLM 之前进行脱敏和哈希替换。
> 3. 同步：采用云端数据库集中存储，多端拉取时通过 Token 鉴权保证一致性。

- **如果线上要做多轮对话，记忆写入策略怎么定，才能避免“越聊越脏”？**

> **参考回答**：避免污染的关键是**定期清理和冲突消解**。写入策略：1) 对于事实更新，采用“覆盖（Upsert）”而非单纯追加；2) 引入记忆遗忘机制，设定衰减因子（Decay），很久没用且权重低的信息自动失效；3) 用 LLM 定期重构和整合散乱的记忆池。

- **怎么判断当前用户的提问需不需要去检索长期记忆？如何避免把过期或不相关的信息塞回上下文？**

> **参考回答**：在提问入口，通过意图分类器或轻量级模型判断查询是否依赖历史上下文（如出现代词“那个项目”、或者涉及个人偏好）。为了避免塞入过期信息，可以在检索长期记忆时引入时间戳过滤（Recency 因子），并结合向量相关性（Relevance）计算最终得分，只取高分的记忆片段。

## 六、代码智能体 (AI Coding / Code Agent)

### 代码 RAG 与理解

- **代码 RAG 中，如果用抽象语法树（AST）解析函数片段，原理是什么？怎么从文本到 AST？**

> **参考回答**：原理是将纯文本代码解析为表示其语法结构的树形数据结构，从而精确地提取出类定义、函数签名、注释和依赖关系，而不是盲目按字符切分。通过使用如 `Tree-sitter` 等解析器，可以将任意编程语言的文本转换成 AST 节点，然后遍历树结构将完整的函数块提取为独立 Chunk。

- **存储解析出来的代码片段和代码注释，数据库表应该怎么设计？**

> **参考回答**：表中应包含核心字段：`id`, `repo_name`, `file_path`, `start_line`, `end_line`, `code_type` (函数/类/全局), `snippet_text` (代码本身), `docstring` (注释或 AI 生成的摘要), 以及对应的 `embedding_vector`。这样既能支持语义检索，又能通过 `file_path` 和行号支持精确回溯。

- **在代码检索场景中，关键词、向量、符号、调用图检索分别解决什么问题？**

> **参考回答**：
> - 关键词（BM25）：精确定位变量名、函数名或特定的报错字符串。
> - 向量（Embedding）：通过自然语言语义搜索相关功能的代码（例如“怎么连数据库”找到相关工具类）。
> - 符号/调用图（Symbol/Call Graph）：用于精确查找“谁调用了这个函数”或“这个类继承自谁”，解决代码间的依赖和跳转逻辑，防止 LLM 改代码时破坏上下游依赖。
>
### 架构与源码解析

- **为什么要自己搞一个 Code Agent？自研 Code Agent 的难点在哪里？**

> **参考回答**：为了与公司内部私有代码库、内部 CI/CD 流程、特有的业务框架和权限体系深度集成，这是外部通用工具难以做到的。难点在于：1) 超大私有代码库的高效检索与理解；2) 复杂的本地构建和测试环境沙箱的维护；3) 防止 Agent 改乱代码导致的级联崩溃。

- **讲一下用户在终端发一个指令，到 Code Agent 完成所有任务的整个链路。**

> **参考回答**：
> 1. 解析指令：理解用户的开发需求。
> 2. 探索代码（Search/Grep/Read）：Agent 在终端中执行文件搜索，定位需要修改的文件。
> 3. 规划修改：Agent 阅读现有代码上下文，决定在何处插入或修改。
> 4. 执行编辑（Edit/Replace）：Agent 调用文件修改工具更新代码。
> 5. 验证测试（Terminal Execute）：Agent 运行 Linter、编译或单元测试。若报错，阅读日志并自我修正。
> 6. 结束任务：通过所有测试后返回完成提示，可能附带执行 `git commit`。

- **任务恢复 (Resume) 是什么意思？Harness 在 Code Agent 项目里面怎么体现？**

> **参考回答**：任务恢复指 Agent 能够在被中断后或错误失败后，保留之前的执行状态、上下文和文件修改历史，重新继续当前任务。Harness 是测试和运行支架，在 Code Agent 中它负责拉取评测代码库镜像、安装依赖、注入 Agent 输出的 Patch 代码并运行单元测试，从而验证修改是否通过了测试。

- **工具使用与评估**

> **参考回答**：在 AI Coding 领域，评价一个 Code Agent 的好坏不仅在于大模型本身，还在于工具链（如检索、Linter、沙箱）的成熟度。本部分考察候选人如何构建高质量的工具集，以及如何设计科学的 Benchmark（如借鉴 SWE-bench），通过真实 issue 和单测来量化评估 Agent 的代码修复与编写能力。

- **同一个模型在不同 Code Agent 中的表现为何不同？**

> **参考回答**：因为不同 Code Agent 提供了不同的系统提示、工具链和上下文拼接策略。比如 Cursor 提供了精准的 Linter 反馈和符号检索（Codebase indexing），而原生框架可能只提供了简单的文件读取，这极大影响了模型获取信息的质量和决策准确性。

- **AI Coding 占比多少？如何防止 AI Coding 工具误改代码或破坏已有架构？**

> **参考回答**：可以通过以下方式防止：
> 1. 限定作用域：Agent 的文件修改仅限当前分支，且需配合严格的 Lint 和单元测试。
> 2. 引入 Reviewer Agent 或人工 Review 机制。
> 3. 使用具有“精确替换”或“AST级别修改”能力的工具（如 StrReplace），而不是让 LLM 重写整个文件。
> 4. 在 Prompt 中强调必须遵循现有文件的代码规范和架构模式。

- **怎么设计 Code Agent 的 Benchmark（评测）？**

> **参考回答**：可以参考 SWE-bench。核心思路：从真实的 GitHub 仓库中收集真实 Issue 及对应的 PR（修复代码），形成测试集。让 Code Agent 根据 Issue 描述在代码库中进行自主修复，最后通过运行该 PR 原本带有的单元测试来评估 Agent 的修复通过率（Pass Rate）。

## 七、场景设计与 Agent 评测

- **场景设计题**

> **参考回答**：场景设计题旨在考察候选人从 0 到 1 构建垂直领域 Agent 的综合架构能力。要求候选人能清晰拆解复杂任务，合理规划 Agent 的角色、工作流（如 Map-Reduce 架构）、所需工具（Tool/MCP）以及记忆机制，最终产出一个具有实操性与鲁棒性的完整系统设计方案。

- **设计一个生成单元测试的 Agent。**

> **参考回答**：
> - 核心模块：代码分析器、测试用例生成器、执行沙箱。
> - 工作流：1) 用户输入源码文件，Agent 读取文件并解析出关键函数和边界条件；2) Agent 生成测试代码片段；3) Agent 将测试代码放入本地沙箱运行；4) 如果测试未覆盖某些分支或出现报错，Agent 读取 Coverage 或 Error Log 重新迭代修改测试代码；5) 最终输出稳定的单测代码。

- **设计一个文档总结 Agent。**

> **参考回答**：
> 针对长文档（超出上下文限制）：
> 1. 使用 Map-Reduce 架构：将长文档切分成多块（Chunk）。
> 2. Map 阶段：子 Agent 分别并行阅读每个 Chunk 并提取关键信息和摘要。
> 3. Reduce 阶段：主 Agent 将所有子摘要汇总，结合用户特定关注点（如“重点关注财务数据”），生成最终的连贯总结。

- **设计一个告警定位 / 日志分析 Agent（怎么关联报警和日志？怎么定位真正的根因）。**

> **参考回答**：
> 1. 触发机制：监控系统（如 Prometheus）触发告警 Webhook。
> 2. 收集上下文：Agent 自动调用工具提取告警时刻前后的业务日志、系统指标和链路追踪（Trace）。
> 3. 关联分析：使用 RAG 或知识图谱查询“历史类似告警”及 SOP 手册。
> 4. 根因推理：通过大模型分析日志中的 Error Stack，结合当前变更记录（如刚发了版），推断可能原因。
> 5. 输出：生成根因分析报告及临时止血方案建议给运维人员。
>
### Agent 评测体系

- **如何科学评测 Agent 系统效果？业务 Agent Evaluation 的流程是什么？**

> **参考回答**：
> 1. 构建 Golden Dataset（测试集）：收集真实用户的高频 query 及预期的标准路径/工具调用结果。
> 2. 维度拆解：评测不能只看最终答案，需分为：**轨迹准确率**（Trajectory Accuracy，是否调对了工具和参数）、**响应质量**（回答是否准确无幻觉）、**稳定性**（重复请求成功率）和**执行效率**。
> 3. 自动化评测：使用 LLM-as-a-Judge 对主观回答打分，使用精确匹配对工具调用参数和系统状态进行断言测试。

- **新版本对比旧版本，如何做实验证明“哪个模型更好”或“新版本效果提升”？**

> **参考回答**：
> 1. **离线评测（Regression Test）**：在新旧版本上跑一遍 Golden Dataset，对比成功率、准确率和工具冗余调用率等客观指标，确保没有严重退化。
> 2. **线上影子模式（Shadow Testing）**：将真实流量复制一份给新版本，不返回给用户，对比新老版本生成的差异。
> 3. **线上 A/B 测试**：灰度发布新版本，观察真实的业务指标（如用户的采纳率、任务完成时长、用户的显式点赞踩反馈），以统计显著性结论证明提升。
