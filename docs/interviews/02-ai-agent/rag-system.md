# 检索增强生成(RAG)真题

## 一、检索增强生成 (RAG) & 向量库

- **整体设计与架构**

> **参考回答**：这一部分主要考察候选人对 RAG 系统全链路（数据处理、召回、生成）的理解，以及在实际 Agent 架构中如何将 RAG 作为工具或核心组件进行设计，同时评估对系统延迟、可用性与数据流转的全局把控能力。

- **RAG 在 Agent 开发中是如何应用的？到底用来解决什么问题？**

> **参考回答**：RAG（Retrieval-Augmented Generation）通过从外部知识库检索相关信息，作为上下文提供给大语言模型，用来解决 LLM 的**幻觉问题**和**知识更新滞后**。在 Agent 开发中，RAG 常被封装为一种特定的 `Tool`（例如“内部文档查询库”），Agent 在遇到缺少垂直领域知识时主动调用。

- **RAG 这块你们是怎么设计的？系统架构是怎样的？数据是怎么流转的？**

> **参考回答**：架构包括三个主要阶段：
> 1. **离线处理（Indexing）**：解析文档 -> 文本切分（Chunking） -> Embedding 向量化 -> 存入向量数据库。
> 2. **在线检索（Retrieval）**：用户提问 -> 提问重写与扩展 -> 转化为 Embedding -> 在向量库中做 ANN（近似最近邻）搜索 -> 多路召回（向量+全文检索）与重排（Rerank）。
> 3. **生成（Generation）**：将高分 Chunk 与原问题组合进 Prompt，交由 LLM 生成最终答案，并附带引用来源。

- **RAG 中单轮推理和多轮推理的区别是什么？多轮推理中，如何避免 Agent 一直追加检索、陷入无效循环？**

> **参考回答**：
> - 单轮推理：用户提问 -> 一次检索 -> 一次生成。
> - 多轮推理（Agentic RAG / Iterative RAG）：Agent 发现检索到的信息不足，主动重写查询进行第二次检索，甚至拆分问题多次检索后综合。
> - 避免死循环：设置最大思考/检索步数（max_steps）；在 Prompt 中明确“若多次未搜到直接回复不知道”；并在循环条件中检测历史工具调用的重复性。

- **了解过 Dynamic RAG 吗？GraphRAG 和普通 RAG 的区别是什么？优势和劣势是什么？**

> **参考回答**：
> - **Dynamic RAG**：指系统能根据问题类型动态决定是否走 RAG，以及动态调整检索参数（Top-K、切分大小等）。
> - **GraphRAG**：普通 RAG 是把文本直接向量化检索（基于语义相似度），缺乏对全局信息的结构化理解。GraphRAG 先利用大模型抽取实体和关系构建知识图谱，再通过图算法（如社区发现）和向量检索结合回答。
> - 优势：非常擅长回答需要跨文档综合的全局性、连结性问题。
> - 劣势：离线知识提取成本极高（消耗大量 Token）；图更新复杂；延时较长。

- **讲讲 GraphRAG 里的社区发现算法是如何划分的。**

> **参考回答**：GraphRAG 使用层次化社区发现算法（如 Leiden 算法），将知识图谱中紧密连接的实体划分成一个个“社区”。接着，为每个社区生成摘要（Community Summaries）。检索时，不是直接查具体的 Chunk，而是去这些社区摘要里查，能够自上而下地把握全局视角。

- **文档切分与处理 (Chunking)**

> **参考回答**：文档切分（Chunking）是 RAG 系统的核心基础。本部分主要考察候选人对不同格式文档（如 PDF、Markdown、Word）的解析能力，对切分策略（硬切分、软切分、语义切分）的理解，以及如何保留文档层级与元数据（Metadata）以提高后续检索的准确性。

- **文档是怎么切分的？切分策略是怎样的？**

> **参考回答**：常见切分策略有：1) **按字符/Token 数（硬切分）**；2) **按标点符号/段落（软切分）**；3) **语法切分**（例如利用 Markdown 标题结构、代码的 AST）；4) **语义切分**（计算相邻句子的向量相似度，差距大时切分）。一般还会设置 overlap（重叠区）防止割裂上下文。

- **固定长度切分截断语句会有什么问题（硬切分在实际场景里有哪些典型弊端）？**

> **参考回答**：硬切分容易导致指代不明（“他”在上一个 Chunk 中），或者把关键事实的上下文（如前提条件）切断，从而使得单看该 Chunk 语义不完整，检索不到或者给 LLM 带来误导。

- **语义切片的优缺点是什么？如何保留文档标题、段落、表格、来源和引用路径？**

> **参考回答**：
> - 优点：能保证一个 Chunk 内部的语义完整，检索更精准。
> - 缺点：计算成本高，边界判断依赖阈值。
> - 保留方法（元数据管理 Metadata）：在解析时记录层级结构，将当前段落的父标题、文件名、页码作为 Metadata 注入 Chunk。检索时可作为过滤条件（Pre-filtering），传给 LLM 时可作为引用的出处。

- **如果要切分的文档是 Markdown 怎么做？如果是 PDF 怎么做？**

> **参考回答**：
> - Markdown：使用特定的拆分器（如 LangChain 的 MarkdownHeaderTextSplitter），按大标题（#、##）进行递归切分，保留层级 Metadata。
> - PDF：通常先做版面分析（Layout Analysis），区分标题、正文、表格、图片。用 OCR 提取文本，表格可以用模型转化为 HTML 或 Markdown 格式，再按自然段切分。

- **如果预输入不是 Markdown，应该怎么做？如果不同文档类别的上下文格式不一样，需要怎么处理？**

> **参考回答**：不同格式需要不同的 Parser，比如用 Unstructured、Docling 等工具先把 Word、PPT、PDF 统一转换成易于处理的内部格式（通常类似 Markdown 结构），再统一做清洗和提取。

- **OCR 识别的准确率是什么情况？识别过程中有遇到什么问题吗？**

> **参考回答**：对于纯文本 OCR 准确率很高，但对于多栏排版、手写体、复杂数学公式、跨页表格等极容易出错。常见问题包括段落顺序混乱和错别字，解决方案是采用深度学习版面分析模型（如 PP-Structure）辅助，并结合 LLM 做后处理纠错。
>
### 向量库与 Embedding

- **Embedding 模型是怎么选的？为什么选这个模型？选错会出现什么现象？**

> **参考回答**：选型考虑：语言支持（多语种还是中文）、维度大小、支持的最大上下文长度以及在评测榜单（如 MTEB/C-MTEB）上的表现。例如选 BGE 系列或 OpenAI 的 `text-embedding-3-small`。选错模型会导致相关语义匹配不上，出现明明有关联的文档却召回分数极低（“找错人”）的情况。

- **讲一下大模型将自然语言向量化的过程。**

> **参考回答**：自然语言首先被 Tokenizer 切分成一组 Token ID；这组 ID 输入给模型（通常是基于 Transformer 的编码器，如 BERT 或大模型的 Encoder 结构）；模型为每个 Token 产生高维隐层表示，最后通过池化层（Pooling，通常是平均池化或取 `[CLS]` token）压缩成一个固定维度（如 768 或 1536 维）的向量。

- **存储选型为什么用 MongoDB / 向量数据库（如 FAISS、Chroma、pgvector）？**

> **参考回答**：
> - FAISS：适合离线或无需频繁更新的纯向量 ANN 计算。
> - Chroma：轻量易用，适合本地开发原型。
> - pgvector (PostgreSQL)：适合同时需要强大的关系型过滤（按用户、权限）和向量检索的企业场景。
> - MongoDB / ES：支持复杂的文档结构存储，适合存原始文档，且新版本也集成了向量索引。

- **向量数据库比较向量相似度一般有哪些算法支撑？底层用的什么数据库结构？**

> **参考回答**：算法包括余弦相似度（Cosine）、内积（IP）、欧氏距离（L2）。底层通常不采用全量线性扫描（耗时太长），而是用近似最近邻（ANN）算法，例如 HNSW（分层可导航小世界图，基于图结构）、IVF（倒排索引）、PQ（乘积量化）。

- **RAG 的信息一般怎么存，为什么不能只扔进向量库？文本原数据里存的是什么？**

> **参考回答**：向量库为了检索效率，通常只存 Embedding 和极少量的 Metadata。如果 Chunk 很大，向量库体积会暴胀。一般采用“分层存储”：向量库存 Embedding + ID；关系型或文档型数据库（如 MongoDB/MySQL）存 ID 对应的原始文本、文档来源、权限信息、图片链接等原数据。检索到 ID 后再去数据库取文本。
>
### 检索、召回与排序

- **检索这一块是怎么设计的？为什么要用混合检索（Hybrid Retrieval）？**

> **参考回答**：混合检索是将**稀疏检索**（如基于关键字频率的 BM25）和**密集检索**（基于 Embedding 语义的向量搜索）结合起来。向量检索擅长同义词、语义理解，但对于人名、产品序列号等专有名词极其糟糕。BM25 擅长精确匹配。两者结合可兼得精准与泛化。

- **多路召回具体是什么？一共几路召回？最后怎么 merge 这些召回结果？**

> **参考回答**：多路召回是从不同维度（语义相似度路、BM25 全文检索路、知识图谱关系路等）同时取回 Top-K 结果。Merge 通常采用交叉排序方法，如 RRF（Reciprocal Rank Fusion 倒数排名融合）将多路的名次打分相加，或者输入给 Reranker 模型做统一精排。

- **说一下 RRF 融合算法。RRF 的权重怎么设计？**

> **参考回答**：RRF 公式为 `Score = 1 / (k + Rank)`，对于每个检索路，将文档所处的名次代入。k 通常取 60 作为平滑因子。如果需要给某一路更高的权重，可以在 RRF 得分外再乘以一个自定义的权重系数，但标准 RRF 是无参数的。

- **补充检索是如何评估数据质量并触发的？怎么保证二次检索能搜到之前没搜到的内容？**

> **参考回答**：补充检索可以由 LLM 来判断（在 Prompt 里加入“判断当前信息是否足以回答”）；或者如果第一次检索召回的分数都很低，自动触发。保证搜到的方法是**查询重写**（Query Rewriting/Expansion），比如把原问题拆分子问题、提取核心关键词、生成假设性答案（HyDE）再拿着新 Query 去搜。

- **向量检索、BM25 和 Rerank 三者在召回链路中分别解决什么问题？双塔召回和 Cross-Encoder 重排有什么区别？**

> **参考回答**：
> - 向量+BM25：解决“粗排”问题，要求在大海捞针时速度快、不漏召回（高召回率）。
> - Rerank：解决“精排”问题，给出的几十个召回结果打分并优中选优（高准确率）。
> - 双塔召回：Query 和 Doc 分别过模型生成向量，计算点积，速度快，适合粗排。
> - Cross-Encoder：将 Query 和 Doc 拼在一起 `[CLS] Query [SEP] Doc` 一起过 Transformer，模型能充分理解两者的交互关系，精度极高但计算极慢，适合重排。

- **排序（Rerank）是怎么做的？粗排和精排的区别是什么？**

> **参考回答**：粗排是从百万库里筛出百级别，要求速度快（向量搜索/BM25）；精排是用重排模型（如 BGE-Reranker、Cohere Rerank）对这几百个文档与用户的查询重新进行深度的 Cross-Attention 打分，并取 Top-K（例如 5 个）作为最终上下文传给生成模型。

- **怎么避免大模型检索到网上被 AI 批量生成的虚假垃圾数据（反投毒）？**

> **参考回答**：
> 1. 数据源过滤：白名单机制，只从高质量垂直网站、公司内部文档、权威数据库索引。
> 2. 预处理清洗：计算文本困惑度或信息熵，清洗掉低质量生成文本。
> 3. 后处理比对：用多个信源做交叉验证。

- **RAG 里 Hard Negative 怎么构造？为什么比随机负样本更有价值？**

> **参考回答**：Hard Negative（困难负样本）是指那些“字面上高度相似或包含大量原句关键词，但实际上回答不了该问题”的段落。可以用 BM25 搜出分数高但不包含正确答案的段落作为 Hard Negative。它比随机负样本有价值是因为它能逼迫重排模型或 Embedding 模型学会关注深层语义和细微逻辑差异，而不只是关键词匹配。

- **诊断与评估**

> **参考回答**：诊断与评估是保障 RAG 系统效果的关键环节。本部分主要考察候选人如何建立 RAG 的评测体系（如使用 Ragas 等框架），如何分别量化评估检索效果（召回率、MRR）与生成效果（相关性、忠实度），以及在系统表现不佳时如何定位并优化问题。

- **RAG 每次召回的效率怎么样？召回耗时多少？**

> **参考回答**：粗排（向量检索/BM25）通常在几十毫秒到百毫秒级；精排（Rerank，依赖大模型或 Cross-Encoder）可能在几百毫秒；整体检索阶段的延时一般能控制在 500ms - 1s 内，具体取决于 Chunk 数量和 Rerank 的 Top-K 大小。

- **RAG 召回率是多少？用什么数据集评估召回效果？**

> **参考回答**：因领域而异。评估数据集通常会通过业务语料由大模型自动生成 QA 对（合成评估集），包括（Query, Ground_Truth_Doc_ID）。可用评测框架（如 Ragas、TruLens）计算指标。

- **RAG 召回不准时怎么优化排查？如何判断是检索出问题，还是生成出问题？**

> **参考回答**：分开评测：
> 1. 看 Retrieval Metrics（如 hit_rate, MRR）：如果检索出的 Top-5 Chunk 根本没有包含正确答案的片段，说明是检索粗排或精排出了问题（需优化切分、重写 Query、换 Embedding 模型）。
> 2. 看 Generation Metrics（如 faithfulness, answer_relevance）：如果检索出来的 Chunk 明明包含了答案，但 LLM 却没答对，说明是生成出问题（幻觉、被其他无关 Chunk 干扰、Prompt 约束不够）。

- **检索结果和最终答案之间如何做引用溯源？如果知识库没有答案，模型如何避免胡编？**

> **参考回答**：
> - 引用溯源：要求模型在回答时带上特定格式的标记，如 `[1][2]`，对应输入 Prompt 中 Chunk 的编号。通过映射还原到文档名和链接。
> - 避免胡编：在 System Prompt 强调“如果提供的上下文中没有相关信息，请明确回答不知道，禁止使用自身的预训练知识进行猜测。”并在生成后校验模型输出的答案是否被上下文所“蕴含”（Faithfulness 检验）。
