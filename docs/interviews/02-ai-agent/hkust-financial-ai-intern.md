## 一、 岗位 A：后端与 Agent 编排方向

### 1. Agent 编排与 Tool Use
- **问题 1**：我们的业务是面向真实金融场景，做 LLM/Agent 驱动的 AI 系统落地。其中需要接入大量的 ETF 行情和投资组合数据。如果让你把这些复杂的金融数据层包成 Agent 可调用的工具（Tool Use），**你怎么设计 Function Calling 的接口和参数，以保证大模型能准确调用且不出错？**
  > **回答思路**：
  > 1. **明确边界与原子化**：工具设计必须功能单一（例如分为 `get_etf_price` 和 `get_portfolio_holdings`），避免一个工具参数过多导致模型理解困难。
  > 2. **强类型的 JSON Schema**：在定义 Tool 的 Schema 时，使用强类型约束（如 Enum 限制只能输入特定的 ETF 代码格式），并为每个参数提供极其详尽的 `description`。
  > 3. **容错与兜底机制**：大模型可能会传错参数或漏传参数。后端工具函数内部必须做好入参校验，如果错误，不要直接抛出代码异常（Traceback），而是返回一段自然语言的错误提示（如“ETF代码格式错误，请使用如 510300.SH 的格式”），让大模型根据提示进行**自我纠错（Self-Correction）**和重试。

- **问题 2**：我们的业务是面向金融投研和交易辅助，做多 Agent 协同的系统。我们需要用 LangGraph 进行 Agent 编排。**你是否了解 LangGraph 的底层原理？在处理金融数据时，如果某一步 Agent 节点调用外部 API 超时或失败，你怎么在图结构（Graph）中设计重试和兜底机制？**
  > **回答思路**：
  > 1. **LangGraph 原理**：LangGraph 的核心是将大模型的思考和执行过程抽象为状态机（State Machine）和有向图（DAG）。它的优势在于**状态持久化（Checkpointing）**和**循环控制（Cycles）**，比原生的 LangChain Agent 更具可控性。
  > 2. **重试机制设计**：在定义 Node（节点）和 Edge（边）时，可以利用 LangGraph 的条件边（Conditional Edges）。当外部 API 节点返回失败状态时，更新 State 中的 `error_count`，并通过条件边路由回该节点进行重试。
  > 3. **兜底机制**：如果 `error_count` 达到阈值，条件边将其路由到一个专属的“兜底节点（Fallback Node）”，该节点不调用外部 API，而是直接读取本地缓存数据或生成带有“数据获取失败”免责声明的降级回答，确保整个系统不会崩溃卡死。

- **问题 3**：我们的业务是面向金融数据服务化，需要将 ETF 行情等数据提供给大模型分析。金融数据对准确性要求极高。**你怎么解决大模型在处理这些结构化金融数据时容易产生的“幻觉”问题？你是否了解 RAG 在结构化数据（如 SQL/数据库）上的应用？**
  > **回答思路**：
  > 1. **Text-to-SQL / Text-to-API**：不让大模型直接“背诵”金融数据，而是让它生成 SQL 或调用 API 获取确定的结构化数据。
  > 2. **数据与解释分离**：在 Agent 工作流中，将“数据获取”和“数据解释”解耦。大模型只负责总结和提炼，最终交付给前端的报告中，必须**附带原始的结构化数据表**作为引用依据，让人工可以随时交叉校验。
  > 3. **引入复核 Agent（Reviewer）**：在生成最终结论前，增加一个专门负责挑错的 Agent 节点，比对生成的结论与原始数据是否存在事实冲突。

### 2. 后端骨架与工程化
- **问题 4**：我们的业务是面向金融机构交付企业级的 AI 系统，后端骨架需要极其稳定，涉及 API 契约、鉴权和数据模型。**你熟悉 FastAPI / Spring Boot / NestJS 中的哪一种？如果前端（或 iOS 端）需要实时展示 Agent 的思考过程和流式输出（Streaming），你会怎么设计后端的 API 契约和通信协议？**
  > **回答思路**：
  > 1. **框架选择**：以 FastAPI 为例，它原生支持异步（Asyncio），非常适合处理大模型 API 这种高 IO 延迟的任务。
  > 2. **通信协议**：对于流式输出，首选 **Server-Sent Events (SSE)** 或 WebSocket。SSE 更轻量，适合单向的流式文本推送。
  > 3. **API 契约设计**：返回的数据块（Chunk）需要结构化。例如，不仅要返回文本，还要返回当前 Agent 的状态（如 `{"status": "tool_calling", "tool_name": "get_etf", "content": ""}` 和 `{"status": "generating", "content": "根据数据..."}`），以便前端能渲染出“Agent 正在查询 ETF 数据...”的动态 UI。

- **问题 5**：我们的业务是面向高频迭代的 AI 系统研发，团队是交付制且过程必须留痕。**你有 Docker、CI/CD 或云部署的经验吗？你怎么解决包含多个 Agent 节点、依赖多种外部工具的复杂 AI 系统的本地测试和云端自动化部署问题？**
  > **回答思路**：
  > 1. **环境一致性**：使用 Docker 容器化，将 FastAPI 后端、LangGraph 依赖和环境变量打包，编写 `Dockerfile` 和 `docker-compose.yml`，确保本地和云端环境一致。
  > 2. **CI/CD 流程**：使用 GitHub Actions 等工具。当代码 Push 时，自动运行单元测试（尤其是对 Tool 函数的 Mock 测试，避免每次测试都消耗真实的 LLM Token），测试通过后自动构建镜像并推送到云端。
  > 3. **密钥与配置管理**：大模型 API Key 和金融数据源的 Token 绝不能硬编码，必须通过环境变量（.env）注入，并在云端使用 Secret Manager 进行管理。

## 三、 开放式场景与 Vibe Coding

- **问题 9**：我们的业务是面向高效交付的 AI 工程研发，团队非常看重 vibe coding，也就是用 AI 工具（如 Cursor / Claude Code）高效产出。**你平时是怎么使用 Cursor 的？如果遇到一个你从未接触过的开源 Agent 框架，你怎么利用 AI 工具快速跑通并讲清楚它的原理？**
  > **回答思路**：
  > 1. **Cursor 使用习惯**：强调自己不仅把 Cursor 当作聊天框，而是深度融入工作流。比如使用 `Cmd+K` 进行内联代码生成与重构，使用 `@Files` 或 `@Docs` 引入整个项目的上下文，利用 Cursor 快速编写单元测试和排查报错。
  > 2. **快速学习开源框架**：
  >    - 第一步：将开源框架的 GitHub 仓库 Clone 到本地，用 Cursor 打开。
  >    - 第二步：使用 `@Codebase` 提问：“这个框架的核心执行入口在哪里？它的状态管理是怎么实现的？”让 AI 帮我梳理架构。
  >    - 第三步：让 Cursor 根据框架的文档或源码，帮我写一个最简单的 `Hello World` 级别的 MVP 代码。
  >    - 第四步：运行报错时，直接把 Error Traceback 喂给 Cursor 修复，直到跑通。最后结合源码和 AI 的解释，总结出框架的底层原理文档。

- 你是否用过小龙虾OpenClaw？
  > **回答：** 我没有在生产项目里深度用过 OpenClaw，但我了解它大致是一个偏个人 AI 助手 / Agent OS 形态的开源框架，核心不是单轮 Chatbot，而是把模型、工具、记忆、技能和多端入口组织成一个可持续运行的 Agent 系统。
  >
  > 如果面试前或入职后需要快速上手，我会按三个层次拆：第一，先本地 Docker 跑通最小 Demo，看它的 Gateway、会话路由、Skill/Tool 调用和权限边界；第二，看它如何管理多 Agent、多模型和工具执行，重点关注状态保存、错误重试、沙箱隔离和审计；第三，结合金融场景做一个小 POC，比如让 Agent 调用行情查询工具、读取本地 ETF 数据、输出结构化分析报告。
  >
  > 我觉得这个问题的关键不是背框架 API，而是能不能快速判断一个 Agent 框架的架构边界：它的控制平面在哪里，工具是怎么注册和调用的，状态和记忆放在哪里，权限和安全怎么做，以及能不能把它改造成金融机构可控、可审计、可私有化部署的系统。

- 你会怎么处理高频数据（Level 2数据）？
  > **回答：** 我会先说明一点：我之前项目里更多处理的是日频、分钟级或行情快照数据，还没有完整做过生产级 Level 2 高频链路。但从工程设计上，我会把 Level 2 数据当成一个高吞吐、强时序、强清洗和强存储优化的问题，而不是直接丢给大模型。
  >
  > 第一层是**数据接入和标准化**。Level 2 数据包括逐笔成交、逐笔委托、盘口档位、买卖队列等，频率高、噪声多、字段口径也可能不同。接入后需要先统一 schema，比如 `symbol`、`exchange`、`event_time`、`receive_time`、`price`、`volume`、`bid/ask levels`，并处理乱序、重复、缺失、停牌、集合竞价和异常价格等问题。
  >
  > 第二层是**存储和计算分层**。原始 Level 2 数据不适合直接进普通 MySQL 做高频查询，我会倾向用 Kafka / Redpanda 做流式缓冲，用 ClickHouse、DolphinDB、QuestDB、kdb+ 或 Parquet 分区文件做时序/列式存储。分区一般按交易日、市场、标的切分，压缩存储原始数据，同时派生出 1 秒、1 分钟等聚合表，供策略回测、监控和 Agent 查询使用。
  >
  > 第三层是**特征加工和服务化**。真正给策略或 Agent 用的，不应该是全量逐笔明细，而是经过本地程序计算后的结构化特征，比如订单簿不平衡、买卖价差、成交强度、主动买卖比例、短周期波动率、盘口撤单率等。后端可以把这些封装成 API 或 Tool，例如 `get_orderbook_features(symbol, window)`，让 Agent 调用确定性工具拿结果，再负责解释原因和生成报告。
  >
  > 第四层是**性能与可靠性**。高频数据要注意延迟、吞吐和数据一致性，需要做批量写入、异步消费、背压控制、幂等去重、监控告警和数据质量校验。金融场景下还要保留原始数据和处理日志，方便复盘和审计。我的原则是：计算和校验尽量本地确定性完成，LLM 不直接处理海量 tick，而是在聚合特征和异常事件层做解释与辅助分析。



- **问题 10**：团队要求“过程和成果懂得可视化呈现，过程必须留痕”。**在你的日常开发中，你是如何记录你的思考过程、架构设计和踩坑记录的？**
  > **回答思路**：
  > 1. **文档沉淀**：习惯使用 Markdown、Notion 或飞书文档记录。在动手写代码前，先写简单的技术方案设计（Tech Spec）或 API 契约。
  > 2. **可视化表达**：遇到复杂的 Agent 状态机或系统架构，习惯用 Mermaid.js、Draw.io 或 Figma 画出流程图、时序图，让非技术人员也能看懂。
  > 3. **留痕交付**：在提交 PR 时，不仅提交代码，还会附带运行成功的截图、Demo 录屏（GIF）以及关键的测试用例日志，做到“所见即所得”的交付。

#### 2. 本岗位自我介绍版本

面试官您好，我叫张茂源，本科就读于南京理工大学金融学与计算机科学双学位，目前已被电子科技大学金融专硕录取。我的背景和这个 AI 系统研发实习岗位比较匹配：一方面我理解金融数据和投研场景，另一方面也有 Python 后端、数据库和 LangGraph Agent 项目的实际开发经验。

首先，在金融数据和后端工程方面，我曾在证券研究所量化方向实习，参与过转债多因子自动化分析系统的建设。这个项目不是单纯写脚本跑数据，而是把因子读取、数据清洗、数据库落库、图表展示、Excel 导出和日报生成串成一个可用系统。我在过程中使用过 Python、Flask、MySQL、Pandas、Plotly 等工具，也参与过需求拆解和接口/页面设计，所以对“把金融数据服务化、产品化交付给研究员使用”有比较直接的理解。

其次，我自己也做过比较完整的金融 AI Agent 项目。比如行业 ETF 成分股异动监控系统里，我用 akshare 获取 ETF、成分股和行情数据，用 Pandas 做滚动 Z-score、量比、超额收益等特征计算，并用 Parquet 和 SQLite 做行情快照、去重和 checkpoint。Agent 层面，我用 LangGraph 编排 ExplainAgent 和 DebateReviewAgent，让本地规则负责确定性计算和告警分级，让 LLM 负责异动解释和反方复核，最后输出结构化日报和报警结果。这个过程让我对 Tool Use、状态传递、失败降级、结构化输出和金融场景下的幻觉控制都有了实际体感。

第三，我也做过多 Agent 量化交易与投资决策系统，用 LangGraph 搭建基本面、技术面、情绪面、辩论、风控和执行等多个 Agent 节点，并通过条件边实现风控通过或拒单的分支逻辑。这个项目让我更关注 Agent 系统的工程边界：哪些计算必须交给本地程序，哪些分析适合交给 LLM，如何通过 JSON 结构化输出、风控硬规则和 Reviewer 节点保证结果可控。

最后，我平时也比较习惯用 Cursor、Claude 等 AI 工具辅助开发，会把项目过程整理成 Markdown 文档、流程图、Demo 截图和复盘记录。贵岗位提到的金融数据源接入、API 契约、Agent 编排、Swagger 文档和交付留痕，和我过去的经历和兴趣都很契合。我希望有机会参与真实金融机构场景下的 AI 系统研发，把自己在金融数据处理、后端开发和 Agent 工作流上的经验，转化为稳定、可演示、可交付的系统能力。谢谢。
