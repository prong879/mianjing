### 2. 岗位理解
- 你怎么理解「Vertical AI Agent」？
  > **回答：** 垂直 AI Agent 是针对特定行业（如金融、医疗、法律）深度定制的智能体。它不仅具备大模型的通用推理能力，更关键的是融入了该领域的**私有知识库（Domain Knowledge）**、**专属工具链（Domain Tools）**和**符合行业标准的业务工作流（SOP）**。它不追求解决所有问题，而是追求在特定垂直场景下的高准确率和高可靠性。
- 金融场景为什么适合做垂直 AI Agent？
  > **回答：** 金融场景数据量庞大且高度碎片化（研报、财报、新闻、异动数据），从业者每天有大量时间耗费在信息搜集和处理上。同时，金融计算逻辑明确（如计算财务指标），而大模型恰好擅长文本处理和逻辑规划。让 Agent 调用量化计算工具并结合 LLM 的阅读理解能力，能极大地提升金融从业者的效率。此外，金融客户具有较强的付费意愿，商业化落地更容易。
- 你觉得金融 Agent 和通用 Chatbot 最大的区别是什么？
  > **回答：** 最大的区别在于**执行能力（Action）**和**准确性要求**。Chatbot 主要是一个知识问答系统，容错率较高，可以聊天；而金融 Agent 是一个“行动派”，它可以调用外部 API 拉取实时行情、查询数据库、执行回测甚至下发交易指令，并且它受到严格的合规边界和风控规则约束，不能有任何“幻觉”。
- 你觉得金融 Agent 最难的是模型能力、数据质量、工具调用、合规，还是业务理解？
  > **回答：** 我认为是**业务理解与数据质量（RAG/Tools的结合）的交叉点**。模型能力现在各家大同小异，单纯写代码调用工具不难。难的是：怎样把投研分析师脑子里模糊的分析框架，拆解成 Agent 可以稳定执行的 DAG 工作流？同时，金融数据往往存在口径不一、缺失或格式混乱的问题，如果喂给大模型的数据是脏的（Garbage in），大模型的输出必定是错的（Garbage out）。因此，懂业务逻辑的数据工程是最难也是最核心的。
- 你觉得一个金融 Agent 的核心价值应该如何衡量？
  > **回答：** 核心价值在于能否**可量化地降本增效**或**带来增量收益**。对内部效率工具，衡量指标是：能否把原本需要 1 小时的研报资料整理压缩到 3 分钟？能否把初级分析师常犯的错漏率降低 50%？对外部客户产品，衡量指标是：用户留存率、API 调用频次以及它在投资决策辅助上提供的一致性是否足够高。
- 你怎么看 Agent 在投资研究、风控、交易辅助、财富管理中的应用？
  > **回答：** 
  > - **投资研究：** 最容易落地，如财报自动解读、异动监控、会议纪要提取，可极大释放分析师生产力。
  > - **风控：** 适合做舆情监控、违约风险排查，通过多维度信息交叉验证提前预警。
  > - **交易辅助：** 适合做量化因子的自动生成与回测，但实盘操作需极度谨慎，必须加入 Human-in-the-loop。
  > - **财富管理：** 偏向 C 端或客户经理助手，通过自然语言生成个性化资产配置建议报告，潜力巨大。
- 你觉得金融 Agent 可以替代分析师吗？
  > **回答：** 短期至中期内**不能完全替代**，而是赋能。金融 Agent 擅长执行 SOP 明确的信息搬运、初级数据清洗和总结工作，能替代初级分析师的“脏活累活”。但金融市场充满非线性博弈、政策突变和未被数据量化的情绪，这些“定性”判断、创新视角的提出以及最终担责，仍然需要资深分析师来完成。Agent 就像是给分析师配了一台“外骨骼机甲”。
- 你觉得金融 Agent 最应该避免什么风险？
  > **回答：** 最应该避免的是**幻觉导致的误导性投资建议（合规与法律风险）**。在金融场景，提供错误的财务数据或编造不存在的新闻，可能导致不可挽回的亏损。因此系统必须在 Prompt 层面加上严格的免责声明约束，在架构上必须引入“反方辩论”或“事实校验”节点，做到没有数据依据绝不瞎编。
- 你对新加坡金融科技应用、资管和银行场景了解多少？
  > **回答：** （按实际情况作答，例如：）新加坡是亚洲的财富管理和 Fintech 中心，拥有大量家族办公室、对冲基金和成熟的银行业。由于监管环境严格且规范（如 MAS 的规定），当地机构对数据隐私安全、私有化部署以及 AI 决策的可解释性要求极高。因此在新加坡推广金融 Agent，不能仅仅看技术，还需要把数据隔离、GDPR/PDPA 合规以及审计追踪（Audit Trail）做到极致。
- 如果入职后让你先做研究调研，你会怎么开展？
  > **回答：** 首先，我会**明确调研的业务目标和产出物**（是调研竞品、复现论文，还是探索某个框架的可用性）。其次，分步骤进行：
  > 1. **文献与开源生态扫描**：阅读最新的 Agent 论文（如 Reflexion, AutoGen）和 GitHub 热榜，梳理当前主流方案。
  > 2. **竞品体验与拆解**：深度使用市面上的 Agent 平台（如 Coze, Dify, Cursor），逆向推导他们的工作流和 Prompt 设计。
  > 3. **Demo 复现与 POC**：选定 1-2 个框架（如 LangGraph），结合一个小的金融测试用例（如财报提取）写个 POC 验证可行性与坑点。
  > 4. **输出报告**：从技术可行性、开发成本、业务契合度输出结构化文档。

## 二、简历项目深挖

### 1. 多 Agent 行业 ETF 成分股异动智能监控系统
- 说一下你做的多 Agent 行业 ETF 成分股异动智能监控系统。
  > **回答：** 这是一个基于 Python、本地量化计算和 LLM 双 Agent 架构构建的系统。它针对 50 只有代表性的行业 ETF 成分股，首先在本地计算滚动 Z-score、量比和超额收益等特征，并通过孤立森林和加权规则进行初筛。对于异常得分超过中高风险阈值的股票，系统会利用 LangGraph 编排工作流，先由 ExplainAgent 按 ETF 维度进行逻辑归因解释，再由 DebateReviewAgent 作为反方进行复核，最终输出结构化的 Markdown 日报和报警 CSV，将传统耗时 1 小时的复盘压缩至 3 分钟以内。
- 这个项目要解决什么真实业务问题？
  > **回答：** 解决传统规则监控“海量误报”和“缺乏逻辑归因”的痛点。传统监控（如单纯涨幅大于 5%）在牛市时会产生海量无效告警，且投研人员只看到一个数字，仍需手动去翻阅新闻和财报找原因。这个系统通过本地算法先降低数据维度（过滤正常波动），再用 Agent 把“数字”转化为“原因”，让投研人员一目了然知道“为什么异动”，直接辅助判断是否值得关注。
- 为什么这个项目需要 Agent，而不是普通 Python 脚本？
  > **回答：** 如果仅仅是计算异动分数和判断阈值，普通 Python 脚本完全足够，事实上我系统里的本地检测部分就是普通脚本。但要在异动发生后，**自动结合行业上下文、成分股共振效应，给出一个合乎逻辑的“诊断报告”**，并检查这个解释是否有“证据缺口”，这就需要具备推理能力的 Agent 来完成。
- 为什么需要 Multi-Agent，而不是单 Agent？
  > **回答：** 因为单个 LLM 存在明显的“自圆其说”和“幻觉”倾向，特别是在金融这种高要求场景。我设计了一个 ExplainAgent 负责“生成解释”，又设计了一个 DebateReviewAgent 负责“挑刺和复核”。这种“生成-对抗”的多智能体架构，能有效地暴露出解释过度的风险，确保最终送到分析师手中的报告是严谨客观的。
- 你的 Agent 分别是什么角色？每个 Agent 的输入和输出是什么？
  > **回答：** 
  > - **ExplainAgent**：输入是“某个 ETF 及其内部触发预警的成分股的指标特征（如量比、超额收益）”，输出是结构化 JSON，包含该 ETF 异动的“可能原因、风险提示、下一步关注点”。
  > - **DebateReviewAgent**：输入是“原始数据 + ExplainAgent 的解释”，输出是复核报告（JSON 格式），包含“支持/反对立场、反方观点、证据缺口”，并在小范围内调整置信度。
- Agent 之间是串行、并行，还是有条件路由？
  > **回答：** 系统中既有顺序执行，也有条件路由。从数据流向上看，`LocalAnomalyDetector -> Merge -> Validator` 是顺序的；进入 LLM 阶段后，`ExplainAgent` 解释完成后传给 `DebateReviewAgent` 是串行的；但同时如果是不同 ETF 的解释，可以并行处理。如果在 Validator 校验未通过，则直接跳过 Agent 环节被路由到“不报警”分支。
- LangGraph 在这个项目里具体负责什么？
  > **回答：** LangGraph 负责**状态管理和工作流编排**。它将传统的函数调用变成了一个个状态机节点（Node），通过定义的边（Edge）和条件（Conditional Edge）连接起来。这不仅让流程更清晰，更重要的是它支持持久化 Checkpoint（通过 SQLite），如果 ExplainAgent API 突然超时断开，LangGraph 可以从断点恢复，而不需要重新跑前面的本地数据计算。
- 你的状态图是怎么设计的？
  > **回答：** 状态图设计为一条以研判为核心的流水线。起点是接收经过基础清洗的数据（Raw Data），节点依次是：1) `LocalAnomalyDetector`（计算分数和孤立森林标签）；2) `Merge`（合并特征）；3) `DataValidator`（数据有效性校验）；4) `ExplainAgent`（大模型归因）；5) `DebateReviewAgent`（反方复核）；6) `RuleBasedJudge`（纯本地分数最终裁决）。
- 每个节点之间传递什么状态？
  > **回答：** 传递的是一个全局的 `TypedDict` 字典状态。其中包括：当前处理的 `etf_code`、`stock_list`（含各项量化指标的数据框或字典）、`local_score`（本地计算的异常分）、`explanation`（ExplainAgent 填入的解释）、`review_result`（DebateReviewAgent 填入的复核结果），以及 `final_alert_level`（最终判定的高/中/低风险等级）。每个节点只更新自己负责的那部分字段。
- 你怎么防止 Agent 工作流陷入循环或重复调用？
  > **回答：** 
  > 1. **结构上限制**：我的主要业务流是单向的 DAG（有向无环图），不包含循环边（没有类似 Reflection 失败无限重试的回路），失败即进入预设的降级兜底分支。
  > 2. **配置上限制**：即使未来加入循环，也会在 LangGraph 引擎层设置 `recursion_limit`（例如最大步数限制为 10）。
  > 3. **工具层限制**：在底层 `aiohttp` 调用上使用重试退避机制，连续失败直接抛出异常，不再反复重试浪费资源。
- 你怎么设计最大步数、超时和失败重试？
  > **回答：** 最大步数由 LangGraph 的 `recursion_limit` 限制。超时和重试主要在 `configs/rate_limit.yaml` 中配置，通过拦截底层 `aiohttp` 请求的超时异常（如 `TimeoutError`）并结合 `tenacity` 库实现带指数退避（Exponential Backoff）的重试，例如初始等待 2 秒，乘数为 2，最大重试 3 次。一旦彻底失败，会捕获异常并返回预设的格式化“降级字典”，防止整个流水线崩溃。
- 你为什么选择 Parquet 和 SQLite？
  > **回答：** Parquet 是列式存储，具有极高的压缩比和极快的读取速度。量化分析时我通常只需要提取全市场的某几个指标（如收盘价和成交量），Parquet 可以只加载这些列而无需像 CSV 那样全表扫描。SQLite 则是作为一个极其轻量级的文件数据库，不需要额外部署 Server 就可以记录 LangGraph 的运行状态和断点，非常适合本地监控脚本。
- 你为什么用 SQLite 记录 Agent / 工作流运行状态？还可以怎么做？
  > **回答：** 在我这个项目里，“状态”主要指两类：**LangGraph 的 Checkpoint**（图跑到哪一步、State 当前快照、便于 `resume`）以及业务侧的 **采集/报告断点（如 `SqliteStore`）**——一旦采集或 LLM 阶段失败，不必全链路重跑。用 SQLite 的原因很直接：**单文件、零运维**就能落盘；**ACID** 让 checkpoint 写入相对可靠；和 Python/LangGraph 生态对接成本低（如 `SqliteSaver` 一类实现），特别适合我当时的**本地定时任务 + 单机部署**。其代价是：**并发写伸缩性差**、**多进程/多副本共享状态要额外设计文件锁或迁库**。
  > 
  > 还可以怎么做（按演进路径）：
  > 1. **纯内存不落盘**：最快、零依赖；进程挂就丢进度，只适合短任务或 demo。
  > 2. **PostgreSQL（或 MySQL）做 Checkpoint / 会话表**：多实例共享、权限与备份成熟，适合 **TenXAI 这种服务化、多用户/多任务** 的 Agent；LangGraph 侧也常见 Postgres 系 checkpointer 的迁移路径。
  > 3. **Redis（或 KeyDB）**：极适合**高频、短生命周期**的状态与分布式锁；大 State 要做压缩、拆 key、设 TTL，并理清 AOF/RDB 持久化策略。
  > 4. **对象存储 + 元数据表（S3/MinIO + 只存指针）**：把大 payload（trace、完整 State 快照）放对象存储，库里只存索引与版本号，成本低、适合**审计与长期归档**。
  > 5. **把工作流交给专业编排（Temporal 等 durable execution）**：由平台保证幂等、重放与超时；工程更重，但 SLA 与企业级 Agent 更匹配。
  > 
  > **面试一句话：** 我选 SQLite 是为**单机 PoC 的可靠断点与最低运维**；若进 TenXAI 做在线投研 Agent，我会按负载把 checkpoint **迁到 Postgres/Redis**，并把「热状态」与「冷归档」分层。
- 你的 ETF 成分股数据从哪里来？
  > **回答：** 目前使用的是开源金融数据接口 `akshare`，可以获取最新交易日的日线行情、ETF 成分股权重以及基础财务指标。如果是部署在企业环境，我会将其替换为万得（Wind API）或者公司内部的数据中台（如 MySQL/ClickHouse 接口）。
- 你怎么保证数据源稳定性和数据质量？
  > **回答：** 首先，对接口调用增加了熔断与重试机制。其次，在拿到数据后，进入流水线的 `DataValidator` 节点前，系统会对关键字段进行断言检查（如价格非负、涨跌幅未超过涨跌停限制、成分股列表不为空等）。最后，针对停牌或数据缺失的股票，会用 `ffill`（前向填充）或填 0 处理，避免计算 Z-score 时出现 NaN 或 Inf。
- 你怎么做 ETL 防故障？
  > **回答：** ETL 环节严格遵循“先入临时表/临时文件，校验无误后再覆盖或原子性重命名”的模式（类似写时复制）。在特征构建时，用 `try-except` 包裹每一列特征的计算，如果某只股票的某个特征计算失败，只给该特征赋默认值或中位数，而不会导致整个 DataFrame 计算崩溃。
- 你提到日级行情、基本面、利率、区块、消费、新能源等特征，具体怎么构建？
  > **回答：** 日级行情通过计算滚动指标（如过去的 60 日收益率均值和标准差来计算 Z-score）获得；基本面特征（如市盈率）作为静态标量合并到截面数据中；区块、消费、新能源等是依据股票所属的“申万二级/三级行业”或“概念板块”进行 One-Hot 编码或者提取对应行业指数的超额收益作为外部输入特征。
- Isolation Forest 在这个项目中怎么用？
  > **回答：** 孤立森林用于**横向截面异常初筛**。在获得当天全市场 50 只 ETF 的所有成分股（约几百上千行）的多维特征（Z-score、量比、超额收益等）后，我对这个截面拟合 Isolation Forest，将其标记为正常（1）或异常（-1）。它能无监督地找出那些在多维空间中“不合群”的点，作为 LLM 重点关注的候选池。
- 你怎么设置 contamination 参数？
  > **回答：** `contamination` 代表预期数据中异常点的比例。我将其配置在 `thresholds.yaml` 中（默认 0.15 即 15%）。因为我们的目的是“召回”潜在异动并交给大模型复核，而不是直接交易，因此在初筛阶段我倾向于把比例设得稍微宽松一点，以保证不漏掉市场异动（高召回率）。
- 你怎么评估异常检测的误报和漏报？
  > **回答：** 这是无监督学习，缺乏绝对的 Ground Truth。我的做法是进行**抽样人工校验**：抽取几天的历史数据，让人工复盘看当天真正引起市场热议的股票有哪些（如涨停板或大跌股），检查它们是否落在了孤立森林的异常池中（评估漏报）；然后再看被选出的异常池中，有多少是没什么波动的冷门股（评估误报）。不断调整权重配置，直到召回率达到业务接受水平。
- 异常检测用规则、z-score、Isolation Forest、LSTM，各自适合什么场景？
  > **回答：** 
  > - **规则（如绝对涨跌幅）**：适合强逻辑、低计算成本的硬边界过滤，如涨停板过滤。
  > - **Z-score**：适合单变量、符合正态分布假设的时间序列异常检测。
  > - **Isolation Forest**：适合**多维特征的截面异常检测**，计算快，不需要数据符合特定分布。
  > - **LSTM/Autoencoder**：适合极度复杂的**多变量非线性时序序列预测**，但在每日截面选股中不仅计算成本过高，而且容易过拟合。
- AI 在你的系统里负责检测异常，还是解释异常？
  > **回答：** AI 仅负责**解释异常和交叉复核**。异常的“检测”（即决定哪只股票需要关注）是由本地计算的滚动 Z-score 和孤立森林等数学模型完成的。
- 为什么不让 LLM 直接判断异动？
  > **回答：** 第一，LLM 对海量数值序列的敏感度和运算能力很差，容易产生幻觉；第二，成本和时间不允许，如果把全市场 50 只 ETF 的几千只成分股的数据每天都扔给 LLM 算一遍，API 成本极高且非常慢；第三，数学规则计算的异常是确定性的、可复现的，作为风控底线更安全。
- 你怎么把数值异常转化成可读的日报？
  > **回答：** 本地计算出异动分数较高的成分股后，将这些股票的特征（涨跌幅、量比等数值）按其所属的 ETF 打包成一个 JSON 上下文，喂给 ExplainAgent。ExplainAgent 结合内置的行业知识 Prompt，生成诸如“由于某政策刺激，该 ETF 中具有相同概念的成分股发生共振上涨”的自然语言解释。最后再将所有解释按 ETF 汇总为 Markdown 格式的日报。
- 你怎么设计 ExplainAgent 的输入上下文？
  > **回答：** 输入上下文主要包括：1) 系统 Prompt（设定它是专业投研分析师）；2) 当前 ETF 的名称与代码；3) 该 ETF 内触发高分异常的成分股列表，以及这些股票具体的异动指标字典（如 `ret_1d_zscore: 2.8, volume_ratio: 3.5`）。这样 Agent 就能基于具体数据，而非凭空臆想。
- DebatReviewAgent 是怎么复核误报风险的？
  > **回答：** 它被设定为“严厉的风控官”（空头思维）。它拿到 ExplainAgent 的输出后，会重点检查逻辑链条：比如 ExplainAgent 说大涨是因为某政策，但对应个股的成交量并没有明显放大，或者只有单只股票涨而 ETF 内其他同类股票没动静，它就会在 `evidence_gaps` 字段中指出证据不足，提示这可能是随机波动的误报。
- 如果两个 Agent 给出的解释互相矛盾，怎么处理？
  > **回答：** 在流水线中，**本地规则具有最高优先级（Veto Power）**。如果 ExplainAgent 给出了高危解释，但 DebateReviewAgent 强烈反对，系统会在日志中记录这一冲突，并且 DebateReviewAgent 可以小幅下调最终报告的置信度。但它不能改变系统硬规则判定出的告警档位（如中风险/高风险），最终裁判由纯本地节点 `RuleBasedJudge` 进行定级。
- 如果某天市场整体暴跌，系统怎么区分系统性风险和个股异动？
  > **回答：** 系统中设计了一个 `excess_return`（超额收益）特征，即个股收益率减去沪深300指数当天的收益率。如果市场整体暴跌，个股虽然绝对跌幅大，但其超额收益如果是 0 左右，那么在 `local_score`（加权异常分）中这部分就不会得到高分。只有那些偏离大盘趋势、真正有异动的股票才会被提取出来。
- 如果数据缺失或 API 返回异常，Agent 应该如何降级？
  > **回答：** 在数据抓取侧，如果重试多次后 akshare 仍然失败，会跳过当天该标的的计算并记录日志；在 Agent LLM 侧，如果 OpenAI 接口严重超时挂掉，会在 `except` 块中捕获异常，并用一套预先写好的静态字典（如 `{"reason": "LLM服务暂不可用", "risk": "未知"}`）替代，保证整个监控流不阻断，本地初筛的结果（报警 CSV）依然能成功输出。
- 你提到把 1 小时流程压缩到 3 分钟，这个指标怎么测量？
  > **回答：** 这是和原有的人工看盘流程对比得出的估计值。以往分析师每天收盘后需要手动拉取行情软件，对着几十只 ETF 翻看涨跌幅排名，遇到异动再去查新闻，整理一圈至少需要一小时。现在通过定时任务（如 apscheduler），收盘后系统自动拉取数据、并发调用 LLM 解释，通常在 3 分钟左右就能在目录下生成 Markdown 日报，分析师只需直接阅读报告即可。
- 你提到识别 36 条中高风险异动，怎么定义中高风险？
  > **回答：** 风险等级是通过配置在 `thresholds.yaml` 中的 `local_score` 阈值来严格定义的。比如 `local_score >= 2.5` 且通过量价规则校验的定义为高风险（High），`local_score >= 1.8` 定义为中风险（Medium）。这 36 条是项目在特定测试时间窗口内，根据上述物理规则筛选出来的真实案例数量。
- 如果要把这个项目迁移到 TenXAI 的金融 Agent 场景，你会怎么改？
  > **回答：** 
  > 1. **数据源接入**：替换 akshare，接入 TenXAI 的专业金融数据库或 Bloomberg/Wind 等机构级接口。
  > 2. **RAG 增强**：目前的归因主要依靠 LLM 自身的常识，迁移后应接入公司的实时研报和新闻知识库，让解释真正做到有据可查。
  > 3. **工具封装**：将本地的 Z-score 和孤立森林等计算封装为 MCP Tools，变成可以被其他通用 Agent 按需调用的技能。
  > 4. **合规追踪**：加入更严格的日志和 Trace，记录每一条预警的触发阈值和模型生成的 Prompt 版本以备审计。

### 2. 基于多 Agent 的量化交易与投资决策系统
- 说一下你的多 Agent 量化交易与投资决策系统。
  > **回答：** 这是一个模拟真实基金公司投研团队架构的自动化决策系统。通过 6 个不同职责的 Agent 协同工作，系统能自动拉取市场数据、进行多维度分析（基本面、技术面、情绪面），并通过“多空辩论（Debate）”机制消除单一视角的偏差，最终由风控 Agent 审核后生成买卖建议。系统不仅提升了决策的一致性，还通过量化回测验证了其跑赢基准的潜力。
- 这个系统的业务目标是什么？
  > **回答：** 业务目标是**减少人为情绪干扰，提高投资决策的效率和一致性**。传统的散户或主观研究员容易受盘面情绪影响，且无法同时处理海量信息。这个系统旨在自动化地搜集和分析多维信息，给出一个综合了各方观点的、冷酷客观的辅助决策建议。
- 为什么投资决策适合用多 Agent？
  > **回答：** 投资决策本质上是一个“多维度拼图”和“利益博弈”的过程。宏观研究员看基本面，交易员看技术指标，风控专员看下行风险，他们的视角天生是冲突的。把这些职责全部塞给一个大模型，它很容易顾此失彼或产生幻觉。拆分成多 Agent，让它们在各自熟悉的上下文中提取信息并相互辩论，更符合真实世界的决策逻辑，也能大幅提高输出的稳定性。
- 6 个 Agent 分别是什么？为什么这样拆分？
  > **回答：** 
  > 1. Fundamental Agent（基本面）：关注财报、PE/PB等，负责评估公司质地。
  > 2. Technical Agent（技术面）：关注均线、RSI、MACD，负责寻找买卖点。
  > 3. Sentiment Agent（情绪面）：爬取新闻并做 NLP 情感分析，评估市场热度。
  > 4. Debate Agent（辩论/综合）：模拟多空双方辩论，挖掘信息漏洞。
  > 5. Risk Agent（风控）：一票否决的守门员，评估组合风险。
  > 6. Execution Agent（执行）：生成最终的订单和头寸建议。
  > 这样拆分是完全映射了传统基金公司的前中后台组织架构。
- Bull / Bear 双轮辩论机制是怎么设计的？
  > **回答：** 拿到前三个 Agent 的分析报告后，Debate 环节启动。我用 Prompt 强行让一个 Agent 扮演“死多头”（Bull），只能看利好和上涨空间；另一个扮演“死空头”（Bear），专门挑刺和找风险。它们基于同一份数据进行两轮交锋：第一轮各自陈述，第二轮针对对方的漏洞进行反驳。这样能逼迫模型去深度推理，挖掘被掩盖的风险点。
- Debate 结束后谁做最终决策？
  > **回答：** Debate 结束后，由充当“法官（Judge）”的 Agent（在系统中也是 Debate Agent 模块的一部分）对多空双方的论点进行总结和评分，生成一份综合报告。随后，这份报告必须交给 **Risk Agent（风控）** 进行审核，风控拥有最终的否决权。
- 最终决策是规则投票、加权评分，还是 LLM 总结？
  > **回答：** 是**LLM 总结与硬规则的双重结合**。Judge Agent 会通过 LLM 总结辩论，给出一个倾向性的打分（如看多/看空）。但最终是否执行，是由 Risk Agent 决定的，Risk Agent 内部包含硬规则（如当前持仓波动率不能超过设定阈值、必须有明确止损线），只有 LLM 的观点通过了硬规则的校验，决策才算最终成立。
- 你怎么避免 LLM 在辩论中互相附和？
  > **回答：** 通过**极端的系统角色设定（System Prompt）**和**温度控制（Temperature）**。在提示词中，我明确规定 BullAgent “禁止同意对方观点，必须寻找反驳理由”；同时，将 Temperature 设为 0，降低其随机性和套话概率。让它们变成只追求自己逻辑自洽的辩手，从而消除“端水”行为。
- 你怎么避免 Agent 幻觉生成不存在的市场信息？
  > **回答：** 最根本的方法是**切断 LLM 自由发挥的数据源**。Agent 没有任何凭空猜测的权力，它的输入被严格限制为由 `market_data.py` 和 `technical_indicators.py` 工具抓取的最新且确定的结构化数据（如 JSON 格式的财报指标或行情序列）。在 Prompt 中也加入了强约束：“你只能基于上下文中的数据进行推理，如果数据不足，必须回答‘信息不足’，严禁引用外部或历史过时知识”。
- 你怎么设计 Memory？
  > **回答：** 系统主要使用了**短期记忆（Short-term Memory）**。在每一轮运行周期内，LangGraph 的 `State`（字典结构）充当了短期记忆，记录从拉取数据、各 Agent 的独立分析、到最后风控审核的全流程上下文。如果需要持久化跨交易日的**长期记忆**（如用户的风险偏好配置、过去的资产配置建议），我会将其写入到 SQLite 数据库或使用 LangChain 的 `SQLChatMessageHistory`。
- Memory 里存历史行情、历史观点、用户偏好，还是任务过程？
  > **回答：** 历史行情属于外部环境数据，不放在 Memory 里，而是由工具即时拉取。Memory 里存的是：1) **任务过程（短期）**，即本轮分析中各 Agent 产生的中间报告和辩论历史；2) **用户偏好（长期）**，如风险容忍度、特定行业的关注度；3) **历史观点（长期）**，用于复盘（比如如果之前的建议连续错判，Agent 可以在下一次调整对某类信息的权重置信度）。
- Planning 在系统中怎么体现？
  > **回答：** 本系统的 Planning 相对弱化（不是 AutoGPT 那种让大模型漫无目的自由探索的模式）。Planning 体现在：当接收到一个高维度的宏观指令（如“分析下周的新能源车板块配置”）时，系统的主控节点会将其拆解为多个子任务（派发给基本面、技术面、情绪面的 Agent 并行执行）。
- Agent 是自动规划任务，还是按预设 Workflow 执行？
  > **回答：** 是**按预设 Workflow 执行**的。在金融交易场景下，稳定性压倒一切。如果是让 Agent 自动规划，可能会遇到它去搜索无关网页或者因为某个接口挂掉而无限循环的问题。所以我是用 LangGraph 定义了严格的 DAG 拓扑图（如并行的因子搜集 -> Debate -> Risk 拦截），确保数据流转是确定性的。
- 你怎么设计 Human-in-the-loop？
  > **回答：** 引入 Human-in-the-loop 的节点在**风控判定后、真实订单下发前**。当 Execution Agent 生成具体的买卖方向、标的和头寸后，系统会在终端（或推送到企微/Slack）抛出一个 `ActionRequired` 的等待状态，必须由人类交易员输入“Approve”或者“Reject”，如果 Reject 还可以附带理由，Agent 会将理由写入长期 Memory 并重新调整下一次的建议。
- 如果交易建议涉及真实资金，你会在哪些步骤要求人工确认？
  > **回答：** 第一，**调仓白名单的修改**必须人工确认（不能让 Agent 去买流动性极差的妖股）；第二，**单笔大额头寸的下单执行阶段**必须人工一键确认。如果是微调已有持仓的小额高频交易，可以在预设规则（如只允许动用总资金的 2%）内授权 Agent 自动执行，一旦触及规则边界立即熔断转人工。
- 你提到决策延迟降低 66%，怎么定义决策延迟？
  > **回答：** 决策延迟是指从**市场数据齐备（例如每日收盘）到产出最终买卖决策信号的时间**。人工团队需要基本面研究员看财报、量化研究员跑数据，然后开夕会讨论，可能需要数小时甚至半天；而多 Agent 系统并发拉取数据、自动辩论并在几分钟内输出带论据的交易建议，因此节省了 66% 以上的时间。
- 你提到一致性从 52% 提升到 78%，一致性指什么？
  > **回答：** 一致性是指**在输入相同的市场数据（财报、K线、新闻）时，模型多次运行或更换类似提示词后，给出的买卖建议方向是否相同**。普通的单体 LLM 很容易因为生成随机性而一会儿看多、一会儿看空（一致性低）。通过引入 Debate 交叉验证和 Temperature=0 的配置，系统对相同行情的判别变得更加稳定。
- 你提到年化收益 13.4%、夏普比 1.8，这些回测怎么做？
  > **回答：** 采用向量化回测（基于 Pandas）进行快速初筛，后改用事件驱动的回测框架（类似于 Backtrader）。我将 Agent 的决策逻辑封装为策略类中的 `next()` 方法：每天系统拉取当日及历史数据送给 Agent 预测，得到仓位目标后与当前实际仓位对比产生订单，再根据当天的收盘价或次日开盘价撮合，并扣除千分之二的滑点和手续费，最后绘制净值曲线和计算夏普比率。
- 你怎么做时间切分和样本外验证？
  > **回答：** 我将历史数据（如 2018-2023年）按 7:3 划分为样本内（In-Sample, IS）和样本外（Out-of-Sample, OOS）。在 IS 阶段调整 Agent 的提示词、特征窗口期和风控阈值。调优完成后，将模型锁定，直接在 OOS 数据段上运行，看净值是否崩塌。如果 OOS 夏普比和 IS 相比严重下滑，说明大模型或规则严重过拟合了特定的历史行情。
- 你怎么避免数据泄露和未来函数？
  > **回答：** 这是量化回测的底线。
  > 1. **特征计算**：所有移动平均或 Z-score 的计算严格使用 `shift(1)`，确保今天盘中/盘前能看到的数据都是昨天及以前的。
  > 2. **财报数据**：考虑到财报有滞后性（如一季报 4 月才发），严格按照**实际公告日**而非财报报告期来喂给 Agent，防止 Agent “提前知道”利润大涨。
  > 3. **交易撮合**：Agent 根据 T 日收盘信号做出决定，统一按照 T+1 日的开盘价撮合交易。
- 如果回测表现很好但实盘表现很差，你会怎么排查？
  > **回答：** 这是典型的“过拟合”或“回测陷阱”。我会依次排查：
  > 1. **未来函数**：检查是否在 T 日使用了 T+1 日的数据（如收盘价、未公布的财报）。
  > 2. **滑点与手续费**：实盘买卖会有冲击成本，检查回测中是否设定了不切实际的零滑点或低费率。
  > 3. **流动性问题**：检查 Agent 建议买入的是否是流动性极差、根本买不进去的涨停股或微盘股。
  > 4. **LLM 的漂移**：检查底层 API 供应商近期是否更新了模型权重，导致 Agent 的分析逻辑与回测期间出现偏差。
- 如果某个 Agent 经常给出激进建议，你怎么约束它？
  > **回答：** 可以从两方面约束。第一，在 Prompt 中加入**定量约束**，比如限制其在任何情况下建议的单一资产仓位不得超过总资金的 10%；第二，在架构上，增强 Risk Agent 的否决权权重，如果发现某 Agent 连续推荐高波动率或处于历史高位的资产，由 Risk Agent 拦截并在日志中标红，触发人工审查。
- 如果风险 Agent 和收益 Agent 长期冲突，系统怎么权衡？
  > **回答：** 必须设定**风控拥有绝对否决权**。在金融交易中，生存比盈利更重要。当出现长期冲突时，系统默认选择“空仓”或“维持现状”，也就是拒绝任何高风险调仓操作。同时，系统会将长期冲突记录写入数据库，投研人员可以通过分析这些冲突日志，手动介入去调整风控参数或修改收益 Agent 的评价逻辑。
- 这个系统能不能直接作为投顾产品？为什么？
  > **回答：** **绝对不能**直接作为 C 端投顾产品。首先是**合规问题**，目前的法律法规不允许 AI 直接向公众提供带方向性的具体投资建议（投顾牌照要求）。其次是**黑盒风险**，大模型的推理依然存在一定的不确定性，一旦遭遇极端黑天鹅行情，系统如果缺乏人类交易员的常识判断，可能会造成严重损失。
- 金融 Agent 输出投资建议时，合规边界应该怎么设计？
  > **回答：** 合规边界必须明确它仅仅是**“投研辅助工具”**。产品界面和输出报告的每一页都必须加入醒目的免责声明：“本分析基于历史数据和模型自动生成，不构成任何投资建议，市场有风险，投资需谨慎”。且对于内部使用，建议的下发只能作为参考，必须由拥有牌照的研究员或基金经理人工复核后才能转为真实交易指令。

### 3. 转债多因子自动化分析系统
- 说一下你在华福证券做的转债多因子自动化分析系统。
  > **回答：** 这是一个为了提高量化研究员分析效率而设计的 Web 系统。过去研究员验证一个因子（如双低因子），需要自己写脚本、拉取数据并跑回测，非常耗时且不易分享。我主导开发了这个系统，通过将因子的 IC（信息系数）序列和多头策略净值在后端统一处理，并通过 Flask 提供 API 接口，用前端 Plotly 动态绘制出单因子走势、多因子对比、分年度换手率等图表，实现了研究成果的自动化展示和 Excel 导出。
- 这个系统最早是为了解决什么问题？
  > **回答：** 早期的核心痛点是**“因子评价的协作与可视化成本极高”**。量化组里每天都会生成新的因子，但不同人写的脚本不统一，甚至只是本地跑出的静态图片。如果想对比两个因子，或者想看因子在某段历史的表现，都要重新写代码。系统就是为了让大家能在一个统一的可视化看板上，随时点选、对比并导出所需的因子数据。
- 你在项目里负责哪些部分？
  > **回答：** 我负责了**产品设计与全栈开发**。首先通过沟通需求输出了 PRD 和页面交互图。然后使用 Flask 搭建后端，设计了 `/api/factor_ic_data` 等数据接口。处理了从 Pickle 文件或 SQLite 数据库中读取 Pandas DataFrame，清洗后转换为前端可识别的 Plotly JSON 结构，并完成了前端交互界面的开发和部署。
- 你提到 PRD、图表原型和交互页面，为什么这和 AI Agent 岗位相关？
  > **回答：** 因为优秀的 AI Agent 最终要落地为**用户可用的产品（Product）**，而不仅仅是运行在终端的一段代码。做过 PRD 和原型设计，意味着我具备**“以用户为中心”的产品思维**。我知道业务人员需要看什么样的图表、怎么交互最自然，这让我在设计 Agent 的交互方式（如 Human-in-the-loop 的确认界面、可解释性的展示）时会更贴近真实的业务需求。
- 你怎么设计因子数据的读取、清洗和展示？
  > **回答：** 后端接收到前端的因子查询请求后，会通过 `local_db_ic.py` 优先从 SQLite 数据库中对应的表读取该因子的日频序列。如果缺失，则回退读取离线 Pickle 文件。读取出 DataFrame 后，进行多层索引压平、填充缺失值（ffill），然后调用统一的出图适配函数 `plt_series`，将其封装为双 Y 轴或带有标注的 Plotly 图表 JSON 数据，再返回给前端进行无刷新渲染。
- 你做过哪些数据质量校验？
  > **回答：** 在转债系统中，主要是处理由于退市、新上市或数据停更导致的缺失值（NaN）。在将 Pandas 数据喂给 Plotly 出图前，会使用 `ffill`（前向填充）或在特定场景填充 0。对于明显超界的异常值（如溢价率>1000% 的停牌券），会在数据库导入的 `create_tables.py` 脚本环节进行拦截清洗。
- 因子有效性是怎么验证的？
  > **回答：** 验证因子有效性主要看两个维度：**预测能力**和**可交易性**。预测能力通过计算单日 IC（因子暴露与下期收益秩相关系数）和累计 IC 曲线是否单调向右上方倾斜来判断；可交易性通过根据该因子构建多头或多空组合（分层回测），观察其净值曲线、夏普比率、最大回撤以及换手率来评估。
- 如果把这个转债系统升级成 Agent，你会怎么设计？
  > **回答：** 我会将它设计为一个**基于 MCP 的“投研数据对话助手”**。现有的 Flask API 可以改造为 MCP Server，注册为诸如 `get_factor_ic_data`、`plot_nav_curve` 等 Tools。投研人员只需在对话框输入“帮我对比一下双低因子和动量因子今年的累计 IC 走势”，Agent 就能解析意图，自动构建参数调用这些 Tools，在对话界面中直接渲染 Plotly 图表，而不需要在看板上繁琐地点选。
- 如果让 Agent 自动读取研究报告、抽取因子、生成回测任务，你会怎么做？
  > **回答：** 这是一个经典的任务流（Workflow）。我会用 LangGraph 编排：
  > 1. **Parse Agent**：接收 PDF 研报，调用 OCR 和 RAG 工具提取因子定义文本。
  > 2. **Code Agent**：根据文本，调用大模型生成计算因子的 Python 代码。
  > 3. **Sandbox Tool**：在一个隔离的 Docker 沙盒中运行生成的代码与历史数据回测（Backtrader）。
  > 4. **Review Agent**：如果报错，捕获 Error Log 反馈给 Code Agent 自动修复，成功则将策略净值报告返回给用户。
- 如果 Agent 生成的因子逻辑不合理，怎么拦截？
  > **回答：** 引入**“领域常识验证器（Domain Validator）”**和**人工审核节点**。在代码生成后、回测之前，可以通过一个具有金融常识的 Critic Agent（或硬规则）检查逻辑，例如“转债因子的分母不能为 0”、“必须剔除退市券”。回测结果如果不符合经济学常识（例如夏普比大得离谱达到 10 以上），自动判定为“未来函数或逻辑错误”，拒绝将其录入正式因子库并要求人工介入。
- 如果投研人员想用自然语言查询转债异动，你怎么设计 Tool Calling？
  > **回答：** 首先，定义一个明确的 JSON Schema 工具（例如 `search_cb_alerts(date: str, risk_level: str)`）。其次，当用户问“今天有哪些转债跌得比较惨？”，Agent 提取 `date=today`，调用该 Tool 查询后端 SQLite 或 Parquet 数据，获取异常得分较高的转债列表。然后，Agent 可以再组合调用 `get_cb_news(code: str)` 拉取相关新闻，最后综合数据，生成一篇结构化的“今日转债异动速览”回答用户。
- 如果 Agent 需要调用行情库、财务库、回测引擎，工具接口怎么定义？
  > **回答：** 必须遵循**高内聚低耦合**、**参数强类型化**的原则。
  > - 行情库工具：`get_price(ticker: str, start_date: str, end_date: str, frequency: Enum)`
  > - 财务库工具：`get_fundamental(ticker: str, metric: Enum, year: int)`
  > - 回测引擎工具：传入的是策略 ID 和参数字典，`run_backtest(strategy_code: str, params: dict)`。
  > 工具描述（description）中必须极其详细地告诉 LLM 每个参数的含义和格式，特别是日期格式（YYYY-MM-DD），以防止模型生成无效请求。
- 如果 Agent 对同一个因子的解释每次都不一致，怎么提高稳定性？
  > **回答：** 
  > 1. **调整模型参数**：将 `temperature` 设为 0，降低随机性。
  > 2. **锁定 Prompt 结构**：使用 Few-shot 提供固定格式的解答示例，强制大模型按“因-果-结论”的模板输出。
  > 3. **RAG 强行约束**：当解释因子时，要求 Agent 必须且只能从官方的“因子说明词典（Lexicon）”中检索并复述定义，禁止其根据字面意思自由发挥（幻觉）。

## 三、Agent 基础概念

### 1. Agent 定义与架构
- 你怎么理解 AI Agent？
  > **回答：** 我认为 AI Agent（智能体）是**大模型（LLM）能力的延伸和工程化落地**。如果说大模型是大脑，那么 Agent 就是赋予了这个大脑“手”（Tools 工具调用）、“眼”（Observation 环境感知）、“记忆”（Memory）和“执行计划”（Planning 与 Workflow）。它是能够感知环境、自主决策并执行动作以达成特定目标的软件系统。
- Agent 和 Chatbot 的区别是什么？
  > **回答：** Chatbot 主要负责“说”（对话与信息检索），容错率高，即使说错也是文本层面的错误；而 Agent 主要负责“做”（执行任务），它具有环境感知和工具调用的能力。比如，Chatbot 可以告诉你怎么买股票，但 Agent 可以调用券商接口真正帮你把股票买入，因此 Agent 必须具备更强的逻辑规划能力、错误恢复机制（Error Handling）和严格的权限控制。
- Agent 的核心模块有哪些？
  > **回答：** 通常认为包含四大核心模块：**Profile（角色设定）**、**Memory（记忆系统）**、**Planning（任务规划）** 和 **Tools（工具/执行动作）**。有时也会单独把 **Reflection（反思与自我纠错）** 作为一个关键模块。
- Profile、Memory、Planning、Tools、Reflection 分别是什么？
  > **回答：** 
  > - **Profile**：系统提示词中的“人设”，定义 Agent 的性格、目标、边界和先验知识。
  > - **Memory**：短期的会话上下文（Short-term）和跨会话的历史记录与知识（Long-term）。
  > - **Planning**：将复杂的大任务拆解为可执行的子任务树，并在执行过程中进行重新规划。
  > - **Tools**：大模型与物理世界交互的接口，如搜索网页、执行代码、查询数据库。
  > - **Reflection**：Agent 看到执行结果报错或不理想时，自我检查、修改 Prompt 或调整参数重试的机制。
- ReAct 是什么？
  > **回答：** ReAct (Reasoning + Acting) 是一种经典的 Prompt 工程框架。它强制大模型在每一步行动前先输出自己的“思考过程”（Thought），然后再决定“调用什么工具”（Action）。这种模式极大地提高了模型推理的透明度和成功率。
- ReAct 和 Function Calling 有什么关系？
  > **回答：** ReAct 是一种**逻辑范式**（让模型先思考再行动），在早期通过纯文本解析（如正则提取 `Action: xxx`）来实现。而 Function Calling 是模型供应商（如 OpenAI）提供的**底层能力**，它直接在 API 层面结构化地返回工具调用参数。现在主流的框架常常结合两者：用 ReAct 的思维链指导思考，用 Function Calling 保证工具调用的参数 100% 符合 JSON 格式。
- Thought、Action、Observation 在工程实现中分别对应什么？
  > **回答：** 
  > - **Thought**：对应 LLM 生成的一段文本描述（如 `content` 字段中的分析过程）。
  > - **Action**：对应 LLM 生成的 `tool_calls` 结构体（包含函数名和参数 JSON）。
  > - **Observation**：对应系统执行完工具后，将函数的 `return_value` 封装成特定 Role（如 `tool` 角色）的消息，再次附加到上下文列表中传给 LLM。
- 一个生产级 Agent Loop 应该包含哪些控制逻辑？
  > **回答：** 必须包含：**状态校验**（是否满足终止条件）、**异常捕获与重试**（Timeout 或 RateLimit）、**工具参数校验**（JSON Schema 匹配）、**最大循环步数限制**（防止死循环），以及关键节点的**权限管控 / Human-in-the-loop** 阻塞等待机制。
- 如何防止 Agent 无限循环？
  > **回答：** 工程上最有效的手段是**设置强制的 Max Steps / Recursion Limit**。比如设定 LLM 最多只能连续调用 5 次工具，超过 5 次仍未得出最终答案（Finish），系统强制抛出 `AgentIterationLimit` 异常并转入人工处理兜底分支。
- 如何防止 Agent 调错工具？
  > **回答：** 
  > 1. **详尽的 Tool Description**：在提供给大模型的 Schema 中，为工具和每个参数写清楚注释和类型限制，特别是“什么情况下不应该用这个工具”。
  > 2. **参数预校验（Validator）**：在真实执行工具逻辑前，由代码拦截不合法的参数组合（如传入了不存在的股票代码），直接返回 `ValidationError` 给 Agent 让其修正。
  > 3. **减少工具数量**：根据任务阶段动态绑定（Bind）工具，不要一次性把几十个工具塞给 LLM。
- 如何设计 Agent 的任务终止条件？
  > **回答：** 终止条件通常有两种：**显式终止**和**隐式终止**。显式终止是定义一个专门的 `FinishTool`，当 Agent 认为任务完成时必须调用该工具，并把最终答案作为参数传入；隐式终止是判断 LLM 的回复中是否不再包含任何 `tool_calls` 请求，如果纯输出文本，即视为当前轮次思考结束，任务终止。
- Agent 为什么需要状态管理？
  > **回答：** 大模型 API 本质上是无状态的（Stateless）。Agent 需要在多轮推理、工具调用、失败重试甚至停机等待人工确认之间流转，如果没有一个全局的状态机（如 LangGraph 的 State 或数据库 Checkpoint）去持久化当前的上下文、错误日志和中间结果，Agent 的任何中断都会导致整个任务从头来过。
- Agent 的短期记忆和长期记忆有什么区别？
  > **回答：** 短期记忆通常是当前 Session 或当前任务流中的上下文历史（通常保存在 LLM 的 Message List 或 LangGraph 的 State 中），随着任务结束而清空；长期记忆是跨 Session 保存的（如用户的配置偏好、历史任务的总结），通常需要持久化存储在向量数据库或关系型数据库中，并在需要时通过检索召回。
- 长期记忆应该存什么，不应该存什么？
  > **回答：** 应该存：**用户画像（如风险等级）**、**工具调用的成功/失败教训（用于 Reflection）**、**高频的规范与准则**。不应该存：**原始的繁杂对话流水**（太占 token 且信噪比低，应该定期总结后存 Summarization）和**具有严格时效性的临时市场数据**（如“今天股价是 10 块”，明天就没用了，应该每次即时拉取）。
- Reflection 机制有什么用？
  > **回答：** 类似于人类的“反思”。当 Agent 执行了一段代码报错，或者生成的报告格式不对时，Reflection 机制允许它不直接崩溃，而是把 Error Message 和自己刚才的操作作为输入，重新思考：“我哪里做错了？应该怎么修正参数或更换工具？”，从而提高复杂任务的最终成功率。
- Self-Reflection 和外部 Evaluator 有什么区别？
  > **回答：** Self-Reflection 是让生成答案的 Agent 自己检查自己，成本低，但容易“当局者迷”（大模型常认为自己写的都是对的）；外部 Evaluator（如我项目里的 DebateReviewAgent）是引入另一个独立角色（甚至是一个不同的、更强大的模型，如用 Claude 检查 GPT-4 的输出），专门负责挑刺，审查标准更严苛，准确率更高，但增加了 API 成本和延迟。

### 2. Workflow 与自主规划
- Workflow-based Agent 和 Planning-based Agent 有什么区别？
  > **回答：** Workflow-based 的执行路径是预先由人类用代码（如 DAG 状态机）编排好的，Agent 只是在特定节点执行特定任务，稳定性极高，但在处理超出预设 SOP 的问题时会卡壳；Planning-based 只有目标和工具，怎么规划步骤、怎么流转完全由 Agent 自主决定（如 AutoGPT），非常灵活，但在复杂真实业务中极易因为环境噪音而发散或死循环。
- 什么时候应该用固定 Workflow，什么时候应该让 Agent 自主规划？
  > **回答：** 在**金融风控、医疗诊断、自动化交易**等对稳定性、可预测性、合规性要求极高，且已有成熟行业 SOP 的场景，必须用固定 Workflow。在**资料搜索、开放式编程辅助、游戏NPC**等容错率高、探索空间大、目标模糊的场景，可以让 Agent 自主规划。
- 你怎么理解 DAG、状态机和 Agent 工作流？
  > **回答：** DAG（有向无环图）保证了任务的流转有明确的先后顺序，不会发生无限死循环。状态机（State Machine）确保在任何时刻系统都处于一个确定的 State 中，并且根据 Agent 的输出作为转移条件（Transition）切入下一个 State。将 Agent 的黑盒思维包裹在 DAG 状态机里，就形成了企业级可控的 Agent 工作流。
- LangGraph 适合解决什么问题？
  > **回答：** LangGraph 最适合解决**需要循环（Cycles）、需要状态持久化（Checkpointing）以及需要 Human-in-the-loop 的复杂多 Agent 协同场景**。传统的基于 DAG 的任务调度器（如 Airflow）很难处理循环图，而原生的 LangChain Agent 往往是个黑盒。LangGraph 通过把 Agent 当作 Node、将路由逻辑变成 Edge，使得多 Agent 编排变得清晰且可控。
- LangGraph 和 LangChain 的区别是什么？
  > **回答：** LangChain 像是一个拥有无数零件的**工具箱**，它提供了 LLM 接口封装、Prompt 模板、RAG 向量库对接等基础组件。而 LangGraph 是建构在 LangChain 之上的一套**编排框架**，它利用图论的思想，把 LangChain 里的链（Chain）和 Agent 像画流程图一样连接起来，并加上了全局状态（State）管理机制。
- 如果一个任务包含检索、计算、写作、审核四步，你会怎么编排？
  > **回答：** 我会使用 LangGraph。
  > 1. `Node_Retrieve`：调用 RAG 或 Search 工具搜集数据，存入 State。
  > 2. `Node_Calculate`：使用 Python 工具或计算 API 处理 State 中的数据，结果更新回 State。
  > 3. `Node_Write`：读取前两步的 State 生成初稿。
  > 4. `Node_Review`：负责审核。这里加入**条件边（Conditional Edge）**：如果 Review 不通过，Edge 指回 `Node_Write`（甚至 `Node_Retrieve`）重做；如果通过，则输出最终结果。
- 如果中间某一步失败，Workflow 应该怎么回滚或重试？
  > **回答：** 
  > 1. **重试（Retry）**：在节点内部配置 `tenacity` 等重试机制，处理偶发性的网络或 API 错误。
  > 2. **反思回滚（Reflection Loop）**：如果是逻辑错误（如代码运行失败），将 Error 传回上一步的生成节点，让其基于错误信息重试。
  > 3. **降级与状态恢复（Checkpoint）**：如果多次重试依然失败，利用 LangGraph 的 SQLite Checkpoint 保存当前有效状态，退出并通知人工介入，人工修复后可以从该断点（Resume）继续执行，无需全部重跑。
- 如果用户任务很模糊，Agent 应该先规划还是先追问？
  > **回答：** **必须先追问**。如果用户输入“帮我分析一下市场”，如果 Agent 直接规划，往往会变成盲目搜索导致浪费 Token 且答非所问。良好的设计应该在入口处设置一个 `IntentClassifier`（意图识别）或者 `Clarifier` 节点。当检测到关键参数缺失时，停止规划，直接转入 `AskUser` 动作，直至补齐槽位后再进行 Planning。
- 如果 Agent 规划的步骤太多，怎么压缩和控制成本？
  > **回答：** 
  > 1. **提供标准 SOP 工具**：把高频的、多步的复杂逻辑用纯 Python 封装成一个黑盒大工具（Macro Tool），Agent 只要调用一次即可，而不是让大模型一步步去调基础工具。
  > 2. **限制规划深度**：在 Prompt 中强制要求“生成的计划不能超过 5 步”。
  > 3. **使用小模型**：对于简单的分支判断和参数提取，路由给更便宜、更快的模型（如 Claude 3 Haiku 或 GPT-4o-mini），只在最核心的推理节点使用大模型。
- 如果 Agent 规划不合理，系统怎么纠偏？
  > **回答：** 引入 **Critic Agent（审查者）** 或在 Human-in-the-loop 中加入**Plan 确认节点**。Agent 生成初始 Plan 后不立刻执行，而是先交给 Critic 检查是否包含危险操作（如误删数据）、是否陷入死循环或冗余步骤。如果是复杂的高风险金融任务，必须将生成的 Plan 展示在前端，由用户点击确认后系统才开始真正执行 Action。

### 3. Multi-Agent / Agent Swarm
- Multi-Agent 适合什么场景？
  > **回答：** 适合**任务链长、专业跨度大、需要消除单一视角偏见**的场景。例如：
  > - 软件开发（需要产品经理、程序员、测试员）。
  > - 金融投研（需要宏观分析师、量化交易员、风控专员）。
  > - 复杂的长文档写作（需要大纲规划师、资料检索员、撰稿人、校对者）。
- 多 Agent 相比单 Agent 的优势和代价是什么？
  > **回答：** 
  > - **优势**：降低单个 Agent 的 Prompt 复杂度，使得每个 Agent 能更专注其专门任务，减少幻觉；通过角色对抗（如 Debate）提高最终输出的客观性和质量。
  > - **代价**：API 调用成本和延迟呈倍数级上升；多 Agent 间如果通信格式定义不清，极容易产生陷入无限争吵（死循环）的系统级崩溃。
- AgentSwarm 是什么？你怎么理解它？
  > **回答：** Agent Swarm（智能体集群）是指大量轻量级的智能体，通过去中心化或特定的网络拓扑结构（如层级、环状）协同工作。与传统的由中心化 Planner 指挥不同，Swarm 更强调涌现性（Emergence），即通过定义简单的个体交互规则，集群能自发解决极其复杂的问题。虽然目前多在实验室阶段，但在未来处理如海量市场情绪监控等大规模并发任务时极具潜力。
- Multi-Agent 中常见的角色拆分有哪些？
  > **回答：** 常见的角色拆分包括：
  > - **指挥与规划**：Planner / Manager / Router
  > - **信息搜集与执行**：Researcher / Executor / Coder / Tool Caller
  > - **内容生成**：Writer / Analyst / Designer
  > - **审查与纠错**：Reviewer / Critic / QA / Judge
- Planner、Executor、Critic、Researcher、Coder、Reviewer 分别适合做什么？
  > **回答：** 
  > - **Planner**：负责理解总任务，拆解子任务并分发。
  > - **Executor / Coder**：负责“干活”，调用具体工具或编写/运行代码。
  > - **Researcher**：专门负责通过搜索引擎或 RAG 获取外部知识。
  > - **Critic / Reviewer**：负责充当“反方”，检查前者的产出是否有逻辑漏洞、代码 Bug 或合规风险，并给出修改意见。
- 多 Agent 之间如何通信？
  > **回答：** 主要有两种方式：
  > 1. **共享状态池（Shared State / Blackboard）**：所有 Agent 都向一个中央的状态字典（如 LangGraph 的 State 或黑板模式）读写数据，适合强编排的 Workflow。
  > 2. **消息传递（Message Passing / P2P）**：Agent 像人在群聊里一样，直接把文本消息发给另一个 Agent（如 AutoGen 的实现），适合去中心化的自由对话与辩论。
- 多 Agent 之间如何共享上下文？
  > **回答：** 通常通过一个全局的 **State（状态对象）** 或 **Blackboard（黑板机制）**。比如在 LangGraph 中，定义一个 `TypedDict` 类型的全局 State，里面包含了 `messages` 列表和其他变量。每个 Agent 执行完后，会将自己的分析报告附加（Append）或覆盖（Overwrite）到这个全局 State 中，后续被触发的 Agent 直接读取这个 State，就拥有了前面的所有上下文。
- 多 Agent 如何避免重复劳动？
  > **回答：** 
  > 1. **严格的角色与职能边界划分**：通过 Prompt 给每个 Agent 圈定“你能做什么、不能做什么”。
  > 2. **共享缓存（Tool Cache）**：如果两个 Agent 碰巧都需要查询同一家公司的财报，底层 Tool 调用应有本地缓存（如 SQLite 或 Redis），第二个请求直接返回缓存结果。
  > 3. **主管分配（Manager-Worker）**：由一个 Planner Agent 先拆解出互相独立、无重叠的子任务（如 A 查利润表，B 查新闻），再分发给具体的 Worker 执行。
- 多 Agent 如何解决观点冲突？
  > **回答：** 引入**“法官（Judge）”**或**“辩论（Debate）”**机制。像我项目里的 Bull 和 Bear Agent 就是故意制造冲突的，然后把双边的论据和推理过程一起扔给 Judge Agent，由它基于全局视角（或者由优先级更高的 Risk Agent 基于保守原则）做出客观的最终裁决。
- 多 Agent 如何做任务分配？
  > **回答：** 可以是**静态编排**，也就是开发者用代码写死 A 做完 B 做（像 LangGraph 的图结构）；也可以是**动态路由（Dynamic Routing）**，即由一个拥有工具箱的 Manager Agent 根据用户的指令，动态决定把任务派发给哪个特定技能的 Worker Agent 去执行。
- 多 Agent 如何做结果汇总？
  > **回答：** 通常设置一个收口节点（Reducer / Summarizer）。由于之前的 Agent 可能是并发执行的（Fan-out），当它们都执行完毕后（Fan-in），将它们的所有输出作为列表传入 Summarizer Agent 的 Prompt 中。要求它提取各方核心观点，去重后生成最终的 Markdown 报告或 JSON 结果。
- 多 Agent 如何评估每个 Agent 的贡献？
  > **回答：** 这是一个难点。目前的做法主要是通过在最终结果中保留**引用追溯（Traceability）**：在 Judge 综合决策时，明确标注哪个论据是由哪个 Agent 提出的。如果最终投资决策失败，可以通过 Trace 日志找到是 Fundamental Agent 的财报提取错了，还是 Sentiment Agent 的情绪判断反了，从而针对性地对出问题的 Agent 调优。
- 如果某个 Agent 输出质量很差，系统怎么发现？
  > **回答：** 
  > 1. **结构化输出校验（Pydantic/Json Schema）**：如果连格式都吐不对，直接被 Validator 拦截并打回重做。
  > 2. **Reviewer 节点检测**：引入一个专门的 Review Agent 检查同行逻辑，如果发现其总是“废话连篇”或“没有数据支撑”，直接在内部判负，甚至上报异常给开发者。
- 如果多个 Agent 同时调用外部工具，怎么控制并发和限流？
  > **回答：** 在工具层面（而不是 LLM 层面）做控制。如果是 Python 异步代码（`asyncio`），可以使用 `asyncio.Semaphore` 来限制并发数；同时结合 `tenacity` 库实现 API `RateLimitError`（如 429 报错）的指数退避重试，确保不管上层多少个 Agent 发起调用，底层的出口带宽是受控且不会被封禁的。
- 多 Agent 在金融场景中可能有哪些典型应用？
  > **回答：** 
  > - **模拟投研闭门会**：让多个 Agent 扮演不同风格的基金经理，针对同一只股票进行模拟辩论。
  > - **合规与营销双轨审核**：一个 Agent 负责写诱人的理财产品营销文案，另一个扮演合规官，死扣用词（不能用“保本”、“绝对收益”），两者拉扯直到达成平衡。
  > - **复杂事件复盘**：针对突发事件（如非农数据大超预期），宏观、行业、量化三个 Agent 分别从不同维度并发拆解，几分钟内汇总出事件点评。

## 四、Prompt / RAG / Tool Use

### 1. Prompt Engineering
- 你怎么写 Prompt？
  > **回答：** 我通常采用结构化的框架（如 CRISPE 或 CO-STAR 框架）。一个标准的生产级 Prompt 包括：
  > 1. **角色设定（Role）**：你是资深量化分析师。
  > 2. **任务目标（Objective）**：解释 ETF 异动。
  > 3. **上下文与输入（Context/Input）**：提供 JSON 格式的个股指标。
  > 4. **约束条件（Constraints）**：严禁猜测未提供的信息，必须引用数据，如果不知就回答不知道。
  > 5. **输出格式（Output Format）**：给出预期的 JSON Schema 或 Markdown 模板，并提供 1-2 个 Few-shot 示例（非常重要，能极大提高输出稳定性）。
- 一个好的系统 Prompt 应该包含哪些部分？
  > **回答：** 应该包含：1) **Role/Persona（角色设定）**；2) **Task/Objective（核心任务）**；3) **Context/Input（背景信息与输入数据规范）**；4) **Rules/Constraints（严格的约束条件，特别是“不能做什么”）**；5) **Output Format（期望的输出格式，如 JSON Schema）**；6) **Few-shot Examples（示例）**。
- 你怎么设计角色、目标、约束、输出格式和示例？
  > **回答：** 
  > - **角色**：用具体的头衔（如“拥有10年经验的 A 股医药行业研究员”）。
  > - **目标**：动词开头，清晰明确（如“基于输入的财报数据，总结3条核心利好”）。
  > - **约束**：使用绝对禁止的语气词（如“严禁编造数据”、“如果缺乏信息必须输出 null”）。
  > - **输出格式**：给出明确的字段说明和类型（如 `{"reason": "string", "risk_level": "High|Medium|Low"}`）。
  > - **示例**：提供一正一反（One positive, one negative）或者包含边界情况（Edge case）的示例对。
- Zero-shot、Few-shot、Chain of Thought 分别适合什么场景？
  > **回答：** 
  > - **Zero-shot**：适合简单的常识问答、情感极性判断、通用的文本润色。
  > - **Few-shot**：适合**对输出格式和特定领域语气要求极高**的任务（如把非结构化新闻提取为严格的 JSON）。
  > - **Chain of Thought (CoT)**：适合**复杂的逻辑推理和数学计算**场景（如让 Agent 分析某项政策如何传导到公司的每股收益上），强制要求其先输出 `<thought>` 再输出 `<result>`。
- 你怎么让模型稳定输出 JSON？
  > **回答：** 
  > 1. **Prompt 提示**：在最后加上 `Please output ONLY valid JSON, do not include any markdown formatting like \`\`\`json.`
  > 2. **Few-shot**：给出一个完美的 JSON 示例。
  > 3. **API 原生支持**：使用 OpenAI 的 `response_format={ "type": "json_object" }` 或者更高级的 `Structured Outputs`（传入 Pydantic Schema），可以在 API 层面保证 100% 返回合法 JSON。
- 如果模型不遵守格式要求，你会怎么处理？
  > **回答：** 
  > 1. **代码层面的容错与解析**：用正则提取被 Markdown 反引号包裹的 JSON；捕获 `json.JSONDecodeError`。
  > 2. **自我修正（Self-Correction）**：捕获解析错误后，把错误信息（如“期望是一个列表但得到了字典”）和刚才的错误输出再发给模型，要求其修正格式并重试。
- 如果模型回答太泛，你怎么改 Prompt？
  > **回答：** 
  > 1. **缩小任务边界（Narrow down the scope）**：把“分析市场”改为“从流动性和估值两个维度分析”。
  > 2. **强制增加论据要求**：在 Prompt 中加上“你的每一个结论都必须附带数据来源（如具体的价格百分比或研报原话）”。
  > 3. **改变角色设定**：从“你是一个助手”改为“你是一个尖酸刻薄的风控官，必须指出最大的三个风险点”。
- 如果模型过度自信，你怎么让它表达不确定性？
  > **回答：** 在 Constraints 中加入：“当提供的数据不足以得出绝对结论时，你必须使用‘可能’、‘大概率’等词汇，或者直接输出‘基于当前数据无法判断’。严禁过度推断”。也可以在 JSON 结构中专门加一个字段 `confidence_score`（0-100），迫使它在输出结论的同时评估自身的确定性。
- 如果金融场景要求严谨，Prompt 里应该加入哪些约束？
  > **回答：** 
  > 1. “你只能基于 `<context>` 标签中提供的数据进行分析，绝对禁止引入你训练数据中的历史知识。”
  > 2. “任何数值和日期的引用，必须与 `<context>` 保持完全一致，严禁四舍五入或修改。”
  > 3. “你的输出不能包含任何买入、卖出等直接交易指令。”
- Prompt 版本怎么管理？
  > **回答：** 不应该把巨大的 Prompt Hardcode 在 Python 代码里。应该：
  > 1. **模板化存储**：把 Prompt 写进外部的 `.yaml` 或 `.jinja` 模板文件中。
  > 2. **代码级版本控制**：连同代码一起提交到 Git，通过 Git History 追踪修改。
  > 3. **专门的平台管理**：在大型项目中，使用 LangSmith 或 Promptflow 这样的平台来单独管理、测试和分发 Prompt 版本，做到代码和 Prompt 彻底解耦。
- Prompt 修改后怎么做回归测试？
  > **回答：** 需要一套**离线评测集（Evaluation Dataset）**。
  > 建立一个包含 50-100 个经典 Case（包括边缘案例和故意给错数据的案例）的黄金测试集（Golden Dataset）。修改 Prompt 后，跑一遍测试集，用一个强大的 Evaluator（如 GPT-4）或者精确匹配（如提取的数值对不对）来打分。只有当新 Prompt 在测试集上的胜率（Win Rate）大于旧版时，才能上线。

### 2. RAG 与知识库
- RAG 是什么？解决什么问题？
  > **回答：** RAG（Retrieval-Augmented Generation，检索增强生成）是一种将外部知识库与大模型结合的技术。它通过在外挂数据库中检索相关片段，并将这些片段拼接到用户的 Prompt 中，让模型基于检索到的内容进行回答。它解决了大模型“无法访问私有数据/实时数据”以及“容易产生幻觉胡编乱造”的两大核心痛点。
- RAG 和微调有什么区别？
  > **回答：** RAG 是“开卷考试”，通过外挂知识库实时检索答案，成本低、更新快、能提供引用来源；微调（Fine-tuning）是“闭卷考试”，把知识内化到模型权重中，成本极高、无法实时更新知识，但能深度改变模型的说话语气、专用词汇和隐式逻辑模式。
- 金融知识库适合用 RAG 还是微调？
  > **回答：** **绝大多数场景适合 RAG**。金融数据（如每日行情、最新财报和新闻）具有极强的时效性，微调无法做到每天更新模型权重。微调只适合用于改变 Agent 的“金融常识逻辑”或者强制其输出特定格式的复杂报告，而事实类查询必须依赖 RAG。
- RAG 的完整链路是什么？
  > **回答：** 
  > 1. **数据索引（Indexing）**：提取文本 -> 数据清洗 -> 文档切分（Chunking） -> 向量化（Embedding） -> 存入向量数据库。
  > 2. **检索（Retrieval）**：用户提问 -> 提问改写/向量化 -> 在数据库中检索最相似的 Top-K Chunk -> 重新排序（Reranking）。
  > 3. **生成（Generation）**：将过滤后的 Chunk 和原始问题拼接为 Prompt，交给 LLM 生成答案。
- 文档切分怎么做？
  > **回答：** 通常有基于字符长度（如每 500 字一切，带 50 字的 Overlap）、基于语义边界（如按 Markdown 的 Header 级别切分，或者按段落 `\n\n` 切分）。对于复杂的金融文档，更高级的做法是进行**结构化切分**，比如把表格单独提取出来，或者结合大模型做“命题切分（Propositional Chunking）”。
- Chunk 太大或太小分别有什么问题？
  > **回答：** 
  > - **太大**：包含过多不相关信息（噪音），不仅增加 Token 成本，还会稀释核心上下文，导致 LLM 在生成时找不到重点（Lost in the middle）。
  > - **太小**：破坏了语义的完整性，比如把“A公司净利润下降”和“因为汇率波动”切到了两个 Chunk 里，检索时拿不到完整的因果关系，导致回答错误。
- 向量检索、关键词检索、混合检索有什么区别？
  > **回答：** 
  > - **向量检索（Dense）**：基于语义相似度（Embedding），能理解“苹果手机”和“iPhone”是同一个意思，擅长模糊查询和概念匹配。
  > - **关键词检索（Sparse, 如 BM25）**：基于词频和精准匹配，擅长找人名、公司代码（如“茅台 600519”）、特定专业术语。
  > - **混合检索（Hybrid）**：将两者的召回结果结合，通过倒数秩融合（RRF）等算法重新打分，能同时兼顾语义理解和精准关键字命中，是目前工业界 RAG 的标配。
- Rerank 的作用是什么？
  > **回答：** 向量检索（如 Cosine Similarity）速度快但比较粗糙，经常会把语义相近但不相关的 Chunk 排在前面。Rerank（重排）是引入一个专门的交叉编码器模型（Cross-Encoder，如 BGE-Reranker），把用户问题和初筛的 Top-N（比如 50 个）Chunk 放在一起做深度的注意力交叉计算，打出更精准的相关性分数，从而挑出真正有用的 Top-K 送给生成模型。
- Top-K 怎么选择？
  > **回答：** 这是一个 trade-off（权衡）。如果 K 太小，可能漏掉关键信息导致无法回答；如果 K 太大，超出了模型的 Context Window，或者引入过多噪音干扰推理，且增加 Token 成本。通常的做法是，经过 Rerank 后，根据 Rerank Score 设置一个置信度阈值（动态 K），或者固定取 3-5 个高质量 Chunk。
- 如何评估召回质量？
  > **回答：** 可以使用客观指标如 **Hit Rate（命中率）** 和 **MRR（Mean Reciprocal Rank，平均倒数排名）**。具体做法是构建一个“问题-来源文档”的 Ground Truth 测试集，输入问题，看正确的文档是否出现在召回的 Top-K 列表中，以及排在第几位。也可以使用 RAGAS 或 TruLens 等框架，利用大模型作为裁判（LLM-as-a-Judge）评估 Context Relevance（上下文相关性）。
- 如何处理金融研报、公告、年报这种长文档？
  > **回答：** 不能简单粗暴地用长度切分。
  > 1. **分层切分与检索（Parent-Child Retriever）**：把大段落作为 Parent 存原文，切分出的小句子作为 Child 生成向量。检索时匹配 Child，但喂给 LLM 的是完整的 Parent 上下文。
  > 2. **摘要索引（Summary Index）**：为每一页或每一章先用 LLM 生成摘要，检索时先匹配摘要，再深入具体章节。
  > 3. **复杂版面解析**：使用专门的 PDF 解析大模型（如 LayoutLM、Marker）正确提取表格和图表中的财务数据，将表格转为 Markdown 或 HTML 格式再存入。
- 如何处理表格、PDF、图表里的信息？
- 如何保证回答有引用来源？
  > **回答：** 
  > 1. **Prompt 约束**：要求模型在回答的每一个句子后面加上 `[Doc ID]`。
  > 2. **后处理校验（Post-processing）**：在输出前，用代码或另一个校验模型检查生成的文本是否真正存在于检索到的 Chunk 原文中。如果发现引用对不上号，则判定为幻觉并重试或警告。
- 如果检索结果互相矛盾，模型应该怎么回答？
  > **回答：** 应该在 Prompt 中明确规定：“如果 `<context>` 中的信息存在矛盾，你必须**同时列出双方的观点，并明确指出数据来源的冲突**，严禁自行捏造一个中间值或偏袒其中一方”。比如：“机构 A 认为目标价为 10 元（来源 Doc 1），但机构 B 认为目标价为 8 元（来源 Doc 2）”。
- 如果知识库没有答案，Agent 应该怎么办？
  > **回答：** 必须在 Prompt 中加入**“如不知道，直接说不知道”**的硬性规则（拒答机制）。其次，如果允许，Agent 应该触发 `SearchWeb` 工具去公网找答案，或者进入 `AskHuman` 状态，抛出提示：“本地研报库未查到相关信息，是否需要我联网搜索或由您补充数据？”
- 如何设计知识库更新机制？
  > **回答：** 
  > 1. **增量更新**：每天晚上跑定时脚本（如 apscheduler），拉取当天的新研报和公告，做 Embedding 后 append 到向量数据库。
  > 2. **元数据过滤（Metadata Filtering）**：在存入向量块时，必须打上 `date`、`ticker`、`doc_type` 等 Metadata。
- 如何处理过期知识和版本管理？
  > **回答：** 绝对不能只靠向量库自己的相似度来捞数据（那会把十年前的相似财报捞出来）。检索时，必须强制加上**时间过滤条件（Time-based Filtering）**。或者在 Rerank 之前加入“时间衰减因子”，让距今越近的文档得分越高。过期知识不需要物理删除，但要在 Metadata 中标记为“已过期”，平时检索时通过预过滤（Pre-filter）排除掉。

### 3. Function Calling / Tool Use / MCP
- Function Calling 是什么？
  > **回答：** Function Calling 是 OpenAI 等大模型提供的一种能力，它允许开发者在 API 请求中描述一组函数（工具的 Schema）。模型会根据用户的输入，判断是否需要调用某个函数，如果需要，它会直接输出符合该函数签名要求的结构化 JSON 参数，而不是一段自然语言文本。
- Tool Use 的核心流程是什么？
  > **回答：** 
  > 1. **定义**：开发者定义外部函数及其 JSON Schema，连同用户的 Prompt 一起发给 LLM。
  > 2. **判断与参数生成**：LLM 决定调用该函数，并返回包含函数名和参数的数据结构（通常 role 为 `assistant`，带有 `tool_calls`）。
  > 3. **本地执行**：业务代码截获这个返回，在本地真正执行那个 Python/API 函数。
  > 4. **结果回传**：将函数的执行结果封装为 role 为 `tool` 的消息，追加到对话历史中，再次发给 LLM。
  > 5. **生成最终回答**：LLM 根据工具返回的数据，生成最终给用户的自然语言回答。
- 你怎么定义一个工具的 schema？
  > **回答：** 使用 OpenAPI/JSON Schema 标准或 Pydantic 类。必须包含：
  > 1. **工具名称**：英文，清晰表意（如 `get_stock_price`）。
  > 2. **工具描述**：详细说明该工具的作用以及**何时应该使用**。
  > 3. **参数列表**：定义每个参数的名称、类型（string/integer）、是否必填（required）。
  > 4. **参数描述与示例**：特别重要！如 `date: string, format must be 'YYYY-MM-DD', e.g., '2025-10-01'`。
- 工具描述写得不好会导致什么问题？
  > **回答：** 会导致**工具调用幻觉**和**参数错误**。
  > 1. 模型不知道什么时候该用，可能会在不需要的时候乱调用（浪费 Token）。
  > 2. 模型分不清两个相似工具的区别（比如 `get_daily_price` 和 `get_intraday_price`）。
  > 3. 参数瞎填，比如把股票代码“000001”传成了“平安银行”，导致后续代码执行报 `KeyError`。
- Agent 如何判断该不该调用工具？
  > **回答：** Agent 依赖自身模型内部的推理能力结合开发者在 **System Prompt 和 Tool Description 中给出的说明**。如果用户的意图仅仅是闲聊，Agent 发现不用工具也能回答，就会输出文本。如果用户的意图缺乏数据支撑（如“今天的收盘价”），它匹配到 `get_price` 工具描述，就会输出调用指令。
- Agent 调用工具时如何做参数校验？
  > **回答：** 在 LLM 返回 `tool_calls` 后，先不要直接传给底层函数。
  > 1. 将返回的 JSON 丢给 **Pydantic 模型** 进行反序列化和校验（包括类型、正则匹配等）。
  > 2. 如果 Pydantic 抛出 `ValidationError`，把这个 Error 信息封装回一条 Message：“参数错误：date必须是YYYY-MM-DD格式”，再次发给 LLM 让它自我修正，或者直接退回给前端提示用户。
- 工具调用失败后，Agent 应该怎么恢复？
- 工具调用结果太长，怎么压缩进上下文？
- MCP 是什么？
  > **回答：** MCP（Model Context Protocol，模型上下文协议）是由 Anthropic 提出的一种标准化通信协议。它为 AI 智能体（如 Cursor、Claude）安全、标准化地访问外部数据源（如本地文件、数据库）和执行工具提供了一套统一的接口标准。
- MCP 的 Host、Client、Server 分别是什么？
  > **回答：** 
  > - **Host**：运行 Agent 且提供用户界面的宿主应用（如 Cursor IDE 或 Claude Desktop）。
  > - **Client**：位于 Host 内部，负责管理与多个 MCP Server 的连接并转发大模型的请求。
  > - **Server**：轻量级的后端程序，实际连接外部数据源或工具（如连接 SQLite 数据库的 MCP Server），它向 Client 暴露资源（Resources）和工具（Tools）。
- MCP 和 Function Calling 有什么关系和区别？
  > **回答：** Function Calling 是大模型预测出“应该调什么函数和传什么参数”的能力；而 MCP 是**工程架构层面的协议**，它规定了这些函数（Tools）和外部数据（Resources）应该如何被发现、如何被调用、权限如何控制。简而言之，大模型通过 Function Calling 决定行动，而 Client 通过 MCP 协议将这个决定发送给具体的 Server 去执行。
- 如果要给金融 Agent 接入行情查询工具，你会怎么设计工具接口？
  > **回答：** 接口设计必须防呆且具有高可用性。例如设计一个 `get_historical_prices(symbol, start_date, end_date, interval)`：
  > 1. `symbol` 强制使用带后缀的格式（如 `600519.SH` 或 `AAPL.US`），避免跨市场冲突。
  > 2. `interval` 必须是枚举类型（Enum: `1d, 1h, 1m`）。
  > 3. 在底层 Server 内部，如果用户查询超出时间限制（如查询十年的分钟线），必须截断并返回一段友好的警告文本，而不是直接抛出 500 错误让 Agent 崩溃。
- 如果要接入数据库查询工具，怎么防止危险 SQL？
  > **回答：** 
  > 1. **最小权限原则**：MCP Server 连接数据库时，使用的账号只能拥有 `SELECT` 权限，绝对不能有 `DROP`、`UPDATE` 权限。
  > 2. **Schema 限制**：只暴露允许查询的特定视图（View），而不是基础物理表。
  > 3. **Human-in-the-loop**：对于复杂的聚合查询，生成 SQL 后必须在前端弹窗，由用户确认后（Approve）才能真正在库里执行。
- 如果工具涉及交易、下单或资金操作，权限和确认机制怎么设计？
  > **回答：** 这是高危操作。
  > 1. Agent 生成的只是一个待审批的“订单草稿（Order Draft）”。
  > 2. 该工具执行后，并不是直接发往交易所，而是调用风控系统的接口，检查是否违规（如自买自卖、资金超限）。
  > 3. 随后触发一个物理界面的多因素认证（MFA），必须由持有交易牌照的人类交易员输入独立密码（或者点击确认）后，指令才真正生效下发。

## 五、金融业务与业务场景

### 1. 金融基础追问
- 你为什么选择金融 Agent 方向？
  > **回答：** 首先，我有金融和量化实习背景，懂业务。其次，金融场景是为数不多的**“高价值密度+高支付意愿+高度数据化”**的场景，AI 在这里能直接帮人赚钱或省钱。最后，金融场景容错率极低，这对 Agent 的工程架构（如并发、风控、一致性）提出了极高的挑战，我觉得解决这些 Hard Problems 非常有成就感。
- 你对股票、ETF、可转债、期货、基金分别了解多少？
  > **回答：** （按实际情况答，例如：）我在华福证券做过可转债多因子系统，熟悉其“下有保底、上不封顶”的期权特性和溢价率计算。我个人开发过 ETF 监控系统，知道 ETF 是行业趋势的最佳代理工具。期货带有高杠杆和到期交割属性，适合 CTA 趋势跟踪；股票和公募基金是底层资产，我看过财报，懂基本面的估值逻辑（PE/PB）和技术面指标。
- ETF 成分股异动监控有什么业务价值？
  > **回答：** ETF 代表了一个板块的整体动向。当某个行业（如半导体）的 ETF 突然异动时，究竟是因为龙头股出利好带动的，还是整个板块的成分股都在共振上涨？监控成分股能让投研人员**剥离指数表象，看清资金流入的真实结构**，从而快速挖掘出真正有潜力的个股或判断行情的持续性。
- 可转债和普通债券、股票有什么区别？
  > **回答：** 可转债是具有“期权属性”的债券。在股价下跌时，它有债券的票面面值和利息作为底价保护（债性）；在股价大幅上涨时，它可以通过转股分享正股上涨的红利（股性）。与股票相比，它在熊市更抗跌；与普通债券相比，它在牛市有极高的向上弹性。
- 量化投资中常见的收益和风险指标有哪些？
  > **回答：** 
  > - **收益指标**：年化收益率、超额收益（Alpha）、基准收益（Beta）、胜率（Win Rate）、盈亏比（Profit/Loss Ratio）。
  > - **风险指标**：最大回撤（Max Drawdown）、年化波动率（Volatility）、夏普比率（Sharpe Ratio）、卡玛比率（Calmar Ratio）、信息比率（Information Ratio）、VaR（在险价值）。
- 夏普比率、最大回撤、VaR、ES 分别是什么？
  > **回答：** 
  > - **夏普比率 (Sharpe Ratio)**：衡量承担每单位总风险所产生的超额回报。公式是（年化收益率 - 无风险利率）/ 年化波动率。越高越好。
  > - **最大回撤 (Max Drawdown)**：策略在历史任意顶点到其后最低点的最大跌幅，衡量策略可能面临的最极端亏损情况。
  > - **VaR (Value at Risk, 在险价值)**：在一定置信水平下（如95%或99%），某一资产组合在未来特定时间段内的最大可能损失。
  > - **ES (Expected Shortfall, 预期尾部损失)**：也叫 Conditional VaR，指在损失超过 VaR 的极端情况下，预期损失的平均值。它比 VaR 更能反映极端尾部风险。
- 金融数据有哪些常见类型？
  > **回答：** 
  > 1. **结构化数据**：行情数据（高频 Tick、日线 OHLCV）、基本面数据（财务报表三大表、市盈率 PE）、宏观经济数据（GDP、CPI、M2）。
  > 2. **非结构化数据**：新闻资讯、券商研报文本、财报附注（MD&A）、社交媒体评论、政策文件、公司高管电话会纪要（Transcript）。
  > 3. **另类数据 (Alternative Data)**：卫星图像（看工厂开工）、信用卡消费记录、电商平台销量爬虫数据。
- 行情数据、基本面数据、新闻舆情、研报数据分别适合 Agent 做什么？
  > **回答：** 
  > - **行情数据**：适合做本地量化特征提取，或者封装为 Tool 供 Agent 查询最近涨跌幅以辅助归因。
  > - **基本面数据**：适合封装为 SQL 数据库让 Agent 用 Text-to-SQL 查询，或者直接提取关键指标做个股质地过滤。
  > - **新闻舆情**：适合接入 NLP 模型做实时情绪打分（Sentiment Analysis），捕捉短期市场热点。
  > - **研报数据**：适合通过 RAG 向量检索，作为长篇大论的“专家外脑”，辅助生成深度行业分析报告。
- 金融场景中数据延迟、数据错误会带来什么风险？
  > **回答：** 金融的核心是信息差。
  > 1. **数据延迟**：导致“刻舟求剑”。比如 Agent 拿昨天的新闻来解释今天的异动，或者基于过期的价格下了市价单，直接导致滑点巨大甚至交易失败。

  > **回答：** 熟悉。开发新功能时通过 `git checkout -b feature/xxx` 创建分支，完成后通过 Pull Request / Merge Request 提交代码。会使用 `git rebase` 保持提交历史整洁，并理解通过 CI/CD 自动跑单测和 Linter 检查的基本流程。

### 2. 数据与存储
- 金融时间序列数据怎么存？
  > **回答：** 
  > 1. **Parquet / Feather**：适合离线的回测和特征工程，支持高效的列式读取。
  > 2. **时序数据库（Time-Series DB，如 DolphinDB, InfluxDB, QuestDB）**：适合实盘高频 Tick 数据的实时写入和快速切片聚合（如算 5 分钟 K 线）。
  > 3. **关系型数据库（MySQL/PostgreSQL）**：只适合存低频数据（如日频因子表），不适合存高频序列。
- 向量数据库和关系型数据库分别适合存什么？
  > **回答：** 
  > - **向量数据库（如 Milvus, Pinecone）**：只存高维向量和少量的 Metadata。适合存研报段落、新闻文本的 Embedding，用于语义相似度搜索。
  > - **关系型数据库（如 MySQL）**：存结构化、有严格关联关系的数据。适合存交易订单明细、用户账号信息、量化因子数值表、Agent 的对话上下文记录等。
- Agent Memory 可以存 SQLite、Redis、向量库还是对象存储？
  > **回答：** 都可以，取决于场景：
  > 1. **SQLite/MySQL**：存短期 Memory（如 LangGraph 的 Checkpoint 和对话记录 `messages`），结构化强。
  > 2. **Redis**：存高并发场景下的极短期 Memory 或 Tool Cache，读写极快但易丢失。
  > 3. **向量库**：存 Long-term Memory。比如用户一年前提过的偏好，需要通过相似度检索才能回想起来。
  > 4. **对象存储（S3/OSS）**：存 Memory 附带的原始大文件（如用户上传的年报 PDF）。
- 如果要存储对话历史，表结构怎么设计？
  > **回答：** 一个核心的 `messages` 表设计：
  > - `id`: 主键 UUID
  > - `session_id`: 关联的会话 ID
  > - `user_id`: 关联的用户 ID
  > - `role`: 枚举类型（user, assistant, tool, system）
  > - `content`: 文本内容
  > - `tool_calls`: JSON 字段（存放调用的函数名和参数）
  > - `created_at`: 时间戳
- 如果要存储工具调用 trace，表结构怎么设计？
  > **回答：** 
  > - `trace_id`: 跟踪这一次 Agent Loop 的全局 UUID
  > - `step_id`: 当前执行步数的序号
  > - `tool_name`: 工具名
  > - `input_params`: JSON，记录传给工具的具体参数
  > - `output_result`: JSON，记录工具的返回结果
  > - `latency_ms`: 耗时
  > - `status`: success / failed (带 Error Traceback)
- 如果要支持多用户隔离，数据模型怎么设计？
  > **回答：** 
  > 1. **数据库层面**：所有的业务表（对话表、Agent 配置表）必须带上 `tenant_id` 或 `user_id` 字段，后端接口查询时强制拼上 `WHERE user_id = ?`。
  > 2. **向量库层面**：在存入 Embedding 时，将 `user_id` 写入 Metadata，检索时使用 Metadata Pre-filtering 保证只搜该用户的数据；或者为每个企业大客户建立独立的 Namespace / Collection 做到物理隔离。
- 如果知识库文档不断更新，索引怎么增量更新？
  > **回答：** 
  > 1. **文档防重**：根据源文件的 Hash 或最后修改时间（Mtime）判断是否需要更新。
  > 2. **Upsert 机制**：大多数向量库支持 Upsert（带主键覆盖）。当文档更新时，先根据文档的 ID 删除旧的 Chunks 向量，再将新切分的 Chunks 向量化后写入，保证知识不重复、不冲突。
- 如果上下文太长，怎么做压缩和摘要？
  > **回答：** 
  > 1. **滑动窗口（Sliding Window）**：只保留最近的 N 轮对话，丢弃最老的。
  > 2. **总结替换（Summarization）**：当 Token 接近阈值时，专门起一个小模型（如 GPT-4o-mini），把前 10 轮对话压缩成一句 Summary（“之前讨论了某公司的财务问题，得出了结论 X”），用这条 Summary 替换掉原本的 10 轮原始 Message。

### 3. 稳定性与性能
- Agent 系统上线后最常见的稳定性问题有哪些？
  > **回答：** 
  > 1. **LLM API 波动**：超时、502、速率限制（Rate Limit/429）。
  > 2. **解析失败**：模型不遵守 JSON 格式输出，导致后续反序列化代码直接抛异常崩溃。
  > 3. **死循环**：Agent 调错工具 -> 报错 -> Agent 再次用同样的错误参数调工具，陷入死循环吃光 Token。
  > 4. **外部数据源挂掉**：如行情接口突然返回空数据或格式改变。
- LLM 接口超时怎么办？
  > **回答：** 
  > 1. **代码级重试**：用 `tenacity` 捕获 `TimeoutError` 进行指数退避重试。
  > 2. **模型 Fallback**：如果主模型（如 Claude-3.5-Sonnet）持续超时，捕获异常后无缝切换到备用模型（如 GPT-4o）。
  > 3. **异步/流式输出**：前端改用 WebSocket/SSE，后端一旦拿到第一个 Token 就推给前端，防止前端因为长时间没收到完整 HTTP Response 而断开连接。
- 工具调用失败怎么办？
  > **回答：** 
  > 1. 如果是**网络问题**，依靠底层框架自动重试。
  > 2. 如果是**参数错误**（比如该传数字传了字符串），通过 Pydantic 捕获错误，将 Error Message 打包发回给 LLM，要求它自我修正（Self-Correction）后重新调用。
  > 3. 如果多次重试后仍然失败，终止调用链，返回一个优雅的空载体，并告知用户“抱歉，暂时无法获取该数据”。
- 如何设计重试、熔断和降级？
- 如果用户并发请求很多，系统怎么扩展？
  > **回答：** 
  > 1. **无状态服务扩展**：把 Agent 的业务逻辑封装成无状态（Stateless）的 Docker 容器，通过 Kubernetes 进行水平扩容（Horizontal Pod Autoscaling）。
  > 2. **异步队列**：对于耗时较长的 Agent 任务（如深度研报总结），不能用同步 HTTP 接口，而是把任务扔进 Redis/RabbitMQ 队列，由后端的多个 Worker 异步消费执行。
  > 3. **API 负载均衡**：接入多个 LLM API 渠道（如 Azure、AWS 和原生 OpenAI），通过 LiteLLM 这样的网关做智能路由和 Fallback，防止单点被打挂。
- 如果多个 Agent 并行执行，怎么控制成本和延迟？
  > **回答：** 
  > 1. **模型分级**：不是所有任务都需要最强大的模型。将需要高智商逻辑推理的（如 Debate）交给 Claude 3.5 Sonnet，将信息提取和排版的工作交给成本只有 1/10 的 Claude 3 Haiku。
  > 2. **共享缓存**：使用 Semantic Cache（如 Redis 结合 Embedding），如果两个 Agent 提了几乎一样的问题，直接返回缓存。
  > 3. **并发优化**：使用 `asyncio.gather` 同时拉起所有无依赖的子任务（Fan-out），极大降低总体墙上时间。
- 如何缓存 LLM 输出或工具结果？
  > **回答：** 
  > 1. **Exact Match（精确匹配）**：对于工具结果（如查昨天茅台的收盘价），可以根据 `函数名+参数` 生成哈希值作为 Redis 的 Key，直接存 24 小时。
  > 2. **Semantic Cache（语义缓存）**：对于 LLM 输出，用户的提问可能只是差了一个字（“茅台业绩如何”与“茅台财报怎么样”）。可以通过向量化问题，如果在向量库中找到相似度 > 0.95 的记录，直接返回历史生成的答案。
- 如何监控 Agent 的任务成功率？
  > **回答：** 需要一套**可观测性（Observability）**平台。
  > 定义成功的标准（比如是否给出了明确的分析结论，或者用户是否点击了“采纳”）。在日志中记录每一笔任务的最终状态（Success / Fail / User-Rejected）。在数据大盘（如 Grafana 或 Langfuse 面板）上，计算 `(成功任务数 / 总任务数) * 100%`，并监控失败报错 Top 10 的异常类型。
- 如何定位一次 Agent 执行失败的原因？
  > **回答：** 通过**全局 Trace ID**。在每次用户请求发起时生成一个唯一的 Trace ID，整个流转过程（API 路由、RAG 检索、Agent 思考、Tool 调用）的日志全部带上这个 ID。一旦报错，在 Kibana 或 Langfuse 中输入 Trace ID，就能看到一棵清晰的调用树（Trace Tree），一眼看出是检索失败、大模型幻觉还是外部 API 超时。
- Langfuse、OpenTelemetry 或自建日志系统可以记录哪些信息？
  > **回答：** 
  > 可以记录一棵完整的 **Trace Tree**：
  > 1. **Metadata**：模型名称、Token 消耗（Input/Output）、耗时（Latency）、用户 ID。
  > 2. **Prompts & Completions**：渲染变量后的最终 Prompt 和模型的原生回复。
  > 3. **Spans（步骤跨度）**：如 RAG 步骤中，检索词是什么，召回了哪几个 Document，耗时多久。
  > 4. **Scores/Feedback**：用户对这条回答的打分（如点赞/踩）。

## 八、开放式应变题

### 1. Agent 设计题
- 假设要给基金经理做一个每天早上 8 点的市场晨报 Agent，你会怎么设计？
  > **回答：** 
  > 1. **Cron 触发**：基于 `apscheduler` 设定每天凌晨运行。
  > 2. **数据收集（并发）**：调用工具拉取隔夜美股走势、外汇汇率、大宗商品价格、最新的宏观数据以及当晚重点公司的公告。
  > 3. **内容生成**：将收集到的数据分组喂给 LLM，严格要求按“隔夜外盘概览”、“重大宏观事件”、“今日核心股票池”三个模块输出。
  > 4. **投递**：将 Markdown 转化为图文卡片，推送到基金经理的企微/钉钉，甚至调用 TTS 接口生成一段 1 分钟的音频播报。
- 假设要给银行客户经理做一个客户资产诊断 Agent，你会怎么设计？
  > **回答：** （与上文相似）分为画像读取、资产量化分析（收益、回撤）、诊断生成（结合最新市场风格点评当前资产的健康度）与持牌人工复核下发四步。重点强调系统只生成“诊断草稿”，由客户经理审批。
- 假设要给量化研究员做一个自动因子挖掘 Agent，你会怎么设计？
  > **回答：** 
  > 1. **灵感生成**：读取最新的量化研报，Agent 根据摘要提取一个新因子（如“高频动量反转”）。
  > 2. **代码生成（Code Agent）**：将因子逻辑转化为 Pandas 运算代码。
  > 3. **沙盒回测（Test Agent）**：在隔离的 Docker 容器中拉取历史数据运行这段代码，如果报错或者遇到 `NaN` 问题，捕获错误交还给 Code Agent 修复。
  > 4. **评估**：计算出 IC、IR 达标后，自动生成一份“因子测试报告”邮件发给研究员。
- 假设要做一个自动生成投研 PPT 的 Agent，你会怎么设计？
  > **回答：** 
  > 大模型写纯文本容易，画图排版难。
  > 1. **大纲 Agent**：先根据研报提炼出 PPT 的章节结构（目录）。
  > 2. **内容 Agent**：针对每一页，抽取 3 个核心 Bullet Points。
  > 3. **图表 Agent**：针对需要数据的页面，提取数值，调用 Echarts/Plotly 工具生成图表截图。
  > 4. **组装**：通过 Python 的 `python-pptx` 库，把文本和截图按照公司固定的模板母版（Template）自动渲染成 `.pptx` 文件，而不是让 LLM 去生成难以控制的排版代码。
- 假设要做一个跨数据库查询和解释的金融数据 Agent，你会怎么设计？
  > **回答：** 
  > 这是一个典型的 Text-to-SQL + LLM 的结合场景。
  > 1. 用户提问：“平安银行去年利润多少？”。
  > 2. **Schema 检索器**：先从系统查出财务数据库的表结构（Schema）和字段定义。
  > 3. **SQL 生成与执行**：LLM 生成安全的 SQL 并在隔离环境中执行，获取数值。
  > 4. **二次处理**：如果还需要跨行情库查询价格，再去生成另一条 SQL。
  > 5. **整合**：最后 LLM 拿着两个库查出的真实数字，生成口语化的回答给用户。
- 假设要做一个可以自动写 SQL、查数据、画图、解释结论的 Agent，你会怎么设计？
  > **回答：** （综合上两题的设计思路，基于 LangGraph 工作流串联起来即可）。
- 假设用户输入「帮我找最近可能受益于降息的 ETF」，Agent 应该怎么拆任务？
  > **回答：** 
  > 1. **知识转化**：降息利好哪些板块？（调用 RAG 检索宏观研报，得出“房地产、券商、创新药”等）。
  > 2. **标的查询**：在本地 ETF 库中，查询属于上述板块的活跃 ETF 代码（如 512880, 512200）。
  > 3. **状态分析**：调用行情接口，获取这些 ETF 近期的资金流入（份额变动）和涨跌幅。
  > 4. **汇总回答**：“基于宏观逻辑，降息通常利好 X 板块。对应市场上的 ETF 有 A、B、C，近期 A 的资金流入最为明显……”
- 假设用户输入「帮我分析某公司是否值得长期持有」，Agent 应该如何控制回答边界？
  > **回答：** 
  > 绝对禁止回复“值得”或“不值得”。Agent 应该将其转换为客观事实的罗列：“基于您的需求，我为您从护城河、财务健康度、行业前景三个维度梳理了该公司的基本面事实：[事实1...][事实2...]。至于是否长期持有，需要您结合上述信息自行判断。”

### 3. 业务判断题
- 如果金融客户说「我们不关心技术，只要准确率高」，你怎么回应？
  > **回答：** 我会引导客户重新定义“准确率”。在金融场景，LLM 裸跑的“准确率”是不可靠的，即使目前测出 99% 也可能在黑天鹅事件中归零。我会向客户说明：我们真正提供的是**高可靠性的工程架构（如 RAG + Multi-Agent 交叉复核 + 硬规则熔断）**。技术的目的不是炫技，而是为这个“准确率”加上安全锁，保证在极端情况下也能优雅降级而不犯致命错误。
- 如果客户要求 Agent 直接给交易指令，你怎么处理？
  > **回答：** 
  > 1. **合规红线**：明确拒绝，说明金融监管（如证监会投顾新规）严禁未经持牌人员复核的 AI 直接生成买卖指令。
  > 2. **替代方案**：向客户建议，Agent 可以输出多维度的“打分卡（Scorecard）”或“量化信号（Signal）”，但最终的 Action 按钮（Approve/Reject）必须由有资质的交易员人工点击。
- 如果一个 Agent 方案技术上很酷但业务价值不明确，你怎么判断是否继续做？
  > **回答：** 作为偏落地的工程师或产品，我会果断**叫停或转为业余探索**。金融场景是高度结果导向的。判断标准是算一笔账：这个很酷的方案能替代几个实习生的人力？能把夏普比提高 0.1 吗？如果都不能，仅仅是多用了两个最新的花哨框架，它就不应该进入核心主线（Main Branch）。
- 如果一个工作流 80% 可以自动化、20% 必须人工判断，你怎么设计产品形态？
  > **回答：** 设计为**Copilot（副驾驶）模式**，而不是 Auto-Pilot。
  > 那 80% 的脏活（拉数据、清洗、排版、初步归因）让系统在后台静默运行。那 20% 的关键节点（如定性评判风险、最终一键下发指令），在 UI 界面上做成醒目的高亮卡片（Highlights），强制要求人类用户填写意见并点击确认。
- 如果 Agent 只能节省 10% 时间，但显著降低错误率，这个需求值不值得做？
  > **回答：** **非常值得**。在金融（如风控审查、交易下单、合规发文）场景中，防错的价值远大于效率。一次“乌龙指”或研报数据错误导致的声誉和资金损失，可能远超几十个人的全年工资。降低错误率本身就是金融产品的核心护城河。
- 如果老板要求快速做 demo，但你担心金融合规风险，你怎么平衡？
  > **回答：** 
  > 1. **物理隔离环境**：在断网或无权限的沙盒环境（如脱敏数据集上）做 Demo，不连接真实的订单 API 和未脱敏的客户数据库。
  > 2. **免责声明与水印**：在 Demo 的 UI 的每一个角落打上巨大的“Beta版本，切勿作为真实投资依据”的水印。
  > 3. **汇报策略**：在演示时，明确指出这只是技术可行性（POC）验证，正式上线前还有哪些必不可少的合规卡点需要跨越。
- 如果客户现场提出一个你没准备过的金融场景，你怎么快速拆解？
  > **回答：** 
  > 遵循从宏观到微观的框架：
  > 1. **数据在哪里**（输入是什么，内部系统有无现成接口，外部需要抓取什么）？
  > 2. **原有 SOP 是什么**（人工目前是怎么处理的，最耗时的是找数据还是写报告）？
  > 3. **能否被 AI 介入**（是算数题还是归纳题，如果是算数题就用工具代码代劳，如果是归纳题再上 LLM）？
  > 4. **验收标准是什么**（客户觉得什么样算是做好了，可以拿它替代人）？

## 九、反问与收尾

- 你觉得自己在这个岗位上最大的优势是什么？
  > **回答：** 我的优势是“懂业务+全栈开发+Agent架构经验”。我不仅在华福证券量化组实习懂因子和金融术语，还能手写 Python/Flask 和前端把功能做出来，并且在个人项目中完整落地了基于 LangGraph 和 RAG 的多 Agent 金融决策流。我不仅能写出调包代码，更知道这个 Agent 做出来能不能用在真实投研里。
- 你觉得自己最大的短板是什么？
  > **回答：** （坦诚作答）在极大并发量（如 10万+ QPS）的企业级微服务架构优化，以及自建千亿参数大模型底座（Pre-training）方面经验不足。我目前更偏向于大模型应用层（App Layer）的工程组装和业务落地。但我学习能力极强，希望能在公司向资深架构师请教。
- 如果入职后第一个任务是调研 AgentSwarm，你会怎么做？
  > **回答：** 
  > 1. **文献与产品扫描**：快速通读 OpenAI 的 Swarm 框架源码和其他主流群智框架（如 CAMEL、MetaGPT）。
  > 2. **提炼核心机制**：重点研究去中心化 Agent 是如何进行 Hand-off（交接）和状态转移的。
  > 3. **结合公司业务**：思考这种模式能不能用在公司现有的高并发任务中（如海量财报并发抽取）。
  > 4. **输出产物**：输出一份带有 Demo 源码、框架优缺点对比表及业务落地建议的调研报告。
- 如果入职后第一个任务是复现一个 Agent 论文，你会怎么做？
  > **回答：** 
  > 1. **通读原文**：提炼论文最核心的创新点（是改变了 Prompt 还是优化了路由）。
  > 2. **找平替环境**：如果论文是在某个特定大模型（如旧版 Llama）上测的，我会先用当前最稳定且便宜的 API（如 GPT-4o-mini）来跑通基础链路。
  > 3. **复现核心代码**：不抄无用的装饰代码，直接剥离出论文最核心的伪代码逻辑并在本地运行。
  > 4. **评估效果与汇报**：对比论文声称的提升和我在本地实测的结果，判断这篇论文是“实验室神作”还是真的能在公司投研体系里落地。
- 如果入职后第一个任务是把你的 ETF Agent 改成公司内部 demo，你会怎么做？
  > **回答：** 
  > 1. **评估对接环境**：申请公司内网的大模型 API Token 和金融数据源接口权限。
  > 2. **剥离重构**：将我代码中的 `akshare` 和外网 `OpenAI` 替换为公司提供的工具接口和私有模型网关。
  > 3. **产品化包装**：花半天时间用 Streamlit 或 Flask 写一个漂亮的极简网页，只要用户输入一个行业 ETF 代码，就能在几秒内吐出一份格式精美的异动归因排版，确保 Demo 有直观的可玩性（Show, don't tell）。
- 你希望在实习期间重点提升研究能力、工程能力，还是业务理解？
  > **回答：** 我希望重点提升**工程能力和业务理解的结合**。研究能力在学校可以通过看论文训练，但在真实的金融环境里，如何把一个 Demo 做成高并发、低延迟、符合合规要求且能真正替业务部门省下钱的生产级系统，是在公司里最宝贵的经验。我希望能打通从 Idea 到企业级上线的全流程。
