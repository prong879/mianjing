### 十、综合题与案例题

#### 1. 如果题目不完整，面试时应该怎么处理？

**参考答法**：

很多业务题和 SQL 题在面试里本来就不会给得特别完整，这时候不能卡住不动，而是要主动补齐假设。

标准做法是：

1. 先复述你对题目的理解
2. 说明你准备补哪些必要假设
3. 在假设清楚后给出分析或 SQL 解法

例如可以说：

> 这个题目里没有完全说明表结构，我先做一个常见业务场景假设：有用户表、订单表和行为表，然后我按这个口径来写解法。如果您的表结构不同，我也可以再调整。

这类表达会让面试官觉得你具备真实工作中的问题拆解能力。

#### 2. 开放题回答的通用结构

面对产品分析、增长分析、功能评估题时，可以优先套下面这个结构：

1. 先定义问题
2. 再拆目标指标
3. 然后拆过程路径
4. 再看分群差异
5. 最后给出结论和建议

这样回答会比“想到哪说到哪”更像真正的数据分析师。

#### 3. 指标搭建 case：围绕“网易云音乐会员收入”搭建指标体系

**参考答法**：

这类题最关键的是先把核心指标拆成公式，再围绕公式逐层下钻。

**第一层：先拆核心公式**

> 会员收入 = 付费会员人数 × 客单价

所以体系至少要围绕这两部分展开。

**第二层：拆付费会员人数**

付费会员人数又可以继续拆成漏斗：

> 付费会员人数 = 触达用户数 × 进入会员页率 × 下单转化率 × 支付成功率

如果业务更贴近日活，也可以说：

> 付费会员人数 = 日活用户数 × 会员购买渗透率

**第三层：拆客单价**

客单价可以看：

- 套餐结构
- 月卡 / 季卡 / 年卡占比
- 折扣活动力度
- 新客首购价与老客续费价
- 捆绑包、联合会员等高客单产品占比

**第四层：补充关键过程指标**

- 日活用户数
- 会员页曝光人数
- 点击率
- 详情页到下单页转化率
- 支付成功率
- 首购人数
- 续费人数
- 自动续费开通率
- 退款率

**第五层：护栏和质量指标**

- 用户投诉率
- 取消续费率
- 会员内容使用率
- 会员留存率
- 会员满意度

一句话总结：

> 我会先把会员收入拆成“人数 × 客单价”，再把人数拆成从日活到付费转化的漏斗，把客单价拆成套餐和价格结构，这样既能分析收入波动，也能定位优化抓手。

#### 4. 简历深挖高频问法：上一段实习如何做指标搭建和异常分析？

**参考答法结构**：

1. 先说业务背景和核心目标
2. 说明你定义了哪些核心指标
3. 说明你如何拆解异常
4. 说明最终定位出的原因
5. 说明你提出了什么优化建议

一个比较稳的模板是：

> 当时业务方发现核心指标出现波动，我先确认口径和数据链路没有问题，再把总指标拆成流量、转化、留存或供给几个环节，逐层看是哪个环节出了问题。定位原因后，我又做了分群和分渠道分析，最后把结论和可执行建议同步给业务方。

#### 5. 项目深挖题：简历里的比赛或建模项目一般会怎么追问？

常见追问包括：

- 项目的业务背景是什么？
- 你的个人贡献是什么？
- 为什么选这个模型？
- 特征工程是怎么做的？
- 模型好坏如何评估？
- 项目有哪些局限？可以怎么改进？

如果要答得更强，建议把项目讲成这条线：

> 业务问题定义 -> 数据来源与清洗 -> 特征工程 -> 模型选择 -> 评估指标 -> 结果解释 -> 改进方向

#### 6. 电商实习深挖题：如何回答“某品类复购率提升 `8%` 是独立贡献还是团队成果”？

**参考答法**：

这类题不是单纯问功劳归属，而是在看你是否能**准确表达个人贡献边界**。

更稳的回答方式是：

> 这是团队项目的结果，但我负责了其中比较核心的一部分分析工作。比如我主要负责复购率口径确认、用户分层、复购链路拆解，以及相关分析结论输出。最终复购率提升是团队共同推动的结果，但我在定位问题和提出优化方向上有较明确的个人贡献。

这样答的好处是：

- 不会把团队成果全说成自己做的
- 也不会把自己说得毫无贡献

#### 7. 电商实习深挖题：如何展开讲“用户购买路径优化”和“大促指标体系搭建”？

**参考答法**：

这类题要避免说得太空，最好按“背景 - 做法 - 结果”来讲。

**用户购买路径优化**可以这样说：

1. 背景：业务方希望提升从浏览到支付的转化效率
2. 做法：
   - 先把购买路径拆成曝光、点击、详情页访问、加购、下单、支付几个环节
   - 定位哪个环节流失最高
   - 再做人群、品类、渠道分层
   - 最后提出优化建议，例如调整推荐位、优化详情页信息、优化促销表达
3. 结果：
   - 某环节转化率提升
   - 加购率、支付转化率或复购率改善

**大促指标体系搭建**可以这样说：

1. 先明确核心目标，比如 `GMV`、订单量、用户数、转化率
2. 再拆成流量、转化、客单价、供给、履约五层
3. 设定实时监控和日维度复盘指标
4. 明确异常预警口径和节奏

一句话总结：

> 大促指标体系不是简单堆很多指标，而是围绕核心目标，把流量、转化、客单价、履约等关键环节串起来，保证能监控、能预警、能复盘。

#### 8. 电商项目题：校园项目“用户分群”和实习中“电商用户行为分析”在特征选取上有什么不同？

**参考答法**：

可以从“目标不同，所以特征不同”来回答。

**校园项目里的用户分群**通常更偏方法练习或画像分析，所以特征可能偏通用，例如：

- 活跃频次
- 使用时长
- 访问次数
- 互动次数
- 基础人口属性

**电商实习里的用户行为分析**会更贴近交易目标，所以特征会更强调：

- 浏览、点击、加购、收藏、下单、支付等链路行为
- 客单价
- 购买频次
- 复购周期
- 品类偏好
- 优惠敏感度
- 活动参与度

更像面试现场的总结可以说：

> 校园项目更偏“把用户分开看”，电商实习更偏“围绕交易目标选特征”，所以会更强调转化链路、消费能力和复购行为。

#### 9. 电商项目题：除了日常 `GMV` 监控看板，你做过类似 `618` 大促的专题分析吗？

**参考答法**：

如果你做过类似分析，可以按这个框架讲：

1. 大促前：
   - 看品类准备度
   - 看库存、价格、活动报名情况
   - 预估核心指标目标
2. 大促中：
   - 实时监控 `GMV`、订单量、支付转化率、客单价、流量来源
   - 对重点品类、重点会场做追踪
3. 大促后：
   - 做人群复盘、品类复盘、渠道复盘
   - 看哪些策略有效，哪些资源浪费了

如果没做过完全同量级的大促，也可以这样答：

> 虽然我未必做过和 `618` 完全同量级的项目，但我做过活动/专题分析，思路上会先围绕核心目标拆指标，再做前中后分阶段监控和复盘，这个方法在大促分析里也是通用的。

#### 10. 电商岗位常见问法：你的核心优势是什么？你说的“分析框架”具体指什么？

**参考答法**：

可以把优势落在三个点上：

1. **业务理解快**：能快速把业务问题转成指标问题
2. **分析框架清晰**：知道怎么拆指标、拆路径、拆人群
3. **落地意识强**：不仅分析问题，还能提出可执行建议

如果面试官追问“分析框架具体是什么”，可以直接举电商漏斗模型：

> 例如在电商场景里，我常用漏斗模型把用户路径拆成曝光、点击、详情页访问、加购、下单、支付。先看总转化，再看每一步转化率，定位损失最大的环节，然后继续按用户、品类、渠道分层，最终找到最值得优化的点。

#### 11. 电商岗位常见问法：希望从京东实习收获什么？

**参考答法**：

这类题不要只说“学到很多东西”，更好的答法是把收获说具体：

> 我希望一方面能把自己在电商分析、数据看板和专题分析上的经验进一步系统化，真正参与到大型电商业务里；另一方面也希望提升自己把分析结果转成业务动作的能力，比如在大促、用户运营、品类运营这些场景里做更有业务价值的分析。

#### 12. 电商岗位常见问法：请做一个简短的自我介绍

**参考答法模板**：

> 您好，我目前主要聚焦数据分析方向，过去有过电商相关实习和校园分析项目经历。实习中我主要做过日常经营指标监控、专题分析、用户行为分析以及看板搭建；项目中也做过用户分群和数据建模相关工作。相较于单纯做数据处理，我更擅长把业务问题拆成指标和分析框架，再结合 SQL 和 Python 做验证，希望后续能在更贴近业务决策的场景里继续积累经验。

#### 13. 你上一段实习中，主要负责哪些工作？

**参考答法**：

这类题建议按“监控 - 分析 - 输出 - 协同”四类去答。

例如可以说：

> 我上一段实习主要做四类工作。第一是日常指标监控和看板维护，比如核心经营指标、转化漏斗和活动数据的跟踪；第二是专题分析，例如用户行为分析、某个品类或活动复盘；第三是数据提取和清洗，使用 SQL 和 Python 支持分析过程；第四是和业务方沟通需求，把分析结果整理成报告或看板，支持后续决策。

#### 14. 在上一段实习里，如果只选一个指标来衡量转化结果，你会选什么？

**参考答法**：

这类题不要一上来就报一个指标名，最好先说明“看业务目标”。

更稳的说法是：

> 如果是电商或交易场景，我通常会优先看支付转化率，或者更直接一点看最终成交转化，因为它比点击、加购更接近真实业务结果。  
> 但如果面试官允许我补充，我会说单看一个指标其实不够，最好和漏斗中的前置指标一起看，这样才能知道问题发生在哪一步。

#### 15. 如果同时收到多个部门的需求，你会怎么处理？

**参考答法**：

这题本质上在看你的优先级判断和沟通能力。

我一般会按四个维度排优先级：

1. **业务影响大小**
   - 是否影响核心指标、重要活动或管理层决策
2. **时效性**
   - 是不是今天必须给，是否卡住别人的工作流程
3. **需求清晰度**
   - 需求是否明确，口径是否统一
4. **投入产出比**
   - 花多长时间，能带来多大价值

处理方式上，我会：

- 先和需求方确认目标和截止时间
- 把需求分类为“紧急重要”“重要不紧急”等
- 对低优先级需求明确排期
- 如果资源真的冲突，就及时同步给带教或负责人做取舍

一句话总结：

> 我不会简单按谁先来就先做，而是按业务价值和时效性排序，同时把排期沟通清楚，避免信息不透明。

#### 16. 你简历里提到过数据产品相关工作，请把全流程讲一遍

**参考答法**：

这类题建议按“需求提出 -> 方案设计 -> 开发上线 -> 验收迭代”来回答。

一个比较标准的流程是：

1. **需求理解**
   - 和业务方确认问题是什么、为什么要做、希望解决什么
2. **指标和口径确认**
   - 明确核心指标、维度、统计口径、更新频率
3. **原型或方案设计**
   - 设计报表结构、页面逻辑、交互方式、下钻路径
4. **数据准备**
   - 确认数据源、字段、表结构以及是否需要新建宽表
5. **开发与联调**
   - 和数据开发、BI、产品或研发协同推进
6. **验收测试**
   - 核对指标正确性、边界情况、权限问题
7. **上线与反馈**
   - 收集业务使用反馈，继续优化

更像面试现场的表达可以说：

> 我理解数据产品工作不只是做一个页面，而是把业务问题抽象成指标和功能，再通过数据链路、看板结构和迭代机制让业务真正用起来。

#### 17. 有没有做过专题分析？分析了什么，最后以什么结果结尾？

**参考答法**：

这类题最好按一个完整案例讲，不要只说“我做过很多专题”。

推荐结构：

1. 问题背景是什么
2. 你看了哪些数据
3. 你如何拆解问题
4. 最终发现了什么
5. 给了什么建议
6. 后续结果如何

一个通用模板是：

> 我做过一次围绕用户转化或某个活动效果的专题分析。当时业务方发现核心指标低于预期，我先确认口径和数据质量，再把问题拆到流量、点击、转化和用户分层几个层面，最后发现主要问题集中在某个环节或某类用户。基于这个结论，我提出了优化建议，并通过后续数据验证，看到关键指标有所改善。

#### 18. 业务专题题：业务给你一个专题分析，一周内完成，你会怎么开展？

**参考答法**：

一周内完成专题分析，关键是先对齐目标和交付物，避免一开始就陷入无边界取数。

可以按时间节奏回答：

1. **第 1 天：明确问题和口径**
   - 和业务方确认背景、目标、核心问题
   - 明确最终交付形式：报告、看板、策略建议还是复盘
   - 确认指标口径、分析范围、时间周期和优先级
2. **第 2 天：搭建分析框架**
   - 把问题拆成核心指标、过程指标、维度下钻
   - 画出指标拆解树或业务链路
   - 确认需要哪些数据表和字段
3. **第 3-4 天：取数和分析**
   - 做数据清洗和口径校验
   - 按时间、人群、渠道、地区、商品/内容等维度下钻
   - 找到主要贡献因素和异常点
4. **第 5 天：验证和补充分析**
   - 做交叉验证、对照组、同期对比或分群验证
   - 和业务方同步初步结论，确认是否符合业务事实
5. **第 6-7 天：输出和复盘**
   - 形成结论、证据、建议和风险提示
   - 给出后续监控指标和验证方案

一句话总结：

> 一周专题分析要先控范围，再搭框架，最后用数据证据支持结论；不要只堆图表，要输出业务能采取的动作和后续验证方式。

#### 19. 得物这类岗位常见反问可以怎么问？

**参考答法**：

反问可以尽量围绕“工作内容、协作方式、成长空间”来问，例如：

1. 实习生主要负责的内容是什么？更偏日常监控、专题分析还是数据产品支持？
2. 这个岗位主要对接哪些部门？更偏业务侧还是中台侧？
3. 团队目前最看重实习生的哪项能力？是业务理解、SQL、看板能力，还是沟通推进？
4. 入职后前一两个月，通常会先接触哪些类型的任务？

#### 20. 出行岗位常见问法：简历深挖时如果追问“指标监控体系”，怎么答？

**参考答法**：

出行场景里可以把监控体系拆成几层：

1. **供给侧**
   - 在线司机数
   - 接单司机数
   - 司机在线时长
2. **需求侧**
   - 发单用户数
   - 发单量
   - 呼叫成功率
3. **履约侧**
   - 接单率
   - 完单率
   - 取消率
   - 平均应答时长
4. **经营侧**
   - `GMV`
   - 订单量
   - 客单价
   - 补贴率

一句话总结：

> 出行监控体系的核心是把供给、需求、撮合履约和经营结果串起来，这样指标一旦波动，才能快速定位问题出在司机侧、乘客侧还是平台撮合侧。

#### 21. 汽车行业岗位常见问法：请做一个简洁的自我介绍

**参考答法**：

汽车行业的数据分析岗位通常更看重两点：

- 你有没有真实业务分析和落地经验
- 你能不能把分析能力和行业场景结合起来

因此自我介绍最好突出：

1. 过往实习经历
2. 数据分析相关技能
3. 和汽车或复杂业务场景相关的经验
4. 为什么和当前岗位匹配

**参考模板**：

> 您好，我目前主要聚焦数据分析方向，之前有过和业务运营、指标监控、专题分析相关的实习经历，也积累了 SQL、Python、看板搭建和业务分析方面的能力。过往项目里，我更偏向把数据分析和业务落地结合起来，比如围绕销售转化、用户行为、服务体验等问题做指标拆解和归因分析。我比较希望在像蔚来这样强调用户体验和数据驱动的业务环境里，继续提升自己把分析结果转成实际业务动作的能力。

#### 24. 汽车行业 SQL 题：如何计算购车用户 `30` 日留存率？

**参考答法**：

这类题首先要确认“留存”的定义。

在汽车行业里，可以先问清楚是“第 `30` 天留存”还是“购车后 `30` 天内留存”：

- **第 `30` 天留存**：购车第 `30` 天是否有活跃行为
- **`30` 天内留存**：购车后 `1` 到 `30` 天内是否有过活跃行为

活跃行为可以理解为：

- 登录 App
- 浏览社区
- 预约服务
- 使用车主权益
- 售后相关行为

假设有两张表：

`purchase_table`

- `user_id`
- `purchase_date`

`user_event`

- `user_id`
- `event_date`

**写法一：自连接思路**

```sql
select
    count(distinct p.user_id) as purchase_users,
    count(distinct e.user_id) as retained_users,
    round(count(distinct e.user_id) * 1.0 / count(distinct p.user_id), 4) as retention_30d
from purchase_table p
left join user_event e
    on p.user_id = e.user_id
   and datediff(e.event_date, p.purchase_date) = 30;
```

如果面试官定义为“`30` 天内留存”，连接条件可以改成：

```sql
and datediff(e.event_date, p.purchase_date) between 1 and 30
```

**写法二：先去重再按窗口判断**

```sql
with event_d as (
    select distinct
        user_id,
        event_date
    from user_event
)
select
    count(distinct p.user_id) as purchase_users,
    count(distinct case when datediff(e.event_date, p.purchase_date) = 30 then p.user_id end) as retained_users,
    round(
        count(distinct case when datediff(e.event_date, p.purchase_date) = 30 then p.user_id end) * 1.0
        / count(distinct p.user_id),
        4
    ) as retention_30d
from purchase_table p
left join event_d e
    on p.user_id = e.user_id;
```

一句话说明：

> 面试里关键不是只把 SQL 写出来，而是先说明“30 日留存”的业务口径，再选自连接或日期函数的实现方式。

#### 26. 汽车行业经营分析题：如何计算蔚来换电业务经营状况？

**参考答法**：

这类题可以先从经营公式出发：

> 经营利润 = 换电收入 - 换电成本

**收入侧**可以拆成：

> 换电收入 = 换电用户数 × 人均换电次数 × 客单价

也可以按订单口径拆：

> 换电收入 = 换电订单数 × 单次换电收入

其中客单价或单次收入会受以下因素影响：

- 电池型号
- 换电套餐类型
- 用户是否会员
- 换电前后电量差
- 是否存在优惠券、权益抵扣或活动折扣

**成本侧**可以拆成：

- 门店租金或站点建设成本
- 人力成本
- 电池折旧成本
- 电费成本
- 运维成本
- 物料和维修成本
- 调度和库存成本

**效率指标**也很重要：

- 单站日均换电次数
- 高峰期排队时长
- 单次换电耗时
- 换电站利用率
- 电池周转率
- 故障率和服务成功率

**用户体验指标**可以看：

- 换电预约成功率
- 取消率
- 投诉率
- 用户满意度
- 换电后复访率

一句话总结：

> 我会从收入、成本和运营效率三层评估换电经营状况。收入看换电次数和客单价，成本看租金、人力、运维、电池折旧和电费，效率看站点利用率、排队时长和单次服务时长，最后结合用户满意度判断业务是否健康。

#### 32. 项目深挖：分享一个你主导的、和数据分析关联度最高的项目

**参考答法**：

这类题建议用“背景 - 目标 - 动作 - 结果 - 个人价值”来讲。

**第一步：项目背景**

- 业务当时遇到了什么问题
- 为什么这个问题值得分析
- 你在项目中的角色是什么

**第二步：关键成功指标**

要讲清楚指标不是随便选的，而是和业务目标一致。

例如：

- 如果目标是提升交易：看支付转化率、`GMV`、客单价、复购率
- 如果目标是提升内容表现：看曝光、点击率、完播率、互动率、涨粉
- 如果目标是提升工具价值：看使用率、留存率、建议采纳率、节省时长

可以这样表达：

> 我们把关键成功指标定义为 XXX，因为它最直接反映业务目标。同时我也设置了过程指标和护栏指标，避免只看最终结果而忽略中间链路或副作用。

**第三步：你做了什么**

- 确认指标口径
- 提取和清洗数据
- 拆解指标链路
- 做分群、分渠道、分时间分析
- 输出结论和建议
- 跟踪后续效果

**第四步：结果是否达成**

如果达成，可以说：

> 最后核心指标提升了 XXX，虽然结果是团队共同推动的，但我在问题定位、指标拆解和建议输出上承担了比较核心的分析工作。

如果没达成，也可以稳住：

> 最终没有完全达成目标，但通过复盘发现根本原因不是分析方向本身，而是 XXX，例如流量质量不足、产品改动周期太短、样本量不够、业务动作执行不到位或外部环境变化。这个项目的价值在于帮助团队明确了真正瓶颈，并为下一轮优化提供了依据。

**面试加分点**：

不要只讲“我做了分析”，要讲你的核心价值：

> 我在项目中的核心价值是把模糊业务问题转成可衡量指标，再通过数据拆解定位主要矛盾，最后把结论变成业务方能执行的动作。

**常见追问：为什么选这三个指标？**

可以这样答：

> 这三个指标不是单纯从数据里挑出来的，而是从业务目标出发，先把目标拆成结果指标、过程指标和风险指标，再结合数据可获得性、可解释性和可行动性筛选出来。

例如做商家策略项目，可以选择：

- 结果指标：商家 `GMV`、动销商品数、成交订单数
- 过程指标：商品发布成功率、活动报名率、BD 触达采纳率
- 围栏指标：退款率、投诉率、补贴率、商家流失率

**常见追问：选指标时怎么做特征工程？靠业务输入吗？**

更稳的回答是“业务输入 + 数据验证”：

1. 先和业务确认候选因素，例如商家规模、品类、历史销售、履约能力、活动参与情况。
2. 再把候选因素转成可计算特征，例如近 `30` 天 `GMV`、动销率、发布失败次数、退款率、补贴敏感度。
3. 做相关性、分箱、单变量分析、模型特征重要性或 SHAP，筛掉解释弱、缺失高、波动大、难落地的特征。
4. 最后保留既能解释业务、又能指导动作的核心指标。

**常见追问：数据是历史数据还是新数据？新数据怎么获得？**

可以分开说：

- 历史数据：订单、商品、商家、流量、活动、BD 触达、售后等业务表，用于建模、回溯和基线评估。
- 新数据：通过新增埋点、策略上线日志、BD 触达记录、问卷或商家反馈获得，用于监控策略执行和后验评估。
- 如果新数据暂时没有，需要先补采集方案，定义字段、口径、埋点时机和数据质量校验。

**常见追问：ROI 怎么算？**

项目 `ROI` 不建议只用总 `GMV / 成本`，更适合看增量：

> `ROI = 增量收益 / 项目成本`

如果是补贴或策略项目，可以更细：

> `ROI = 增量毛利 /（补贴成本 + 人力成本 + 流量资源成本 + 系统开发成本）`

面试里要强调：

- 分子要尽量用实验或准实验估计的增量收益
- 分母要覆盖真实投入成本
- 不要把项目期间所有 `GMV` 都归因到项目上
- 长期价值还可以看商家留存、供给质量、BD 效率和策略资产沉淀

   - 这决定了分析是否有逻辑、能否定位真正原因
3. **落地验证**
   - 好的分析不能停留在结论，要能形成建议、推动动作、验证效果
   - 这决定分析最终能不能产生业务价值

一句话回答可以是：

> 我认为数分核心竞争力是业务理解、结构化拆解和落地验证。业务理解决定方向对不对，结构化拆解决定分析深不深，落地验证决定分析有没有真正产生价值。

#### 34. 快手数分一面常见流程：自我介绍、业务理解、指标体系、SQL 和活动评估

**面经整理版**：

- `1` 分钟自我介绍：突出实习经历、数分技能，以及短视频内容运营场景下的数据分析和业务落地经验
- 对快手数分岗位的了解：数分如何支持短视频内容创作、直播带货、用户社区运营

>  
> 我理解快手这类内容平台的数据分析，不只是看播放量，还要帮助业务理解什么内容能被看见、什么内容能产生互动、什么内容最终能带来商业转化。所以我希望能在快手这样的业务场景里，把数据分析能力和内容、直播、电商业务结合起来。

**对快手数分岗位的理解**：

可以围绕三条业务线讲：

1. **短视频内容创作**
   - 分析爆款视频因素，例如题材、封面、标题、发布时间、完播率、互动率

2. **直播带货**

   - 帮助提升直播带货效率
3. **用户社区运营**
   - 分析用户活跃、留存、互动、关注关系和社区氛围
   - 支持内容生态和用户增长

可以结合快手“拥抱每一种生活”的理念补一句：

> 我理解这个理念背后对应的是多元内容生态。数分的价值就是用数据理解不同创作者、不同用户和不同内容类型的表现差异，让平台既能发现优质内容，也能支持更多普通创作者成长。

**SQL 慢的追问答法**：

这道题可以复用“技术追问题：如果数据量很大，SQL 查询变慢怎么处理”的框架，重点说：

- 先筛选再关联，减少扫描数据量
- 避免 `select *`
- 对日期、创作者 ID、视频 ID 等高频筛选和关联字段建索引或分区
- 对日级创作者表现先做预聚合
- 高频报表可以用中间表或缓存

一句话总结：

> 快手数分面试的核心不是只会 SQL，而是能把短视频、直播和电商链路拆成指标，并用数据分析支持内容优化、转化提升和业务决策。

#### 35. 蔚来数分面经：简历深挖、换电 Top 用户和换电经营指标

**面经整理版**：

这类面试通常分为简历面、技术面和业务面。

**简历面常见追问**：

- 如何构建数据指标？

- 你在某个指标达成中起到了什么作用？

**简历面回答框架**：

回答时建议按“业务背景 - 数据来源 - 指标口径 - 分析方法 - 结论动作 - 个人贡献”来讲。

可以这样组织：

1. **业务背景**
   - 当时业务要解决什么问题
   - 为什么需要这个指标或分析
2. **数据来源**
   - 数据来自业务系统、埋点日志、订单表、用户表、设备表还是人工维护表
   - 是否经过清洗、去重、口径统一
3. **指标口径**
   - 分子是什么，分母是什么
   - 统计周期是什么
   - 是否需要去重、过滤异常、分渠道或分端口
4. **分析结论**
   - 指标表现如何
   - 主要问题出在哪个环节
   - 你给了什么建议
5. **个人贡献**
   - 你负责的是口径定义、SQL 拉数、分析拆解、看板搭建、结论输出还是业务推动

如果被问“端口使用率怎么计算”，可以套这个表达：

> 我会先明确端口使用率的业务定义。通常可以理解为实际被使用的端口数 / 可用端口总数，或者端口实际使用时长 / 端口可用总时长。具体采用哪种口径，要看业务更关注资源占用数量还是时间利用效率。计算前还要排除故障端口、测试端口和异常数据，保证分母口径准确。

**技术面题目**：

> 数据表包含车 ID、用户 ID、换电下单时间，找出每个月换电次数排名前十的用户 ID。

答题时可以说明：

- SQL 用 `date_format` 提取月份，按月份和用户聚合，再用窗口函数排名
- Python 用 `pd.to_datetime()` 提取月份，`groupby` 统计次数，再用排序和 `cumcount()` 取每月前十

**业务面题目**：

> 如何计算蔚来换电经营状况？会选择什么指标？

核心思路是从收入、成本、效率和体验四层回答：

- 收入：换电用户数、换电次数、客单价、套餐收入
- 成本：门店租金、人力、电费、运维、物料、电池折旧
- 效率：单站日均换电次数、站点利用率、排队时长、单次服务时长
- 体验：预约成功率、取消率、投诉率、满意度、复访率

一句话总结：

> 蔚来这类面试很重视简历真实性和业务理解，技术题不一定难，但要能把 SQL/Python 写法、指标口径和换电业务经营逻辑讲清楚。

#### 50. 硬核数科面经：简历深挖、DAU 连续活跃、贝叶斯、PSM 和优惠券长期效果

**面经整理版**：

这类面试两轮都偏硬核，简历深挖会围绕项目逻辑、A/B、因果推断反复追问；技术题不一定多，但每道题都要求讲清楚口径、假设和边界。

**一面常见问题**：

- 简历深挖：前两段实习经历、每个项目、A/B 实验、因果推断细节
- SQL：有 `DAU` 表，字段为 `p_date`、`uid`
- SQL 第一问：哪些用户累计活跃 `10` 天以上
- SQL 第二问：连续活跃天数大于 `10` 的用户有哪些
- 贝叶斯题：检测结果为阳性时，真正患病的概率是多少

**二面常见问题**：

- 简历深挖：不断追问项目最后的业务逻辑和分析结论
- 说一说 `PSM` 流程
- 如果用 `XGBoost` 预测 `PSM` 倾向得分，但分布集中在 `0` 和 `1`，如何解决
- 发优惠券短期看实验组 `GMV` 和对照组差别大，但长期差异变小，如何评估一年后的差异

**回答主线**：

1. **简历深挖**
   - 每个项目都要准备“业务背景 -> 指标口径 -> 数据来源 -> 分析方法 -> 结论动作 -> 后续效果”
   - 如果简历写了 A/B 或因果推断，要能讲清为什么用、怎么分组、怎么验证假设、有哪些局限
2. **SQL**
   - 累计活跃：按 `uid` 统计 `count(distinct p_date)`，筛选大于 `10`
   - 连续活跃：先按用户和日期去重，再用“日期减行号”构造连续区间
   - 口述时要先确认 `> 10` 和 `>= 10` 的口径
3. **贝叶斯**
   - 不要把“患病时检测阳性概率”误认为“检测阳性后患病概率”
   - 分母要用全概率公式拆成真阳性和假阳性
4. **PSM**
   - 流程是选协变量、估计倾向得分、匹配或加权、检查平衡性、估计处理效应
   - 倾向得分集中在 `0` 和 `1` 时，核心问题是共同支持不足或模型过拟合
   - 处理方式包括修剪极端样本、简化模型、检查泄露变量、重新选择协变量或改用其他识别策略
5. **优惠券长期效果**
   - 短期 `GMV` 高不一定代表长期有效，可能是一次性补贴刺激或透支未来消费
   - 要看 `30` 日、`90` 日、半年、一年累计 `GMV`、毛利、券成本、留存、复购和 `LTV`
   - 如果长期差异收敛，要判断是否仍有净增价值，而不是只看活动窗口的短期差异

一句话总结：

> 硬核数科面试最看重“假设意识”：SQL 要讲口径，贝叶斯要讲条件概率方向，PSM 要讲可比性和共同支持，优惠券实验要讲短期增量是否能沉淀为长期价值。

- 如何确定流失用户，是否考虑用 `Uplift` 模型
- 现场写两道编程题

**二面常见问题**：

- 自我介绍
- 项目深挖：分层和归因怎么做，如何做常态化归因
- A/B 测试怎么做
- 实验怎么分流，结果怎么评估
- toB 商家发券实验：给高、中、低三档消费额商家定券面额，如何设计实验
- 追问：商家和消费者之间有网络效应时，如何分流；实验要不要正交互斥
- 最小样本量怎么计算
- 第一类错误和第二类错误如何通俗解释

**回答主线**：

1. **建模项目**
   - 先讲业务目标和 `label` 定义，再讲数据预处理、特征构建、模型选择和评估
   - 如果用 `XGBoost`，要能讲清它是 `boosting`，逐步拟合残差或梯度
   - 分类变量、类别不平衡、阈值选择和上线部署都是高频追问
2. **模型评估**
   - `F1` 适合平衡精确率和召回率
   - `ROC-AUC` 反映排序能力，不代表某个阈值下一定最优
   - 阈值要结合业务成本，例如误召回、漏召回、补贴成本、销售触达成本
3. **商业化实验**
   - 核心指标可以看增量收入、广告消耗、`GMV`、毛利或净收入
   - `ROI = 增量收益 / 实验成本`
   - 护栏指标要看用户体验、商家体验、退款、投诉、长期留存和生态挤压
4. **toB 发券实验**
   - 先按商家规模、品类、城市、历史销售额分层
   - 在层内随机分商家到对照组和不同券面额实验组
   - 如果存在网络效应，考虑按商圈、城市或商家簇做 cluster 分流
   - 多实验互相影响时要互斥；影响较小时可以正交提高流量利用率
5. **流失与 Uplift**
   - 流失用户可以按连续未活跃、消费下降、预测留存概率等定义
   - 如果目的是发券召回，不能只预测谁会流失，还要预测发券带来的增量挽回效果
   - `Uplift` 模型更适合判断“券应该发给谁”，避免把券发给本来就会回来的用户

一句话总结：

> 字节商业变现数科面试的核心是“模型能不能服务商业增量”：建模要讲清 label、特征、评估和上线，实验要讲清 ROI、护栏、分流和网络效应，补贴策略还要进一步考虑 Uplift 增量价值。

#### 53. AI Agent 数科面经：简历优化、黑盒白盒、样本量、A/B 和工作流智能体

**面经整理版**：

这类面试会从简历深挖开始，重点看你能否把零散实习经历提炼成数据科学能力；技术追问集中在模型效果评估、样本量、A/B 实验，以及如何用 `API` 和工作流搭一个智能体。

**常见问题**：

- `2` 分钟自我介绍
- 面试官介绍具体业务线后，你可以围绕业务做一个小反问
- 简历深挖：技能、上一段实习、一个相关项目
- 如果实习内容比较零散，如何提取和数据科学相关的部分
- 如何测试模型效果，黑盒和白盒分别是什么
- 为避免过拟合，为什么更看重黑盒泛化评估
- 样本量如何确定
- A/B 实验的概念和样本量确定
- 手撕：不是写代码，而是用 `API` 和工作流搭一个智能体

**回答主线**：

1. **简历表达**
   - 不要把实习写成流水账，要突出一个最相关项目
   - 每个项目按“业务问题 -> 数据来源 -> 方法 -> 结果 -> 个人贡献”组织
   - 难量化结果时，也要写清楚产出，例如指标口径、分析框架、看板、策略建议、自动化流程
2. **黑盒与白盒**
   - 黑盒看输入输出和泛化效果，例如验证集、测试集、线上实验
   - 白盒看模型内部逻辑，例如特征重要性、`SHAP`、模型系数、规则解释
   - 防过拟合时更看重黑盒，因为独立样本表现更能说明模型是否泛化
3. **样本量**
   - 样本量太小，置信区间宽，结论不稳定
   - 样本量太大，实验成本高、周期长、资源占用多
   - 可以结合置信区间缩小幅度和业务成本找相对合理的“肘点”
4. **A/B 实验**
   - 先明确实验假设、分组、核心指标、护栏指标、样本量和实验周期
   - 分析时不仅看显著性，也要看业务收益和长期影响
5. **工作流智能体**
   - 先定义智能体目标，例如异常归因、报告生成、客服工单分类
   - 再设计工作流：理解任务、调用 API、校验数据、执行分析、生成结论、收集反馈
   - 评估时看任务完成率、工具调用正确率、数据准确率、人工修正率和安全风险

一句话总结：

> 这类面试不是单纯问会不会用 AI，而是看你能不能把数据科学项目、实验思维和工作流智能体设计结合起来，讲出一个可落地、可评估、可迭代的方案。

#### 54. 统计实验与因果推断面经：指标检验、正交实验、PSM、逻辑回归和 SQL

**面经整理版**：

这类面试把统计检验、A/B 实验、因果推断、机器学习基础和 SQL/Python 混在一起考，重点看你能不能把“用什么方法”讲成“为什么这个方法适合这个指标或场景”。

**常见问题**：

- `CTR`、`UV` 等指标如何做统计检验
- 大样本为什么可以用 `z` 检验，需要知道总体方差吗
- 多个实验同时上线，如何避免策略之间互相干扰
- 如果没法开实验，如何评估策略效果
- `PSM` 怎么评估匹配得好不好
- `PSM` 的倾向分怎么拟合
- 逻辑回归和线性回归有什么区别，损失函数有什么不同
- 还知道哪些分类模型，各自优点是什么
- SQL：每个月超时订单比例大于 `0.1` 的城市
- SQL：上述城市里连续 `3` 个月都出现这种情况的城市
- Python：用 `pandas groupby` 做聚合处理

**回答主线**：

1. **指标检验**
   - `CTR` 是比例指标，常用两比例 `z` 检验、卡方检验或 bootstrap
   - `UV` 要看口径，如果是用户粒度均值可做均值检验，如果是计数可考虑泊松近似或 bootstrap
   - 大样本使用正态近似主要依赖中心极限定理
2. **多实验**
   - 互相影响的策略要互斥
   - 影响路径相对独立的实验可以正交
   - 最好由统一实验平台管理分流、互斥层和实验优先级
3. **不能实验时**
   - 可以用 `PSM`、`DID`、前后对比加同期对照等准实验方法
   - 关键是解释选择偏差，以及为什么构造出来的对照组尽量可比
4. **PSM**
   - 倾向分常用逻辑回归拟合，也可用树模型
   - 匹配质量看协变量平衡、标准化差异、倾向分重叠、策略前指标是否接近
5. **机器学习基础**
   - 逻辑回归通过 `sigmoid` 输出概率，损失函数是交叉熵
   - 线性回归预测连续值，常用均方误差
   - 分类模型可以从逻辑回归、决策树、随机森林、`XGBoost` 讲起
6. **SQL/Python**
   - SQL 连续月份题本质是“连续登录”变体，用“月份减行号”
   - Python 的 `groupby` 要熟悉分组聚合、筛选和排序这些基础操作

一句话总结：

> 这类面试的核心不是背检验名词，而是先判断指标类型和业务场景，再选择统计检验、实验设计、准实验方法或模型方法，并讲清楚关键假设。

#### 55. 本地生活广告数科面经：聚类分类、PCA/因子分析、距离特征、广告归因和贝叶斯

**面经整理版**：

这类面试一面偏简历、机器学习基础和 SQL，二面偏广告投放归因、信息流实验偏差和贝叶斯思维。核心是能区分“相关、归因、增量”和“模型解释”。

**一面常见问题**：

- 简历深挖
- 聚类和分类的区别
- 因子分析和主成分分析 `PCA` 的区别
- 本地生活中用户到店铺的距离很重要，如何验证这个指标的重要性
- SQL 考察

**二面常见问题**：

- 简历深挖
- 抖音投放广告后，把用户点击广告且 `24` 小时内下单的 `GMV` 记为广告带来的，这样算对吗
- 信息流广告实验组里可能只有 `40%` 用户实际刷到广告，这样计算出来的 `GMV` 增量有什么偏差，如何解决
- 一枚硬币投了 `1000` 次均为正面，第 `1001` 次大概率是正面还是反面

**回答主线**：

1. **机器学习基础**
   - 分类是监督学习，有标签；聚类是无监督学习，没有标签
   - `PCA` 更偏方差保留和降维压缩，因子分析更偏解释变量背后的潜在因子
2. **距离特征重要性**
   - 先按距离分桶，看点击率、转化率、核销率是否有梯度
   - 再控制城市、商圈、品类、价格、店铺热度等混淆因素
   - 最后看加入距离特征后模型效果是否提升，或通过排序实验验证
3. **广告归因**
   - 点击后 `24` 小时内下单是规则归因，不等于真实增量
   - 真实增量最好通过 A/B 或 holdout 组估计
   - 需要同时看 `GMV`、毛利、广告成本、`ROI`、新客和长期复购
4. **信息流曝光不足**
   - 全体实验组 vs 对照组得到的是 `ITT`，会被未曝光用户稀释
   - 只看实际刷到广告的人会引入选择偏差
   - 可以先报告 `ITT`，再在合理假设下用曝光率或工具变量估计实际曝光效果
5. **贝叶斯硬币题**
   - 如果确定硬币公平，第 `1001` 次正反各 `50%`
   - 如果不确定硬币是否公平，`1000` 次全正面会让我们强烈怀疑硬币偏正面，所以第 `1001` 次更可能正面

一句话总结：

> 本地生活广告数科面试最看重因果和增量意识：广告点击归因不等于增量，信息流未曝光会稀释实验效果，距离特征重要性也要控制混淆后再判断。

#### 56. 腾讯数据科学面经：点击率检验、PV 独立性、非参数检验、CLT 和集成模型

**面经整理版**：

腾讯数科一面会围绕一个满意项目深挖，再展开到 A/B 检验、统计假设、非参数检验、中心极限定理和集成模型。SQL 题相对基础，但统计追问会比较细。

**常见问题**：

- 自我介绍
- 挑一个最满意的项目介绍，并继续深挖

- A/B 实验详细流程是什么
- 样本量和检验统计量怎么确定
- 点击率如果不是 `UV` 层面，而是 `PV` 层面，计算过程怎么考虑

- 中心极限定理的定义
- 除了独立同分布，还有哪些潜在假设
- 期望和方差计算公式
- 是否了解 `XGBoost`
- `bagging` 和 `boosting` 的区别
- 在 `bagging` 和 `boosting` 背景下，预测效果有哪些差异
- 随机森林的随机性体现在哪里
- SQL：求每个用户登录次数最多的日期

**回答主线**：

1. **点击率检验**
   - 先明确点击率口径，是用户点击率还是曝光点击率
   - `UV` 层面可以按用户独立样本比较
   - `PV` 层面要注意同一用户多次曝光不独立，最好回到用户粒度或使用用户聚类稳健标准误
2. **A/B 流程**
   - 明确假设、随机分流、核心指标、护栏指标、样本量、实验周期
   - 上线后检查分流均衡、埋点质量和实验污染
   - 最后结合显著性、业务收益和风险决定是否上线
3. **统计假设**
   - 中心极限定理要求样本量足够大、样本相对独立
   - 真实业务还要注意同一用户多次行为、时间相关、聚类效应和长尾分布
   - 不满足参数检验时，可以考虑 Mann-Whitney U、Wilcoxon、Kruskal-Wallis、卡方检验或 bootstrap
4. **集成模型**
   - `bagging` 是多模型并行训练再平均，重点降低方差
   - `boosting` 是串行训练，后一轮修正前一轮错误，重点降低偏差并提升拟合能力
   - 随机森林随机性来自样本 bootstrap 和节点分裂时的特征随机选择
5. **SQL**
   - 先按用户和日期聚合登录次数
   - 再用窗口函数按用户内排序
   - 并列保留用 `dense_rank`，只取一个用 `row_number`

一句话总结：

> 腾讯数科面试很看重统计假设意识：点击率检验不能只套公式，要先确认用户粒度、独立性、样本量和分布假设，再选择合适的检验方法。

- 设计一个 A/B 实验
- SQL：三月份有消费行为用户的人均 `GMV`
- SQL：人均 `GMV` 分布，按 `0-100`、`100-200`、`200-300`、`300-400`、`400-500` 分五档
- SQL：如果没有 `500` 上限，如何用 `floor(gmv / 100) * 100` 动态分箱

**回答主线**：

1. **项目深挖**
   - 三个指标要从业务目标、可解释性、可行动性和数据可得性解释
   - 特征工程要说清楚“业务输入 + 数据验证”，不要只说凭经验
   - 新数据要讲埋点、策略日志、BD 触达记录和数据质量校验
2. **策略评估**
   - 不能把项目周期内全部 `GMV` 归因于项目
   - 有条件优先 A/B；不能 A/B 时说明为什么，并用 `DID`、`PSM`、回归控制或同期对照估计增量
   - `CI` 用来表达估计不确定性，`DID` 用来剥离共同趋势影响
3. **商家品类指标体系**
   - 平台层看 `GMV`、支付用户数、订单数、利润
   - 商家层看入驻、活跃、发布、成交、留存
   - 商品层看发布成功率、有效供给、动销率、库存和品类结构
   - 体验层看退款、退货、差评、投诉和履约时效
4. **SQL**
   - 时间戳题先确认秒级还是毫秒级
   - 复购率题先确认平台、店铺、品类还是商品口径
   - 人均 `GMV` 分箱题先按用户聚合，再用 `case when` 或 `floor` 做分桶

一句话总结：

> 天猫商家品类 DS 面试要体现“策略增量意识”：项目指标、商家画像、BD 使用、ROI 和 SQL 都要围绕可解释、可行动、可验证来回答。

#### 59. AI 数据分析/数科三轮面经：建模项目、实验、搜索业务、Agent 和 AI 职业定位

**面经整理版**：

这组面试覆盖建模项目、实验设计、搜索业务、AI 实践和个人发展定位，整体特点是：项目会追问到模型细节，业务题会纠正候选人是否真正围绕题目本身回答，AI 题会看你是否能把大模型落到数据分析流程里。

**一面 40min：建模项目 + SQL/Python + 评分体系**

项目介绍通常要求讲一个自己满意或最闭环、能体现数据驱动业务决策的项目。

常见追问：

- 特征选择怎么做，特征重要性怎么计算
- 模型的 `target` 是什么
- 为什么后面又用逻辑回归，具体公式是什么
- 样本量多少
- `XGBoost` 和 `LightGBM` 的优劣势
- 解决过拟合有什么手段
- 正则化有哪些方法，`L1` 和 `L2` 有什么区别
- 损失函数了解吗，`XGBoost` 的损失函数是什么，有什么优劣势
- 是否做过显著性检验，还有没有考虑其他数学化评估方式
- SQL 和 Python 手撕
- 业务场景：重构评分体系，引入两方面特征
  - 针对数据文本的先验特征
  - 用户行为数据特征
- 追问：各分类维度权重怎么得到
- 追问：如果 AI 介入，还会提取哪些特征

回答主线：

1. **建模项目**
   - 先讲业务目标和 `target`，再讲数据、特征、模型、评估和落地。
   - 特征选择要从业务相关性、数据质量、模型增益和上线可获得性回答。
2. **模型细节**
   - `XGBoost` 适合结构化表格数据，效果上限高；`LightGBM` 更快、更省内存，但要防 `leaf-wise` 过拟合。
   - 逻辑回归公式是 `p = 1 / (1 + e^(-wx-b))`，适合概率输出和解释特征方向。
3. **评分体系**
   - 权重不能只看模型重要性，要结合业务先验、数据验证、专家校准和线上实验。
   - AI 介入后可以加入文本语义、多模态质量、用户行为和人群交互特征。

**二面 35min：实验 + Agent + 搜索业务**

常见问题：

- 项目介绍及追问
- A/B 实验全流程
- 最小样本量公式
- 实验结果不显著怎么办
- 如何搭建 Agent，可以根据实验结果自动输出报告
- 业务场景题：搜索指标体系如何搭建
- 从什么角度分析这个问题，准备看什么数据
- 搜索和推荐的差别在哪里
- 如果回答跑偏到推荐策略，面试官会及时纠正
- 反问主要工作内容

回答主线：

1. **实验**
   - 先讲假设、分流、指标、样本量、实验周期、数据质量检查、显著性检验和上线决策。
   - 不显著时排查样本量、MDE、实验周期、指标方差、分群异质性、埋点和实验污染。
2. **自动报告 Agent**
   - 输入实验配置和指标数据。
   - 做数据质量检查、指标计算、显著性检验、分层分析和报告生成。
   - 输出结论时保留证据、置信区间、护栏指标和人工复核入口。
3. **搜索业务**
   - 搜索指标体系要围绕 query、召回、排序、点击、二次搜索、放弃率和转化。
   - 搜索是用户主动表达需求，推荐是系统主动分发兴趣，二者分析链路不同。

**三面 25min：AI 实践 + Prompt + 幻觉 + 个人定位**

常见问题：

- 项目介绍及追问
- 有什么成就感，困难和卡点在哪里
- 介绍自己与 AI 实践相关的项目，如何使用 AI 帮助业务在数据层面提效
- 如何写 prompt，使我们能正确取数
- 如何解决模型幻觉问题
- AI 时代个人定位是什么
- 反问：技术栈、后续转型方向

回答主线：

1. **AI 实践项目**
   - 最好讲清楚 AI 介入前后的效率对比，例如取数耗时、分析报告生成时间、归因准确率、人工修正率。
   - 强调自己做了指标口径、数据校验、工作流设计和 bad case 复盘，而不是只会调用模型。
2. **Prompt 正确取数**
   - 写清楚指标口径、表结构、时间范围、筛选条件、输出格式和校验规则。
   - 要求模型不确定时先提问，不允许编造字段。
3. **幻觉治理**
   - 用指标口径库、元数据、数据 API、SQL 工具调用、证据链和回归评测约束模型。
   - 高风险结论保留人工复核。
4. **个人定位**
   - AI 时代更需要能定义问题、确认口径、判断因果和推动落地的数据分析师。
   - 技术栈可以围绕 SQL/Python/统计实验/因果推断/BI/数据产品/RAG/Agent 展开。

一句话总结：

> 这类 AI 数据分析面试不是单纯考会不会用模型，而是看你能否把建模、实验、搜索业务和 Agent 工作流连成可验证、可复核、能真正提效的数据分析体系。
