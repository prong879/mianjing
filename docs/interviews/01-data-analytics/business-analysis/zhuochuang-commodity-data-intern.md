# 卓创资讯：大宗商品数据实习（数据科学）

> **岗位性质**：卓创该实习岗本质是 **数据科学实习**（清洗、建模、统计与 ML、指标体系与结论交付）。JD 里的「智能量化分析」「产品化」指 **数据侧的可复用建模与交付形态**，**不是**金融机构语境下的「量化投资 / 量化交易」独立岗位，也 **不是产品经理岗**。  
> 适用岗位：卓创资讯 **数据实习生**（大宗商品相关数据挖掘、模型搭建与评估；定制项目中的数据分析与建模；以及把通用研究与项目沉淀成 **标准数据产出 / 流程**——仍是 **数据与建模角色**，不是单独招「量化策略」或「产品 Owner」）。技能栈常见表述：Excel/BI + 统计/计量/多元时序/机器学习 + Python 或 R 等。  
> 实习条件（招聘信息常见写法，以 offer/HR 为准）：**厦门**、**每周 5 天**、约 **3 个月**、**本科**及以上学历、约 **200–210 元/天**。  
> **HR 补充（初筛）**：公司称 **厦门暂无独立分公司**；在厦工作多与 **大客户项目驻场/本地协作** 等实际安排相关，**具体用工与办公地点以录用通知为准**。  
> 核心判断：不是纯「跑数表哥」，而是**多行业大宗数据 + 算法与模型 + 分析结论能讲清楚、呈现得漂亮 + 可对客/可复用的数据流程**；JD 会同时提到定制项目与「标准数据产品」，理解为 **数据产出与流程沉淀**，勿与互联网「产品经理」路线混为一谈。

## 四、这个岗位最该准备的知识点

### 1. 从证券量化到产业数据的「迁移叙事」（面试金句）

两者同源：**多源数据 → 特征/规则 → 验证与复盘 → 可视化交付**。差异在标的与约束：大宗商品更强调**产业链变量**（库存、开工、进出口、区域价差），且部分序列更短、更噪；金融因子库更成熟，产业侧要把**专家规则**与模型结合。**方法论都是：口径先行、异常可解释、可复现流水线**。

### 2. 分析总结与数据呈现（任职资格第 1 条，易忽略）

JD 要求**较强的分析总结能力**和良好的**数据呈现能力**，与「只产出代码/中间表」区分开。

- **分析总结**：建议结构 **背景 — 口径与数据 — 方法要点 — 核心发现（So What）— 局限与下一步**；结论写**可行动**（预警阈值、关注列表、是否需补数），慎用「因果」措辞除非有识别策略。
- **数据呈现**：**少而精**（趋势/季节、同比与环比带、TopN 结构、异常高亮）；每张图**标题或脚注写口径**；Excel 可用条件格式、透视 + 切片；BI 设计默认回答「本周异动在哪、对谁重要」。
- **和建模的关系**：模型是手段，**读者要记住的是结论与不确定性与维护成本**。

口播：

> 同样的数，给研究员可以密一些，给业务或客户要**信息减荷**：两三张主图加上口径说明比十张花哨图更有说服力。

### 3. Excel 与 BI

你要能讲清：

- Excel：**透视表**、聚合函数（如 `SUMIFS` / `XLOOKUP`）、图表规范、与「导出层」对齐字段名。
- BI：度量值 vs 维度、**刷新机制**、下钻路径；Dashboard 讲清「谁、多久看一次、决策动作是什么」。

口播示例：

> 我把 BI 当成指标口径的呈现层：背后是统一明细表或语义层，前层做同环比、TopN 与钻取；和写代码一样，先锁口径再画交互，否则报表越多、信任越差。

### 4. 统计、计量与多元时间序列（守住常识即可深挖）


| 主题   | 面试可用要点                                  |
| ---- | --------------------------------------- |
| 时间序列 | 趋势/季节/噪声；ARIMA 直觉；**滞后特征**；换月与节假的对齐     |
| 多元时序 | VAR 等「谨慎谈因果」；领先滞后要先做**业务假设**            |
| 基线   | 季节性 naive、移动平均——**复杂模型必须赢基线**           |
| 验证   | 滚动样本外、前向验证；严防**泄漏**（用到了未来才可知的_revision） |
| 结构断点 | 政策、疫情、产能出清——大宗商品里很常见                    |


### 5. 机器学习（岗位够用层）

- **特征工程**优于盲目堆模型；正则化、交叉验证、分样本评估。
- 树模型与 SHAP（概念级）用于可解释；**异常检测**（分位数、Z-score、稳健统计）常比深度模型更贴近业务。
- 说清：**预测** vs **预警** vs **归因** 三类目标评价指标不同。
- **算法基础（JD 原文「算法基础良好」）**：能口头解释**损失函数、拟合与过拟合、正则化、偏差–方差**；复杂模型上线前**必须先打败透明基线**，并能说**时间/空间复杂度直觉**（避免只会调包）。

**要点：** 方法论一致；希望贴近**实体产业**价格形成；贵司**数据产品化**与实习中「转债流程产品化」同构。

**优化口播（按个人情况替换括号内细节）：**

### 问题3：你做过转债多因子系统，迁移到某大宗品种会怎么做？

**要点：** 先锁业务问题与 horizon → 映射可用字段 → **因子/特征改成产业可解释变量**（库存同比、基差、区域价差）→ 口径文档 + 异常规则 + 复盘页。

**优化口播：**

> 我不会先着急选模型，会先和研究员或业务把三件事钉死：**要解决什么问题**（预测、预警还是归因）、**预测/更新频率和可接受的误差**、**数据延迟和可得字段**。然后在字段映射上，把转债里类似的**价差、期限结构、情绪代理**等思路，换成该品种可解释的**基差、区域价差、库存与开工同比、进出口**等；用不了的就坦诚标为缺口。工程上会同步做**口径说明、异常与跳点规则、换月/节假对齐**，最后留一页**复盘**：样本外误差最大的阶段（如春节、政策冲击）和模型是否在那些区间回退基线。这样既体现迁移能力，也体现大宗场景里**稳健比炫技重要**。

### 问题4：业务方只说「帮我做个预测模型」，你怎么接？

**要点：** 用途与容忍误差、更新频率、可用延迟、**基线**、评估指标、上线监控与**人工覆盖**边界。

**优化口播：**

> 我会把「预测模型」拆成一张需求清单，和业务一起勾选：**第一**，预测什么、决定什么——如果只是周报叙事，可能简单基线加可视化就够；如果要触达客户或辅助交易，指标和容忍度要更严。**第二**，**更新频率、数据几点到位、能接受延迟几小时**，这会直接决定特征能不能用。**第三**，**评价指标**用 MAE/MAPE 还是更关心方向，以及是否要分行情、分品种报告。**第四**，**上线后**谁看监控、异常是否熔断、模型失灵时有没有**人工覆盖或规则回退**。我会承诺先出**基线+小型样本外验证**再给复杂模型，避免范围不明就开始堆特征。

### 问题5：你怎么做样本外或滚动验证？

**要点：** 滚动窗口、不用未来信息、分**制度变更区间**讨论稳健性；报告里写清**误差最大场景**（春节、极端行情、数据缺失）。

**优化口播：**

> 我习惯**时间序列上前向验证**：用过去一段训练、在紧接着的未见过的时间段测，再滚动窗口往前推，而不是随机打乱——避免「未来信息」进训练集。特征和标签的时点我会单独 audit，**修订数据、换月、财报披露**这些容易泄漏的点会标注。报告里不止写平均误差，会写**最差分位、分 regime（如高波动/低波动）和大宗里常见的结构断点**；如果某段政策或疫情导致分布变了，会单独讨论模型是否该重训或回退。对业务我会说清楚：**模型在哪些场景最不可靠**，方便他们心里有数。

### 问题13：详细讲讲你做过的数据清洗——流程和质量标准是什么？

**要点：** 与「问题7（出事怎么办）」互补：本题考 **常态流水线**。分层：**raw → curated → 指标层**；主键与粒度（交易日/地区/牌号/合约）；验收：**覆盖率、一致性、规则命中率、changelog**。

**优化口播：**

### 问题14：异常值 / 离群点你怎么筛？主要靠写脚本规则还是用算法？

**要点：** **并行**：硬规则（物理约束、业务阈值）+ **统计**（分位数、IQR、Winsorize、z-score）+ **模型**（Isolation Forest 等）适用边界；LLM **只做解释与归因**，不宜单独当判别器。

**优化口播：**

> 我不会只用一种办法：**规则**解决显然不合逻辑的值（如缺失日历对齐导致的错误收益）；**统计**处理极端但可能真实的尾部；多变量相关时用 **Isolation Forest** 一类但要调 contamination、并在时间上滚动验证。**大模型**在我们项目里更多是生成解释、对齐公告——**是否判异常**仍应由规则和模型打分分级，最后留给研究员确认，避免「看起来很合理的幻觉」。

### 问题15：介绍一种聚类算法（考点：不要答成异常检测）

**要点：** 面试官点名 **聚类** 时，优先 **K-means / 层次聚类**：假设、预处理（标准化）、缺点（形状、K 选取）；说完再补一句「若是异常检测会用 IF，和聚类目标不同」。

**优化口播：**

> 我说 **K-means**：把样本分到 K 个簇使簇内平方和最小；之前会做 **标准化**，K 用肘部法或轮廓系数辅助。缺点是簇形状偏球形、对噪声敏感。**层次聚类**适合小规模、想看树状结构。卓创场景里聚类可用于 **品种/区域的走势分型、客户分群画像**，但交付前要 **命名可解释**（每条簇的典型剖面），不能只给一个簇编号。

### 问题16：用树模型或 Isolation Forest 做异常检测时，特征工程怎么做？

**要点：** 忌只答「业务提需求我验证」。要列举：**多窗口涨跌、波动、量比、区域价差、季节性残差**等；缺失与极值处理；**时间切分**防泄漏；伪标签如何用规则生成。

**优化口播：**

> **特征**会从业务与时间序列两边拉：比如多窗口收益率、波动率、成交量分位、相对均线的偏离；大宗可加 **基差、库存同比、区域价差**。**处理**：缺失策略写死、极值 Winsorize 或截尾，训练和上线同一套。**标签**若是半监督，会用规则先筛一批高置信异常，再用模型扩召回。**验证**一定要 **前向时间切分**，并统计误报成本——预警类场景宁可分级报警也不要一刀切。

### 问题17：你怎么理解「指标体系」？它要解决什么问题（大宗语境）？

**要点：** **目标—拆解—口径（OSM）**：北极星可以是「客户可信赖的价格/供需洞察」→ 拆解为 **价格层、基本面层、预警层、交付层**；区别于仅罗列回测指标。

**优化口播：**

> 指标体系不是堆砌字段，而是服务 **决策**：对内管理产能与质量，对外服务周报/API。**北极星**可以是关键品种的 **及时性与准确率** 或客户续约相关的代理指标；**过程指标**抓采集延迟、缺失率、模型误差分布；**诊断指标**做 Top 异动品种与归因。**每一条**要有定义、公式、数据来源和刷新频率——和 JD 里的 **标准数据产品 + 数据管理流程** 是同一件事的不同侧面。

### 问题18：如何判断「风险是否可接受」——模型或预警阈值怎么落地？

**要点：** 金融可说 **VaR/ES、夏普、最大回撤**；大宗交付可说 **误报/漏报代价、预警阈值、熔断规则、样本外最差分段**；忌把统计术语和业务阈值混为一谈。

**优化口播：**

> **风险**分两层：**统计层**用样本外误差、分 regime 最差表现、漂移监控；**业务层**和客户对齐「错了会怎样」——例如预警迟一天或误报一次的成本。技术上可以设 **VaR/ES 式尾部指标** 或简单的 **分位阈值 + 人工复核队列**。上线前约定：**触发熔断回退基线或规则**，不留灰色地带。

### 问题19：你了解 Transformer / 大语言模型吗？和数据实习有什么关系？

**要点：** 忌「学过忘了」。至少 **Attention、自回归、RAG、工具调用** 各一句话；结合岗位：**文献摘要、查询辅助、报告草稿、内部知识库问答**——**口径与人审**不可缺。

**优化口播：**

> **Transformer** 用 Attention 捕捉长依赖，训练并行度比 RNN 好。**LLM** 典型是预训练 + 对齐；落地常见 **RAG** 和 **工具/MCP 调用**。在数据团队里我会把它当 **加速器**：例如辅助写 SQL 草稿、解读公告，但 **指标口径与对客数字** 必须以库表和规则为准，走 **复核与权限**。态度是 **可用、可控、可审计**。

### 问题20：Docker 在数据分析或建模环境里有什么用？

**要点：** **环境一致**、依赖锁定、可复现交付；与 **Git** 版本对齐；数据卷与密钥不进镜像。

**优化口播：**

> 研究所或项目组多人多机器时，Docker 用来 **锁定 Python 依赖和系统库**，避免「我本地能跑」。镜像里打包通用特征工程或定时任务环境，**版本跟 Git tag**；挂载数据卷读库表或 parquet，**密钥用环境变量或密钥管理**，不写进镜像。卓创若以内网为主，同样逻辑：**可复现批处理**比每人一套散装环境重要。

### 问题21：Git / Gitee 协作你怎么做？常用命令和工作流顺序？

**要点：** 分支策略 + **具体命令**：clone → checkout -b → add/commit → push → MR → merge；main 保护、禁止乱 force push。

**优化口播：**

> 我们是 `**main` 受保护**：新需求 `git checkout -b feature/xxx`，本地开发完 `git add`、`git commit`，`git push` 开 **Merge Request**，review 通过后合回 `main`。上线前 `git pull` 同步，冲突按文件解决。团队若用 Gitee，流程与 GitHub/GitLab 一样；我会避免在共享分支上 **force push**，重要节点 **打 tag**。

### 问题22：NumPy、Ollama、Langfuse 这类栈你用过吗？LLM 产出如何可追溯？

**要点：** NumPy 基础栈如实；Langfuse **未用**则说了解 + 用日志替代；强调 **trace、prompt 版本、回归测试集、人工抽检**。

**优化口播：**

> **NumPy/Pandas** 日常在用。**Ollama** 本地轻量模型我（按事实）试过或了解用途。**Langfuse** 我了解是做 trace 和评测观测；若团队没用，我们会用 **结构化日志 + 会话 id** 保留调用链。原则：**生成内容不直接进对客指标**，要经过规则校验与人审；保留 **bad case 集** 做回归。

**备注（概念速览）：**

- **NumPy**：Python 数值计算基础库；核心是 **多维同构数组 ndarray** 与向量化运算（含广播），性能好，常作为 **SciPy / sklearn / Pandas** 的底层积木。数据分析里多用于矩阵化特征、预处理与和科学计算衔接。
- **Pandas**：在 NumPy 之上做 **表格/时间序列**：`Series`、`DataFrame`、分组聚合、对齐与缺失处理；和业务侧 CSV、数仓导出对接最常见。
- **Ollama**：在本机 **拉取并运行开源大模型** 的工具链（CLI + **本地 REST API**，常见端口 11434，多提供 OpenAI 兼容调用形态）。侧重 **离线/低成本/数据不出域** 的试错与私有化推理，不改变「数据预处理仍靠 NumPy/Pandas」分工。
- **Langfuse**：**LLM 可观测与工程化平台**（可云可自建）。典型能力：**Trace**（把一次问答或 Agent 链路里各步耗时、prompt、返回值、检索等串起来）、**Prompt 版本管理**、**评测/标注/数据集**。SDK 常与 OpenTelemetry 生态衔接；团队未用时可用「结构化日志 + 会话 id」做轻量替代，但治理能力通常弱一档。
- **可追溯（口述里几条怎么对应）：**
  - **Trace / 会话 id**：每笔生成能回溯到同一请求链路（含上游检索 chunk、模型名、参数版本）。
  - **Prompt 版本**：模板改了能定位「哪版 prompt 产出哪批结果」，便于回滚与对比。
  - **结构化日志**：字段固定（时间、用户/任务 id、路由、延迟、token、错误码等），便于检索与告警，区别于纯控制台 print。
  - **规则校验 + 人审**：生成文本不直接写入对客指标或合同数字；硬性约束（数值范围、引用库表口径）程序化拦一层，关键场景人工复核。
  - **Bad case 集 / 回归**：沉淀失败样例成小集合；改模型或 prompt 后在集合上跑一遍，防止已知问题复出。

### 问题23：Cursor Agent 里的 Skills 是什么？MCP 是什么？客户端和服务端各指什么？

**要点：** **Skills**：给 Agent 的规程包（SKILL.md：何时启用、步骤、约束）。**MCP**：Host–Client–Server；Client 不是泛指电脑，是 Host 内嵌模块；Server 是暴露 tools 的进程（stdio/SSE）。

**优化口播：**

> **Skills** 像是「岗位操作手册」：**先对齐指标字典再写 SQL**、**周报结构固定为结论—图表—口径脚注**，减少模型自由发挥。**MCP** 把数据库、文档库封装成 **标准工具接口**，不同模型都能调。**Host** 是 Cursor 这类壳；**Client** 在 Host 里负责连 Server；**Server** 进程注册具体工具（查库、读文档）。治理上：**只读账号、审计、限流**，符合公司数据合规。

### 问题24：数据结构基础——介绍几种排序算法及其复杂度

**要点：** 插入/冒泡 **O(n²)**；归并、快排、堆 **O(n log n)**（快排最坏 **O(n²)**）；Python **Timsort**；海量数据提 **外部排序**。

**优化口播：**

> 小数据 **插入排序** 简单；通用 **快排** 平均 **O(n log n)**，最坏 **O(n²)**；要稳定用 **归并**，多占内存。**堆排序** 原地 **O(n log n)** 不稳定。Python `sorted` 是 **Timsort**，适合真实数据里已有序的段。若单表极大，会在 **数仓或分批外部排序**，不单靠内存排序。

### 问题25：SQL 基础——增删改查？DELETE 与 WHERE/HAVING？联表与子查询？

**要点：** `**UPDATE … SET … WHERE` 必背**；**DELETE 只用 WHERE**，不用 HAVING；HAVING 跟 **GROUP BY**；删改前 `**SELECT … WHERE` 试跑**；JOIN 与索引。

**优化口播：**

> CRUD：**SELECT / INSERT / UPDATE / DELETE**。删改前我一定先用 **SELECT 同样 WHERE** 看命中行。**HAVING** 只对 **聚合后的分组** 过滤，不能写在 DELETE 里代替 WHERE。**JOIN** 大宗里常见 **日频价格表 JOIN 日历维、地区维**；大表优先 **JOIN key 上有索引**，子查询能改写 JOIN 就改写。

### 问题40：请介绍常见的排序算法（复杂度与特点）。

**要点：** 与 **问题24** 同一考点，可 **合并背诵**；本题补一张 **「全家桶」** 并带 **何时用、是否稳定**；实习岗重在 **复杂度直觉 + 工程场景**（语言内置排序、数仓大表），不必手写快排。


| 算法              | 平均时间           | 最坏时间                     | 额外空间           | 稳定性         | 简评                                                  |
| --------------- | -------------- | ------------------------ | -------------- | ----------- | --------------------------------------------------- |
| **冒泡 / 选择**     | **O(n²)**      | **O(n²)**                | **O(1)**       | 冒泡可稳定；选择不稳定 | 教学意义大，生产少见                                          |
| **插入排序**        | **O(n²)**      | **O(n²)**                | **O(1)**       | 稳定          | **近乎有序** 时很快，小数组好                                   |
| **希尔排序**        | 视间隙序列          | 约 **O(n^1.3)**～**O(n²)** | **O(1)**       | 不稳定         | 插入改进版，了解即可                                          |
| **归并排序**        | **O(n log n)** | **O(n log n)**           | **O(n)**       | **稳定**      | 要稳定、可预测用归并                                          |
| **快速排序**        | **O(n log n)** | **O(n²)**（枢轴差时）          | **O(log n)** 栈 | 不稳定         | **最常用** 实践之一；三数取中等可缓解最坏                             |
| **堆排序**         | **O(n log n)** | **O(n log n)**           | **O(1)**       | 不稳定         | **原地**、TopK 友好                                      |
| **计数 / 桶 / 基数** | 视数据范围          | 视数据范围                    | 视实现            | 可设计为稳定      | **键值范围可控** 时可线性级；整型键常见                              |
| **Timsort**     | **O(n log n)** | **O(n log n)**           | **O(n)**       | 稳定          | **Python `list.sort` / `sorted`** 所用，真实数据有「已有序段」时很省 |


**优化口播：**

> **面试口诀**：平方级 **冒泡选择插入**；近乎有序想 **插入**；要稳定、最坏也稳用 **归并**；平均最快常用 **快排**，注意最坏 **O(n²)**；要原地又 **n log n** 看 **堆**；整数范围小提 **计数/基数**。**Python** 里日常 `**sorted` 是 Timsort**，工程上 **少手写排序**，但要理解 **为何是 n log n** 以及 `**key=` 比较次数**。在我们数据场景里，更多是对 **品种波动、偏离度** 做 **TopN**，在 **pandas `nlargest` / SQL `ORDER BY`** 层完成；表特别大时会靠 **索引、分区、外部排序**，而不是单机暴力全排——和 **问题24** 说的思路一致。

### 问题41：什么是内生性？后果是什么？如何检测与处理？

**要点：** 与 **OLS 一致性** 挂钩；**内生性 ≠ 多重共线性**（后者主要放大方差）。大宗商品分析里常在 **遗漏变量、联立、测量误差、样本选择** 上出现；对客勿把回归系数 **口头说成因果**。


| 维度       | 内容（口试版）                                                                                                                                                        |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **定义**   | 某解释变量 X 与误差项 u **相关**（\mathrm{Cov}(X,u)\neq 0）。直觉：u 里仍有「与 X 一起动」的因素，**进了误差项却没进方程**。                                                                            |
| **常见来源** | **遗漏变量**（兼及 X 与 Y）；**联立/反向因果**（Y 影响 X）；**测量误差**（X 测不准）；**样本选择/缺失非随机**；错误函数形也会混淆讨论，但面试通常先谈前四类。                                                                  |
| **后果**   | **OLS 一般有偏、不一致**；符号可能反；置信区间与假设检验 **名义上不可信**；伪「显著」误导决策。                                                                                                         |
| **怎么检测** | **先画 DAG / 讲故事**：X 是否可能被 Y 或未观测因子驱动？形式上：**联立方程**可用 **秩与阶条件**谈识别；若有候选 **工具变量**，可用 **内生性检验 / Hausman 思想**（外生子集 vs IV）。实践辅助：**残差模式、子样本稳定性**；核心仍是 **经济机制 + 识别设计**。 |
| **怎么处理** | **IV / 2SLS**（工具 **相关且外生**）；**控制函数 / Heckman**（选择）；**面板固定效应**（消 **时不变** 遗漏，对「随时间变遗漏」无效）；**RDD / DiD / 事件研究** 等准实验；若无识别则 **降级为预测/相关表述**，不写因果口径。                 |


**优化口播：**

> **内生性**就是自变量和扰动项「绑在一起」，常见 **少控制了共同驱动 Y 的因素**、**X 和 Y 互相影响**、**X 量测噪音大** 或 **样本不是随机的**。后果是 **OLS 系数不能像课本那样当「平均因果」解释**，推断也容易骗人。我会 **先把机制画清楚**，再想有没有 **工具变量、自然实验、断点、双差** 这类识别；没有的话 **坦诚写「相关/预测」**，尤其在 **大宗—宏观—产业链** 这种 **混杂特别多** 的场景。工程上若客户只要 **预测精度**，我可以用 **树模型保样本外**，但 **解释层** 仍不写越界的因果话。

### 问题42：什么是多重共线性？如何判断、后果与处理？

**要点：** **线性回归**语境下多只自变量 **近似线性相关**；与内生性的差别：共线性主要伤 **精度与可解释**，不一定制造 **方向性偏误**（除非与遗漏变量纠缠时要分开讨论）。


| 维度       | 内容（口试版）                                                                                                                                         |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **定义**   | 多个自变量之间 **高度线性相关**，设计矩阵 **近似不满秩** → 对 **(X'X)^{-1}** 数值上 **不稳定**。                                                                               |
| **怎么判断** | **相关系数矩阵**、**VIF**（如 \mathrm{VIF}_j > 5 或 10 作经验红线，视领域）；**条件数**（condition number）；**方差膨胀**体现在 **单个系数标准误极大、t 很小** 但 **整体 R^2 仍高**；也可看 **岭迹** 辅助。 |
| **后果**   | **系数估计方差变大**、**符号/显著性对样本极敏感**；难以 **单独解释** 某一变量边际贡献；**多重假设下看起来更不稳定**。                                                                            |
| **怎么处理** | **删冗余变量**或 **合并为指数**；**业务上选主变量**；**岭回归 / Lasso / Elastic Net**（有偏换稳定）；**PCA 因子**（解释需克制）；**增加样本与变异**；目标若为 **预测** 可用 **正则化或树模型**，与「线性边际解释」需求分开谈。  |


**优化口播：**

> **多重共线性**就是解释变量 **互相线性「长得像」**，比如一堆 **高度同步的价格、库存、开工指标** 一起丢进回归。判断我会看 **相关矩阵和 VIF**，也会观察是不是 **系数全不显著但 R^2 不低**。它主要让 **系数「抖」、标准误胖**；我会优先 **减维或正则**，或者让业务定一个 **主解释变量**，其它当 **控制**；若报告要写 **因子边际**，就避免 **十个同源因子** 堆在一起。卓创这类 **多宏观、多产业链字段** 时，这是 **高频问题**。

### 问题43：什么是因果推断？一般怎么做因果推断？

**要点：** **因果** 关心 **干预/反事实**（「若 X 多一单位，Y 会怎样」），不是仅有 **条件期望/相关**；观测数据需 **识别假设**。与岗位结合：**预测任务不必伪称因果**；**策略/政策评估** 才必须亮明设计。


| 层次             | 做法（面试可分层答）                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **思想框架**       | **潜在结果（Rubin）** / **因果图（Pearl）**：理清 **混淆、中介、对撞**，什么该控、什么 **不能乱控**（如对撞子一开就错）。                                             |
| **金标准**        | **随机对照试验 RCT / A/B**：可辩称期望上 **打破混淆**。产业数据少见，但 **试点、规则微调** 有时近似。                                                          |
| **准实验 / 观测识别** | **IV**（外生冲击作工具）、**RDD**（断点两侧可比）、**DiD / 事件研究**（平行趋势）、**合成控制 SCM**、**匹配 / 倾向得分**（强 **条件独立** 假设）、高维可用 **DML / 双学习**（概念级）等。 |
| **落地态度**       | 每一步写清 **识别假设** 与 **威胁**；**稳健性**：安慰剂、置换、不同时间窗与对照组。                                                                        |
| **大宗场景**       | 价格、库存、政策冲击等可尝试 **事件研究 / DiD / RDD** 做 **叙事+量化**；若仅有 **时序相关**，则交付 **领先滞后或预测**，报告写 **「与…一致，非因果证明」**。                       |


**优化口播：**

> **因果推断**回答的是「**变动 X 会不会真的引起 Y**」，不是屏幕上回归跑出了星号。**相关** 可能来自 **第三因子、反向、样本筛选**。做法上：**RCT** 最好；没有的话就靠 **IV、断点、双差、匹配、合成控制** 等，每一类都自带 **强假设**，要 **先画 DAG、再选工具**，并做 **稳健性**。在卓创语境里，我先把交付分两类：如果只是 **预警、预测、看板**，我就以 **样本外与可运维** 为主，不把系数讲成 **调控政策**；如果是 **政策评估/客户策略** 课题，再上 **准实验叙事**，并对 **平行趋势、工具外生性** **单独开一页风险提示**。这样既满足 **计量岗专业感**，又不给客户 **过度的因果承诺**。

### 问题44：你之前是怎么处理时间序列数据的？

**要点：** 按 **「时间轴 → 质量 → 对齐 → 特征 → 划分/验证」** 口述一条流水线；紧扣 JD **多元时序** 与 HR **建模+调参**；强调 **前向验证、防泄漏**；大宗场景补 **交易日历、换月、节假**。


| 环节        | 做法（口试版）                                                                                                                          |
| --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **索引与粒度** | 统一 **DatetimeIndex**（或 Period）与 **频率**（日/周/小时）；明确 **采样是业务日、自然日还是交易日**；需要时用 `resample` / `asfreq` 并约定 **agg 规则**（OHLC、last、mean）。 |
| **缺失与异常** | 区分 **真缺失** 与 **停更/停牌**；**前向填充** 要注明是否引入 **泄漏**（预测任务慎用未来信息）；跳点用 **规则 + 业务阈值**，大宗里警惕 **口径变更、换合约**。                                 |
| **多序列对齐** | 不同来源用 **merge / merge_asof**（后向匹配常见）对齐 **时间戳**；多品种、多地区时统一 **主键**（时间 + 维度）。                                                       |
| **日历与换月** | **交易日对齐**、**节假日**；期货类注意 **主力合约换月**、**连续价格拼接** 的范式（若业务有定义则跟定义走）。                                                                  |
| **特征构造**  | **滞后项** L_1, L_2…、**滚动均值/波动**、**同比环比**、（可选）**傅里叶/季节哑变量**；与 **问题5** 中样本外、防泄漏原则一致。                                                 |
| **分解与诊断** | **趋势–季节–残差** 直觉、**结构断点**（政策/疫情）；非预测场景才谈 **平稳/差分**，避免机械套 ADF。                                                                     |
| **验证**    | **时间序列上前向/滚动切分**，禁止随机打乱；复杂模型须 **赢朴素季节基线**；报告 **最差时段**（如春节、极端行情）。                                                                 |


**优化口播（可按经历替换括号）：**

> 我习惯把时序当成 **带时间主键的表**：先 **锁频率和业务日历**，用 pandas 把索引做实，再做 **缺失与跳点** 的可审计处理——哪一步填了、哪一步删了都留着记录。多条序列先 **按时间对齐**（必要时 `merge_asof`），再构造 **滞后和滚动特征**；标签和特征之间我会单独检查 **有没有用到未来才可知的信息**（财报修订、换月错误对齐都容易踩坑）。切分一定是 **向前滚动的验证**，并与 **朴素季节或漂移基线** 对比。  
> **（经历举例）** 在 **转债/行情监控** 里主要是 **日频或更高频**，侧重 **异常 Z-score、量比、相对基准超额** 和 **滚动窗口**；若做过 **ARIMA/LSTM** 类项目，会强调 **样本外与断点**。到 **卓创/大宗**，我会把 **品种、地区、含税口径、评估价 vs 成交价** 一并并进 **维度键**，换月与 **源数据修订** 按研究员或字典规则对齐，保证 **同一套流水线** 既能喂传统时序模型，也能喂 **GBDT/LSTM**，并满足 **PM 验收与复现**。

### 问题45：你是怎么处理**多元**时间序列数据的？

**要点：** 「多元」指 **同一时间轴上多个相关序列**（多品种、多宏观、价量仓利等多字段），或 **多维面板**（时间 × 截面 × 地区/牌号）。与 **问题44** 差一层：重点在 **联合对齐、维数与共线、多变量模型选型、解释边界**；JD 要求 **多元时间序列** 时，面试官常听 **VAR / 领先滞后 / 特征矩阵** 能否说清楚。


| 维度           | 做法（口试版）                                                                                                                                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **数据形态**     | **宽表**：每列一条序列，索引为时间（适合 `VAR`、多变量 LSTM 输入）。**长表**：`time + entity + value`（适合面板、混多品类入库后再 pivot）。大宗里常见 **多源频率不一** → **统一到业务频率**或 **混频近似**（如周度宏观对齐日度用 `merge_asof` + 前值/插值策略写清）。 |
| **联合对齐与缺失**  | 多序列 **内连接 vs 外连接** 会改变样本长度；缺失是 **整条删** 还是 **逐列填充** 影响 **可用 T**；多变量预测要防止 **某一列未来泄露通过填充规则灌进过去**。                                                                               |
| **维数与共线**    | 序列多时 **特征爆炸**（每序列一堆滞后）→ **业务筛主变量、正则、PCA/因子、或树模型做非线性组合**；与 **问题42 多重共线性** 同一脉络。                                                                                               |
| **计量视角（概念）** | **VAR**：变量互为解释、看 **脉冲响应/IRF**（慎口述成因果）；**协整/VECM**：价差类、长期均衡（大宗套利/价差叙事可提一句）；**Granger** 只说明 **预测意义上的领先**，不写成 **因果机制**。                                                         |
| **机器学习视角**   | 把 **多序列滞后 + 横截面特征** 展成 **监督学习表**（行=时间，列=多变量滞后）；**多输出回归** 或 **逐品种单任务**；深度网络可 **多通道输入**，仍要做 **滚动验证与防泄漏**。                                                                      |
| **验证与交付**    | 与 **问题5** 一致：**前向/滚动**；多元时额外报告 **变量删失后稳定性**、**单序列失灵** 是否拖垮整体；对客区分 **联合预测** 与 **单序列可解释边际**。                                                                                   |


**优化口播：**

> **多元时序**我会先定 **对象**：是 **同一品种的多指标**（价、量、库存…），还是 **跨品种/跨市场的多块序列**。数据上优先落成 **同一时间索引 + 统一频率**，不同来源用 **对齐规则** 写进文档，避免「悄悄丢段样本」。特征是 **每个序列的滞后与滚动统计** 拼成一张表——序列一多就会 **维数膨胀**，我会用 **业务主变量 + 正则/因子/降维** 控住，并请研究员帮忙挡掉 **同源共线** 的字段。  
> **模型路线** 分两条说：**计量线** 上 **VAR、协整** 我理解是 **联合动态与价差均衡** 的入口，汇报时 **Granger、IRF 不写越界的因果**；**机器学习线** 上就是把 **多变量滞后** 当 **表格特征** 喂 **GBDT/神经网络**，核心仍是 **滚动样本外** 与 **断点稳健性**。在卓创场景里，多元常对应 **产业链上下游多指标并进**，我会把 **口径与延迟**（哪条序列几点更、能否进当日预测）在特征层就标好，交付时对 **联合模型 vs 分品种模型** 和客户对齐预期。

### 问题48：你了解数据库的类型吗？有哪些？各自适合什么场景？

**要点：** 按 **「OLTP / OLAP / NoSQL / 专项（时序、搜索、向量）」** 分层口述，每类 **1～2 个代表产品 + 一句选型**；与 JD **存储**、**问题25（SQL）**、**问题47（落库）** 互参；不必穷举厂商，重点在 **工作负载匹配** 与 **大宗资讯常见分层（明细/汇总/分析）**。


| 大类                  | 常见产品（举例）                                                                       | 典型场景                                                                   | 不适合 / 注意                     |
| ------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ---------------------------- |

| **嵌入式 / 本地分析**      | **SQLite**、DuckDB（偏 OLAP）                                                      | 单机脚本、**本地分析**、测试、轻量交付                                                  | 非高并发 Web 主库                  |

| **文档型**             | **MongoDB** 等                                                                  | **半结构化**、schema 多变、日志与内容                                               | 复杂事务弱于关系库                    |
| **宽列 / 分布式**        | **Cassandra**、HBase                                                            | **超高吞吐写入**、海量标签时序、横向扩展                                                 | 运维与建模门槛高                     |
| **图数据库**            | **Neo4j** 等                                                                    | **血缘、产业链图、知识图谱**                                                       | 通用报表非主项                      |
| **时序专用**            | **InfluxDB**、**TimescaleDB**、TDengine 等                                        | **高采样监控**、**降采样/保留策略** 内置                                              | 通用 ERP 式 CRUD 不必强上           |
| **搜索 / 日志**         | **Elasticsearch**、OpenSearch                                                   | **全文检索**、日志与事件 **近实时查询**                                               | 与主库 **同步成本**、一致性             |
| **向量检索**            | **Milvus**、**pgvector**、云向量服务等                                                 | **RAG**、embedding **近邻**（智能体常见）                                        | **对客权威数字** 仍以关系库/数仓为准        |

### 问题50：你是否知道什么是动态图表？什么是切片器？

**要点：** 对接 JD **「Excel 及各类 BI 工具」「数据呈现能力」**；与 **问题6（Excel 还是 Python）**、**问题9（呈现证明）**、第四节「Excel 与 BI」互参。口语里 **Excel** 与 **Power BI / Tableau** 各提一句即可。


| 概念              | 是什么                                                                                                          | 常见实现 / 注意                                                                                                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **动态图表**        | 图表所依赖的数据或筛选条件 **变化时，图形随之自动更新**，而不是静态截图。用户在 **切片器、下拉框、时间范围** 上操作后，**同一视图**反映最新聚合结果。                           | **Excel**：**数据透视图（PivotChart）** 随透视表刷新；或 **表格/动态区域** + `OFFSET` / 名称管理器定义「伸缩区域」再绑定图表；数据源更新后 **刷新全部**。**Power BI / Tableau**：视觉对象绑定 **度量与维度**，随 **报表筛选器、交叉筛选** 联动。**原则**：动态不等于花哨——**口径写在图旁**，避免筛选后 silently 改定义。 |

**优化口播：**

> **动态图表**我理解就是 **「数据和筛选一变，图跟着变」**，适合研究员或客户 **自助钻取**，而不是每次改数都要重画一张静态图。Excel 里我最熟的是 **透视表 + 透视图**，数据源规范化后记一次，后面 **刷新** 就能更新；有时也会用 **名称管理器/动态区域** 做简单伸缩。**切片器**就是 **挂在透视表或图上的可视化筛选**——比如按 **品种、地区、周** 点选，比只在行字段里勾勾选选更直观。

### 问题53：结合你之前的业务，你会怎么进行假设检验？

**要点：** JD **统计学 / 计量**；答题结构 **业务问题 → H0/H1 → 数据与检验统计量选择 → 结论表述（效应量+置信区间+p）→ 局限**。与 **问题41～43**（显著 **≠** 因果）、**问题5**（样本划分）、第四节「统计、计量」互参；**时序数据** 交代 **独立同分布假设** 常被违背时的处理（分段、稳健、重排需谨慎）。


| 环节               | 口试要点                                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. 业务翻成统计**    | 先问：要检验 **「谁和谁是否相同」** 还是 **「系数是否为零」** 还是 **「分布/比例是否变化」**？例如：**两组成交量均值**、**因子 IC 是否显著为正**、**政策前后均值跳跃**（后者更接近 **结构变化/准实验**，见 **问题43**）。                             |
| **2. H0 / H1**   | **H0** 写清楚：**无差异 / 系数为 0 / 比例等于某值**；**H1** **单侧或双侧** 与业务一致（如只关心 **是否变好** 可能单侧）。**检验前**固定 **显著性水平 α**（常 5%）与 **样本定义**。                                            |
| **3. 检验选型（常见）**  | **独立样本 t 检验 / Welch**（方差不等）；**配对 t**（同一实体前后）；**比例**：**z 检验 / 卡方**；**多组均值**：**ANOVA**；**回归系数**：**t 检验** 或 **F**；**列联/独立性**：**χ²**。非正态小样本可提 **Mann–Whitney**（概念）。  |
| **4. 时序 / 金融实务** | 日收益、因子序列常 **相关、肥尾** → **简单 i.i.d. t 检验可能偏乐观**；可 **分块/聚类自助法、HAC 标准误（回归里）**、**子样本/滚动** 看 **稳健性**；**多重检验**（试了很多因子）要提 **FDR/Bonferroni** 或 **样本外**，避免 **p-hacking**。 |
| **5. 结论怎么说**     | 报 **点估计 + 置信区间 + p 值**；**拒绝 H0** ≠ **业务上重要**——补 **经济/业务幅度**；对客不写「证明因果」，与 **问题41～43** 一致。                                                                         |


**优化口播（量化实习示例，可按事实改编）：**

> 在 **转债/因子** 场景里，常见问法是：**某因子分组的多空收益差** 是否 **系统为正**，或 **改造前后** 流程下的 **回测指标** 是否 **差异来自噪声**。我会先把 **H0** 讲成 **「差异为零 / IC 均值为零」**，**H1** 与研究员对齐是 **单侧还是双侧**。数据上 **时间序列截面** 要 **先定样本期、排除 ST、对齐复权与停牌规则**，划分尽量 **前向**（对齐 **问题5**），避免用 **全样本调参再同一样本检验**。检验手段上：**两组均值** 用 **t（或 Welch）**；**多组** 用 **ANOVA**；若在 **回归里看因子系数** 就看 **系数的 t/F**，并愿意在 **稳健标准误** 或 **分块抽样** 下复算一遍。  
> **多重检验** 会坦白：**扫过很多因子时，单独 p 值要打折**，更信 **样本外、经济显著幅度、分行情分阶段**。对客报告写 **「在 α=5% 下拒绝/不拒绝 H0 + 置信区间」**，不把 **统计显著** 口头说成 **策略一定赚钱或因果机制**。到 **卓创/大宗**，同样逻辑：**两套口径或两时段均价** 是否 **统计可区分**——先 **锁口径**，再选 **检验**，最后 **业务解释保守**。

### 问题54：请你讲一下什么是正则化？

**要点：** JD **机器学习、算法基础**；与 **问题39**（Ridge/Lasso）、**问题42**（多重共线时 Ridge/Lasso）、**问题46**（建模）、第四节「机器学习」互参。面试 **定义 → L1/L2 → 直观效果 → 偏差–方差 → 调参** 五句话即可。


| 概念            | 内容（口试版）                                                                                                                                                                                    |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **要解决什么**     | 经验风险最小化容易 **过拟合**（训练极好、样本外崩）。**正则化**是在损失函数里 **加惩罚项**，约束 **参数过大 / 有效参数过多**，换 **更好的泛化**。                                                                                                     |
| **线性模型里常见形式** | 最小化：**经验损失 + λ · 惩罚**。**Ridge（L2）**：惩罚 **系数平方和**，系数 **整体收缩**，缓和 **多重共线** 导致的系数爆炸（见 **问题42**）。**Lasso（L1）**：惩罚 **绝对值和**，倾向产生 **稀疏解**（部分系数恰好为 0），可作 **自动特征选择**。**Elastic Net**：L1+L2 **折中**。 |
| **直观**        | λ **越大**：模型 **更简单、更平滑**，训练拟合变差一些，但 **方差** 常下降；λ **太小**：接近原模型，**仍可能过拟合**。用 **交叉验证 / 滚动验证**（**问题5**）选 λ。                                                                                     |
| **偏差–方差**     | 强正则 → **偏差↑、方差↓** 的典型权衡；目标是 **测试误差** 最小，不是训练误差最小。                                                                                                                                          |
| **与树/神经网络**   | **树模型**：`max_depth`、`min_samples_leaf`、学习率、列/行子采样等起 **类似「约束复杂度」** 的作用，口语里也可叫 **正则化手段**，但和 **L2 惩罚权重的含义** 不完全同一公式。 **深度网络**：**权重衰减（weight decay）** 常等价 L2；还有 **Dropout、早停** 等防过拟合。          |


**优化口播：**

> **正则化**就是在优化目标里 **多加一项惩罚**，不让参数无约束地拟合噪声，核心目的是 **控过拟合、抬样本外**。线性里最典型是 **Ridge 的 L2** 和 **Lasso 的 L1**：L2 **收缩系数**、对 **共线** 更稳；L1 倾向 **稀疏**、做 **变量筛选**。λ 用 **验证集或交叉验证** 调。我会连着 **偏差–方差** 一句：正则强了 **拟合会偏简单**、但 **波动小**。在 **卓创** 的 **表格型大宗特征** 上，如果 **滞后特征特别多**，我会 **先试 Ridge/Elastic Net 或树里的深度与叶子约束**，再看 **样本外** 是否稳定，而不是训练集追极致。

| 板块            | 常见手段（口试举例）                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **清洗与缺失**     | **类型对齐**、去重主键、**缺失策略**（剔除/标记/前向填充——预测任务慎防泄漏）、**异常与 Winsorize**、对数/Box-Cox（按需）。                                         |
| **类别与文本**     | **One-hot**（低基数）、**目标编码**（高基数需谨慎、防泄漏需 **out-of-fold**）、**哈希**；文本 **分词、TF-IDF、嵌入**（概念）。                                 |
| **数值变换**      | **标准化/归一**（线性、KNN、神经网络常需；树模型多数 **不敏感**）、**分箱**、**对数收益率/比率**（金融、大宗价差）。                                                  |
| **时序 / 领域特征** | **滞后** L1…Lk、**滚动均值/波动/最大回撤窗口**、**同比环比**、**日历特征**（月、周、节假日）、**量价衍生**（相对均线偏离）；大宗里 **区域价差、基差、库存同比** 等——与 **问题44～45** 同脉络。 |
| **交互与降维**     | **乘积/比值**（业务驱动）、**PCA/因子**（降维但解释要谨慎，见 **问题42**）。                                                                       |
| **选择与泄漏**     | **过滤法**（相关、互信息）、**包裹/嵌入**（L1、树重要度）；**严禁** 用 **未来标签或全样本统计** 做编码；训练/验证 **同流水线 `fit_transform`**（对齐 **问题5**）。             |


**优化口播：**

> **特征工程**我理解成：**在不过拟合、不泄漏的前提下，把业务里「该知道的形状」编码进输入**。操作上会先做 **清洗与主键**，再按问题选 **时序滞后与滚动统计**、**同比环比**、**大类里常见的价差与库存类字段**；类别变量看基数决定 **One-hot 还是谨慎的目标编码**。数值是否 **标准化** 看模型族。**每一段变换**尽量写进 **字段字典**（公式、窗口、是否用未来信息），训练和预测 **同一套代码路径**。最后配合 **问题54 的正则或树深度** 控住 **特征膨胀**，用 **滚动样本外** 验收。实习里 **转债/因子** 就是典型 **横截面 + 时序面板** 特征：**行业、评级、券龄 + 价量滞后 + 相对指数** 等，逻辑到 **卓创** 只是把 **品种与产业链字段** 换一套。

### 问题56：请你说一下什么是树模型？

**要点：** JD **机器学习**；**决策树 → 集成树（RF / GBDT）** 一条线讲清即可。与 **问题39**（算法族谱）、**问题46**（实习用过 LightGBM 等）、**问题54**（深度、叶子即正则）、**问题55**（特征与树不配平也要）、**问题15/16**（聚类 vs IF 勿混）互参。


| 层级              | 内容（口试版）                                                                                                                                                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **单棵决策树**       | **递归二分**：每一步选一个特征和 **阈值**，把样本划成左右子集，使 **不纯度下降最大**（分类常用 **Gini/信息增益（熵）**，回归常用 **MSE 下降**）。叶子上的预测：分类 **多数票/概率**，回归 **均值**。 **优点**：**非线性**、自动 **特征交叉**、对 **单调缩放不敏感**。**缺点**：单树 **高方差、易过拟合**；**轴平行**分割，对光滑函数不如线性外推。                       |
| **随机森林（RF）**    | **Bagging**：多棵树各用 **bootstrap 样本** + **随机子特征**，**投票/平均** 降低方差。**特点**：稳健、可 **OOB 估计**、**特征重要度**；不如 Boosting 追求极致精度时常够用。                                                                                                                |
| **梯度提升树（GBDT）** | **Boosting**：**串行**加树，每棵拟合 **前一轮的负梯度（伪残差）**，逐步减小损失（如 MSE、对数损失）。**XGBoost / LightGBM / CatBoost** 为工业界常见实现（直方图、叶子生长策略、类别处理各异）。**调参**：`n_estimators`、**学习率**、`max_depth`、`min_child_samples`、子采样/列采样等——本质是 **偏差–方差与正则** 平衡（见 **问题54**）。 |
| **解释与交付**       | **特征重要度、SHAP（概念）** 辅助叙事，但 **不等于因果**（**问题41～43**）。时序上仍要 **防泄漏、滚动验证**（**问题5**）。                                                                                                                                                         |


**优化口播：**

> **树模型**就是以 **决策树** 为基本单元：从根到叶是一串 **「若特征 A ≤ 阈值走左，否则走右」** 的规则，分类树叶子上 **投票**，回归树叶子上 **取平均**。单树容易 **过拟合**，所以实务里几乎都是 **集成**：**随机森林** 用 **多棵树平均** 降方差；**GBDT** 用 **串行残差拟合**（**XGBoost/LightGBM** 一类）把误差一点点吃掉，**表格型、特征里有交互** 的场景很强。  
> 我会说清 **树不要求特征标准化**，但要 **严重依赖特征工程与时间切分**——在 **卓创** 这种 **价量仓+宏观** 的表里，树常和 **滞后、滚动、价差** 特征搭；交付时用 **重要度或 SHAP** 帮业务 **讲故事**，同时提醒 **只是相关贡献排序，不是因果系数**。调参我会在 **学习率–树数量–深度** 三角里用 **验证集或滚动窗** 收敛。

### 问题57：请你说一下什么是聚类分析？

**要点：** **无监督学习**：只有特征 **没有标签**，把样本划成若干 **簇**，使簇内 **相似**、簇间 **相异**。与 **问题39**（算法族谱）、**问题15**（聚类题勿答成异常检测）、**问题14/16**（IF 与聚类目标不同）互参；交付上要 **簇命名 + 业务剖面**，避免只报 **Cluster 3**。


| 概念             | 内容（口试版）                                                                                 |
| -------------- | --------------------------------------------------------------------------------------- |
| **问题定义**       | 给定 **n** 个样本的特征向量，划分为 **k 个簇**，使 **簇内尽可能相似、簇间尽可能不同**（各算法优化目标不同）。**无标签**，不直接最小化预测误差。     |
| **K-means**    | 迭代 **分配–更新质心**；需预先指定 **K**，对 **球形簇** 假设较强；特征常 **标准化**。K 可用 **肘部法、轮廓系数、业务可解释** 联合定。      |
| **层次聚类**       | **凝聚**或分裂，产出 **树状图**；适合 **探索阶段**、样本量 **中等** 时看结构。                                       |
| **GMM（概念）**    | **软分配**（隶属概率），可拟合 **椭圆簇**。                                                              |
| **DBSCAN（概念）** | 基于 **密度**，可发现 **任意形状**，标 **噪声点**——勿与 **异常检测业务定义** 自动等同。                                 |
| **与异常检测**      | **聚类**首要 **分段/画像**；**Isolation Forest 等**首要 **找离群**。面试别混答（详见 **问题15**）。                 |
| **评估**         | **外部**：若有弱标签可用 **ARI/NMI**；**内部**：轮廓系数、DB 指数等 **仅供参考**；最终常靠 **业务复盘簇是否说得通**。             |
| **大宗场景**       | **品种/区域走势分型**、**客户/询盘行为分群**、**多指标综合画像**；每条簇输出 **典型剖面**（均值曲线、核心驱动指标），供研究员或 PM **命名与策略**。 |


**优化口播：**

> **聚类**是无监督里最常见的一类：**没有 y**，只有特征，看数据自己能不能 **成团**。我最熟的是 **K-means**：先定 **K**，迭代把每个点划到 **最近质心** 再更新质心；实际会 **标准化** 特征，用 **肘部/轮廓** 辅助选 K，但 **最终 K 要听业务** 能不能解释。**层次聚类** 适合**中小样本**看 **树状结构**；**GMM、DBSCAN** 我了解适用边界——**密度聚类**能找 **奇怪形状**，但 **噪声点** 不等于业务定义的「异常单」。  
> 和 **Isolation Forest** 的差别我会主动讲清：**聚类**是 **分段画像**，**异常检测**是 **找离群**（**问题15/16**）。在 **卓创** 可以把 **多品种日收益/波动/基本面 proxy** 拉成特征矩阵做 **走势分型**，交付时每个簇写 **「高波动+高库存同比」** 这类 **人话标签**，而不是 **只有编号**。聚类结果 **不做因果断言**，和 **问题41～43** 一致。

### 问题58：请你说一下什么是过拟合？咱们怎么防止、怎么处理过拟合？

**要点：** JD **机器学习、算法基础**；先 **定义 + 训练/验证差距 + 偏差–方差一句话**，再 **分层说治理手段**。与 **问题5**（划分与泄漏）、**问题34**（业务敢用）、**问题54～56**（正则/特征/树复杂度）、**第九节「过拟合、泄漏」** 并背。


| 维度           | 内容（口试版）                                                                                                    |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| **是什么**      | 模型把 **训练集里的噪声和偶然模式** 也学进去了，表现为 **训练误差很低，但样本外/测试误差明显变差**——**泛化差**。与 **高方差** 常联系在一起（相对 **欠拟合/高偏差**）。         |
| **怎么发现**     | **训练 vs 验证/测试曲线** 分叉；**交叉验证/滚动验证**（**问题5**）上不稳定；**复杂模型打不过朴素基线** 在非训练段。                                     |
| **数据侧**      | **更多代表性数据**、**降噪与清洗**、**检查标签与口径错误**、**时序上严禁信息泄漏与全样本调参**（未来进特征、测试集参与特征构造等）。                                 |
| **模型与复杂度**   | **简化模型**（少层少树浅深度）、**剪枝**、**限制多项式次数**；**树/GBDT**：减小 `max_depth`、提高 `min_child_samples`、子采样、降低学习率 + 更多树配合早停。 |
| **正则与贝叶斯思路** | **L1/L2/Elastic Net**（**问题54**）、**权重衰减、Dropout（NN）**、**早停（early stopping）**。                               |
| **特征侧**      | **减特征、降维、去掉高度共线冗余**（**问题42、55**）；**Dropout 列特征**（树里的 colsample）。                                           |
| **集成**       | **Bagging/RF** 降方差；**适度 Boosting** 仍需 **强验证** 防迭代过拟合。                                                      |
| **流程侧**      | **验证集/时间窗选超参**；**样本外、多分段** 报告；对客 **不确定性与人工覆盖**（**问题34**）。                                                  |


**优化口播：**

> **过拟合**就是 **「练卷纸 100 分，真考不及格」**：训练集拟合得太死，把 **噪声当真规律**，换一段数据就崩。判断上我看 **训练–验证 gap** 和 **滚动样本外**（**问题5**），复杂模型还要 **和季节基线比**。  
> **治理**我会分四刀：**第一** **数据和标签**——有没有 **泄漏、错误口径、幸存者偏差**；**第二** **减复杂度或加约束**——浅树、强正则、早停、Dropout；**第三** **特征**——别堆 **无效/同源** 列，该删删该正则正则（**问题54～55**）；**第四** **流程**——超参只在 **验证窗** 上调，交付带 **误差区间和业务熔断**（**问题34**）。卓创 **时序多、政策断点多**，我会特别警惕 **用全历史拟合再在同期验收** 的假漂亮——宁可 **朴素可解释+稳**，也不要 **训练集炫技**。

### 问题59：你怎么理解大宗商品的产业信息和分析？若由你来做，怎么展开？框架是什么？

**要点：** 偏 **业务面 + 研究员思维**，不是背单一品种细节。核心：**把产业链语言 → 可观测变量 → 可对账口径 → 可交付结论/监控**；与 **第四节**「数据产品生产流程」、**第七节**口径与抽象、**问题8、13、34**、第九节「必背业务词」一致；分析输出上仍守 **问题41～43**（相关≠因果）。


| 层次             | 内容（口试版）                                                                                                                                                                                                                                                                 |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **怎么理解「产业信息」** | **结构化事实**：谁在产/谁在买、产能与开工、库存与物流、进出口与替代、政策与行业标准。要落到 **时间、地域、品种规格、含税/评估口径** 等可对齐维度（**问题13、第七节 Q1**）。                                                                                                                                                                        |
| **怎么理解「分析」**   | 在可得数据与延迟约束下，回答 **「现在处在供需周期的什么位置、价格在反映什么、下一步要盯哪些关键数」**——用 **指标 + 历史分位/季节图 + 情景** 表达，而不是信息堆砌。模型是工具，**口径与叙事**要对业务可读（**问题34、第六～七节**）。                                                                                                                                       |
| **展开顺序（实操）**   | ① **冻结对象与口径**（品种边界、现货/期货、主力与换月、客户决策场景）；② **画产业链与传导**（上中下游、替代与关联品种）；③ **列核心指标体系**（价、价差、库存/开工、进出口、利润 proxy 等，按品种删繁就简）；④ **数据源与 SLA**（官方/产业/成交与评估差异、修订风险 **问题35**）；⑤ **基线叙事 + 可选模型**（规则/统计预警优先，复杂模型滚动验证 **问题5、44**）；⑥ **交付物**（一页结论、BI 切片、定时任务与 changelog **问题6、9、50～52**）。 |
| **框架（可背诵版）**   | **「供需—库存—价差—事件」**：供需与平衡表思路看 **松紧**；库存与物流看 **缓冲与逼仓风险**；基差/区域差/期限结构看 **现货预期与结构性矛盾**；日历与事件看 **边际冲击**。交叉验证：**多源价格与库存是否讲同一个故事**。                                                                                                                                             |
| **卓创语境**       | 强调 **标准数据资产 + 定制项目**：共性进模板与字典，差异进配置；对外 「**预测/监测**」与 「**因果断言**」分栏写（**问题41～43**）。                                                                                                                                                                                         |


**优化口播：**

> 我对 **产业信息** 的理解是：不是新闻摘要，而是能 **指导盯盘和排产** 的那套 **结构化事实**——谁产谁用、库存在哪、物流和政策怎么动，都要能 **落到时间、地区和口径** 上，否则没法和系统里的数对齐（**问题13**）。  
> **分析**就是把这套信息和公司数据拼成 **可复述的故事线**：现在 **供需偏紧还是偏松**、价格在反映 **现实还是预期**、库存和价差 **是否矛盾**。我会用 **「供需—库存—价差—事件」** 当骨架：平衡表思路看松紧，库存看缓冲，基差/区域差/曲线看结构性矛盾，再叠 **季节性和政策日历**，看多源数据 **是不是同一叙事**。  
> 若由我落地：先和客户 **冻结品种与口径和成功标准**（**问题8、第七节 Q1**），再 **画产业链、定 5～10 个核心指标**，接 **数据与 SLA**，然后 **基线图表 + 必要模型**，最后 **模板化交付**——重复逻辑进参数，一次性需求不污染主干。全程区分 **我们能预测/监测什么** 和 **不能因果拍脑袋**（**问题41～43**），和研究员 **人机协同**。

### 问题60：若要产出日报、周报、月报、年报，它们有什么区别和共同点？

**要点：** 咨询产品线常见 **连续交付**；答 **时间窗与统计口径 → 叙事深度 → SLA 与数据成熟度 → 自动化与人审配比 → 版本归档**。与 **问题9**（分析总结/呈现）、**问题13**（清洗与口径）、**问题59**（产业叙事骨架）、**第六节场景1**（周均价口径）、第四节「分析总结」互参。


| 维度          | 共同点                                                            | 区别（面试按频度对比说）                                                                                                                                                                          |
| ----------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **数据与口径**   | 同源 **指标字典 / 单一真源**；都要写清 **含税、地域、现货期货、评估价 vs 成交价**（**第七节 Q1**）。 | **日报**常踩 **最新值未终版、官方修订未到齐**——要约定是否允许 **盘中/隔夜** 标「待定」或二次刷新。**周报**必对齐 **自然周 vs 交易日**、**周均/最高最低** 算法（**场景1**）。**月报**对齐 **完整公历月或业务月**、月内 **节假日与换月**。**年报**常涉及 **历史口径统一、多源对齐与定稿节点**，修订窗口长。 |
| **时间尺度与噪声** | 都是 **时间序列切片**。                                                 | **日报**看 **边际变化与异常**（日环比、隔夜事件）；信噪比低、忌过度解读。**周报**承上启下，兼顾 **周内结构与一周主线**。**月报**压一部分日噪，突出 **趋势与同比、结构性段落**（开工/库存/进出口节奏）。**年报**强调 **年度定调、分季度复盘、多年对比**。                                       |
| **叙事与篇幅**   | 建议结构 **现象 — 口径与数据 — 要点 — 局限/下一步**（**问题9、第四节**）。                | **日报短**：**头条异动 + 三五个数 + 关注列表**。**周报**：**一周回顾 + 下周关注点**。**月报**：**供需/价/库存的月度结论 + 图表组**。**年报**：**行业年度画像、策略级小结、附录口径表**——人笔重、审稿链更长。                                                        |
| **生产与协作**   | **调度 + 校验 + 模板 + changelog**；异常走熔断（**问题7**）。                   | **日报**：**自动化比例高**、截稿紧、值守轮值。**周报～月报**：模板稳定，仍留 **研究员补评**。**年报**：**跨月沉淀、多轮校对、固定排版与引用规范**。                                                                                                |
| **产品化**     | 重复板块应 **参数化**（品种树、阈值、段落开关）（**第七节 Q5**）。                        | 从 **日报参数** 抽象到 **周报骨架** 再到 **月报图表包**，年报验证 **跨期可复用资产** 是否真省人日。                                                                                                                         |


**优化口播：**

> **共同点**我会抓三条：**同一套指标字典和口径**，不能日报一个均价、周报另一个；**同一套质量与调度**，该告警告警、该打修订标就打；**叙事结构一致**，都是先让别人看懂「**这周/这月怎么了**」，再展开依据。  
> **区别**主要看 **时间窗和数据成熟度**：**日报**盯 **隔夜和当日的边际变化**，容忍度上要知道有的数 **还没终版**，版面上要写清 **统计时点**；**周报**关键是 **自然周还是交易日、周均价怎么算**，否则和客户系统对不齐（**场景1**）；**月报**要扣 **完整月、节假日和换月**，叙事比日报 **稳**，多讲 **同比和结构**；**年报**是 **长周期复盘 + 定稿**，强调 **历史口径对齐、多年可比**，人和流程的 **审稿成本** 最高。  
> 工程上我会把四类报告想成 **同一流水线不同 `frequency` 参数**：底层明细一致，上层 **模板段落、聚合窗口、人审节点** 不同——这样既 **产品化**，又不会在日报里写年报篇幅拖垮时效。

### 问题61：你是否知道「Cloud Code」/ **Claude Code** 的源码泄露事件？你有没有看过他的源码？请说三个点。

**要点：** 口语里常被说成 **「Cloud Code」**，公开报道与社区讨论多指 **Anthropic 的终端 AI 编程工具 Claude Code**（**不是** Google 的 Cloud Code / Cloud Shell 一类产品名）。**2026 年 3 月** 起多家技术媒体转载：其 **npm 发布包中误含可在生产环境还原源码的 source map**（如 `cli.js.map`），`sourcesContent` 等字段使下载包者能拼回大量 TypeScript；Anthropic 侧表述为 **发布流程失误**，非外部入侵。另有报道提及 **此前类似事故曾发生并被撤包**，属于 **重复类构建/发布配置问题**。与 **问题26（AI 工具安全）**、**问题23（MCP/Agent）** 同链路：时事 + **供应链合规** + **不写密钥、不无授权外传内部数据**。公开讨论可参考例如 [腾讯云开发者社区相关报道](https://cloud.tencent.com/developer/news/3774775)、[阿里云开发者社区文章](https://developer.aliyun.com/article/1722443)（均为二手整理，细节以厂商说明与可追溯构建制品为准）。

**面试时三个点怎么说（任选组合，口径诚实）：**

1. **技术性根因**：生产 npm 包里 **不应附带可逆的 source map**（或须在构建时关掉 `sourcesContent`、分拆发布流水线），否则等价于「把源码粘在压缩文件旁边」；属于 **release 门禁与 artefact 审计** 问题，与安全入侵不同类。  
2. **合规与职业边界**：**泄露出来的**源码 **著作权仍属厂商**，个人/团队 **不以泄露仓为商用基础、不鼓动二次分发**；可关注公开架构讨论，但与 **公司内部代码与密钥** 的保密义务 **不是一回事**。  
3. **对工作方法的启示**：和 **问题26** 一致——用 Agent/CLI 时坚持 **密钥最小化、内网数据策略、依赖与制品可审计**；把这次事件当成 **供应链风险 + 构建配置也会在「无意识」下设敞口** 的案例，而不是花边新闻。

**优化口播：**

> 我知道网上说的多数是 **Anthropic Claude Code**，有时被叫成「Cloud Code」容易和别的产品混在一起——我按 **Claude Code** 来理解。公开的叙述是 **npm 包里带了 source map**，里面 **嵌了原始 TS 内容**，所以装包的人能还原出很大一坨源码；官方说是 **发版失误**，不是被黑。  
> **三个点**：第一，**工程上**这是 **发布物里不该带可逆 map** 的典型坑，要有 **构建/发布检查**；第二，**合规上**那是别人的知识产权，我 **不会拿泄露副本当业务依赖或传播**；第三，**对我自己**是提醒：用 **Cursor、Claude Code 这类工具** 时更要守 **密钥、内网数据、团队政策**（和您刚问的 **AI 工具安全** 同一条线）。  
> **有没有看过源码**：我只从 **公开报道** 了解规模和成因，**没有**也不打算把 **非授权泄露的完整仓库** 当学习材料深读——真要看架构，情愿等 **官方文档或正规开源**。

## 六、场景题准备

> **表达技巧**：场景题先一句**表态**（客户/业务体验优先、风险可控），再**步骤**，最后**预防**——显得成熟、可协作。

### 场景1：客户说周报里的「周均价」和系统导出不一致

**思路：** 对齐含税/不含税、时间窗、地域/牌号、**评估价 vs 成交价**、缺失处理；输出一页口径说明；选**单一真源**或**多版本字段并列**，禁止默混用。

**优化口播：**

> 我会先道歉并表态：数对不齐，责任在我们先把**口径摊开**。然后拉一张**差异核对表**，逐项对齐：含税不含税、自然周还是交易日、地域和牌号是否同一层级、缺失是插值还是剔除、用的是评估价还是成交价。对齐后输出**一页口径说明**带版本号，必要时在系统里**并列两个明确命名的字段**而不是混用一个名字。以后这类指标上线前增加**对照验收**（与手工或金样例比对），减少二次客诉。

### 场景2：定制项目后期需求不断加，团队快延期

**思路：** MVP 与二期分层；新增项**置换**或单列排期；变更走**工单/变更记录**；能抽象的进参数，一次性需求单独立项。

**优化口播：**

> 先把**范围三角**摊开：在现有人力下，按期交付意味着什么必须砍或延期。和项目经理、客户开一次**优先级会议**：Must 进本期，Should 协商进二期或加价加人，Could 先不上。新增需求一律**走变更单**，写清对工期影响；能并进标准能力的抽象成**参数**，纯一次性的单独排期不入主干。对内部我会同步**风险**：若坚持全做，延期概率是多少，让对方选而不是我们默默扛。

### 场景3：模型回测不错，业务不敢给客户用

**思路：** 对齐决策场景；**强基线对比**；区间与不确定性；**可解释分层**；人机协同与研究员覆盖；必要时改为**规则预警 + 轻量 ML**。

**优化口播：**

> 回测好不等于**决策场景可信**，我同意业务谨慎。下一步是一起对齐：**客户将用这个数做什么、错了会付出什么代价**。我会补充**和朴素基线的对比**、**分行情的表现**、以及**预测区间或分位数**而不是只报点估计。解释上用分层或 SHAP 类叙述讲清**主要驱动**，约定**研究员可覆写**和熔断条件。若仍压力大，可以折中为**规则预警 + 轻量模型**分阶段放开，用真实跟踪期建立信任。

### 场景4：多客户都要「指数 + 预警 + 周报」，但逻辑略有不同

**思路：** 抽取共性→**可配置参数**（品种树、阈值、窗口）；统一底层明细；定制只做**插件点**；用数据证明抽象节省人日，分期上线。

**优化口播：**

> 先画**共性**：底层都是同一套明细与时间对齐、同一套指标骨架，差异在品种树、阈值、窗口和周报模版。把差异收进**配置表或参数**，代码走**插件点**，避免每个客户分叉一套仓库。对内部用**人日对比**说服 PM：抽象后下一轮交付能省多少；对上客户分期上线**核心能力 + 定制层**，降低一次性大项目风险。

### 场景5：英语能力被追问

**思路：** 如实陈述读写与听说现状 + **具体提升计划**（技术文档、会议跟读）；愿意承担**方法论精读与英文化图表**类任务；JD 为**熟练掌握听说读写优先**，可主动问 HR 是否硬性。结构化长答见 **第五节问题49**。

**优化口播：**

> 我**如实说**：目前（读/写）能独立读技术文档和邮件，（听/说）仍在加强，例如每周（跟读 / 技术播客 / 英文会议复盘）×（次数）。岗位若涉及**方法论资料、图表与注释英文化、海外数据源说明**，我愿意承担并在实习期内把听说拉到**能参加英文短会记要点**的水平。JD 写「英文优先」我会**向 HR 确认**是不是硬性门槛，以便自己补课优先级清晰。

### 场景6：招聘写「本科」与出勤强度，你担心被质疑学历或在读时间

**思路：** JD 为**本科及以上学历**——硕士在读/已录取通常符合「及以上」；一周 **5 天、约 3 个月**体现定制项目需要连贯投入，回答时给出**可验证的作息安排**（勿空口承诺出勤）。

**优化口播：**

> 学历上：JD 是**本科及以上**，我（硕士在读 / 已录取研究生）符合简章里的「及以上」，若公司需要我可以配合提供在读证明。出勤上：我理解**每周 5 天、约 3 个月**是定制项目要**连续投入**，我已和学校/导师对齐（或：选课集中在某几天），能保证实习期内的**具体坐班安排**是（如实填写天数与时段）。若后续论文或考试有冲突，我会**至少提前两周**和 mentor 报备并把手头任务交接清楚，不突然撂挑子。

## 七、业务高发问题（务实 Q&A）

下列五条对应**口径、范围、模型落地、数据质量、标准产品化**——与 JD 中「体系建设 + 定制 + 标准」直接同频。

### Q1：口径之争导致验收卡死，怎么办？

**核心：** 停止猜测，**书面冻结口径**，用并排对比找差异根因，再定单一真源或显式多版本。

**优化口播：**

> 验收卡死多半是双方说的「同一个词」其实不是同一件事。我会建议**暂停争论、先列维度**：价格定义、时间窗、含税规则、成交还是评估、地域与牌号粒度、缺失怎么处理。拉**金样例**和**并排对比表**，让差异可视化。落实成带**版本号**的口径说明；若业务确实需要两种定义，就**两个字段名**都进词典，而不是口头混用。推动团队选一个**权威出口**作为对客默认，其它走「历史兼容」或定制视图。

### Q2：定制需求蔓延怎么治？

**核心：** **变更可见化** + **优先级** + **抽象与一次性分流**。

**优化口播：**

> 蔓延通常是没有**代价共识**：加一项需求对工期意味着什么没说清。治理上我会坚持**统一需求入口**和变更记录，每期开工前做 Must/Should/Could；探索性的先 **POC 小闭环**再扩 scope。能固化的**参数化进标准链路**，报表型、一次性的**不污染主干**。和商务、PM 对齐：**三角必舍一边**（范围、时间、资源），让对方选。

### Q3：模型「能用」但业务「不敢用」？

**核心：** 信任来自**场景对齐 + 透明 + 兜底**。

**优化口播：**

> 技术上「能用」是离线指标；业务担心的是**线上决策风险**。我会对齐**错了会怎样**和**可接受误差**，强制展示**相对基线的增益**和**失效区间**；交付里写清**更新延迟、数据依赖、何时熔断**。产品上接受**人机协同**：模型给建议，研究员或风控保留覆写。架构上可采用**规则保底、模型增强**，先解决「不敢用」再谈「全自动」。

### Q4：数据源改版或断更引发黑天鹅？

**核心：** **分级响应**：监控 → 熔断 → 溯源补数 → 公告与复盘。

**优化口播：**

> 黑天鹅往往缺**前置契约**：源站改版、合同到期、字段下线没有 SLA。事后要补**分级**：关键指标触发阈值自动告警，严重情况**停止对客或打数据质量标**。同时排**溯源**（采集、中间层、接口）和**补数/替代源**；短期内模型**回退基线或规则**。对外该**公告**就公告，对内**复盘进运维手册**：谁值班、谁批熔断、谁签字恢复。

### Q5：多个定制相似却抽象不动？

**核心：** 用**数据证明重复成本**，先统一明细层再谈模板。

**优化口播：**

> 抽象不动常因为**有人怕被通用方案拖累差异化**。我会拉**近 N 个项目的人日与代码重复度**，算一笔账：参数化后能省多少测试与维护。技术上先**统一明细与指标字典**，差异只留在**配置与少量插件**，BI 也模板化。推动节奏上分两期：**先并底层**，再谈体验统一，减少一次性大重构风险。

- **标准回答（贴合大宗商品与LGBM场景）**：
  - **表态**：在大宗商品库存预测中，特征工程是决定LGBM上限的核心。我会从基础时序、业务交叉、周期性以及宏观/价格动量四个维度，借助 AI 编程工具批量生成数千个候选特征。
  - **基础时序特征**：进出货量和库存的滞后项（如滞后1周、4周、12周，代表近期、月度、季度影响），以及这些指标在不同滚动窗口（如近4周、近12周）下的均值、极值和波动率。

  - **价格与基本面的交叉特征**：
    - **价格动量下的行为特征**：将日度价格聚合为周度涨跌幅，并与进货量交叉（如：价格连续上涨时的进货量），这能捕捉到贸易商“买涨不买跌”的投机性备货行为。
    - **价格波动率与库存的交互**：高波动率往往伴随产业观望或恐慌性抛售，影响出货节奏。
  - **为什么有用**：这些特征将分析师在调研中体感的“产业情绪”、“备货节奏”和“库存压力”转化为了量化指标。LGBM 擅长处理非线性关系，把这些复杂的交叉特征喂给它，能大幅提升样本外的预测能力。

### 问题4：时间序列数据，如果要去对它的训练集和测试集做切分的话，要用什么方法？

- **我回答的陷阱与不足**：
  - 回答过于基础（70%训练，30%预测），没有提到时间序列交叉验证（Time Series Cross Validation），只是简单的前后切分，显得缺乏工程经验。

- **标准回答**：
  - **表态**：时间序列绝对不能像普通表格数据那样随机打乱切分，必须严格遵循时间顺序，否则会导致严重的未来信息泄露。
  - **具体方法**：
    - **简单时间截断（Hold-out）**：按时间顺序前80%作为训练集，后20%作为测试集（或验证集）。
    - **滚动窗口交叉验证（Rolling Window CV）**：这是实盘中最常用的方法。保持训练集大小固定（例如固定过去一年的数据），随时间向后滑动，每次预测未来一周或几周。这非常适合大宗商品，因为市场结构和逻辑会随时间发生“概念漂移（Concept Drift）”，滚动窗口能让模型始终学习最近期的模式。
    - **扩展窗口交叉验证（Expanding Window CV）**：训练集起点固定，随时间不断向后扩大，测试集也随之向后滑动。

### 问题5：在时间序列数据的切分中，什么是数据泄露（信息泄露）？

- **我回答的陷阱与不足**：
  - 解释不够精确，提到了“把预测集的数据特征训练进去了”、“把噪声作为特征”，但没有点透时间序列中特有的“未来函数”和“宏观数据修正”问题。

- **标准回答**：
  - **核心定义**：数据泄露（Data Leakage）在时间序列中，就是指在预测 $t$ 时刻的目标变量时，不小心使用了 $t$ 时刻及之后才可能获取到的信息，也就是俗称的**“引入了未来函数”**。
  - **大宗/时序场景的典型泄露**：
    - **特征构造泄露**：在计算滚动均值或滞后特征时，窗口平移错误（例如 `shift` 没对齐），导致当前周的特征里包含了下周的进出货量。
    - **全局统计量泄露**：在做数据标准化（如 Z-score）时，使用了包含测试集在内的全样本均值和方差。正确的做法是只能用训练集的统计量去 `transform` 测试集。
    - **宏观/基本面数据修订泄露**：大宗商品很多官方数据（如进出口、产量）有初值和终值。如果在回测时使用了事后几个月才修正的“终值”去预测当时的市场，这就是严重的业务泄露。必须严格使用“当时那个时间点能拿到的快照数据”。

  - 没有点出**树模型对趋势（非平稳）敏感的致命弱点**。

- **标准回答（结合LGBM特性与经济意义）**：
  - **树模型特性**：LGBM 这类树模型本质上是基于历史数据的区间划分，它**无法外推趋势**（即无法预测出比训练集最大值更大、或比最小值更小的值）。因此，如果目标变量有强烈的非平稳趋势，必须将其转换为平稳序列。
  - **差分 vs 对数收益率的选择逻辑**：
    - **看经济意义与方差特性**。如果序列的绝对波动幅度比较稳定（比如某些港口的铁矿石绝对库存增减量），我会选择**一阶差分**，它代表的是绝对变化量。
    - 如果序列呈现指数增长，或者其波动幅度（方差）随着数值水平的增加而变大（比如价格指数、宏观经济总量），我会选择**对数差分（即对数收益率）**。对数化可以稳定方差，差分可以消除趋势，它代表的是相对变化率。
  - **总结**：在大宗商品价格或库存预测中，如果是预测价格指数，通常用对数收益率；如果是预测具体的库存吨数变化，一阶差分往往更符合业务直觉。
